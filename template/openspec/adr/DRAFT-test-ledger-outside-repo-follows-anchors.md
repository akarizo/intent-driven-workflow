# DRAFT. 测试账本：逐用例数据放 git common dir，耗时跟着锚点沿用，入库的只有摘要

- Status: proposed
- Date: 2026-11-18
- 关联：DRAFT-baseline-reuse-via-dependency-anchor · DRAFT-final-incremental-by-dependency-anchor（锚点是可沿用的测试结论，保持在役；本决策只给锚点条目加一个可选字段）· DRAFT-measurements-stay-out-of-plan-files（度量不进计划文件，保持在役）· DRAFT-gate-test-result-handoff-and-runner-contract（结果文件字段不变，保持在役）· DRAFT-machine-wide-test-lock（测量在独占锁内，保持在役）
- 来源 change：test-ledger（design D2–D8、D10）

## Context

门禁只留整套测试的秒数。哪条用例慢、一个 change 给套件加了多少用例和多少秒，没有记录；afa 的集成用例两周涨了 41%，是事后体检才发现的。后续的分层预算（单条上限、层总量、豁免）与体检整改命令，都需要一份逐用例的账本作为数据来源。

约束：

- 万级用例的逐用例数据每份约 1 MB，一个 change 会产生两三份；
- 多数 baseline 与 final 是增量运行，只重跑一部分测试文件，其余用例的结论沿用自锚点；
- 依赖图没测到的仓库（包装脚本丢了插件、非 pytest）拿不到 nodeid，只有 junit；
- 新机制失效时门禁的结论不能变（铁律 10）。

## Decision

1. **逐用例账本不入库**，放 `<git common dir>/flight-ledger/<change>/`：`baseline.json`、`final.json`、`delta.json`，覆盖写，只保留最近若干个 change 的目录。入库可追溯的只有两处摘要：final 时间线备注里的一小段，与 PR 正文里的「## 测试变更」。
2. **账本的每条用例记四样**：结局、耗时、所属层、本次实测还是沿用。耗时取不到记 `null`，不估算、不填 0。
3. **耗时跟着锚点沿用**：锚点条目带可选的 `secs = {nodeid: 秒}`。增量运行里没重跑的用例，结局沿用谁的，耗时就沿用谁的。锚点的选取、保留、链长规则都不变。
4. **两种用例 id，各用原生来源**：依赖图测到时用 nodeid，耗时由依赖图插件累计；没测到时用 junit 的 `classname::name`，结局与耗时都取自 junit。一份账本只用一种。需要把两种放到一起时（junit 形式的账本并入 nodeid 观测、对账时两边形式不同），只做 nodeid → junit 的正向换算（pytest 自己写 junit 的规则，确定）；不做反向猜测。
5. **账本只报告**：对账（新增 / 删除 / 变慢 / 各层前后）与建议行都不产生判红。要不要按账本判红、按什么线判，由后续决策另定。
6. **账本永不让门禁失败**：账本模块缺失、目录不可写、数据形状意外 → 只留一条警告，baseline / final 的结论与没有账本时相同。

## Consequences

- 正面：
  - 每次 baseline / final 之后都能回答「哪些用例最慢、各层多少条多少秒、这个 change 加了什么」；
  - 增量运行也能给出整套的层耗时，而不只是重跑的那部分；
  - 仓库历史不因逐用例数据膨胀；账本目录可以随时整个删掉，下一次运行会重建。
- 负面：
  - 账本只在产生它的机器上。换机器、清 common dir、或在另一台机器上开 PR 时，没有基线账本可对，对账为空并说明原因；
  - 锚点文件变大（每条用例多一个数），选锚点时要读的字节更多；变慢到可感知时把 `secs` 挪到旁路文件；
  - 升级后到第一次全量之前，沿用自旧锚点的用例没有耗时，账本如实记「无耗时」；
  - 正向换算后两条不同的 nodeid 可能重名（极少见），对账时并成一条。
- 中性：
  - 时间线的 final 备注多一段 `用例 +A/-R（新增 Xs）`；读时间线的脚本若按固定片段数解析需要适配（模板自带的解析方按关键字取，不受影响）；
  - 后续若决定「对账摘要入库」或「按账本判红」，在本决策之上新立 ADR，不需要推翻它。
