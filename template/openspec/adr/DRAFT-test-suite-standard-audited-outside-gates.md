# DRAFT. 测试套件的合规标准写成明文规则表，由门禁之外的只读体检来量

- Status: proposed
- Date: 2026-11-18

## Context

模板对测试套件的要求分散在几处：分层（两层、按路径归层）、纯度与单元层的线（探针）、预算与放行期限（分层文件）。每一处都只在飞行经过时判，而且判的是「这次变更有没有让它更坏」：集成层的老债只警告，放行到期前没人看，区域没写上限就不设线。

于是有两个缺口。一是没有一处把「合规的测试套件长什么样」完整写出来；二是没有办法随时量「现在离它多远」——2026-11-18 的一次测试体检用了 15 个临时脚本。

不能靠把门禁调严来补：集成层的历史包袱重，全部判红等于无法启用（`DRAFT-time-budgets-ratchet-on-ledger` 的棘轮正是为此）。

## Decision

1. **标准是一张规则表**，写在运行器契约文档的「测试套件合规标准」一节：R1 有合法的分层文件；R2 每个测试文件恰属一层；R3 单元层纯；R4 单元层单条不超线；R5 每个集成区域写了单条上限；R6 集成区域单条不超线；R7 写了总量预算的范围不超预算；R8 放行条目有效且有边界。
2. **文档与脚本各持一份，由测试对账**：类别名、规则号、可选去向在脚本里是常量，一条测试逐项对照文档。
3. **量标准的是体检，不是门禁**：`test-tiers.py audit` 只读、不跑测试，读分层文件、测试文件清单与最近一次测量（测试账本，可叠加探针结果）。
4. **体检比门禁严**：门禁只警告的集成层老债与区域总量超预算，在体检里是不合规。门禁回答「这次变更有没有变坏」，体检回答「离标准多远」；两者的判定函数是同一套。
5. **判不了单列一档**：没有测量、测量不全的范围记「未判」，退出码 3，不并进合规也不并进不合规。
6. **体检不进门禁的判红路径**：要不要把它声明成某个仓库的检查，由仓库自己决定。

## Consequences

- 任何人任何时候能得到一份可比较的读数；同一份 JSON 存档可以做前后对比。
- 标准改动有固定落点：改规则表，同改脚本常量，对账测试会拦住只改一边。
- 历史包袱重的仓库，体检会在很长时间里显示「不合规」。这是如实的；分批整改靠「本轮目标」的复核，不靠把标准调松。
- 体检的准确度取决于测量有多新：读到别的分支留下的账本时，对不上的用例被丢弃、没测量的文件进「未判」，而不是给出一个看似完整的结论。
- 门禁与体检对同一条用例可以给出不同的处置（警告对不合规），文档须把这一点写明，否则会被当成矛盾。
