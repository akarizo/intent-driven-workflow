# DRAFT. 每个 wave 合回后做集成检查，红了走工作流内的跨片修复

- Status: proposed
- Date: 2026-11-18
- 关联：DRAFT-final-incremental-by-dependency-anchor（集成检查的测试那一半沿用它的选测）· DRAFT-test-ledger-outside-repo-follows-anchors（预算估算用锚点的逐用例耗时；集成检查不落账）· DRAFT-gate-evidence-not-self-reported（修复改了什么由脚本算）
- 来源 change：wave-integration-guard（design D1–D5）

## Context

切片门禁只验本片的 `verify`，合回之后到 final 之前没有任何一步检查合起来的树。跨片问题因此在下一个 wave 的别的切片里、或在 final 里才暴露，而工作流内唯一的修复阶段只收评审 finding，且排在全部 wave 之后（交接文档 F4 / F5）。

仓库往往已经有几秒就能跑完的全局检查（分层、依赖声明、组合根），但它们要靠规划的人记得写进每一片的 `verify`。

## Decision

1. **全局守护是检查的第三条命令**：`gate.checks` 的检查可带 `slice`，在 baseline、每片门禁（`G15 guard`）与每个 wave 的集成检查里运行；仓库默认清单声明了 `slice` 的检查，计划必须带上。
2. **每个 wave 合回后运行一次集成检查**（`slice-gate.py wave-check`）：守护全跑；测试只重跑按依赖图受影响的那些，与增量 final 同一选法。
3. **测试那一半有界**：没有可用锚点、估算耗时超过预算（缺省 120 秒）、配了分层文件或 `gate.impacted` 时跳过并写明原因。**不退化成全量**。
4. **集成检查不写锚点、不落测试账本**：半成品树的结论不该被沿用，也不该覆盖收口账本。
5. **红了当场修一次**：工作流派一个不受 owns 限制的修复执行体，它在自己的 worktree 里修完并重跑集成检查；绿了才合回，修复提交单独评审。
6. **仍红就停**：守护红时后面的 wave 全部不派；只有测试红时只停依赖本 wave 的切片。
7. **所有权不放宽**：切片执行体写 owns 之外的文件仍是 `G6`。修复改了哪些文件、哪些在所有切片的 owns 之外，由脚本算出并进时间线、`gate-report.md`、`review-findings.json` 与 PR 正文。
8. **集成检查的红参与收口裁决**：`gate-report.md` 里 `wave` 的最新一行是红的，`ship` 判 draft。

否决的方案：

- **合回后直接跑 final**：后面的 wave 还没解锁骨架，必红；final 的副作用（锚点、账本、同树沿用）也不该发生在半成品上。
- **没有锚点时跑全量**：每个 wave 一次全量，成本不可接受。
- **只按本 wave 的改动选测**：依赖图是锚点那一刻测的，会漏掉经由前一个 wave 改过的中间模块传导的影响。
- **修复重试到绿为止**：没有上限。
- **放宽切片的 owns（飞行中自动追加）**：等于取消所有权；发现提前、重新批准做便宜才是方向（方案页 Q6）。

## Consequences

- 每个 wave 多一次集成检查的墙钟：守护秒级，测试有预算；耗时进时间线与 `flight-doctor.py cost`。
- 改动波及面大的仓库（几乎所有测试都依赖的文件被改），测试那一半会被预算挡下，集成检查只剩守护；要它生效得调高预算。
- 检查的运行契约多一条：`slice` 命令会被并行调用，对共用目录只读。
- 分层仓库与配了 `gate.impacted` 的仓库只得到守护与修复通道，得不到 wave 里的受影响测试。
- 多一种 draft 原因（红的 `wave` 行），处理办法是修复后重跑 `wave-check`。
- 预算 120 秒是草案（43 次增量运行的样本：77% 不超过 120 秒，其余都在 500 秒以上）。
