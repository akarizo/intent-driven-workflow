# DRAFT. 全机测试锁：门禁的测量运行经一把用户级读写锁排队

- Status: proposed
- Date: 2026-11-18
- 关联：DRAFT-gate-test-result-handoff-and-runner-contract（`FLIGHT_` 前缀变量的约定，保持在役）· DRAFT-test-tiers-unit-baseline-by-audit-probe（G10 慢单测的判定，保持在役）· DRAFT-gate-evidence-not-self-reported（留痕由脚本写，保持在役）
- 来源 change：machine-test-lock（design D1–D8）

## Context

门禁的 baseline、final、切片 verify 都假定机器归自己独占。同一个用户在一台机器上同时跑多条飞行时，每条都满核并行：afa 的测试分层体检（2026-11-18）取证时，18 核机器负载 37–45。墙钟被拉长却没有记录；时间类判定（单条耗时上限）在争抢下失真；时序敏感的用例偶发红。

模板没有任何并发闸，成本记录里也没有排队与负载。后续要做的逐用例耗时账本与分层预算，都以「测出来的秒数可信」为前提。

约束：

- 模板只用标准库，hook 必须能在没有这把锁的平台上照常工作（铁律 10：回退必存在）；
- 一条飞行内同一 wave 的切片是并行执行的，这是飞行模式的提速来源，不能被锁串行化；
- 门禁只能加严，不能因为新机制失效而放宽已有判定。

## Decision

1. **一把读写锁，放在用户级目录**（缺省 `~/.claude/flight-lock/`），跨仓库、跨 worktree 共用，用 `flock` 实现。持有进程退出（含被杀）时内核放锁，不留需要人清理的锁文件。
2. **两种持有方式**：
   - **独占**：baseline、final、`test-tiers.py run` / `probe`——同一时刻全机至多一套；
   - **共享**：切片门禁的 verify——彼此并行，但不与任何独占运行重叠。
   - 独占方排队时后来的共享方不得先于它进入（闸口锁）。
3. **整段测量持有一次**：一次 baseline / final 从第一条测试命令到最后一项检查只排一次队，中途不放锁。
4. **重入**：持锁进程给子进程带标记（含锁目录）；同一把锁之下的子进程不再排队。
5. **放弃等待按持有者判**：持有者取锁时声明自己的持有上限；排队方只在最早的持有者超过它声明的上限时放弃，随后不加锁继续运行。正常排队（队伍在前进）不算超时。
6. **锁永不让门禁失败**：平台不支持、锁目录不可用、锁模块缺失或出错 → 不加锁照跑并留下原因；`FLIGHT_LOCK=off` 显式关闭。
7. **时间类判定只在确知争抢时降级**：放弃等待后跑出来的那一次，单条耗时类的失败降为警告；显式关闭与平台不支持时照常判定。对错类判定任何情况下都不变。
8. **留痕**：每次测量运行在输出与时间线里记录锁的状态、排队秒数、起止负载；final 另记 gate.test 与每项检查的秒数。

否决的方案：

- **整机一把互斥锁**：实现最简单、测量最干净，但同一 wave 的切片门禁变成串行，抵消飞行模式的并行收益。
- **只留痕不排队**：能看见争抢，但时间类判定仍然不可信，后续的耗时预算无从判红。
- **pid 文件 + 存活探测**：进程崩溃后要靠别人判死，判错就双持或永久占用。
- **槽位信号量（按并行度配额）**：能限制共享方的并行度，但「全量独占」要一次拿满全部槽位，部分持有与死锁的处理复杂得多；先不做。
- **按排队方自己的全量耗时定等待上限**：小仓库排在大仓库后面必然超时，一超时就并跑，等于没有锁。
- **没拿到锁就一律把时间类判定降为警告**：在不支持 `flock` 的平台和显式关锁的 CI 里，耗时判定会永久失效，相当于放宽门禁。

## Consequences

- **变容易**：
  - 同机多条飞行的全量不再互相拉长；排队多久、当时负载多少有据可查；
  - 时间类判定在持锁时可信，后续的逐用例耗时预算可以判红；
  - 门禁之外的测试运行也能用同一把锁排队（`flight-lock.py run`）。
- **变难 / 代价**：
  - 单条飞行的墙钟里多了排队时间，体感上「门禁在等」；
  - lint / typecheck 夹在独占段内，也占着锁；
  - 包装脚本若剥掉 `FLIGHT_` 前缀的环境变量，被测进程里再调门禁会排到持有上限才继续。
- **已知天花板**：
  - 共享方之间不限流：多个切片同时 verify 且各自满核并行时仍会超订；
  - 轮询取锁，不保证先来先到；
  - 锁在用户级目录：多用户共用一台机器互不可见；主目录在网络文件系统上时 `flock` 可能不可靠；
  - 锁是协作式的：人直接敲测试命令不受约束；
  - gate.test 本身没有运行超时，挂死的持有者要等排队方按持有上限放弃。
- **待数据定稿**：持有上限的倍数与下限、是否要给共享方加配额、lint / typecheck 是否移出独占段，上线后看时间线里的排队秒数与负载再定；改动这些数字不需要新的 ADR，改变第 2、5、7 条的语义需要。
