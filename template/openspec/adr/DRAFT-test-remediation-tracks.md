# DRAFT. 测试整改按去向分三条轨道：机械处置命令内做，放行归人，改用例实现另立 change

- Status: proposed
- Date: 2026-11-18

## Context

体检列出不合规的用例之后，要把它们改到合规。改法差别很大：有的只是把文件搬到另一层的目录，有的要改 fixture、缩样本甚至删用例。

仓库铁律要求中级以上变更先有工件再写代码；但 `/test-tiers` 第一次划分时搬几百个测试文件，用的是 `/opsx-mini` 留痕加审批页加人类批准，没有走 change——因为它不改任何用例的行为。整改如果一律走 change，搬一个文件的成本与风险不成比例；如果一律在命令内做，最容易出事的那类改动（为了提速把断言改弱）就没有评审。

放行另有既定规则：只认人类原话，由 `test-tiers.py allow-slow` 写入，模型不得代写。

## Decision

整改的去向分三条轨道，由去向决定，脚本归类，模型不自行判断：

1. **命令内执行**（`move` 搬文件、`split` 拆用例、`retier` 改分层文件的归属、`budget` 写或调预算、`drop-allow` 删失效放行）：
   - 不改任何用例的行为；
   - 流程：整改稿 → 脚本渲染审批页 → 人类批准 → `/opsx-mini` 留痕后执行 → 护栏脚本核对 → 重新取测量复核；
   - 护栏对着 git 改动核对：没动被测代码与稿外文件；测试函数的集合、每个函数的断言与参数化没变；分层文件里预算放宽、放行增删都在稿里；核对不了的文件如实列出。
2. **交人放行**（`allow`）：放行与补上限、期限只能由人类原话经 `allow-slow` 写入。
3. **转 change**（`speedup` 提速、`purify` 改纯、`delete` 删用例）：命令不动手，把条目整理成清单交 `/opsx-propose`，走起飞批准、TDD 留痕与独立评审；验收可以直接用体检的前后对比。

另有 `keep`（本轮不处理），必须写理由。

## Consequences

- 最常见的整改（搬层、拆混合文件、补预算）一条命令做完，不需要五工件。
- 命令内的护栏可以是一条简单的不变式——用例集合与断言不变——因为会改变它们的去向都不在命令内。
- 删用例比方案页原设想的更重（要走 change）。换来的是：减覆盖的改动一定有评审。
- 护栏的断言比较只懂 Python；其他语言的测试文件搬动只能列为「未核对」，靠人看 diff。
- 审批页上的勾选是软约束（脚本看不到浏览器里的操作）；硬约束在护栏（实际改了什么）与 `allow-slow`（谁放行的）。
- 一次体检的整改可能分散到命令内的一批改动与若干个 change 里，没有单一的「整改完成」时刻；用体检存档与整改稿做前后对比来收口。
