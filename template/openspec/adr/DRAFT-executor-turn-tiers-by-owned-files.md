# DRAFT. 执行体的轮次上限按切片的现存文件数分两档

- Status: accepted
- Date: 2026-11-18
- 关联：DRAFT-apply-as-flight（执行体受 maxTurns 约束）· DRAFT-measurements-stay-out-of-plan-files（脚本不写计划文件）
- 来源 change：slice-resume-deterministic（design 调查二 · D3 · D4）

## Context

`DRAFT-apply-as-flight` 给执行体定了轮次上限，防止失控。上限写在 agent 定义文件的 frontmatter 里（`maxTurns: 40`），Workflow 的 `agent()` 调用没有轮次参数，所以它对所有切片是同一个数。

afa 的 `key-features-keyft` 飞行里，约 20 个文件与 91 个文件的两个切片分别撞了四次与两次上限，下游四片连带 blocked。回放本机六个仓库的 821 个带上限的首轮执行体：计划时 owns 展开超过 8 个现存文件的切片，撞 40 轮或未交回的占 28.4%，不超过 8 个的占 5.5%。没有上限的 69 个首轮全部交回，最多 58 轮。scenario 数几乎不带区分度。

## Decision

1. **上限仍然存在，分两档**：标准档 40 轮，大片档 80 轮。每档一份 agent 定义文件；大片档的定义只有 frontmatter 加一句指向标准档定义的话，纪律正文只有一份。
2. **档位由脚本算**：`slice-gate.py turns` 取切片 owns 展开后的现存文件数，超过 8 个为大片档。文件在基线记录的 commit 的树上数（没有基线时在 HEAD 上数），所以一次飞行里档位不随实现新增文件而变。
3. **计划只能升档**：切片可写 `"turns": "large"`；按规模是大片档的不能写回标准档。脚本不把档位写进计划文件。
4. **工作流按档位选定义文件**，首轮与重派同档；档位在审批页的切片表里显示。
5. **阈值与上限是可调常量**（8、40、80），调整时附回放数据；增加第三档或改用别的量，需要新的 ADR。

否决的方案：

- **取消上限**：上限是防失控的，问题在它不随切片大小变。
- **每片在计划里写一个数字**：定义文件得按数字生成，Workflow 无法在调用时传上限；人也估不准。
- **用 scenario 数或 owns 条数分档**：回放里区分度都不如现存文件数。
- **加「超大切片判红」**：回放里撞限率在 13 个文件以上不再上升，没有上限的样本无一未交回，定不出线。

## Consequences

- **更易**：大切片不必靠人工绕开定义文件才能做完；撞上限的理由里有档位与上限，知道是哪一档不够。
- **更难**：多一份定义文件要随 `slice-executor.md` 的 frontmatter 同步（由测试对账）；工作流脚本里有一处与定义文件重复的上限数字。
- **不覆盖**：agent 类型未注册的仓库（先读定义文件的默认 subagent）没有轮次上限，档位在那里只决定读哪份文件。
- **约束后续变更**：新增的执行体角色如果也要轮次上限，沿用「定义文件给上限、脚本给档位」的分工，不在 prompt 里约定轮数。
