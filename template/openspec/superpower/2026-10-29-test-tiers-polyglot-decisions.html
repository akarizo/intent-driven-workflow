一句话：一个仓库可能由多个子项目组成，每个子项目各有自己的语言和 runner。所以分层文件从「一个单元层 + 若干区域」改成「多个部件，每个部件有自己的单元层和区域」。一个部件 = 一个子项目目录里的一种 runner。全仓的单元层就是各部件单元层的并集，由库自带的驱动命令逐个部件运行、逐个测量、汇总判定。单项目单语言的仓库等于只有一个部件，现在的分层文件写法继续有效。

2. monorepo / 多语言会撞上哪些现状

现状在多语言 monorepo 里会怎样
分层文件只有一个 unit.cmd，lint 要求 gate.test == unit.cmdGo、Python、TS 三个子项目的单元测试没法用一条命令跑 表达不了
失败用例差分要求输出里恰好一行 pytest 汇总（slice-gate.py:986）就算让 agent 写个聚合脚本，只要先后跑两个 Python 子项目，就会被判「调用了多次 pytest」，差分失效 退化
命令都在 git 顶层目录运行，用例 id 也相对顶层子项目各有自己的工具链根（go.mod、package.json、pyproject.toml），runner 输出的路径是相对子项目的，和 owns、scenario_tests 对不上 坐标错位
探针、金丝雀自检按「一个仓库一种语言」设计每种语言甚至每个子项目的 runner 配置都不同，要分别自检 需拆分

3. 目标形态

repo/
├─ openspec/test-tiers.json        ← 全仓只有一份，内含多个部件
├─ services/api/   go.mod          → 部件 api-go     （root = services/api）
├─ services/ml/    pyproject.toml  → 部件 ml-py      （root = services/ml）
├─ web/            package.json    → 部件 web-ts     （root = web）
└─ libs/shared/    Cargo.toml      → 部件 shared-rs  （root = libs/shared）

agent · /test-tiers

  • 扫描 manifest 和 workspace 文件（go.work、pnpm workspace、Cargo workspace 等），列出候选部件
  • 逐个部件调研切法、junit、探针，并实测
  • 逐个部件跑金丝雀自检
  • 起草 → 审批页 → 人类批准
→

test-tiers.json（多部件）

  • 每个部件：root · test_files · unit · regions
  • 区域名全仓唯一（出现在 gate.integration 里）
  • 文件里的路径一律相对 git 顶层（与 owns 同一坐标）；runner 输出由库自动补上 root 前缀
→

驱动 · test-tiers.py run unit

  • 逐个部件在其 root 下运行，各自取 junit 和探针
  • 汇总成一份用顶层相对 id 的结果
  • G10 / G11 逐部件判；check 校验每个测试文件恰好属于一个部件的一层
// 多部件（示意，命令由 agent 实测后填写）
{
  "parts": {
    "api-go": {
      "root": "services/api",
      "test_files": ["services/api/**/*_test.go"],
      "unit": {
        "list": "scripts/tiers/go-list.sh unit",
        "cmd": "gotestsum --junitfile $FLIGHT_JUNIT ./...",
        "probe": {"cmd": "...", "sha": "…", "canary": "…"}
      },
      "regions": {
        "api-db": {"paths": ["services/api/it/**"],
                   "covers": ["services/api/store/**"],
                   "cmd": "..."}
      }
    },
    "ml-py": {
      "root": "services/ml",
      "unit": {"paths": ["services/ml/tests/unit/**"],
               "cmd": "python -m pytest -q tests/unit"}
    }
  },
  "slow_allow": {}
}
// 单部件简写 = 现在的写法，继续有效
{
  "unit": {"paths": ["tests/unit/**"],
           "cmd": "python3 -m pytest -q tests/unit"},
  "regions": { "...": "..." },
  "slow_allow": {}
}

5. 第二轮里由设计直接定、不单独问的细节

细节定法
坐标系分层文件、owns、covers、scenario_tests、slow_allow 的键，全部相对 git 顶层。runner 的 junit 和 list 输出由库按部件 root 补前缀
区域命名沿用 [a-z0-9-]+，全仓唯一，lint 校验
部件归属每个测试文件必须恰好落在一个部件的 test_files 里，再在该部件内恰好落一层。check 和 G12 点名违规
金丝雀自检逐部件进行，因为同一种语言在不同子项目里 runner 版本和配置可能不同。适配器文件可以共用，哈希按文件记录，每个用到它的部件各自记一条自检记录
部件失败任一部件红，单元层就红。门禁报告按部件列出耗时与结论（tier_sec 增加 parts 分项）

6. 代价与风险（第二轮新增）

  • 增量 final 退回全量：现在的增量逻辑只认得 pytest 前缀，多部件时会退回到整个单元层全量运行。单部件 Python 仓库不受影响。依赖图语言通用化已在 Q5 列为后续 change。
  • 非 Python 部件的预存红：由于差分只看退出码，基线里某个部件已经是红的，这个部件就会让 baseline 停下，而不是记成预存红放行。这和现在非 pytest 仓库的处理一样，等「差分走 junit」那个后续 change 解决。
  • 部件发现靠 agent：漏识别一个子项目时，check 会因为它的测试文件不属于任何部件而报错（前提是该子项目的 test_files 被写出来了）。完全没写 test_files 的语言，由内置命名规则兜底，兜不住的部分写进审批页的「未覆盖」清单交人确认。
