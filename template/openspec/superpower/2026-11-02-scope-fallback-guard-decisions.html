选测范围不被分类元数据拖成全量 · 决策页

拟建 change：scope-fallback-guard · 2026-11-02 · 已定：A + B 两件都做，B 用「计划期表态」
一句话：工作流自己写的分类元数据（afa 的集成登记表、模板的 test-tiers.json）一改动，选测逻辑就把整个文件当成「基础设施」，范围退回全量。
A 修模板自己的这处：test-tiers.json 按条目差分，只有单元层变了才全量。
B 管项目自带的选测：模板管不到项目自己的选测代码，所以在计划期让选测命令报告范围；一旦退化为全选，计划必须逐项写理由，人类批准飞行计划前就能看到。

1. 起因：afa 的 baseline 跑了 474.7 秒全量

事实证据
propose 期登记 3 个真实库测试文件为集成用例，改动了 executor/tests/tiering_registry.json（+23 行，全是新文件的条目）git diff --stat（afa worktree cpdb-lru-position）
该文件在 afa 的 INFRA_PATTERNS 里，命中即全选集成用例executor/tests/tiering_select.py:26、:177
实际：集成用例全选（登记 888 条 / 240 个文件）全选只读复算 select_impacted（不跑测试）
反事实：只拿掉登记表 → 只选 3 个集成文件（都是本 change 新加的 *_real.py）应有范围
final 还会再全选一次（登记表相对 merge-base 的改动一直在）同上逻辑

afa 侧的 tiering_select.py 修复（登记表按条目差分）你已同意，但它是 afa 自己的代码，不在本 change 范围；本 change 只改模板。

2. 模板自己也有同一类问题（已在临时仓库实证）

baseline 之后只做了这件事，再改一行 src/a.pyfinal 结果
在 test-tiers.json 的 slow_allow 加一条（等同 apply 期跑了 allow-slow）{"mode": "full", "full_why": "没有可用锚点"} 被迫全量
给区域 hooks 的 covers 加一个 glob{"mode": "full", "full_why": "没有可用锚点"} 被迫全量
对照：不碰分层文件incremental：重跑 1 个文件、沿用 2 个用例、区域 hooks 跳过 增量

原因有两处：

  • slice-gate.py:3967：锚点按 tiers_key 过滤，而 tiers_key 是整个分层文件的 blob 哈希（:3982），文件里改任何一个字节，所有锚点都失效；
  • slice-gate.py:3977：GLOBAL_FILES 含 test-tiers.json，即使有可用锚点，Δ 里出现它也全量。

这条行为是在役 ADR DRAFT-final-incremental-by-dependency-anchor 决策 4 明文规定的（「全局文件（…、分层文件）变动 → 全量」）。ADR 不可改，本 change 会另起一份新 ADR，只 supersede 决策 4 里「分层文件」这一项。

3. 目标形态

A：test-tiers.json 拆成三块参与增量判定（简写形态）

apply 期分层文件的改动现在改后
unit.paths / unit.cmd全量全量（不变：单元层范围变了，锚点里的单元层结论不可信）
已选区域 R 的 paths / covers全量增量；区域 R 必跑
已选区域 R 的 cmd全量 + 红「重跑 baseline」红「重跑 baseline」（现有规则，不变）
未选区域的任何改动、新增未选区域全量增量，不受影响（本 change 不跑它）
slow_allow 条目增 / 删 / 改全量增量；这些用例所在的测试文件重跑，G10 按新名单重判

做法：锚点里记三样东西——单元层指纹（替代现在的整文件哈希）、各区域条目指纹、slow_allow 的用例清单；final 取锚点后逐块比对。部件形态的 final 本来就恒全量，不在范围。

B：项目自带选测的范围报告契约（计划期表态）

propose 写计划

  • gate.scope：只算范围、不跑测试的命令
  • 或用仓库级默认（见 Q4）
→

lint / preflight 实跑

  • 库给 $GATE_SCOPE_OUT
  • 命令写 {"full", "triggers", "count"}
→

全选时须表态

  • gate.scope_full_reason 逐个触发项写理由
  • 缺一项、多一项都判红
→

spec.html

  • 显示选测命令与「触发项 → 理由」表
  • 人类批准飞行计划前可见
// 选测命令写到 $GATE_SCOPE_OUT 的内容
{
  "full": true,
  "triggers": ["executor/tests/tiering_registry.json"],
  "count": 10698
}
// 计划里的表态（slices.json 的 gate，示意）
"scope": "bash tools/testgate/run.sh scope",
"scope_full_reason": {
  "executor/tests/tiering_registry.json":
    "登记表改动只涉及本 change 新增的 3 个文件；
     afa 选测修复合入前接受一次全量"
}

如果当时有这条契约：afa 那次 propose 在 lint 就会红，并点名 tiering_registry.json。人类在 spec.html 里能看到「全选」和理由，而不是 baseline 默默跑 8 分钟。afa 要用上，还得在 afa 里给 testgate 加一个输出这个 JSON 的子命令（afa 侧工作，不在本 change）。

5. 默认取向（不单独提问，有异议写在任一题的补充里）

  • 不进 plan_sha：gate.scope / gate.scope_full_reason 不影响 baseline 的测试结论，改理由不需要重跑 baseline。
  • 不做 baseline / final 侧的范围记录：你选的是计划期表态。
  • 不管 gate.impacted 在 final 的退化：本 change 只管 baseline 范围（gate.test）。
  • 锚点格式变化：升级后各仓库第一次 final 会全量一次，之后恢复增量；不写兼容旧锚点的代码。
  • 文档同改：schema 的 tasks instruction、/opsx-propose 与同名 skill、/test-tiers 的「放行慢单测」一节。

6. 代价与风险

  • lint 变慢：配了选测命令的仓库，每次 lint / preflight 多跑一次（见 Q5）。
  • 契约靠项目实现：模板只定 JSON 格式并核对；选测命令报 full: false 但实际全选，模板看不出来。这是「项目自带选测」的固有边界。
  • 区域收窄的盲区：区域 paths 改动只让该区域重跑，不追究「被移出该区域的文件」——前提是单元层 paths 没变，这些文件不会悄悄进入单元层；落到别处由 G12 / check 拦。
