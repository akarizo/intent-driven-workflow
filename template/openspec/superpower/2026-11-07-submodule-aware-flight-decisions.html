结论：afa 那边的退化，原因在模板：飞行模式从隔离 worktree、执行体提交、合回到门禁，每一环都只按「单仓」设计。submodule 一进来，共有 6 处断点。3 处是 afa 会话实测的，另 3 处是我读代码定位的。
推荐：在本仓库开 change submodule-aware-flight。办法有三条：
  • 隔离 worktree 里的 submodule 不再去远端 clone，改为借用 change 家 submodule 的 linked worktree。这一步由 slice-gate.py start 机械完成。
  • gitlink 冲突交给新增的 slice-gate.py merge 脚本处理：在家 submodule 内合并，再钉 gitlink。
  • 门禁、快照、起飞前校验都会把 gitlink 展开成 submodule 内的文件来判。
不含 submodule 的仓库，行为与现在逐项一致。

2 · 实验证据（/tmp 玩具仓，git 2.54；脚本 /tmp/subm-exp/exp1.sh、exp2.sh）

实验做了什么结果
E1
  • 父仓建 change 家 worktree，家 submodule 做一个本地、未 push 的提交，并钉 gitlink。
  • 另开一个隔离 worktree，执行 git -C 家/admin/viewer worktree add --detach 隔离/admin/viewer <gitlink>。
  • 在隔离 worktree 的 submodule 内提交，再在父仓 git add admin/viewer 提交。
 通过
  • 吸收进 modules/ 的 gitdir 带有 core.worktree，但不影响 linked worktree：toplevel 指向隔离目录。
  • 父仓 status 干净。
  • 执行体的提交在家 submodule 里立即可见（cat-file -t 返回 commit）。
  • 父仓 diff 为 :160000 160000 old new M admin/viewer。
  • git worktree remove 拒删含 submodule 的 worktree，加 --force 可以删。删除后提交对象仍在，家里的登记变为 prunable。
E2同一 wave 的 S1、S2 各开一个隔离 worktree，都改 submodule、都提交 gitlink。在家里按「父仓 merge --no-ff --no-commit → 判断 gitlink → 必要时在家 submodule 内 merge → update-index --cacheinfo 160000 → commit → 家 submodule 分支 ff」逐片合回 通过
  • S1：gitlink 是快进，无冲突。
  • S2：gitlink 冲突，在家 submodule 生成合并提交后解掉。
  • 家 submodule 分支包含双方提交，父仓 status 干净。
  • 下一 wave 的隔离 worktree 能按新 gitlink 填充。
  • 重派场景：在未填充 submodule 的隔离 worktree 里 cherry-pick 上一轮父仓提交，成功，gitlink 随之更新。
  • 家里执行 git show --submodule=diff <切片 commit>，能展开执行体在 submodule 内的 diff，路径带 admin/viewer/ 前缀。

afa 现状核对：家 submodule 的 gitdir 是 afa/.git/worktrees/raw-file-viewer/modules/admin/viewer，在共享 .git 内。分支 feat/raw-frame-viewer 的 HEAD 是 be74886，与父仓 gitlink 一致。viewer 的 .gitignore 写的是 node_modules（不带斜杠），run-viewer.sh 建的软链会被忽略，不会误报 G6。

3 · 修复后的保证

  • I1 隔离 worktree 自带 submodule：
    • 家里已初始化的每个 submodule，start 都会在隔离 worktree 里检出到 HEAD 的 gitlink。
    • 不访问远端，本地未 push 的提交也能用。
    • 家 submodule 未初始化 → G0 红，并给出修法。
  • I2 提交不丢：执行体在 submodule 内的提交进入家 submodule 的对象库；门禁同时写 ref 锚住它，防止被 gc。
  • I3 并行不冲突：同一 wave 多片改同一 submodule 时，由脚本在家 submodule 内合并后钉 gitlink；所有权不相交，所以不会出现内容冲突。合回后家 submodule 的检出和分支与 gitlink 一致。
  • I4 门禁按文件判：G3、G6、G8、GWT 看到的是 admin/viewer/src/... 这类真实文件。submodule 里有提交、但 gitlink 没提交进父仓 → 红（这种提交合回时会丢）。
  • I5 重派可续：撞上限后重派，submodule 内的半成品照样能从快照恢复。
  • I6 无 submodule 的仓库零变化：所有新逻辑都以「存在 gitlink」为前提；没有 gitlink 时，merge 子命令等价于逐条 git merge --no-ff。

4 · 全景：家 / 隔离 worktree / submodule 对象库

隔离 worktree 的实际位置以 afa 的 git worktree list 为准：在 afa 主 checkout 的 .claude/worktrees/wf_* 下，不在家目录里。所以 start 要靠 --expect-branch <branch> 在 git worktree list --porcelain 里找到检出该分支的 worktree，把它认作「家」。飞行模式起飞时已经传入 branch。

5 · 合回时序（一个 wave，S1 ∥ S2 都改 admin/viewer）

wave 起点：父仓 HEAD gitlink = GL；家 submodule 分支 tip = GL
 ├─ S1 执行体（隔离 A）: start → sub-sync 借出 A/admin/viewer@GL → 子仓提交 s1 → 父仓提交 C1（含 gitlink GL→s1 + 父仓 owns 文件）→ gate（展开判文件）
 └─ S2 执行体（隔离 B）: 同上 → s2 / C2
integrator（家）: slice-gate.py merge --change-dir … S1=C1 S2=C2
 ├─ C1: 父仓 merge --no-ff --no-commit；gitlink GL→s1 是快进 → 钉 s1 → commit "integrate: S1" → 家子仓分支 ff 到 s1
 ├─ C2: 父仓 merge → CONFLICT (submodule) 只在 gitlink 上
 │     → 家子仓（HEAD = s1）merge --no-ff s2 → M  （所有权不相交 ⇒ 无内容冲突；真冲突 → 两边都 abort，返回 ok:false）
 │     → update-index --cacheinfo 160000,M,admin/viewer → commit "integrate: S2"
 └─ 返回 {ok, merged:[S1,S2], failed:[], warnings:[]}；父仓 status 干净；下一 wave 从 gitlink M 填充

9 · 风险与回退

风险缓解残余
Q1-A 让 hook 脚本在 Claude Code 的文本检查之外，写家 submodule 的 git 元数据
  • 只做三件事：worktree add --detach、写 refs/flight/…、提交对象落库，全部在共享 .git 内。
  • 不改家的分支、不改家的工作区文件。
  • 家子仓分支只由家里的 merge 推进。
  • 写进 ADR，交人审批。
Claude Code 以后若把「写共享 .git 内其他 worktree 的元数据」也列入拦截范围，需要回到 Q1-B
含已填充 submodule 的隔离 worktree，git worktree remove 会拒删（E1）
  • 有提交的隔离 worktree 本来就保留到定期清扫。
  • G0 不通过时不填充，所以不会出现「无改动但删不掉」。
Claude Code 清扫时如何处理这种 worktree 未实测；可能残留，届时用 git worktree remove --force 加子仓 git worktree prune 清理
每个隔离 worktree 多检出一份 submodule只检出家里已初始化的 submodule；afa 的 viewer 是 197 个文件大型 submodule 会增加每片的起步耗时
家子仓有未记录进 gitlink 的本地提交，或检出了别的分支preflight 判红并给出修法；merge 开跑前再复核一次—
merge 子命令替换了 integrator 原来的手动 merge无 gitlink 时，行为由场景测试锁定为与原来等价；Agent 回退路径用的是同一个 integrator—

回退：

  • revert 本 change，回到「含 submodule 的 change 用 --gate=per-task」的现状。
  • 单个 change 也可以继续显式走 --gate=per-task：新的门禁展开对 per-task 路径同样生效，那 6 片也能写出门禁记录。
