Why · 01为何而做

baseline 从别的来源继承结论时，有两处会继承错东西。两处都是 C2（propose-speedup，#27）留下的。

- 全量耗时继承错：C2 的第一次 baseline 经锚点补跑了 131.6 秒，锚点条目里没有全量耗时，所以 full_suite_sec 留空。第二次 baseline 复用这份基线时，把它的 test.sec（也就是补跑的 131.6 秒）当成全量耗时记下，而真实全量约 470 秒。final 的超时上限因此只有 3 × 131.6 ≈ 395 秒，两次 final 都以「G2 test：增量重跑超时」红掉（openspec/changes/propose-speedup/gate-report.md 第 11、12 行）。 - 预热来源随机：预热（slice-gate.py warm）按 slices.json 的修改时间选来源 change。新 worktree 里全部 32 个 slices.json 的修改时间完全相同（实测），选中的其实是目录遍历顺序里排在前面的那个。本仓库各 change 的 gate.test 都一样，所以没出过事；下游仓库的 gate.test 一旦换过，就可能沿用到旧命令。

What · 02变更范围

  • 锚点条目带全量耗时：全量 baseline 与全量 final 写锚点时记下本次全量耗时 full_suite_sec；增量 baseline 与增量 final 写的新锚点沿用来源锚点的值，沿锚点链一路传下去。
  • 经锚点的 baseline 继承全量耗时：取值顺序是本 change 上一次已知的全量耗时（例如预热），再到来源锚点的 full_suite_sec。
  • 增量来源不再拿 test.sec 充当全量：复用本 change 旧基线时，只有那份旧基线是全量运行，才用它的 test.sec；它本身是增量时，full_suite_sec 留空（final 超时上限退到 600 秒）。基线池只收全量结果，行为不变。
  • 预热来源按 git 最后提交时间选：取每个 change 的 slices.json 在 git 里最后一次提交的时间，最新的胜出；时间相同取 change 名字典序最后一个；从没提交过的排在所有已提交的之后，它们之间也按名字定。
  • 文档措辞：/opsx-propose 命令与同名 skill 里「沿用最近一个 change 的 gate.test」改为「沿用最后提交的 change 的 gate.test」，两处同改。
代码：template/.claude/hooks/slice-gate.py，涉及 _run_baseline 的全量耗时取值段、全量 baseline 与全量 final 的锚点写入、_anchor_forward、_warm_source。数据：锚点池条目（<git common dir>/flight-anchors/*.json）新增可选字段 full_suite_sec。旧条目没有这个字段时按「未知」处理，不需要迁移。文档：template/.claude/commands/opsx-propose.md、template/.claude/skills/openspec-propose/SKILL.md 各一行。测试：新增 tests/test_baseline_full_sec.py、tests/test_warm_source.py。tests/test_baseline_pool.py 断言基线池复用时 full_suite_sec == test.sec，这条行为不变，需保持绿。

Specs · 04行为规范 (Gherkin)

baseline-full-suite-sec ADDED

Requirement: 锚点条目记录全量耗时

全量 baseline 写出的锚点 SHALL 带 full_suite_sec，值等于该基线记下的全量耗时。增量 baseline 与增量 final 写出的新锚点 SHALL 沿用来源锚点的 full_suite_sec。全量 final 写出的锚点 SHALL 带本次全量运行的耗时。

Feature: 全量耗时沿锚点链传递 Rule: 锚点是跨 change 复用的来源，全量耗时要跟着锚点走

Scenario: anchor-carries-full-suite-sec

  • GIVENchange c 跑过一次全量 baseline
  • WHEN读取锚点池里最新的锚点
  • THEN它的 full_suite_sec 是数值，等于 c 的 gate-baseline.json 里的 full_suite_sec

Scenario: final-anchor-keeps-full-suite-sec

  • GIVENchange c 跑过一次全量 baseline，记下的全量耗时为 T；之后提交了非测试文件 src/a.py 的改动
  • WHEN对 c 运行 final，读取锚点池里最新的锚点；再运行 final --full，再读一次
  • THEN第一次 final 走增量，最新锚点的 full_suite_sec 等于 T
  • ANDfinal --full 之后，最新锚点的 full_suite_sec 是大于 0 的数值

Requirement: 经锚点的 baseline 继承全量耗时

经锚点走增量的 baseline，在本 change 没有已知全量耗时时，SHALL 把来源锚点的 full_suite_sec 记作自己的 full_suite_sec，SHALL NOT 用补跑耗时代替。

Feature: 增量基线的全量耗时 Rule: 全量耗时只来自真实的全量测量

Scenario: anchor-baseline-inherits-full-suite-sec

  • GIVENchange other 跑过全量 baseline，全量耗时为 T；change c 与 other 的 gate.test 相同，c 还没有基线
  • WHEN对 c 运行 baseline
  • THENc 的基线经锚点走增量，来源是 other
  • ANDc 的 full_suite_sec 等于 T

Requirement: 复用增量基线不拿补跑耗时充当全量

复用本 change 旧基线时，旧基线 mode 为 incremental 且没有 full_suite_sec，新基线的 full_suite_sec SHALL 为空，SHALL NOT 取旧基线的 test.sec。旧基线带 full_suite_sec 时 SHALL 沿用它。

Feature: 复用链上的全量耗时 Rule: 增量基线的 test.sec 是补跑耗时，不是全量耗时

Scenario: own-reuse-keeps-inherited-full-suite-sec

  • GIVENchange c 的基线经 other 的锚点走增量，full_suite_sec 等于 other 的全量耗时 T
  • AND之后只提交了测试文件的改动
  • WHEN再对 c 运行 baseline
  • THENc 的基线复用本 change 旧基线（增量）
  • ANDfull_suite_sec 仍等于 T，不等于本次或上次的 test.sec

Scenario: legacy-anchor-leaves-full-suite-sec-unknown

  • GIVENchange other 跑过全量 baseline，锚点池里的锚点都去掉了 full_suite_sec（模拟旧版本写的锚点）；change c 还没有基线
  • WHEN对 c 运行 baseline，之后只提交测试文件的改动，再运行一次 baseline
  • THEN两次 c 的基线都是增量，full_suite_sec 都为空

warm-source-selection ADDED

Requirement: 预热按 git 最后提交时间选来源

slice-gate.py warm 在没有 --cmd 时，SHALL 从 changes 根下其它 change 中选来源。候选是除 archive 与本 change 外，slices.json 存在且 gate.test 非空的 change。选择规则如下： - 取 slices.json 在 git 里最后一次提交时间最新的； - 时间相同取 change 名字典序最大的； - 从没提交过的排在所有已提交的之后，它们之间同样按名字取。

结果 SHALL NOT 取决于文件修改时间。

Feature: 预热来源确定 Rule: 同一份 git 历史与 change 集合，预热总是选中同一个来源

Scenario: warm-picks-latest-committed-change

  • GIVENchange old 与 new 的 gate.test 不同；new 的 slices.json 在 old 之后提交；之后把 old 的 slices.json 的修改时间改得比 new 晚
  • WHEN对新 change c 运行 warm
  • THEN退出 0，stdout 的 test_cmd 是 new 的 gate.test

Scenario: warm-breaks-commit-tie-by-name

  • GIVENchange alpha 与 beta 的 gate.test 不同，两者的 slices.json 在同一次提交里
  • WHEN对新 change c 运行 warm
  • THEN退出 0，stdout 的 test_cmd 是 beta 的 gate.test

Scenario: warm-ranks-uncommitted-after-committed

  • GIVENchange kept 的 slices.json 已提交；change draft 的 slices.json 从没提交过，修改时间更晚；两者 gate.test 不同
  • WHEN对新 change c 运行 warm
  • THEN退出 0，stdout 的 test_cmd 是 kept 的 gate.test

Design · 05技术设计

Context

本 change 命中两条触发器： - 数据模型：锚点池条目新增字段 full_suite_sec； - 跨模块：baseline 与 final 写锚点，baseline、final、preflight 读全量耗时。

全量耗时的现状（slice-gate.py）：

  • 读取只经 suite_sec(change_dir, data)。取值顺序是 gate-baseline.json 顶层的 full_suite_sec，再到计划里旧的 gate.full_suite_sec（DRAFT-measurements-stay-out-of-plan-files 决策 2、3）。
  • final 的超时上限是 _g7_timeout：有全量耗时时取 max(120, 3 × 全量耗时)，没有时取 600 秒。
  • baseline 结束时按下面的顺序写 full_suite_sec（_run_baseline 结尾，约 5207–5214 行）：

| 情形 | 取值顺序（现状） | |---|---| | 全量运行 | 本次墙钟 | | 增量（复用旧基线 / 锚点 / 基线池） | last_sec（开跑前 suite_sec）→ src.full_suite_sec → src.test.sec |

缺陷链：C2 实测，各 change 的 gate-baseline.json 与 timeline.md 可查。

`` baseline #1（经锚点） last_sec=None · 锚点包装没有 full_suite_sec / test → full_suite_sec = None；test.sec = 补跑 131.6s baseline #2（复用 #1） last_sec=None · src=#1：full_suite_sec=None → 取 src.test.sec = 131.6 → full_suite_sec = 131.6（真实全量约 470s） final 超时上限 3 × 131.6 = 394.8s；增量重跑 394.9s → 「G2 test：增量重跑超时」×2 ``

预热来源的现状：_warm_source 在 changes 根下按 slices.json 的 os.path.getmtime 取最新的那个，比较用严格的 >。新 worktree 是一次检出的，32 个 slices.json 的 mtime 完全相同（实测），结果取决于 os.listdir 的顺序。

Goals / Non-Goals

Goals: - 增量 baseline 的 full_suite_sec 只来自真实的全量测量（本次全量、预热、来源锚点沿链继承下来的全量）；取不到时留空，不拿补跑秒数充当全量。 - 锚点条目带上全量耗时，并随增量 baseline 与增量 final 写出的新锚点传下去。 - 预热来源的选择只取决于 git 历史与 change 名，和检出时刻、文件系统顺序都无关。

Non-Goals: - 不改 _g7_timeout 的公式与 600 秒缺省。 - 不回填旧锚点：没有字段就按未知处理（用户 2026-11-20 选定）。 - 不改基线池：池只收全绿的全量，它的 test.sec 就是全量耗时，tests/test_baseline_pool.py 钉住的行为保持。 - 不改预热的其它规则：分层仓库跳过、--cmd 显式命令、包装脚本沿用都不动。

Decisions

last_sec 仍然排第一

沿用 DRAFT-measurements-stay-out-of-plan-files 决策 2「增量基线沿用上一份的值」。预热写的就是真实全量，排第一能让 /opsx-propose 的常规流程拿到最新测量。

判定「是不是增量」

旧基线看自己的 mode 字段。基线池条目没有 mode，但按 _pool_write 的入池条件（hit is None）全是全量，所以按全量处理。

备选

锚点值优先于 last_sec。被否：last_sec 来自本 change 自己的测量，比跨 change 的锚点更贴近当前代码树；两者都是真实的全量测量。

排序键

每个候选 change（除 archive 与本 change 外，slices.json 存在且 gate.test 非空）记作 (提交时间, 名字)，取最大的那个。

提交时间

git 里最后一次改动该 slices.json 的提交的 committer 时间（%ct）。

从没提交过的

提交时间记为 -1，所以排在所有已提交的之后。

时间相同

取名字字典序最大的。

取时间的方式

一次 git log --format=%ct --name-only -- <changes 根>/*/slices.json，逐行解析，每个路径取第一次出现时的时间（git log 从新到旧排，第一次出现的就是最新提交）。git 调用失败时，全部按 -1 处理，退化为按名字排序。

备选
最近一条锚点所属的 change

锚点池为空、或那个 change 已经归档时还得再退一步，规则更长。被否（用户 2026-11-20 选定 git 提交时间）。

只按名字排序

确定，但名字和新旧无关。被否。

边界

slice-gate.py 是唯一的写方；锚点池是跨 change 共享的测量存储；gate-baseline.json 是本 change 的测量归宿。

假设

锚点池里的旧条目没有 full_suite_sec，按未知处理。

Risks / Trade-offs

[风险] 过渡期旧锚点没有字段

经旧锚点、本 change 又没有预热时，full_suite_sec 为空，final 超时上限退到 600 秒。本仓库 C2 的增量 final 跑过 609.6 秒，可能超时。→ 缓解：

/opsx-propose 的常规流程先预热，last_sec 排第一；
锚点池只留最新 20 条，每次 baseline / final 都写新锚点，旧条目很快被挤出；
必要时可设 FLIGHT_G7_TIMEOUT 临时覆盖超时上限（现有行为）。
[风险] git 调用失败

比如不在 git 仓库内。→ 全部按 -1 退化为按名字排序，结果仍然确定，预热照常进行。

[权衡] 已提交的旧 change 会胜过没提交的新 change

同一 worktree 里正在规划、还没提交的另一个 change，排在已提交的后面。这种布局本来就少见（每个 change 有自己的 worktree），换来的是结果不依赖检出时刻。

Migration Plan

  • 不迁移数据：旧锚点没有字段按未知处理，旧 gate-baseline.json 不改。
  • 回滚：revert 本 change 的代码 commit 即可。新锚点多出的字段旧代码不读，不影响回滚。

Open Questions

  • 无。两项决策已在 grill-me 定下（2026-11-20）：预热来源按 git 最后提交时间；旧锚点留空、退到 600 秒。
  • 与在役 ADR 一致：DRAFT-measurements-stay-out-of-plan-files 规定增量基线沿用上一份的值、读取经 suite_sec，本 change 两条都沿用，不需要 supersede。
