Why · 01为何而做

afa 的 key-features-keyft 飞行一共要了 4 次「起飞」，其中 2 次与计划内容无关，是模板自己造成的（交接 F8）：

- baseline 改计划文件：slice-gate.py baseline 结束时无条件重写 slices.json，把全量耗时回填到 gate.full_suite_sec（slice-gate.py:4196）。起飞门禁按 slices.json 的修改时间判批准是否过期（takeoff-gate.py:43、:212）。baseline 在后台跑，人在它结束前批准，或批准后重跑 baseline，批准必然过期。 - 子仓 gitlink 的指纹前后不一：基线的内容快照不记子仓目录（_snapshot 跳过目录）。gitlink 在 baseline 时只是暂存、随后提交，preflight 就判「基线过期：自基线以来有改动：<子仓>」，只能重跑 baseline。

同一次飞行还暴露了另一件事（交接 F10 / T3）：包装脚本不转发运行器契约变量，依赖图从没测到，final 每次都整跑 gate.test。这件事只出现在基线的 warnings 与 flight-doctor 的输出里，不拦任何步骤；afa 已有 14 份基线带着同一条告警起飞。2026-11-09 那轮定的是「只预告、不阻断」（unified-test-result-reuse design 的 Q3），结果就是没人处理。

2026-11-18 用户在方案页 docs/flight-fixes-and-test-governance.html 里定下（本 change 是其中的 C1；这些决策来自该页的问答，没有另开 grill-me 访谈）：

- Q5 = A（表态制）：契约没接、依赖图未测时判红，直到修好，或在计划里写明接受全量的理由，理由显示在 spec.html。 - 范围：只做计划卫生四件事；inert 声明、final 的无图退路、pr-ship 先裁决再重跑属于后面的 C1b；全机测试闸与 final 耗时进时间线属于 C2。

What · 02变更范围

  • baseline 不再写 slices.json（template/.claude/hooks/slice-gate.py）：
  • 全量耗时改记在 gate-baseline.json 顶层的 full_suite_sec；增量基线沿用上一份的值，没有时取候选的测试耗时（语义与原来回填 slices.json 时相同）。
  • 运行标记（{"running": true, …}）带上上一份的 full_suite_sec，「基线仍在跑」的提示才说得出「上次全量约 N 秒」。
  • 三处读取方改读基线：G7 超时推算、运行中提示、flight-doctor.py forecast 的 final.sec。读不到再认旧的 gate.full_suite_sec（过渡，已安装仓库的在途 change 不用改）。
  • gate.test 缺失时 baseline 直接停（与 lint「须显式写出」一致），不再探测后写回。
  • BREAKING（对读 slices.json 取耗时的外部脚本）：gate.full_suite_sec 不再由模板写入；模板自带的读取方都已改。
  • 子仓 gitlink 进内容快照（slice-gate.py 的 _snapshot）：有未提交改动的 gitlink 路径记子仓当前 HEAD 的 commit，与提交后树里的值同口径。gitlink 暂存后再提交，基线不再过期。
  • 依赖图未测须表态（slice-gate.py 的选测复核）：
  • 本 change 的基线带 deps_unmeasured 时，选测复核多一个伪触发项 runner:deps-unmeasured，沿用现有的 gate.scope_full_reason 机制：没写理由 → lint、preflight 判红，final 开跑前复核判 G2 scope 红；违规文字带未测类别与契约文档路径。
  • 豁免：配了 gate.impacted（仓库自己选测）；内建声明下的非 pytest 运行器与部件形态（在役 ADR 已定为设计边界）。
  • 基线还没跑出来时不判红，允许预写这条理由；包装脚本的静态闭包里没出现 FLIGHT_PYTEST_ARGS 与 FLIGHT_PLUGIN_PATH 时，lint 打印一行提示并点名脚本。
  • 增量基线（复用旧结论）沿用来源的 deps_unmeasured，状态不因「这次没重测」而消失。
  • ship 的「final 过期」理由带补跑预告（slice-gate.py 的 cmd_ship）：后面接一句「补跑将是增量（锚点 …，Δ N 个文件）」或「补跑将是全量（原因）」。预告函数放在 slice-gate.py，flight-doctor.py forecast 改为调用同一个函数。
  • 文档（命令与同名 skill 同改）：opsx-propose.md / openspec-propose/SKILL.md 删掉「耗时写回 slices.json」的两处说法，写明 baseline 不改计划文件、baseline 报告后重跑一次 lint 以及红了怎么办；flight-runner-contract.md、README.md、schema 的 tasks instruction 补上 runner:deps-unmeasured。
  • 不做：
  • 起飞门禁的新鲜度判据仍按修改时间，不改成内容指纹（baseline 不写计划文件之后，修改时间已经稳定）。
  • 不调换「工件在 baseline 报告之后提交」的顺序（见 design D4：提前提交会让 gate-baseline.json 把工作树弄脏，/opsx-apply 的干净检查会拦下）。
  • 不改 flight-doctor.py 恒退出 0 的约定；doctor / cost 两个子命令不动。
  • 不给 not-pytest 之外的仓库引入新的选测手段；inert、无图退路、全机锁都不在本 change。
代码：template/.claude/hooks/slice-gate.py、template/.claude/hooks/flight-doctor.py。文档：template/.claude/commands/opsx-propose.md、template/.claude/skills/openspec-propose/SKILL.md、template/.claude/flight-runner-contract.md、template/openspec/schemas/intent-driven/schema.yaml、README.md。ADR：新增 DRAFT-measurements-stay-out-of-plan-files.md、DRAFT-unmeasured-deps-need-plan-statement.md。测试：新增 4 个测试文件；改 4 个钉着「耗时写回 slices.json」的旧测试（tests/test_slice_gate.py、tests/test_baseline_pool.py、tests/test_baseline_incremental.py、tests/test_slice_gate_baseline_preflight.py）。下游：已安装的仓库跑 ./install.sh --upgrade 后：在途 change 不用重跑 baseline，旧的 gate.full_suite_sec 仍被读取；依赖图未测的仓库（afa 的 executor）下一次 lint / preflight 会判红，须修包装脚本或写理由——这是本 change 要的效果，升级说明里要写明。

Capabilities · 03能力清单

New

plan-hygiene：baseline 不改计划文件；全量耗时记在基线里并被三处读取方使用；gate.test 缺失即停；子仓 gitlink 计入内容快照。

New

runner-statement：基线的依赖图没测到时，计划必须在 gate.scope_full_reason 为 runner:deps-unmeasured 写理由，lint / preflight / final 复核同一口径。

New

ship-rerun-forecast：ship 判「final 过期」时说明补跑是增量还是全量；成本预告与它用同一个判定函数。

Modified

无。template/openspec/specs/ 不存在，现有行为的规格都还在各自的 change 目录里；本 change 的增量全部以 ADDED 写在上面三个新 capability 里。

Specs · 04行为规范 (Gherkin)

plan-hygiene ADDED

Requirement: baseline 不改计划文件

slice-gate.py baseline MUST NOT 写 slices.json，也 MUST NOT 写本 change 的任何其他计划工件（proposal.md / design.md / specs/** / 切片包）；它只写 gate-baseline.json 与飞行记录。gate.test 缺失时 baseline SHALL 在写运行标记之前以非 0 退出并点名 gate.test，MUST NOT 探测测试命令后写回。「运行期间 gate / verify 被修改」的判定 SHALL 保留。 Feature: 批准之后，测量不让批准过期 Rule: 计划文件的内容全部来自人批准的那一版；脚本测出来的东西不往里写

Scenario: baseline-leaves-plan-file-untouched

  • GIVEN一个已提交的 change，gate.test 是直接的 pytest 调用，slices.json 里没有 full_suite_sec
  • ANDslices.json 的修改时间被钉在过去的某一刻
  • WHEN运行 slice-gate.py baseline
  • THEN退出码为 0
  • ANDslices.json 的字节与修改时间都没有变
  • ANDgate-baseline.json 顶层的 full_suite_sec 是一个数值

Scenario: approval-survives-baseline-rerun

  • GIVEN一个跑过一次 baseline 的 change，计划工件的修改时间早于人类在会话里说「起飞」的时间
  • WHEN在批准之后再运行一次 slice-gate.py baseline --full，然后运行 takeoff-gate.py --change-dir <change> --session <转录>
  • THEN起飞门禁退出码为 0，stdout 是那条批准证据

Scenario: baseline-stops-without-gate-test

  • GIVEN一个已提交的 change，slices.json 的 gate.test 为空，仓库里有 tests/ 目录（探测得出 pytest 命令）
  • WHEN运行 slice-gate.py baseline
  • THEN退出码非 0，stderr 点名 gate.test
  • AND没有生成 gate-baseline.json，slices.json 的字节没有变

Requirement: 全量耗时记在基线里，读取方都从基线取

全量基线 SHALL 把本次全量测试的墙钟秒数写进 gate-baseline.json 顶层的 full_suite_sec；增量基线 SHALL 沿用本 change 上一份基线的值（没有时依次取旧计划的 gate.full_suite_sec、候选的 full_suite_sec、候选的 test.sec）。运行标记 SHALL 带上开跑前已知的 full_suite_sec。slice-gate.py SHALL 提供 suite_sec(change_dir, data=None)：先取 gate-baseline.json（含运行标记）里的数值，取不到再取计划里旧的 gate.full_suite_sec，都没有返回 None，布尔值不算数值；G7 超时推算、「基线仍在跑」的提示与成本预告 SHALL 都经它取值。 Feature: 耗时换个地方记，用它的地方照常工作 Rule: 新字段优先，旧字段只作回退；已安装仓库的在途 change 不用重跑 baseline

Scenario: incremental-baseline-keeps-suite-sec

  • GIVEN一个 change 跑过一次全量基线，gate-baseline.json 的 full_suite_sec 为某个数值
  • AND之后只改了一个测试文件并提交
  • WHEN再运行 slice-gate.py baseline
  • THEN新基线的 mode 为 incremental
  • AND它的 full_suite_sec 与第一次相同

Scenario: running-marker-carries-last-suite-sec

  • GIVEN一个 change 跑过一次基线，gate.test 是一个在运行期间读取 gate-baseline.json 的脚本
  • WHEN再运行 slice-gate.py baseline --full，脚本在运行期间检查该文件
  • THEN脚本看到的是运行标记（running 为真），且其中 full_suite_sec 等于上一份基线的值

Scenario: running-baseline-hint-shows-last-suite-sec

  • GIVENchange 的 gate-baseline.json 是一个进程仍在的运行标记，full_suite_sec 为 12.5，slices.json 里没有 full_suite_sec
  • WHEN运行 slice-gate.py preflight
  • THEN退出码非 0，stderr 含「仍在跑」与「12.5 秒」

Scenario: suite-sec-resolver-prefers-baseline

  • GIVEN一个 change 目录，计划里旧的 gate.full_suite_sec 为 816
  • WHEN分别在四种状态下调用 suite_sec：没有基线；基线的 full_suite_sec 为 300.5；基线的 full_suite_sec 为布尔值 true；没有基线且计划里也没有该字段
  • THEN依次得到 816、300.5、816、None

Requirement: 子仓 gitlink 计入内容快照

基线的内容快照 SHALL 对有未提交改动的 gitlink 路径记录子仓当前 HEAD 的 commit（子仓未就绪时记索引里的值），使「gitlink 已暂存」与「同一 gitlink 已提交」按内容判为相同。其他目录 MUST 照旧不记。 Feature: 带子仓的 change 提交工件后不必重跑基线 Rule: 快照里 gitlink 的取值与 git 树里的表示同口径

Scenario: staged-gitlink-commit-keeps-baseline-fresh

  • GIVEN一个带子仓的仓库，change 的计划已提交
  • AND子仓里新增了一个提交，父仓把新的 gitlink 暂存但还没提交
  • WHEN运行 slice-gate.py baseline，随后把 gitlink 与基线文件一起提交，再运行 slice-gate.py preflight
  • THENpreflight 退出码为 0，不报「基线过期」

Requirement: propose 文档写明 baseline 不改计划文件

opsx-propose.md 与 openspec-propose/SKILL.md SHALL 用同一句话写明 baseline 的耗时记在 gate-baseline.json、不改计划文件；SHALL 用同一句话写明子仓 gitlink 的改动与计划工件同一次提交；MUST NOT 再出现「耗时写回 slices.json」的说法。 Feature: 文档与脚本说同一件事 Rule: 命令与同名 skill 同改

Scenario: propose-docs-say-baseline-leaves-plan-alone

  • GIVENtemplate/.claude/commands/opsx-propose.md 与 template/.claude/skills/openspec-propose/SKILL.md
  • WHEN阅读两份文档的基线步骤与硬交接
  • THEN两处都不含 full_suite_sec，也不含「slices.json 的耗时」
  • AND两处有同一行同时含 gate-baseline.json、「耗时」与「不改」「计划文件」
  • AND两处有同一行同时含 gitlink 与「同一次提交」

runner-statement ADDED

Requirement: 基线的依赖图未测时计划须表态

本 change 有一份跑完的基线且它带 deps_unmeasured 时，选测复核 SHALL 追加伪触发项 runner:deps-unmeasured，按现有 gate.scope_full_reason 的规则处置：slice-gate.py lint 与 preflight 在计划没为它写理由时 SHALL 判红，违规文字 SHALL 含该触发项、gate.scope_full_reason、未测类别与 .claude/flight-runner-contract.md；final 开跑前复核 SHALL 在它不在已批准的理由里时判 G2 scope 红且不运行测试（final --full 豁免）。计划配了 gate.impacted，或属于在役的设计边界（内建声明下的非 pytest 运行器、部件形态）时 MUST NOT 追加。基线测到了依赖图时，计划里留着的这条理由 SHALL 按「不是本次触发项」判红。理由 MUST NOT 计入 plan_sha。 Feature: 依赖图没接通不能再被无视 Rule: 要么修好，要么写理由给批准的人看；判定以基线为准，不以脚本文本为准

Scenario: unmeasured-baseline-needs-statement

  • THEN退出码非 0，有一行违规同时含 runner:deps-unmeasured、gate.scope_full_reason、plugins-dropped 与 flight-runner-contract.md
  • AND给计划加上 gate.impacted 后再运行 lint，退出码为 0

Scenario: statement-lets-lint-and-preflight-pass

  • GIVEN同样的包装脚本，计划在 gate.scope_full_reason 为 runner:deps-unmeasured 写了理由
  • ANDbaseline 已跑完并提交，依赖图未测
  • WHEN运行 slice-gate.py lint 与 slice-gate.py preflight
  • THEN两者退出码都为 0

Scenario: measured-baseline-rejects-leftover-statement

  • GIVEN一个 change 的 gate.test 是按契约转发两个变量的包装脚本，计划却为 runner:deps-unmeasured 写了理由
  • ANDbaseline 已跑完，依赖图已测到（没有 deps_unmeasured）
  • WHEN运行 slice-gate.py lint
  • THEN退出码非 0，有一行违规同时含 runner:deps-unmeasured 与「删除」

Scenario: final-refuses-unstated-unmeasured

  • GIVEN一个 change 的基线依赖图未测，计划没写理由，没有 approve 提交
  • WHEN运行 slice-gate.py final
  • THENfinal 为红，失败项有一条以 G2 scope 开头、含 runner:deps-unmeasured
  • ANDgate.test 没有被运行

Requirement: 基线跑出来之前可以预写理由，脚本文本只作提示

还没有跑完的基线时，以及 baseline 开跑前的复核里，runner:deps-unmeasured SHALL 是待定项：计划可以预写理由，不写也不判红。此时若 gate.test 不是可识别的直接测试命令、没配 gate.impacted，且命令里直接写出的仓库文件及其 shell 静态闭包的文本里没有同时出现 FLIGHT_PYTEST_ARGS 与 FLIGHT_PLUGIN_PATH，lint 通过时 SHALL 多打印一行以 runner: 开头的提示，点名命令里直接写出的脚本与这两个变量；这行提示 MUST NOT 影响退出码。 Feature: 计划期就能看见风险，但不凭猜测拦人 Rule: 文本是线索，基线是事实

Scenario: statement-may-be-prewritten-before-baseline

  • WHEN先不写理由运行 slice-gate.py lint；再为 runner:deps-unmeasured 写上理由运行一次
  • THEN两次退出码都为 0
  • AND第一次的 stderr 有一行以 runner: 开头，含 tools/gate.sh 与 FLIGHT_PYTEST_ARGS
  • AND把脚本换成按契约转发两个变量的版本后运行 lint，stderr 没有以 runner: 开头的行

Requirement: 增量基线沿用来源的未测状态

Scenario: incremental-baseline-keeps-unmeasured-state

  • AND之后只改了一个测试文件并提交

flight-runner-contract.md、README.md、schema 的 tasks instruction 与 propose 的命令 / 同名 skill SHALL 写明伪触发项 runner:deps-unmeasured：何时出现、怎么消除（修包装脚本后重跑 baseline，或配 gate.impacted）、怎么表态（gate.scope_full_reason）。propose 的两份文档 SHALL 用同一句话要求 baseline 报告之后重跑一次 slice-gate.py lint。schema MUST 保持 openspec schema validate intent-driven 通过。 Feature: 接入方与写计划的模型都知道这条规则 Rule: 契约文档是项目侧的唯一依据

  • THEN契约文档含 runner:deps-unmeasured、gate.scope_full_reason 与 gate.impacted

  • ANDschema 的 tasks instruction 含 runner:deps-unmeasured
  • ANDpropose 的两份文档有同一行同时含 slice-gate.py lint 与 runner:deps-unmeasured

ship-rerun-forecast ADDED

Requirement: ship 的「final 过期」理由带补跑预告

slice-gate.py ship 判定 final 过期时，SHALL 在该条理由后追加补跑预告：预计走增量时写「补跑将是增量」与锚点、Δ 文件数；预计走全量时写「补跑将是全量」与原因；计划配了 gate.impacted 时写「补跑由 gate.impacted 选测」。预告 SHALL 由 slice-gate.py 自己的判定函数给出，MUST NOT 调用 flight-doctor.py；预告算不出或出错时 MUST NOT 影响裁决与退出码，该条理由保持原样。 Feature: 说「过期」的同时说清补一次要多大代价 Rule: 裁决不因预告而失败

Scenario: stale-final-reason-says-incremental-rerun

  • GIVEN一个 change 的基线测到了依赖图，final 已绿并留下锚点
  • AND之后提交了对一个源码文件的修改
  • WHEN运行 slice-gate.py ship
  • THEN退出码为 1
  • AND有一条理由同时含「final 过期」与「补跑将是增量」

Scenario: stale-final-reason-says-full-rerun-with-why

  • GIVEN同样的 change，final 已绿并留下锚点
  • AND之后提交了对全局文件 pytest.ini 的修改
  • WHEN运行 slice-gate.py ship
  • THEN退出码为 1
  • AND有一条理由同时含「final 过期」「补跑将是全量」与 pytest.ini

Requirement: 成本预告与 ship 用同一个判定，耗时取自基线

flight-doctor.py forecast 对 final 的预告 SHALL 调用 slice-gate.py 的同一个判定函数，输出的 mode 与 why 文字 MUST 与改动前一致；final.sec SHALL 经 suite_sec 取值（基线优先，旧计划字段作回退）。flight-doctor.py MUST 仍恒退出 0。 Feature: 一个判定，两处使用 Rule: 预告的文字是 spec.html 与人读的输出，搬家不改字

Scenario: forecast-reads-suite-sec-from-baseline

  • GIVEN一个 change 的 slices.json 里没有 full_suite_sec，gate-baseline.json 的 full_suite_sec 为 300.5
  • WHEN运行 flight-doctor.py forecast --json
  • THEN退出码为 0，final.sec 为 300.5
  • AND另一个 change 的基线没有该字段、计划里旧的 gate.full_suite_sec 为 816 时，final.sec 为 816

Design · 05技术设计

Context

现状（行号指 template/.claude/hooks/，main b7be9ed）：

  • baseline 写计划文件：cmd_baseline 结束时重读 slices.json，回填 gate.full_suite_sec（缺 gate.test 时连同探测到的命令），再整份 save_plan（slice-gate.py:4187–4196）。这是全仓唯一一处 save_plan 调用。
  • 起飞门禁按修改时间判新鲜：takeoff-gate.py 的计划工件是 proposal.md / design.md / slices.json / specs/**/spec.md（:43、:212），人类批准的时间早于它们的最大修改时间即「批准已过期」。
  • 耗时有三处读取方：_g7_timeout（slice-gate.py:2887，G7 与增量重跑的超时 = 3 倍全量耗时）、_die_running_baseline（:4303，「上次全量约 N 秒」）、flight-doctor.py:142（成本预告的 final.sec）。
  • 内容快照不记子仓：_snapshot 遇到目录直接跳过（:4626，注释「目录（嵌套仓库 / 子模块）不记」）。gitlink 暂存时快照里没有它，提交后 _delta 从两棵树里读到新旧两个 commit → 判为改动。
  • 依赖图未测只是告警：全量基线测不到依赖图时写 deps_unmeasured: {kind, why} 与一条 warning（:4206–4208）；flight-doctor 恒退出 0。
  • 表态机制已经有一套：选测退化为全选时，gate.scope_full_reason 须逐个触发项写理由（_scope_reason_errors）；lint、preflight、baseline 开跑前经 _lint_scope 复核，final 开跑前经 _final_scope_guard 与 approve 提交里的理由对账；spec.html 的「选测范围」小节把理由表原样列出（spec_html.py:621）。已有一个伪触发项先例 scope:undeclared。
  • ship 的过期理由只有两个 commit：final 过期：记录 X，HEAD Y（:5699）。「补跑要多久」要另跑 flight-doctor.py forecast，而它的判定写在 flight-doctor.py 的 _final_part 里。

用户决策（2026-11-18，方案页 docs/flight-fixes-and-test-governance.html）：Q5 = A，契约没接 / 依赖图未测走表态制；本 change 只做 C1。

在役 ADR 的约束：

  • DRAFT-repo-selector-reports-scope-at-plan-time 决策 5、6、7（逐项表态、审批页可见、理由不进 plan_sha）与 DRAFT-scope-provider-mandatory-with-runtime-guard 决策 4、5（开跑前复核、理由以 approve 提交为准）：D3 直接复用，不改。
  • DRAFT-builtin-scope-provider-and-shell-closure：「非 pytest 运行器与部件形态的 final 恒全量，属于设计边界，只注明，不要求写理由」。D3 保留这条豁免。
  • DRAFT-baseline-reuse-by-content-fingerprint：快照记「未提交改动的 git blob id；软链取链接文本的 blob」。D2 给 gitlink 补一种取值，是同一规则的延伸，不取代它。
  • DRAFT-gate-test-result-handoff-and-runner-contract 决策 4（依赖图未测给四类原因与修法）：D3 在它之上加处置，不改分类。

``` C4 · 容器图（轻量 C4 风格；◆ 修改，✂ 删除的写入）

  • 边界：计划文件只由人和 propose 写；脚本测出来的东西只进 gate-baseline.json 与飞行记录。
  • 强制点：依赖图未测的处置落在已有的三处复核上，不新增复核点。
  • 假设：下游仓库读 gate.full_suite_sec 的只有模板自带的三处；外部脚本若读它，升级后拿到的是旧值（不再更新）。

Goals / Non-Goals

Goals：

  • 批准之后，baseline 何时结束、重跑几次，都不让批准过期。
  • 子仓 gitlink 暂存后再提交，基线不过期。
  • 依赖图未测不能再被无视：要么修好，要么在计划里写理由给批准的人看。
  • ship 说「final 过期」时，同一句里说清补跑的代价。

Non-Goals：

  • 不改起飞门禁的判据（仍按修改时间）。
  • 不做 inert 声明、final 的无图退路、pr-ship 先裁决再重跑（C1b）。
  • 不做全机测试闸、final 耗时进时间线（C2）。
  • 不改变「非 pytest 运行器 / 部件形态」的设计边界豁免。
  • 不让 flight-doctor.py 阻断任何步骤。

Decisions

写
全量基线

gate-baseline.json 顶层 full_suite_sec = 本次 gate.test 的墙钟（部件形态 = 各部件单元层之和），与原来回填的数相同。

增量基线（任一复用路径）

沿用本 change 上一份基线的 full_suite_sec；没有时取旧计划里的 gate.full_suite_sec；再没有取候选的 full_suite_sec，最后取候选 test.sec。与原回填逻辑（:4192–4195）语义一致。

运行标记

{"running": true, "pid", "started"} 之外带上开跑前解析到的 full_suite_sec（没有就不带）。

读

新增一个解析函数 suite_sec(change_dir, data=None)：gate-baseline.json（含运行标记）里的数值 → 旧计划的 gate.full_suite_sec → None。三处读取方都经它取值。布尔值不算数值。

删

cmd_baseline 末尾的 save_plan 调用，以及随之无人使用的 save_plan 函数。「运行期间 gate / verify 被修改」的判定保留（结束时重读计划、比 plan_sha），只是不再写回。

gate.test 缺失

baseline 在写运行标记之前退出 2，stderr 写明 gate.test 须显式写出。原来的「探测后写回」与 lint 的硬性要求矛盾，而且不写回之后 preflight 的 plan_sha 会对不上。detect_test_cmd 仍由 final（/opsx-verify 可不经 preflight）与内建预测使用，不删。

为什么不保留字段、只是不落盘

字段留在计划里就还会有人往里写。计划文件的内容应当全部来自人批准的那一版。

否决
起飞门禁排除纯度量字段（交接的备选）

要在两个脚本里各维护一份「哪些字段不算计划」，写入方仍在改文件。

起飞门禁改比内容指纹

改动大，而且不解决「脚本写计划文件」本身。

_snapshot 遇到目录时，若该路径是索引里的 gitlink（mode 160000），记子仓当前 HEAD 的 commit；子仓未就绪（没有 .git）时记索引里的值。其他目录照旧不记。
_delta 不改

树一侧 git ls-tree 对 gitlink 给出的本来就是 commit，两边同口径。

效果

gitlink 已暂存（或子仓已前进但未暂存）时跑 baseline，之后把同一个 commit 提交进父仓，Δ 为空。

子仓工作区里的未提交内容仍不进快照（与现状相同，写进 Risks）。
判定以基线为准，不以脚本文本为准。触发条件（全部满足）
本 change 有一份跑完的基线（不是运行标记），且带 deps_unmeasured；
计划没配 gate.impacted；
不属于设计边界（_builtin_by_design

内建声明下的 npm test / go test ./... / cargo test，或部件形态）。

并入方式

在提供方报告之上追加——报告原本未全选时变为全选、触发项只有它；原本已全选时在触发项后追加它。之后走现有的 _scope_reason_errors，键集合须相等。

各阶段
违规文字

在现有「触发项 … 缺理由」之后追加一句，带未测类别（plugins-dropped 等）与 .claude/flight-runner-contract.md，让人知道修哪里。

静态检查只作提示

gate.test 不是可识别的直接测试命令、没配 gate.impacted、还没有跑完的基线时，取 _test_gate_files 的结果（命令里直接写出的仓库文件及其 shell 静态闭包），这些文件的文本里没有同时出现 FLIGHT_PYTEST_ARGS 与 FLIGHT_PLUGIN_PATH → lint 通过时在摘要后多打印一行 runner: 提示，点名直接写在命令里的脚本。

不拿它判红的原因

照常继承环境的包装脚本（如 pixi run test、一行 exec pytest "$@"）文本里没有这两个名字，依赖图却测得到；按文本判红会逼这类仓库写一条套话理由，等基线测到后又得删。基线是事实，文本只是线索。

方案页写的是「闭包里缺了就要表态」，这里改成「缺了提示、基线未测才要表态」，在 Open Questions 里点名。
增量基线沿用状态

经旧基线 / 基线池复用（非锚点）时，新基线带上来源的 deps_unmeasured；基线池条目多存这个字段。经锚点复用说明依赖图是测到的，不带。

plan_sha 不变

理由仍不进 plan_sha（在役 ADR 决策 7）。

否决
新开一个字段（如 gate.runner_unmeasured_reason）

要在 lint、final 复核、approve 绑定、spec.html 四处各接一遍，现有机制已经全有。

doctor 加退出码、接会话钩子定期打印（Q5 的 B）

仍然没有人必须回应。

把 not-pytest 也按文本静态判

非 pytest 的仓库出路是 gate.impacted，由基线的 deps_unmeasured.kind 说明即可。

方案页原想把「子仓 gitlink 与计划工件在 baseline 之前一起提交」写进 propose 指引。读代码后不采用
baseline 的产物 gate-baseline.json 在 change 目录里。工件先提交，baseline 跑完它就是未提交改动，/opsx-apply step 2 的「工件已单独 commit、工作树干净」会拦下；要放行就得再改 /opsx-apply 与它的同名 skill，或多一次提交。
顺序靠模型照文档做，gitlink 那个缺口仍在脚本里；D2 在脚本里把它补上后，先提交后提交结果相同。
文档改三处（命令与同名 skill 同文）
基线步骤

删「把耗时写回 slices.json.gate.full_suite_sec」，改为「耗时记在 gate-baseline.json，不改任何计划文件」。

硬交接第 4 条

提交时机仍在 baseline 报告之后，理由改为「gate-baseline.json 是本次基线的产物，随工件一起入库」；补一句「子仓 gitlink 的改动与工件同一次提交，暂存与否不影响基线」。

baseline 报告之后、forecast 之前

把 flight-doctor.py 的 _final_part 原样搬成 slice-gate.py 的 final_forecast(change_dir, data, baseline)，返回 (mode, why)，取值与文字不变（impacted / full / incremental / unknown）。flight-doctor.py 改为调用它，自己不再留判定。
cmd_ship 判 final 过期时调用它，在理由后追加
incremental → ；补跑将是增量（<why>）
full → ；补跑将是全量（<why>）
impacted → ；补跑由 gate.impacted 选测
unknown 或调用抛异常 → 不追加（裁决不能因预告出错而失败）。
forecast 的 final.sec 改经 D1 的 suite_sec 取值。
否决

ship 起子进程跑 flight-doctor.py forecast——判定函数本来就该在门禁里，反向依赖会让 ship 多一个失败点。

Risks / Trade-offs

[下游仓库升级后 lint / preflight 变红（afa 的 executor 在途 change）] → 这是决策要的效果；违规文字带类别与契约文档路径；写理由即可放行；升级说明写明。
[在途 change 的旧基线没有 full_suite_sec] → suite_sec 回退读旧计划字段；两处都没有时超时取现有缺省（600 秒），与今天「尚无耗时」时相同。
[外部脚本读 slices.json 的 gate.full_suite_sec] → 值不再更新；proposal 标了 BREAKING；模板内已无读取方依赖它被更新。
[子仓工作区有未提交内容时快照仍看不见] → 与现状相同；G6 的 gitlink 检查与 submodule 就绪检查照旧兜着。
[基线未测的状态靠增量基线沿用，来源是很旧的基线池条目时可能缺字段] → 缺字段按「测到」处理（与今天相同，不会误拦）；下一次全量基线会重新写准。
[final_forecast 搬家时文字走样，spec.html 的成本预告跟着变] → 现有 tests/test_flight_doctor.py 钉着这些文字，S3 的 verify 带它。
[静态提示误报 / 漏报] → 只是一行提示，不影响退出码；真正的判定在基线。
