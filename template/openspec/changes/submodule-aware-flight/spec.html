Why · 01为何而做

含 git submodule 的仓库飞不起来。2026-11-07 afa change raw-file-viewer 有 9 片，其中 6 片改 submodule admin/viewer。飞行模式在三处实测失败，只能退化为 --gate=per-task 串行：

1. 隔离 worktree 里 submodule 是空目录。submodule update --init 去远端 clone，本地未 push 的 gitlink 报 not our ref。执行体自己也不能从 change 家取：Claude Code 的隔离检查会拦 git -C <家>。 2. 执行体在隔离 worktree 自己的子仓里提交，家里的子仓看不到这个提交，合回后 gitlink 指向一个不存在的提交。 3. 同一 wave 两片都改 gitlink，合回时出现 CONFLICT (submodule)。integrator 按纪律只能 abort。

读代码又定位到三处同根问题：

4. 切片门禁只看父仓 diff（slice-gate.py:2429 changed_files、:2443 added_lines），只拿到 admin/viewer 这一条 gitlink，于是 G6 判它在 owns 外、G3 看不到测试、G8 漏掉 ceiling 行。afa 那 6 片写不出门禁记录，ship 只能判 draft。 5. 快照（:2960 _checkpoint）只看父仓 porcelain，submodule 内的半成品不进快照。 6. preflight（:3857）不校验 submodule 是否就绪，问题要到合回时才暴露。

根因在模板：飞行模式从隔离、提交、合回到门禁，全程按单仓设计。决策页 template/openspec/superpower/2026-11-07-submodule-aware-flight-decisions.html 列了 Q1–Q8，用户 2026-11-07 全部采纳推荐项。

What · 02变更范围

  • 隔离 worktree 自带 submodule：
  • slice-gate.py start 通过 G0 基点校验后，为隔离 worktree 填充 change 家里已初始化的每个 submodule。做法是从家子仓借出 linked worktree，检出到 HEAD 的 gitlink，不访问远端。
  • 家子仓未初始化、gitlink 不在家子仓的对象库 → 以 G0 submodule 拒绝起跑，并给出修法。
  • 已填充的子仓不被改动。
  • 新增子命令 sub-sync，供 fix 执行体用（slices.json 没有 fix 条目，不能靠 start 填充）。
  • 门禁按文件判：
  • gate 把 gitlink 展开为 submodule 内的文件：已提交部分取 gitlink 前后的子仓 diff，未提交部分取子仓 status。
  • 新增 G6 gitlink：子仓检出未记录进父仓 HEAD 即红。
  • added_lines 带上 --submodule=diff，G8 能看到子仓内的 ceiling 行。
  • 门禁绿时在子仓写 refs/flight-sub/<change>/<S>，锚住本片的子仓提交，防 gc。
  • 快照与恢复覆盖子仓：checkpoint 与 start --resume-checkpoint 对每个有 owns 落在其中的 submodule，各做一份同名 ref 的快照与恢复。
  • preflight 就绪校验：计划 owns 落在某个 submodule 内时，家里该子仓必须已初始化、检出等于父仓 HEAD 的 gitlink，否则拒绝起飞。这一项排在基线检查之前。
  • 合回脚本化：新增子命令 merge <S>=<sha> ...，integrator 第 1 项一律调用它。
  • 逐片执行 git merge --no-ff。
  • gitlink 是快进时直接钉；分叉时先在家子仓内合并，再用 update-index 钉。
  • 合回后家子仓的分支和检出都与 gitlink 一致。
  • 非 gitlink 冲突，或子仓内容冲突 → 父仓与子仓都回滚，返回 ok:false。
  • 无 submodule 的仓库与原来逐条 merge --no-ff -m "integrate: <S>" 等价。
  • 编排与文档：
  • opsx-apply.js：integrator 与 finalize 改调 merge；fix 在基点校验后跑 sub-sync；评审改用 git show --submodule=diff。
  • integrator.md、slice-executor.md 补上子仓提交纪律：先 git -C <P> 提交，再把 gitlink 并入同一个切片 commit。
  • opsx-apply.md 与同名 skill 同步改；openspec-git-discipline 新增 Submodule 小节；README、WORKFLOW_zh 补一句。
  • 不变：
  • final 增量选测不认识 gitlink：gitlink 变动按「未被用例触及的非 Python 文件」触发全量，记为天花板。
  • 不支持嵌套 submodule、新增或删除 submodule 的切片：前者给 warning，后者由 G6 点名伪路径，提示改走 --gate=per-task。
  • --gate=per-task 照旧可用，也同样受益于门禁展开。
代码：template/.claude/hooks/slice-gate.py 一个文件。新增：_gitlinks、_home_root、_sub_sync、gitlink 展开、G6 gitlink、子仓锚定 ref、sub-sync / merge 子命令。改动：快照与恢复按仓分别进行，preflight 加就绪校验。编排与文档：代码与 agent 定义：template/.claude/workflows/opsx-apply.js、agents/integrator.md、agents/slice-executor.md。命令与 skill：commands/opsx-apply.md、skills/openspec-apply-change/SKILL.md、skills/openspec-git-discipline/SKILL.md。说明文档：README.md、docs/WORKFLOW_zh.md。测试：新增夹具 tests/submodule_helpers.py（父仓 + 本地子仓 + change 家 + 隔离 worktree）。新增 tests/test_submodule_gate.py、tests/test_submodule_sync.py、tests/test_submodule_merge.py、tests/test_submodule_docs.py。既有用例 test_integrator_agent_contract 断言正文含 git merge，S4 须保留该措辞。ADR：新增 DRAFT-submodule-slices-borrow-home-worktree。它不取代现行决策，补充 DRAFT-apply-as-flight 的原则 3（确定性调度）。已装仓库：无 submodule 的仓库零变化。含 submodule 的仓库升级后可以飞行：在飞的 change 用的是自己分支里的旧 .claude，不受影响。afa raw-file-viewer 按决策 Q8-A 继续走它自己的混合路线，新机制在下一个改 viewer 的 change 上实测。无新依赖、部署或数据变化。

Capabilities · 03能力清单

New

submodule-gate-expansion：切片门禁把 gitlink 展开成子仓内文件判 G3 / G6 / G8 / GWT，gitlink 未记录判红，门禁绿锚定子仓提交。

New

submodule-worktree-sync：隔离 worktree 从 change 家借出子仓 linked worktree（start / sub-sync），基点校验先于填充，重派续跑，快照恢复覆盖子仓，preflight 就绪校验。

New

submodule-merge：slice-gate.py merge 逐片合回，gitlink 冲突在家子仓内合并后钉，失败全回滚，无 submodule 时与 merge --no-ff 等价。

New

submodule-flight-orchestration：工作流与回退路径的 integrator / fix / 评审接上上述命令，agent 定义与命令文档写明子仓纪律。

Specs · 04行为规范 (Gherkin)

submodule-flight-orchestration ADDED

Requirement: 工作流用脚本合回

Rule: opsx-apply.js 有两处合回，SHALL 都让 integrator 运行 slice-gate.py merge，并原样带上各片的 <S>=<commit>： - 每个 wave 的合回； - finalize 前合回 fix（fix=<commit>，位于 slice-gate.py final 之前）。

merge 退出非 0 时，integrator 把它的 failed 原样作为返回值。

Scenario: integrator-merges-via-script

  • GIVENwaves [[S1, S2], [S3]] 门禁全绿，S1、S2 的 commit 为 a…a、b…b
  • ANDS1 评审给出 1 条 HIGH，fix 返回 9…9
  • WHEN用 mock agent 跑完工作流
  • THENintegrate:w1 的 prompt 含 slice-gate.py merge S1=a…a S2=b…b
  • ANDfinal-gate 的 prompt 含 slice-gate.py merge fix=9…9，且在 slice-gate.py final 之前

Requirement: fix 执行体先填充子仓

Rule: fix 的 prompt SHALL 在基点校验之后、start fix 之前，运行 slice-gate.py sub-sync，带 --change-dir 与 --expect-branch。它非 0 时，fix 不做改动，原样返回其 failed；以 G0 开头的失败按基点拒绝处理（重派一次）。

Scenario: fix-prompt-syncs-submodules

  • GIVEN一条 HIGH 触发 fix
  • WHEN跑完工作流，取 fix 派发的 prompt
  • THENprompt 里 slice-gate.py sub-sync 命令带 --expect-branch worktree-c 与 --change-dir openspec/changes/c
  • AND位于 merge-base --is-ancestor 之后、slice-gate.py start fix 之前

Requirement: 评审读含子仓改动的 diff

Rule: 评审 prompt SHALL 用 git show --submodule=diff <commit> 读切片 commit，使子仓内的改动随 diff 展开。没有 submodule 时输出与原来相同。

Scenario: reviewer-reads-submodule-diff

  • GIVENS1 的 commit 为 a…a
  • WHEN跑完工作流，取 review:S1 的 prompt
  • THENprompt 含 git show --submodule=diff a…a

Requirement: agent 定义与命令文档写明子仓纪律

Rule: agent 定义与命令文档 SHALL 写明以下内容： - integrator.md 第 1 项：用 slice-gate.py merge 合回，并写明它逐片 git merge --no-ff、模型不手解冲突。 - slice-executor.md 纪律段：owns 落在 submodule 内时，先 git -C <子仓路径> 提交，再把 gitlink 与父仓 owns 文件并入同一个切片 commit；不在子仓里切分支、不 push。 - opsx-apply.md 与 openspec-apply-change/SKILL.md 的回退段：同样写明 slice-gate.py merge 与 slice-gate.py sub-sync。 - openspec-git-discipline/SKILL.md：新增 ## Submodule 小节，写明隔离 worktree 借用家子仓的 linked worktree，以及 gitlink 的提交与合回规则。

Scenario: agent-docs-describe-submodule-discipline

  • GIVENslice-executor.md 与 integrator.md
  • WHEN取 integrator 第 1 项与执行体纪律段
  • THEN第 1 项含 slice-gate.py merge 与 git merge --no-ff
  • AND纪律段含 git -C、gitlink、submodule

Scenario: apply-docs-mirror-submodule

  • GIVENopsx-apply.md、openspec-apply-change/SKILL.md、openspec-git-discipline/SKILL.md
  • WHEN取命令与 skill 的回退段
  • THEN两处都含 slice-gate.py merge 与 slice-gate.py sub-sync
  • ANDgit-discipline 含 ## Submodule 小节与 linked worktree

submodule-gate-expansion ADDED

Requirement: 切片门禁把 gitlink 展开成子仓内的文件

Rule: slice-gate.py gate 统计区间改动时，对 mode 为 160000 的条目（gitlink），SHALL 用子仓内的真实文件代替 gitlink 伪路径，路径带 <子仓路径>/ 前缀： - 已提交部分：取区间前后 gitlink 之间的子仓 diff。 - 未提交部分：取子仓 status，含未跟踪文件，遵守子仓自己的 .gitignore；外加子仓检出领先父仓 HEAD gitlink 的那一段。

展开后的路径与父仓路径一起参与 G3 配对、G6 所有权、GWT 判定，字节码副产物照旧不计。以下情况 SHALL 保留伪路径，交 G6 点名：子仓未填充、gitlink 一侧为空（新增或删除 submodule）、子仓里找不到 gitlink 指向的提交。

门禁绿时，对区间内 gitlink 有变化、且已填充的子仓，SHALL 在子仓写 refs/flight-sub/<change>/<S> 指向新的 gitlink 提交，防止子仓提交被 gc。

没有 gitlink 的仓库，门禁结果 SHALL 与改前一致。

Scenario: gate-expands-gitlink-to-files

  • GIVENchange 家里 start S1，子仓已初始化
  • AND子仓里写了 owns 内的 lib1.py 与配对测试并提交，父仓把 gitlink 并入切片 commit
  • WHEN运行 slice-gate.py gate S1
  • THEN门禁绿，failed 为空
  • AND子仓里 refs/flight-sub/c/S1 指向本片的子仓提交

Scenario: gate-flags-unowned-submodule-file

  • GIVEN同上，但子仓提交里还多了一个 owns 之外的 stray.py
  • WHEN运行 slice-gate.py gate S1
  • THEN门禁红，failed 里有一条 G6 点名 mods/sub/stray.py

Requirement: 子仓检出未记录进父仓即红

Rule: 已填充的子仓，其检出提交与父仓 HEAD 记录的 gitlink 不一致时（子仓提交了，但没有 git add <子仓路径> 并入切片 commit），gate SHALL 判红。失败项以 G6 gitlink 开头，点名子仓路径与检出提交前缀，并给出修法：git add <子仓路径> 后并入本切片 commit。这种提交在合回时会丢。

Scenario: gate-flags-unrecorded-gitlink

  • GIVEN子仓里提交了 owns 内的改动，父仓没有提交 gitlink
  • WHEN运行 slice-gate.py gate S1
  • THEN门禁红，failed 里有一条以 G6 gitlink 开头，含 mods/sub 与该子仓提交的前 10 位

Requirement: 子仓内的 ceiling 标记进 G8

Rule: G8 扫描新增源码行时，SHALL 同时扫描区间内 gitlink 变化所对应的子仓 diff。门禁 JSON 的 ceilings 行位置为 <子仓路径>/<文件> 与子仓文件内的行号。

Scenario: gate-collects-ceiling-in-submodule

  • GIVEN子仓 lib1.py 第 3 行新增 # ceiling: 全局锁串行写入 -> 按键分片后并发写入，已提交并钉 gitlink
  • WHEN运行 slice-gate.py gate S1
  • THEN门禁 JSON 的 ceilings 含 ["mods/sub/lib1.py", 3, "全局锁串行写入", "按键分片后并发写入"]

submodule-merge ADDED

Requirement: merge 子命令逐片合回并处理 gitlink

Rule: slice-gate.py merge <S>=<sha> ... SHALL 按参数顺序逐片执行父仓 git merge --no-ff --no-commit，再以说明 integrate: <S> 提交。被合入一侧改了 gitlink 时，按两侧 gitlink 的关系处理： - 快进（一方是另一方的祖先）→ 直接钉较新的那个。 - 分叉 → 先在本仓（change 家）子仓内执行 merge --no-ff，合入被合入一侧的子仓提交；再用 update-index --cacheinfo 160000,<子仓合并结果>,<路径> 钉 gitlink。

每片合回后，子仓的检出 SHALL 等于父仓 HEAD 的 gitlink：子仓在分支上时分支快进，detached 时检出到该提交。

开跑前，已填充子仓的检出 SHALL 等于父仓 HEAD 的 gitlink，否则不合任何一片。

输出 JSON {ok, merged, failed, warnings}，全部成功时退出 0。

Scenario: merge-parallel-submodule-slices

  • GIVEN同一 wave 的 S1、S2 在各自的隔离 worktree 里改子仓（文件不相交），各自提交 gitlink，门禁都绿
  • WHEN在 change 家运行 slice-gate.py merge S1=<C1> S2=<C2>
  • THEN退出 0，merged 为 [S1, S2]
  • AND家子仓的分支与检出都等于父仓 HEAD 的 gitlink，并包含两片的子仓提交
  • AND父仓工作树干净，最近两个提交的说明依次为 integrate: S1、integrate: S2

Scenario: next-wave-populates-from-merged-gitlink

  • GIVENwave 1 的 S1、S2 已由 merge 合回
  • WHENwave 2 的 S3 在新的隔离 worktree 里走完执行体流程
  • THENS3 的子仓起点包含 S1、S2 的文件，门禁绿

Requirement: 合回失败全回滚

Rule: 遇到以下任一情况，merge SHALL 中止父仓合并（merge --abort）、中止子仓合并，并回滚本片已做的子仓合并，然后停止，不再合后续片： - 非 gitlink 的文件冲突； - 子仓内的合并冲突； - 子仓未填充； - 遇到新增 submodule。

返回 ok 为 false，merged 只列此前成功的片。failed 首项以 merge <S> 开头，点名冲突文件或子仓路径。

Scenario: merge-rolls-back-on-submodule-conflict

  • GIVENS1 改子仓 lib1.py；S2 在另一个隔离 worktree 里把同一个 lib1.py 改成不同内容
  • WHEN运行 merge S1=<C1> S2=<C2>
  • THEN退出 1，merged 为 [S1]，failed 首项含 S2 与 mods/sub
  • AND父仓与子仓都不在合并中，子仓检出等于父仓 HEAD 的 gitlink，HEAD 说明为 integrate: S1

Scenario: merge-aborts-on-file-conflict

  • GIVEN没有 submodule 的仓库，两个旁支把 README.md 改成不同内容
  • WHEN运行 merge S1=<a> S2=<b>
  • THEN退出 1，merged 为 [S1]，failed 首项以 merge S2 开头并含 README.md
  • AND不在合并中，HEAD 说明为 integrate: S1

Requirement: 无 submodule 时与 merge --no-ff 等价

Rule: 仓库没有 gitlink 时，merge 的结果 SHALL 与逐条执行 git merge --no-ff <sha> -m "integrate: <S>" 一致：每片一个双亲 merge commit，说明为 integrate: <S>。

Scenario: merge-plain-repo-equals-no-ff

  • GIVEN没有 submodule 的仓库，两个从 main 分叉的旁支分别新增 a.txt、b.txt
  • WHEN运行 merge S1=<a> S2=<b>
  • THEN退出 0，输出为 {"ok": true, "merged": ["S1", "S2"], "failed": [], "warnings": []}
  • ANDHEAD~1、HEAD 都是双亲 merge commit，说明依次为 integrate: S1、integrate: S2

submodule-worktree-sync ADDED

Requirement: start 为隔离 worktree 借出 change 家的子仓

Rule: slice-gate.py start SHALL 先通过 G0 基点校验，再处理父仓索引里的每个 gitlink： - 未填充，且 change 家的同一子仓已初始化 → SHALL 在家子仓执行 worktree add --detach <隔离 worktree>/<子仓路径> <HEAD 的 gitlink>，借出一个 linked worktree： - 与家共享对象库，不访问远端； - 本地未 push 的 gitlink 也能检出。 - 已填充 → SHALL NOT 改动它；检出与 gitlink 不一致时只给 warning。

change 家定位方式：在 git worktree list --porcelain 中找检出 --expect-branch 分支的那个 worktree。

基点校验不通过时，SHALL NOT 填充任何子仓。

Scenario: start-populates-isolated-submodule

  • GIVEN从主 checkout 建出的隔离 worktree，HEAD 为 change 分支 tip，其中 mods/sub 是空目录
  • AND家里子仓的 gitlink 是本地未 push 的提交
  • WHEN在隔离 worktree 运行 start S1 --expect-branch worktree-c
  • THEN退出 0
  • AND隔离 worktree 的子仓检出在 gitlink 上
  • AND家里子仓的 worktree 列表登记了该目录

Scenario: executor-commit-visible-at-home

  • GIVEN隔离 worktree 已 start，子仓已填充
  • WHEN执行体在隔离 worktree 的子仓里提交
  • THEN不经 fetch，家里子仓的对象库就能找到这个提交

Scenario: start-skips-populate-when-base-check-fails

  • GIVEN隔离 worktree 从 change 分支 tip 的上一个提交分叉
  • WHEN运行 start S1 --expect-branch worktree-c
  • THEN以 G0 base 拒绝（退出 1）
  • AND子仓不被填充

Requirement: 子仓无法就绪时以 G0 submodule 拒绝起跑

Rule: 本片 owns 落在某个子仓内，而该子仓无法就绪时，start SHALL 退出 1，在 stdout 打印 ok 为 false 的门禁 JSON，SHALL NOT 写切片标记。无法就绪包括三种情况： - 定位不到 change 家； - 家里该子仓未初始化； - gitlink 不在家子仓的对象库。

失败项 SHALL 以 G0 submodule 开头，点名子仓路径与修法（如 git submodule update --init <路径>）。

Scenario: start-refuses-when-home-submodule-missing

  • GIVENchange 家里的子仓被 deinit，隔离 worktree 的子仓为空
  • WHEN在隔离 worktree 运行 start S1 --expect-branch worktree-c
  • THEN退出 1
  • ANDstdout JSON 的 failed 首项以 G0 submodule 开头，含 mods/sub 与 submodule update --init
  • AND没有 .openspec-slice 标记

Requirement: 重派续跑按新 gitlink 填充

Rule: 重派时，start SHALL 按运行时 HEAD 的 gitlink 填充子仓，使上一轮的子仓提交在场。处理顺序： 1. 执行体在新的隔离 worktree 里，先 cherry-pick 上一轮的父仓提交（gitlink 随之更新）； 2. 再运行 start。

Scenario: retry-after-cherry-pick-populates-new-gitlink

  • GIVEN上一轮执行体在隔离 worktree A 提交了子仓 s1 与父仓 C1（gitlink → s1）
  • AND重派开了新的隔离 worktree B
  • WHEN在 B 里 cherry-pick C1，再运行带上一轮 --base 的 start
  • THEN退出 0
  • ANDB 的子仓检出在 s1 上，上一轮的文件在场

Requirement: 快照与恢复覆盖子仓

Rule: checkpoint hook SHALL 对每个已填充、且有本片 owns 落在其中的子仓，单独做快照： - 快照内容为子仓里 owns 内的未提交改动，以及相对 gitlink 的子仓提交； - 快照写在子仓的同名 ref refs/flight/<change>/<S>。

start --resume-checkpoint SHALL 在子仓填充之后，把子仓快照里 owns 内的文件恢复为未提交改动。恢复的路径带 <子仓路径>/ 前缀，计入 checkpoint.restored。

首轮 start 与门禁绿时清理快照，SHALL 同时清理子仓里的同名 ref。

Scenario: checkpoint-covers-submodule

  • GIVEN隔离 worktree A 已 start S1，子仓里写了 owns 内的 lib1.py 但未提交
  • AND快照 hook 跑过一次，执行体随后未返回
  • WHEN在新的隔离 worktree B 运行 start S1 --resume-checkpoint --expect-branch worktree-c
  • THEN退出 0，checkpoint.restored 含 mods/sub/lib1.py
  • ANDB 的子仓里该文件内容与 A 的半成品一致

Requirement: preflight 校验子仓就绪

Rule: 计划里有切片 owns 落在某个子仓内时，slice-gate.py preflight SHALL 在检查基线之前校验 change 家里该子仓： - 已初始化； - 父仓 HEAD 的 gitlink 在子仓对象库里； - 子仓检出等于该 gitlink。

任一不满足即退出非 0，点名子仓路径与 gitlink，并给出修法。

Scenario: preflight-refuses-unsynced-home-submodule

  • GIVENchange 家里子仓多了一个本地提交，父仓 gitlink 没跟上
  • AND计划的切片 owns 落在 mods/sub 里
  • WHEN在家里运行 slice-gate.py preflight
  • THEN退出非 0，stderr 含 mods/sub 与 gitlink，不含「缺基线」

Requirement: sub-sync 子命令供 fix 执行体填充子仓

Rule: slice-gate.py sub-sync [--expect-branch <branch>] [--change-dir <dir>] SHALL 对当前 worktree 执行与 start 相同的填充规则： - 给了 --change-dir 时，计划里任一切片 owns 所在的子仓都算必需； - 输出 JSON {ok, synced, failed, warnings}，退出 0（ok）或 1； - 重复运行幂等。

Scenario: sub-sync-cli-for-fix

  • GIVEN一个子仓为空的隔离 worktree
  • WHEN运行 slice-gate.py sub-sync --expect-branch worktree-c --change-dir openspec/changes/c
  • THEN退出 0，JSON 的 ok 为 true、synced 为 ["mods/sub"]，子仓检出在 gitlink 上
  • AND再运行一次仍 ok，synced 为空

Design · 05技术设计

Context

飞行模式的执行体一律跑在 Claude Code 的隔离 worktree（isolation: worktree）里，由 integrator 在 change 家把各片 commit 合回。整条链路默认是单仓：

  • 隔离 worktree 只检出父仓的 tracked 文件。submodule 是空目录。
  • 执行体不能自己从家里取。Claude Code 官方文档（worktrees · How Claude Code enforces isolation）写明，Bash 里 git -C、--git-dir、GIT_DIR 指向主 checkout 的命令会被拦下；本会话所在的 linked worktree 及其主 checkout 都算在内。
  • 合回、门禁、快照都只看父仓。gitlink 只是一条 mode 160000 的伪路径。

afa（2026-11-07）实测了三处失败（proposal 第 1–3 条）。本会话在 /tmp 玩具仓（git 2.54）做了两组实验：

  • E1：让隔离 worktree 借用家子仓的 linked worktree，可行。
  • 吸收进 modules/ 的 gitdir 带有 core.worktree，但不影响 linked worktree。
  • 执行体的提交在家里即刻可见。
  • 父仓 status / add / diff 都正常。
  • E2：两片并行改子仓后合回。
  • S1 是快进，无冲突。
  • S2 冲突只出现在 gitlink 上，在家子仓内合并后再 update-index 即可解。
  • 合回后，下一 wave 能从新 gitlink 填充。
  • 在未填充的隔离 worktree 里 cherry-pick 上一轮提交可行。
  • git show --submodule=diff 能展开子仓 diff。
  • 核对项：
  • diff -U0 --submodule=diff 输出的路径带 <子仓>/ 前缀。
  • 合并态下 commit -m 生成双亲提交，说明不变。
  • worktree list --porcelain 能按 branch refs/heads/<B> 定位家。

在役 ADR： - DRAFT-apply-as-flight：五原则。本设计不改原则，只让原则 2（所有权）、3（确定性调度）、4（机械门禁）在多仓下成立。 - DRAFT-gate-evidence-not-self-reported：门禁证据不靠自述。gitlink 展开同样是机械判定。

Goals / Non-Goals

Goals: - 含 submodule 的 change 能走飞行模式：同一 wave 内多片并行改同一子仓，结果正确合回。 - 门禁按子仓内的真实文件判。per-task 路径同样受益。 - 重派、快照恢复、preflight 的语义在子仓上与父仓一致（铁律 10）。 - 无 submodule 的仓库零行为变化（场景 merge-plain-repo-equals-no-ff 加上既有全量用例守住）。

Non-Goals: - final 增量选测展开 gitlink（Q5-A）：gitlink 变动 → 全量，保守而且正确。 - 嵌套 submodule，以及新增或删除 submodule 的切片（Q6-A）。 - 访问远端：不 fetch、不 push 子仓。 - 子仓自身的 MR 编排：子仓分支的推送与 MR 仍由人或 /pr-ship 之外的流程处理。

Decisions

做法

_sub_sync(root, branch, need) 在 start（G0 通过后）和新子命令 sub-sync 里执行：

家定位

在 git worktree list --porcelain 中找 branch refs/heads/<branch> 那一块，取它的 worktree 路径。

gitlink 清单

git ls-files -s -z 里 mode 为 160000 的条目。目标提交为 git rev-parse HEAD:<P>。

已填充（<root>/<P>/.git 存在）

不改动。检出 ≠ 目标时只给 warning。

未填充

家里同一子仓已初始化，且目标在家子仓对象库里 → 执行 git -C <家>/<P> worktree add --detach <root>/<P> <目标>。

失败

以下任一情况，若该子仓属于 need（本片 owns，或 --change-dir 下全部切片 owns 有路径落在 <P>/ 下）→ 记 G0 submodule: …；否则 warning 并跳过：

家定位不到，或家就是本 worktree；
家子仓未初始化；
目标不在家子仓对象库；
<root>/<P> 非空；
worktree add 失败。
嵌套 submodule

子仓里有 .gitmodules → warning：嵌套 submodule 不填充。

为什么借 linked worktree

对象库共享，执行体提交即落进家子仓，不需要搬运。写入只发生在共享 .git 内：家子仓 gitdir（如 afa/.git/worktrees/<家>/modules/<P>）下的 worktrees/<id> 登记、对象、per-worktree HEAD。不碰家的工作区文件，也不改家子仓的分支。这与父仓提交写共享 .git 是同一类操作。

由 hook 脚本代办

执行体直接 git -C <家> 会被隔离检查拦下，所以这一步由 hook 脚本执行。这是有意的选择，ADR 记录，人在决策页 Q1 批准。

备选
B · clone --shared 后由 integrator 从隔离目录 fetch

门禁 JSON 要带路径；重派要从上一轮的隔离目录取；隔离目录被清理就丢提交。

C · WorktreeCreate hook

会替换 Claude Code 默认的 worktree 创建逻辑，要自行实现 baseRef、.worktreeinclude、锁、LFS 中和，而且不进定期清扫。

D · 改 submodule 的切片不隔离、串行

这正是本次要消除的退化。

纯子仓切片的父仓 commit 为空；
评审与重派都要另传子仓提交；
「别 git add P」是反直觉纪律。
changed_files(root, base)

签名不变，在结果上展开 gitlink：

已提交

git diff --raw -z --no-renames base..HEAD 中旧 / 新 mode 任一为 160000 的条目 P。两侧都是 160000、P 已填充、两个提交都在子仓里 → 用 P/ + git -C P diff --name-only -z --no-renames old new 替换 P；否则保留 P，由 G6 点名。

未提交

父仓 porcelain 列出的路径中属于 gitlink 的 P，替换为两部分之和：

P/ + git -C P status --porcelain -z --untracked-files=all 的路径（改名取新路径）；
子仓检出与 HEAD:P 不同、且两者都在子仓时，P/ + diff --name-only HEAD:P..子仓 HEAD。
展开结果同样过 is_bytecode 过滤。
G6 gitlink

cmd_gate 对每个已填充的 gitlink P，若子仓检出 ≠ HEAD:P，记一条：

added_lines

git diff 加 --submodule=diff。git 原生输出 +++ b/<P>/<文件>，解析逻辑不用改。

锚定

门禁绿时，对区间内 gitlink 变化、已填充的子仓，执行 git -C P update-ref refs/flight-sub/<change>/<S> <new>。

命名不用 refs/flight/<change>/<S>/…

子仓里同名快照 ref 已存在，会形成 D/F 冲突。

这些 ref 不清理（每片一条，体积可忽略），用来覆盖「门禁绿后飞行中断、数周后恢复」的 gc 窗口。
_checkpoint

拆出 _ckpt_commit(repo, head, files, msg)，即临时 index → read-tree → add → write-tree → commit-tree。父仓与子仓共用。

父仓段原来的提前 return 改为「跳过父仓段」，避免漏掉子仓。
子仓段

对每个已填充、owns 有 P/ 前缀的 P，处理 owns 内的未提交文件（相对子仓）。若有这类文件，或子仓 HEAD ≠ <marker.base>:P，就快照到子仓的同名 ref _ckpt_ref(change_dir, S)。

_ckpt_restore

父仓段不变。另对每个已填充、有 owns 的子仓：子仓 HEAD 须是快照的祖先，然后恢复差异里匹配 owns 的文件，restored 记 P/<f>。父仓「无快照」时不得提前返回。

_ckpt_delete

调用点（cmd_start 首轮、cmd_gate 绿、cmd_record）改为 _ckpt_delete_all，同时删除各已填充子仓里的同名 ref。

开跑前复核

每个已填充的 gitlink P，子仓检出须等于 HEAD:P，且不在合并中。否则一片不合，failed: ["merge: <P> 的检出 … 与 gitlink … 不一致，先同步"]。

逐片
相等 → 跳过；
ours 不存在（新增 submodule）→ 回滚，记「不支持」；
一方是另一方的祖先 → 取较新者；
分叉 → 在子仓 merge --no-ff --no-edit -m "integrate: <S>" theirs。失败则依次执行

子仓 merge --abort；已在本片做过的其他子仓 reset -q --keep <合前>；父仓 merge --abort。记 merge <S>: <P> 子仓合并冲突 …，停止。

最后 update-index --cacheinfo 160000,<目标>,P。
输出

{ok, merged, failed, warnings}，退出 0 / 1。参数格式错 → die（退出 2）。

零 token 优先（铁律 9），integrator 不解冲突。没有 gitlink 时，第 4、6 步为空，结果与原来的逐条 merge --no-ff -m 等价。备选「只在冲突时调脚本」被否：每次合回后的检出同步也要模型判断，容易漏。

Risks / Trade-offs

[绕开文本检查的写入] hook 脚本在 Claude Code 文本检查之外写家子仓的 git 元数据 → 只做 worktree add --detach、update-ref refs/flight*、落对象，全部在共享 .git 内。不改家的分支和工作区；家子仓分支只由家里的 merge 推进。写进 ADR，人已在 Q1 批准。若 Claude Code 将来把这类写入也列为拦截对象，回退到 D1 备选 B。
[执行体用 git -C <P> 提交] 未在真实 Claude Code 里实测。路径在隔离 worktree 内，按文档不属于「指向主 checkout」。若被拦，执行体可改用 cd <P> && git …（文档只拦 cd 进主 checkout）。合入后在 afa 的下一个 viewer change 上实测（Q8-A）。
[含已填充 submodule 的隔离 worktree，git worktree remove 会拒删]（E1 已验证）→ 有提交的隔离 worktree 本来就保留到定期清扫；G0 不通过时不填充，所以不会出现「无改动却删不掉」。Claude Code 清扫时如何处理未实测，最坏是残留，用 git worktree remove --force + 子仓 git worktree prune 清理。
[每片多检出一份子仓] → 只检出家里已初始化的子仓；afa 的 viewer 是 197 个文件。大型子仓会增加起步耗时，记为天花板。
[final 遇 gitlink 变动即全量] → 保守而且正确（Q5-A）；配了 gate.scope 的仓库由提供方裁决。升级条件

内建依赖图展开 gitlink。

[本 change 自己的 final 近乎全量] S1–S3 改的 slice-gate.py 被绝大多数用例加载，增量也近乎全选；以 lint 实际报告为准。

Migration Plan

  • 升级：合入后，已装仓库执行 ./install.sh --upgrade 即获得新机制。无 submodule 的仓库零变化。在飞的 change 用的是自己分支里的旧 .claude，不受影响。
  • afa（Q8-A）：raw-file-viewer 按它自己会话里的混合路线继续。升级后，下一个改 viewer 的 change 实测，重点看三项：
  • 隔离 worktree 填充；
  • 执行体 git -C 提交是否被拦；
  • 两片并行合回。
  • 回退：revert 本 change，回到「含 submodule 用 --gate=per-task」。单个 change 也可以继续显式走 --gate=per-task，门禁展开对它照样生效。
