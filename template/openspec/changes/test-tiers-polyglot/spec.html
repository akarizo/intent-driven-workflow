Why · 01为何而做

测试分层（change test-tiers）目前只认 pytest、只认一个单元层：

- 分层文件只有一个 unit.cmd，lint 要求 gate.test == unit.cmd。Go、Python、TS 三个子项目的单元测试没法用一条命令表达。 - 探针只认 pytest，非 pytest 仓库的 G10 / G11 只能降级为警告。逐用例耗时只来自 pytest 插件。 - 失败差分要求输出里恰好一行 pytest 汇总行（slice-gate.py run_test_gate）。先后跑两个 Python 子项目，就会被判「调用了多次 pytest」，差分失效。 - 命令都在 git 顶层运行，用例 id 也相对顶层。子项目各有自己的工具链根（go.mod / package.json / pyproject.toml），runner 输出相对子项目，和 owns、scenario_tests 对不上。 - 测试文件靠 TEST_FILE_RE 认，它不认识 _test.go、FooTest.java 这类命名。

用户要求（2026-10-29）：分层要语言通用，还要支持 monorepo，且 monorepo 可能是多语言的。

用户决策（2026-10-29，决策页 template/openspec/superpower/2026-10-29-test-tiers-polyglot-decisions.html，代替 grill-me 访谈；两轮共 8 项，全取推荐）：

- Q1 切法：路径与列表两种选择器（paths / list），check 机械校验不重不漏。 - Q2 逐用例耗时：JUnit XML 契约（$FLIGHT_JUNIT 或报告路径 glob）。 - Q3 单测纯度：探针适配器契约 + 库出题的金丝雀自检，适配器哈希锁定。 - Q4 测试文件：test_files glob，按部件填写。 - Q5 范围：只做分层。G7、失败差分走 junit、依赖图语言通用化，另立后续 change。 - M1 结构：全仓一份分层文件，内含多个部件。一个部件 = 一个子项目目录 × 一种 runner。旧写法视作单部件简写。 - M2 gate.test：部件形态下写库自带的驱动命令 python3 .claude/hooks/test-tiers.py run unit。baseline / final 认出它后逐部件运行、逐部件差分。 - M3 跑哪些部件：baseline / final 跑全部部件的单元层。

What · 02变更范围

  • 分层文件新增「部件形态」 {"parts": {NAME: {root, test_files?, unit, regions?}}, "slow_allow"}：
  • 旧的 {unit, regions, slow_allow} 是简写形态，字段、行为、输出不变；
  • 简写形态不接受新字段。要用 list / junit / probe / test_files，就写部件形态（一个部件也行）。
  • 坐标系：分层文件、owns、covers、scenario_tests、slow_allow 键里的路径一律相对 git 顶层。部件的命令在部件 root 下运行。runner 输出的路径由库补上 root 前缀。
  • 选择器：单元层与区域二选一：paths（glob）或 list（在部件 root 下运行的命令，每行输出一个测试文件路径）。
  • 测试文件识别：部件写了 test_files 就以它为准，没写就用 root 下的内置命名规则（在 TEST_FILE_RE 之外另认 Go、JVM、C#、Ruby、Rust 的常见命名）。
  • JUnit 契约：库给每次部件运行设 $FLIGHT_JUNIT。命令可以把 junit 写到这里，也可以在 unit.junit 写报告路径 glob。耗时取自 junit 的 time。
  • 探针适配器契约：unit.probe = {cmd, canary, canary_files, sha, checked}：
  • 库运行 probe.cmd 时传 FLIGHT_UNIT_CMD（要跑的测试命令）与 FLIGHT_TIER_OUT（逐用例记录），格式与内置 pytest 探针相同；
  • test-tiers.py canary 生成随机令牌出题，跑金丝雀用例。纯用例无触碰、文件 / 子进程 / 网络三个用例各被报出、文件确实落盘，才算通过；
  • 通过后把适配器文件的 sha256 写进 sha。文件一改，lint 就红，直到重新自检。
  • 部件形态下的门禁：
  • lint：gate.test 须逐字等于驱动命令；区域名全仓唯一；不允许 gate.impacted；
  • baseline / final 不运行驱动命令，而是在各部件 root 下直接逐个运行单元层；
  • 差分：pytest 部件按 junit 逐条差分，其他部件只看退出码；
  • G10 / G11 逐部件判：耗时取探针或 junit，慢候选以整部件重跑一次确认；纯度取探针，测不了时只给警告；
  • preflight 逐部件对账单元命令；
  • final 恒全量；
  • tier_sec 增加 parts 分项。
  • G12 / check：每个测试文件须恰好属于一个部件，再在该部件内恰好落一层。
  • test-tiers.py：
  • 新增 run unit（驱动）与 canary；
  • probe 增加 --root / --adapter；
  • check / render 支持部件形态。
  • 文档：/test-tiers 命令、schema tasks instruction、opsx-propose 命令与同名 skill、README、CLAUDE.md.snippet。
template/.claude/hooks/slice-gate.py：分层文件加载：区分两种形态，部件形态做形状校验、选择器解析、适配器哈希核对；_lint_tiers 与 cmd_gate 的 G12 支持部件形态；新增部件运行器：在 root 下运行，提供 FLIGHT_JUNIT / FLIGHT_UNIT_CMD / FLIGHT_TIER_OUT，用例 id 换成相对顶层；新增逐部件 G10 / G11 判定；cmd_baseline / cmd_final / cmd_preflight 增加部件形态分支，tier_sec.parts。简写形态与无分层文件的代码路径不改行为。template/.claude/hooks/test-tiers.py：新增 run、canary 子命令；probe / check / render 扩展。文档：template/.claude/commands/test-tiers.md、schema.yaml、opsx-propose 命令与 openspec-propose skill、README.md、template/CLAUDE.md.snippet。测试：新增 tests/test_tiers_parts_plan.py、tests/test_tiers_parts_runner.py、tests/test_tiers_parts_gate.py、tests/test_tiers_parts_cli.py、tests/test_tiers_parts_docs.py；既有测试不改。ADR：新增 DRAFT-test-tiers-parts-and-runner-contracts。DRAFT-test-tiers-unit-baseline-by-audit-probe 继续有效，不 supersede（关系见 design D10）。兼容：没有分层文件、或用简写形态的仓库，lint / gate / baseline / final / preflight 的行为与输出不变；包括 plan_sha、增量 final、gate-baseline.json 的键。已知边界（Q5 与决策页「代价与风险」）：部件形态下 final 不走增量（依赖图只认 pytest）；非 pytest 部件只看退出码，基线上已红的非 pytest 部件会让 baseline 停下；G7 仍只实跑 pytest 形式的 scenario 测试；适配器能否测准取决于它自己，金丝雀只证明它报得出三类触碰；sha / checked 被人手编辑可绕过自检，与 slow_allow 同一信任模型。

Requirement: 分层文件的部件形态由 lint 校验

分层文件 <openspec 根>/test-tiers.json 顶层含 parts 时为部件形态，否则为简写形态。简写形态的字段、校验与门禁行为 SHALL 与本 change 之前相同；简写形态里出现 root / test_files / list / junit / probe SHALL 按现有「未知字段」报错。

部件形态下，slice-gate.py lint（preflight 内同一份校验也一样）SHALL 在下面任一条不满足时退出非 0，stderr 每条违规以 tiers: 开头并点名对象：

- 顶层只含 parts 与 slow_allow；parts 不得与 unit / regions 同时出现；parts 是非空对象，部件名匹配 ^[a-z0-9-]+$； - 部件只含 root、test_files（可选）、unit、regions（可选）； - root 是非空字符串、不以 / 开头、不含 .. 段，且是 git 顶层下存在的目录（. 表示顶层）； - test_files 缺省，或是非空数组、每项非空； - unit 与每个区域恰有 paths、list 之一：paths 是非空数组、每项非空；list 是非空字符串；cmd 是非空字符串；unit 另可有 junit（非空字符串）与 probe；区域另须有 covers（数组，可为空）； - 区域名匹配 ^[a-z0-9-]+$，且在全部部件之间唯一； - probe 只含 cmd、canary、canary_files、sha、checked；cmd、canary 非空，canary_files 是非空数组；没有 sha 或 checked 时报「未自检」；sha 里每个路径的文件 sha256 与记录不符或文件不存在时，报该路径并提示重跑 test-tiers.py canary； - 在部件 root 下运行每个 list 命令（超时 60 秒），退出非 0 或超时 → 点名部件与层；输出每行一个相对 root 的路径，库补上 root 前缀后作为该层的文件集合； - gate.test 去掉首尾空白后逐字等于 python3 .claude/hooks/test-tiers.py run unit； - 计划不得有 gate.impacted； - gate.integration / gate.integration_skip 与 covers 表态规则同简写形态，区域按全仓唯一的名字查找； - scenario_tests 指向的每个测试文件 SHALL 落在某个部件的单元层，或某个已选区域。

plan_sha 的算法 SHALL 不变。

Requirement: 部件形态下测试文件恰属一个部件、恰落一层（G12）

部件形态下，部件 P 的测试文件集合 SHALL 是：P 写了 test_files 时为匹配它的文件；否则为 P 的 root 下匹配内置命名的文件。内置命名 SHALL 在 TEST_FILE_RE 之外另认：

- Go：*_test.go； - JVM：*Test.java、*Tests.java、*IT.java（.kt 同）； - C#：*Tests.cs、*Test.cs； - Ruby：*_spec.rb、test_*.rb、*_test.rb； - Rust：部件 root 下 tests/ 目录里的 *.rs。

匹配任一部件 probe.canary_files 的文件 SHALL 被排除在外。

slice-gate.py gate 的 G12 在部件形态下 SHALL 对本切片区间改动且仍存在、且属于全仓测试文件（匹配内置命名或任一部件的 test_files）的文件逐个判定，下面任一情况报一条 G12 tiers: 失败并点名文件：

- 不属于任何部件； - 属于某部件，但不在该部件单元层，也不在任何已选区域内。

Requirement: 逐部件判定 G10 与 G11

Requirement: baseline / final / preflight 逐部件运行

部件形态下，baseline / final / preflight SHALL 逐部件运行与对账，规则如下：

- baseline 与 final SHALL 不执行 gate.test，改为逐部件运行单元层。 - baseline SHALL： - 记 test.parts.<P> = {exit, sec, cmd[, failed]}：可度量的 pytest 红记 failed 并警告；不可度量的红进 reasons，文本含「部件 <P>」； - 逐部件判 G10 / G11，失败进 reasons； - 在区域所属部件的 root 下运行已选区域； - 输出与 gate-baseline.json 的 tier_sec 增加 parts.<P>.unit 与 parts.<P>.integration。 - final SHALL： - 在 G7 绿时逐部件运行； - 基线缺 test.parts.<P> 或记录的 cmd 与当前 unit.cmd 不同 → G2 part <P>：基线缺记录或命令已变，重跑 baseline； - 否则按基线 failed 差分（标签 part <P>），再判 G10 / G11； - incremental.mode 恒为 full，full_why 含「多部件」。 - preflight SHALL 在基线各部件记录的 cmd 与当前 unit.cmd 不一致、或部件集合不一致时，报「基线过期」并点名部件。 - 简写形态与没有分层文件时，三者行为与输出 SHALL 不变。

Goals / Non-Goals

Goals: - 一份分层文件描述多语言 monorepo：每个子项目 × runner 是一个部件，各有单元层与区域。 - 全仓单元层 = 各部件单元层之并，有一条人与 CI 都能跑的命令（驱动）。 - 门禁逐部件运行、逐部件判定。pytest 部件保留逐条差分与内置探针。 - 非 pytest 部件的 G10 有 junit 耗时可判。G11 有适配器可判，适配器经金丝雀自检、哈希锁定。 - 坐标统一相对 git 顶层：owns / covers / scenario_tests / slow_allow 与 runner 输出对得上。 - 测试文件「恰属一个部件、恰落一层」由 check 与 G12 机械校验。 - 简写形态与无分层文件时行为、输出、plan_sha 不变。

Non-Goals: - 不做非 pytest 部件的失败差分（junit 差分是后续 change，Q5）。 - 不做部件形态下的增量 final（依赖图语言通用化是后续 change，Q5）。 - 不让 G7 实跑非 pytest scenario 测试（后续 change，Q5）。 - 不提供任何语言的现成适配器，由 /test-tiers 的 agent 按仓库调研实测后写。 - 不按 covers 选择性跑部件（M3 选了全跑）。

Decisions

判别

顶层有 parts 就是部件形态，否则是简写形态。同时出现 parts 与 unit / regions → lint 红。

简写形态

字段集、校验、gate.test == unit.cmd、全部门禁代码路径（含增量 final、逐 nodeid 重跑）原样不动。新字段（list / junit / probe / test_files / root）写进简写形态，按现有「未知字段」报错。

部件形态

顶层只含 parts、slow_allow。parts 是非空对象，部件名 [a-z0-9-]+。部件只含 root、test_files（可选）、unit、regions（可选）。

为什么不把简写在内部规范化成部件、走同一路径

那样简写仓库会失去增量 final 与逐 nodeid 重跑（部件形态都不支持），属于行为变化。两条路径的代价是代码多一个分支，换来既有用户零变化（铁律 10）。

否决

每个子项目一份分层文件、库递归发现（M1-B）。跨子项目的 change 要合并多份，区域名唯一与不重不漏都得跨文件校验。

否决

仍一个单元层、由 agent 写聚合脚本（M1-C）。先后跑多个 pytest 会被判不可度量，库也无法逐部件判。

一律相对 git 顶层

root、test_files、paths、covers、scenario_tests、owns、slow_allow 键、门禁文本里的用例 id，都相对顶层。

root
非空、相对路径、规范化后不含 .. 段、不以 / 开头，. 表示顶层；
lint 校验它是顶层下存在的目录；
多个部件可以共用 root（同一子项目两种语言），这时必须各写 test_files，否则 check 会报文件属于多个部件（D4）。
命令都在 root 下运行

unit.cmd、区域 cmd、list、probe.cmd、probe.canary。

补前缀
list 的输出、适配器记录的 nodeid、junit 的 file 属性，相对 root，由库拼上 root；root 为 . 时不变；
内置 pytest 探针直接记相对顶层的路径（D6），因为 pytest 的 rootdir 可能不是 root（上层有 ini 时）。
二选一

单元层与每个区域恰好写其中一个，两个都写或都不写 → lint 红。

paths

glob 数组，与 owns 同一语义（glob_match）。

list

在 root 下运行的命令，stdout 每行一个测试文件路径（相对 root），空行忽略。退出非 0 或超时（60 秒）→ lint 红并点名部件与层。同一进程内同一 (root, list) 只运行一次。

为什么 list 输出文件而不是用例

沿用 test-tiers 的文件级粒度（ADR「按路径归层」），check / G12 / scenario_tests 都按文件判。需要用例级切分（如 Go 同包内按 build tag 分）时，由 list 脚本按文件内容挑文件。

谁用选择器

lint 的 scenario_tests 校验、G12、check、render、tier_sec 的 G7 用例归层。

否决

只支持 paths。Rust 内联单测、Go 同目录按 tag 分层这类布局，路径表达不了。

部件的测试文件 T(P)
写了 test_files → 匹配这些 glob 的文件；
没写 → root 下匹配内置命名的文件。
内置命名 TIER_TEST_NAME_RE

TEST_FILE_RE 之外另认：

Go *_test.go；
JVM *Test.java / *Tests.java / *IT.java（.kt 同）；
C# *Tests.cs / *Test.cs；
Ruby *_spec.rb / test_*.rb / *_test.rb；
Rust 部件 root 下 tests/ 里的 *.rs。
只在部件形态用。TEST_FILE_RE 本身不改，G3 等既有判定不受影响。
金丝雀文件

匹配任一部件 probe.canary_files 的文件从全部集合里排除。

全仓测试文件 R = 匹配内置命名的文件 ∪ 各 T(P)，减去金丝雀文件；文件来源 git ls-files --cached --others --exclude-standard。
规则

R 中每个文件恰属一个 T(P)：

属于 0 个 → 「不属于任何部件」；
属于多个 → 「属于多个部件」；
属于一个时，在该部件内恰被一个选择器（单元层或某区域）命中。
G12（部件形态）

本切片区间改动且仍存在的 R 中文件，须落在所属部件的单元层，或落在已选区域；不属于任何部件也是 G12。

兜底

漏写了某个子项目时，它的测试文件只要命中内置命名，就会报「不属于任何部件」。完全不命中内置命名的语言，由 /test-tiers 审批页列「未覆盖」交人确认（文档）。

库每次运行部件单元层都设 FLIGHT_JUNIT=<临时目录>/junit-part.xml。
部件 unit.junit（可选）是相对 root 的报告 glob，用于 runner 只能写到固定位置的情形（如 surefire）。只读 mtime 不早于本次运行开始的文件，防止读到旧报告。
读取次序
三处都没有 → 该部件 G10 不可度量。
用例 id
testcase 带 file 属性 → <root>/<file>::<name>；
不带 → <部件名>::<classname>::<name>；
用作 slow_allow 的键与门禁文本。
否决

解析各 runner 的文本输出取耗时。每种 runner 一套解析器，维护不起；JUnit XML 是几乎所有 runner 都有的公共格式（Q2）。

部件没写 probe
走内置 pytest 探针（与简写形态同一插件）；
插件另写 top 字段 = os.path.relpath(item.path, $FLIGHT_TIER_TOP) + :: + nodeid 的用例部分，库按 top 合并；简写形态不设 FLIGHT_TIER_TOP，记录不变；
不是 pytest（没有开跑记录）→ G11 不可度量。
部件写了 probe
库在 root 下运行 probe.cmd，环境变量 FLIGHT_UNIT_CMD = 要跑的测试命令（单元层运行时为 unit.cmd，自检时为 probe.canary）、FLIGHT_TIER_OUT、FLIGHT_JUNIT；
适配器自己执行 FLIGHT_UNIT_CMD，退出码即测试结果；
往 FLIGHT_TIER_OUT 追加 JSONL

先一行 {"probe": "start"}，每个用例一行 {"nodeid": "<相对 root 的文件>::<用例名>", "sec": 秒, "hits": {"文件"|"子进程"|"网络": 样例}}。与内置探针同一格式，读取复用 _read_probe，再补 root 前缀。

为什么适配器包住命令，而不是替换 unit.cmd

人和 CI 跑的仍是 unit.cmd，门禁跑的是「适配器包住 unit.cmd」，被测的是同一组用例。适配器不自带选测逻辑。

sha 锁定
probe.sha = {仓库相对路径: sha256}，记录 probe.cmd 里每个能解析成仓库内文件的词（先按 root、再按顶层解析）；
lint 逐个重算，文件缺失或哈希不符 → 红，「重跑 test-tiers.py canary」；
没有 sha / checked → 红，「未自检」；
probe.cmd 里没有任何仓库内文件 → canary 拒绝（退出 2），因为无从锁定。
否决

每种语言内置一个探针。语言与 runner 组合太多，Go / JVM / Node 都没有 Python 审计钩子那样的进程内机制；能用的多是系统级追踪（strace、dtrace、LD_PRELOAD），与平台强相关。所以只定契约，由 agent 按仓库实测后写（Q3）。

agent 用该部件的语言写，放在 probe.canary_files 里，没有令牌环境变量时跳过。用例名去掉非字母数字、转小写后分别含 flightcanarypure / flightcanaryfile / flightcanaryproc / flightcanarynet：

pure 只做计算；
file 写文件 D/T；
proc 起一个子进程；
net 在 127.0.0.1 上 bind 或 connect 一个套接字。
判定（全部满足才通过）
适配器输出有开跑记录；
四个用例都有记录；
pure 无触碰；
file 有「文件」触碰且样例含 T，并且 D/T 确实存在；
proc 有「子进程」触碰；
net 有「网络」触碰。
结果
通过 → 写 probe.sha 与 probe.checked（ISO 时间），其余键原样保留，退出 0；
不通过 → stdout 逐条点名未满足的条件，不改文件，退出 1。
为什么要「库出题」

令牌与目录每次随机，适配器无法预先写死结果；D/T 落盘由库亲自检查，证明金丝雀确实跑了。它证明的是「这个适配器在这个部件的 runner 配置下报得出三类触碰」，不证明它没有盲区（D9）。
