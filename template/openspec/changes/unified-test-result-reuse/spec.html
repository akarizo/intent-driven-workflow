Why · 01为何而做

模板里"复用测试结果"的三条路——基线复用、增量 final、检查——彼此不通，代价也看不见。afa 一个 change 一天跑了 5 次全量基线，final 里又多跑一遍全量，最后是人自己发现才来问。对本机 7 个已安装项目做了只读盘点（2026-11-09，数字均为下限）：

- afa： - 全量基线 95 次、合计 37,633 秒，复用成功只有 6 次； - 首次基线没有任何候选：64 次 / 28,161 秒； - 重新规划时，切片代码已经落地，基线必然全量：17 次 / 6,337 秒； - final 因"没有可用锚点"全量 33 次；锚点池 20 条里只有 2 条测到依赖图； - 检查因缓存键混进了 FLIGHT_*，再跑一遍全量：25 次。 - gateway：不是 pytest，又没配 gate.impacted，final 每次全量。 - 其余 6 个项目的 slice-gate 都比模板旧。

方案与证据见 docs/full-suite-reuse-rootfix.html（主仓库工作区，未入库）。用户已逐项决策（Q1–Q6）：合成一个 change，项目侧适配由用户在各项目自己做。

What · 02变更范围

  • 结果交接：final 跑完 gate.test 后写出本次测试结果文件，经新变量 GATE_TEST_RESULT 交给 gate.checks；锚点另记逐用例结局，增量 final 也能交出完整结局。FLIGHT_* / GATE_* 写进契约，声明为每次运行都会变的变量；gate.test 的环境里加上 GATE_PHASE / GATE_CHANGE，包装脚本不必再写死 change 名。
  • 运行器契约：新增导出 FLIGHT_PLUGIN_PATH / FLIGHT_PYTEST_ARGS，会重建环境的包装脚本把这两个变量转发给 pytest，依赖图就能测到。"依赖图未测"拆成四类原因（不是 pytest / 插件被丢弃 / 插件导入失败 / 记录不完整），每类带修法。新增契约文档 template/.claude/flight-runner-contract.md，随安装下发。
  • 项目级声明：<openspec 根>/gate-scope.json 在 cmd / builtin 之外可选 global（命中即全量）、blind（匹配的测试文件每次都重跑）、anchor_max_hops（锚点链上限）。
  • 基线走锚点：基线候选扩大为"本 change 旧基线 → 锚点池（任意来源，可跨 change，须测到依赖图）→ 基线池"。有非测试改动时，按 final 已有的选测与全量触发规则只补跑受影响的测试。跨 change 带预存红只能经锚点路径复用（锚点上失败的文件一定重跑），基线池仍只收全绿（修订 2026-10-15 用户决策，新 ADR 取代旧论证）。红基线的测试部分本身有效时可按部件复用。同 change 门禁脚本只计 gate.test 闭包里实际用到的。
  • cmd_key 归一：命令直接引用的文件内容里出现的本 change 名，先归一再算指纹，并纳入静态 shell 闭包。各 change 的同款包装脚本因此能互相复用。BREAKING（一次性）：升级后旧的基线、锚点、池条目指纹全部失配，各跑一次全量后恢复。
  • 锚点链上限：锚点记录"由增量推出的代数"，达到 K 代（默认 5，anchor_max_hops 可调）就强制全量。基线与增量 final 共用这条规则（用户决策）。BREAKING（行为）：已经在正常增量的项目，升级后会周期性多跑一次全量。
  • 测试成本可见：新增零 token 脚本 flight-doctor.py：
  • forecast：在 baseline 报告行、/opsx-apply 起飞前和 spec.html 里，给出"这次 baseline / final 会不会全量、为什么、大约多少秒"；
  • cost：收口时汇总本 change 的全量次数与原因，分"必要"与"可避免"两类；
  • doctor：项目级体检，install.sh --upgrade 结束时自动跑，只报告。
  • 全部只预告，不阻断（用户决策 Q3）。
  • 规划指引：propose 的命令与 skill 同步写明——包装脚本要转发运行器契约、用 $GATE_CHANGE、不写死 change 名；基线复用规则的描述随实现更新。
代码：template/.claude/hooks/slice-gate.py（基线、final、run_test_gate、锚点、cmd_key、选测声明、检查环境）；新增 template/.claude/hooks/flight-doctor.py；template/.claude/hooks/spec_html.py（成本预告段）；install.sh（升级后跑 doctor）。文档：新增 template/.claude/flight-runner-contract.md；opsx-propose / opsx-apply 命令与同名 skill；template/openspec/schemas/intent-driven/schema.yaml 的选测声明描述；README。ADR：新增 DRAFT-baseline-reuse-via-dependency-anchor，取代 DRAFT-baseline-reuse-by-content-fingerprint 的"跨 change 只复用全绿"与"只认测试文件 Δ"两项；新增 DRAFT-gate-test-result-handoff-and-runner-contract（检查与包装脚本的两份运行契约）。兼容：旧检查不读 GATE_TEST_RESULT，行为不变；旧的 gate-scope.json 不带新字段，行为不变；不转发契约的包装脚本行为不变（全量），只是现在会被预告和归因；cmd_key 算法变化与锚点链上限，各让每个项目多跑一次全量。不在本 change：afa testgate 的契约适配、检查改读 GATE_TEST_RESULT、headrun 缓存键剔除 FLIGHT_*、gateway 配 gate.impacted（用户在各项目自己做，本 change 只交付契约文档）；把 afa 临时修复加回去。

Specs · 04行为规范 (Gherkin)

baseline-anchor-reuse ADDED

Requirement: 基线经锚点复用，非测试改动按依赖图补跑

Rule: baseline（不带 --full、没有测试分层文件）SHALL 依次尝试三类候选： 1. 本 change 的旧基线（现有规则）； 2. 锚点池：条件是 gate.test 指纹与分层指纹都匹配、measured 为真、未达锚点链上限；多条可用时取 |Δ| 最小的； 3. 基线池。

经锚点复用时： - Δ 命中全量触发项（与 final 同一套规则，含项目声明的 global）→ 不复用，原因写进 reuse_skipped； - 否则只补跑 final 同一选择集合：依赖与 Δ 相交的测试文件 ∪ Δ 里现存的测试文件 ∪ 锚点失败所在的文件 ∪ 盲区 ∪ 声明的 blind。

经锚点复用的基线： - 预存红 = 补跑结果中 FAILED / ERROR 的 nodeid，记在 test.failed_nodes，并标 test.failed_form 为 nodes； - mode 为 incremental，incremental.source 为 anchor，incremental.from 点名锚点的 change 与 commit，incremental.rerun_files 列出补跑的测试文件。

基线池入池条件不变（只收全绿的全量）。跨 change 带预存红的结论只能经锚点路径复用；锚点失败用例所在的文件一定在补跑集合里。

Requirement: 红基线里有效的测试部分按部件复用

Rule: 基线 SHALL 记 test_ok：测试部分本身有效时为真（跑了、可度量、运行期间没有已有文件被改动）。 - 本 change 旧基线 ok 为假、但 test_ok 为真，且 Δ 满足复用条件时，复用它的测试部分；verify、lint、typecheck 与检查照常判定与重跑； - 旧基线缺 test_ok 字段时不复用测试部分。

Requirement: cmd_key 归一 change 名并覆盖 shell 闭包

Rule: cmd_key SHALL 取命令直接引用的仓库内文件及其静态 shell 闭包（被 source / . / bash 调用的仓库内脚本）的内容，先把其中本 change 目录名（按词边界）替换成 <change>，再与归一后的命令文本一起算指纹。 - 两个 change 的包装脚本只差 change 名时，指纹相同； - 闭包里任一脚本的内容变了，指纹就变。

  • THEN两个指纹相同
  • AND改动 beta 的 _common.sh 之后，beta 的指纹与 alpha 不同

Requirement: 本 change 门禁脚本只按 gate.test 闭包影响测试结论

Rule: 用本 change 旧基线复用测试结论时，本 change 目录里的门禁脚本 SHALL 只计 gate.test（与 gate.pytest）静态 shell 闭包里的那些。其余脚本（例如只被 gate.lint 引用的）改动不让测试结论失效；lint、typecheck 与 verify 的沿用判定照旧把它们计入。

Scenario: lint-only-gate-script-change-keeps-test-reuse

  • AND之后只改了 <change>/verify/lint.sh
  • WHEN再运行 baseline
  • THENmode 为 incremental
  • ANDlint 记录没有 reused 标记（已重跑）

Requirement: 锚点链上限

Rule: 锚点 SHALL 记 hops： - 全量运行写出的锚点为 0； - 由增量推出的锚点（增量 final、经锚点的增量基线）为来源锚点的 hops + 1。

hops ≥ K 的锚点不作 final 与基线的候选；K 取 gate-scope.json 的 anchor_max_hops，缺省 5。因此没有可用锚点时，full_why 或 reuse_skipped 写「锚点链已达上限 K 代」。

旧锚点缺 hops 时，source 为 final-incremental 的视为已达上限，其余视为 0。

  • WHEN运行 baseline
  • THENmode 为 full
  • ANDreuse_skipped 有一条含「上限 1」

flight-runner-contract ADDED

Requirement: 导出供包装脚本转发的契约变量

Rule: run_test_gate 加载 flight 插件时，SHALL 在保留现有 PYTEST_ADDOPTS / PYTHONPATH 注入的同时，另外导出两个变量： - FLIGHT_PLUGIN_PATH：flight 插件与 sitecustomize.py 所在目录； - FLIGHT_PYTEST_ARGS：本次要传给 pytest 的 -p 插件参数与 --junitxml 参数，按 shell 规则引号。

会重建子进程环境的包装脚本，只要把前者放进被测进程的 PYTHONPATH、把后者原样传给 pytest，依赖图即可测到。去掉插件的重跑（_plain）不导出这两个变量。

  • WHEN运行 baseline
  • THEN基线 warnings 里没有「依赖图未测」
  • AND最新锚点 measured 为真

Requirement: 依赖图未测的原因分四类

Rule: 依赖图没测到时，SHALL 给出机读类别和带修法的人话。类别： - not-pytest：既没有 junit 输出，也没有 pytest 汇总行； - plugins-dropped：pytest 跑了（有 junit 或汇总行），但外层防护标记没写、也没有插件导入错误——包装脚本没把 -p 参数传给 pytest； - plugin-import-failed：输出里有 flight 插件导入错误（沿用现有的去插件重跑）； - incomplete：依赖图记录有开始、没有结束，或已损坏。

gate-test-result-handoff ADDED

Requirement: final 把本次测试结果交给检查

Rule: final 跑完 gate.test（全量、内建增量或 gate.impacted）之后、运行任何 gate.checks 的 final 之前，SHALL 写出结果文件 <git common dir>/flight-gate-checks/<change>/.gate-test-result.json，并在每项检查的环境里设 GATE_TEST_RESULT=<该文件绝对路径>。

结果文件字段： - change、commit、at； - mode：full / incremental / impacted； - cmd、cmd_key：gate.test 命令与它的指纹； - nodes：{仓库相对 nodeid: outcome}，outcome 取 passed / failed / error / skipped / xfailed / xpassed；impacted 模式或依赖图未测时为 null； - inherited：沿用锚点结论的用例数；全量为 0；impacted 为 null； - failed_nodes：本次判为失败（failed / error）的 nodeid，排序； - junit：本次 junit 副本（同目录 .gate-test-junit.xml）的绝对路径；增量时只含重跑部分，取不到时为 null； - complete：nodes 覆盖锚点与本次重跑的全部用例时为真。

同树沿用的 final 不运行检查，也不写结果文件。

Scenario: final-full-hands-result-to-checks

  • GIVEN计划配了一项检查，它的 final 命令把 GATE_TEST_RESULT 指向的文件复制到仓库外
  • ANDbaseline 已跑过
  • WHEN运行 final --full
  • THEN复制出的结果 mode 为 full、inherited 为 0、complete 为真
  • ANDnodes 里 tests/test_a.py::test_a 的结局为 passed
  • ANDjunit 指向的文件存在

Scenario: final-incremental-result-composes-anchor-outcomes

  • GIVENbaseline 已写下测到依赖图的锚点，之后只提交了 src/a.py 的改动
  • AND计划配了同样复制结果文件的检查

Goals / Non-Goals

Goals: - 每份测试结果只产出一次，基线、final、检查都能取用。 - 重新规划（切片代码已落地）与首次基线，在锚点可用时按依赖图只补跑受影响的测试。 - 包装脚本有一条稳定、写成文档的路，把依赖图插件接进被测进程。 - 每次全量都有机读原因；起飞前预告，收口时归因。 - 依赖图盲区的累积有上限，项目能声明全局路径与盲区。

Non-Goals: - 不改任何项目仓库（afa testgate、gateway 的 gate.impacted）：只交付契约文档（Q5）。 - 不改基线池入池条件（仍只收全绿）。 - 有测试分层文件时，基线仍恒全量（现状，DRAFT-test-tiers-unit-baseline-by-audit-probe）。 - 不做"源路径 → 测试 glob"的影响映射（只做 global / blind，见 Open Questions）。 - 不做跨机器共享锚点；不改 G7；不加 CI。 - 不阻断起飞（Q3）。
