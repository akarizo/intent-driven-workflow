Why · 01为何而做

afa 仓（ameco-rsr2602/decoder/air-fanst）正在把 executor 的测试体系拆成 S0–S4 五个 change 重构，用户硬要求每一步「迁移之后代码覆盖对得上」。落到门禁上要两类检查：

- 覆盖对拍：merge-base 量一次、分支头再量一次，按「模块 · 函数 · 行文本」对齐比较； - 共用包联动回归：改动碰到 packages/ 时另一个子项目的环境也跑回归，按它自己的基线差分。

两者都是「两次测量 + 比较」或「按改动触发、自带基线」，今天的 gate.test / lint / typecheck 只有单次运行加失败集差分，表达不了。afa 的 CI 里 executor 没有测试 job，所以飞行流程的 slice-gate 是唯一生效的门禁。

覆盖测量、对齐规则、子项目回归都与仓库强相关，不进模板。模板只需要一个通用扩展点：baseline 与 final 各调用一次仓库自定义命令，红就不收口。

来源：afa 的跨仓提案 docs/proposals/2026-10-17-slice-gate-paired-checks-from-afa.md（主仓库工作区，未入库）。对照代码 template/.claude/hooks/slice-gate.py @ main 766d3fa。

用户决策（2026-10-17，评审页逐项选择，代替 grill-me 访谈；6 项全取推荐）：

- 沿用规则完全照 D10（baseline-incremental-reuse design D10）：本次增量、候选是本 change 旧基线、严格差异为空、命令与 cmd_key 不变才沿用；跨 change 候选与 --full 一律实跑。提案 §2.3「增量模式一律不沿用」与此矛盾，按 D10 改正。 - preflight 不加新规则：检查的 name 与 baseline 命令并入 plan_sha（只在配置了检查时追加），复用现有「基线红 / 基线过期」。 - 仓库默认检查本 change 一起做，默认文件按 change 目录往上两级找（<change_dir>/../../gate-checks.json），安装后的仓库与本仓库（template/openspec/）两种布局都成立。 - 检查的 baseline 实跑前清空它的共用目录，防止 final 读到上一次基线的残留。 - 完整输出落盘：$GATE_CHECK_DIR/.gate-<phase>.log；红时只带末尾 20 行加日志路径。 - 命名照提案：gate.checks / gate.checks_skip / 环境变量 GATE_* / 目录 flight-gate-checks / 失败编号 G9。

评审页还列了 6 条直接写进规格的约定，用户未反对：final 缺基线记录即红；超时整组结束进程；未配置时行为与输出不变；G7 红时另加一条「G9 检查未跑」；lint 校验检查的形状；命令与同名 skill 同改。

What · 02变更范围

  • 配置：slices.json 的 gate 新增可选 checks（数组：name / baseline / final / timeout_sec）与 checks_skip（{name: 理由}）。
  • 运行契约：检查命令在 git toplevel 经 shell 执行，注入 GATE_PHASE / GATE_CHANGE / GATE_BASE_COMMIT / GATE_CHECK_DIR；共用目录在 <git common dir>/flight-gate-checks/<change>/<name>/，同仓各 worktree 可见、不进 commit；只看退出码；完整输出写 .gate-<phase>.log；配置了 timeout_sec 时超时整组结束进程并判红。
  • baseline：在全量、lint / typecheck、每片 verify 之后运行每个 baseline 非空的检查，记入 gate-baseline.json 的 checks.<name>；红即基线红；沿用照 D10；实跑前清空共用目录；基线池条目不含检查结果。
  • preflight：只把检查的 name 与 baseline 命令并入 plan_sha，不新增校验代码。
  • final：G7 绿时，在全量 gate.test 判定之后（无论全量红绿）运行每个检查的 final，非 0 记 G9 check <name>；基线缺记录也记 G9；G7 红时不跑并另加一条警告。
  • 仓库默认检查：openspec 根目录下可放 gate-checks.json；slice-gate.py lint 要求其中每个检查出现在本 change 的 gate.checks，或在 gate.checks_skip 写明非空理由。
  • lint 校验形状：name 合法且不重复、final 非空、baseline 为 null 或非空字符串、timeout_sec 为正数、不认识的字段报错、checks_skip 理由非空且不与 gate.checks 同名。
  • 文档：schema 的 tasks instruction 写明 gate.checks 与仓库默认检查；opsx-propose / opsx-verify 命令与同名 skill、README 写明检查的运行时机与契约。
template/.claude/hooks/slice-gate.py：lint_plan 增加检查形状与仓库默认检查规则（调用方 cmd_lint / cmd_preflight 传 change 目录）；plan_sha 在配置了检查时追加 [name, baseline]；cmd_baseline 在 verify 之后、运行期间改动判定（D6）之前运行检查；cmd_final 在全量判定之后运行检查；新增带超时、整组结束进程、完整输出落盘的检查运行函数。文档：template/openspec/schemas/intent-driven/schema.yaml（tasks instruction）、template/.claude/commands/opsx-propose.md 与 template/.claude/skills/openspec-propose/SKILL.md、template/.claude/commands/opsx-verify.md 与 template/.claude/skills/openspec-verify-change/SKILL.md、README.md。测试：新增 tests/test_gate_checks_lint.py、tests/test_gate_checks_baseline.py、tests/test_gate_checks_final.py、tests/test_gate_checks_docs.py；既有测试不改。ADR：新增 DRAFT-gate-paired-checks-by-exit-code；DRAFT-test-gate-baseline-diff、DRAFT-baseline-reuse-by-content-fingerprint 继续有效，不 supersede。兼容：没有 gate.checks、也没有仓库默认文件时，baseline / final / preflight / lint 的行为与输出不变，plan_sha 算法结果不变，gate-baseline.json 不出现 checks 键；旧基线照常可读。已知边界：检查测的往往是仓外状态（如 afa 的数据仓指纹），沿用时看不出仓外变化，与 lint / typecheck 一样用 --full 兜底；检查脚本如果被本 change 的切片划进 owns，执行体可以改弱它；信任模型与 gate.test 相同，靠计划审批与 G6 所有权兜住；共用目录随 change 留在 git common dir 里，没有自动回收。

Specs · 04行为规范 (Gherkin)

gate-paired-checks ADDED

Requirement: 计划里的检查配置与仓库默认检查由 lint 校验

slices.json 的 gate MAY 带 checks（数组）与 checks_skip（对象）。slice-gate.py lint（preflight 内的同一份计划校验也一样）SHALL 在下面任一条不满足时退出非 0，stderr 每条违规以 checks: 开头并点名对象：

- gate.checks 是数组，每项是对象，只含 name、baseline、final、timeout_sec 这几个字段； - name 匹配 ^[a-z0-9-]+$，在本 change 内不重复； - final 是非空字符串； - baseline 缺省、为 null，或是非空字符串； - timeout_sec 缺省，或是大于 0 的数（布尔值不算数）； - gate.checks_skip 是对象，每个值去掉首尾空白后非空，键不同时是 gate.checks 里的 name。

仓库默认检查文件是 openspec 根目录下的 gate-checks.json，openspec 根目录 = change 目录的上两级（<change_dir>/../..）。文件存在时：

- 它 SHALL 是 JSON 数组，每项是带合法且不重复 name 的对象；否则 lint 红，点名该文件； - 其中每个 name SHALL 出现在本 change 的 gate.checks 里（同名即可，命令可以不同），或是 gate.checks_skip 的键；否则 lint 红，点名该检查。

文件不存在时，这条规则不触发。

Scenario: lint-rejects-malformed-checks

  • GIVENgate.checks 有这几项：name 为 Bad 的、no-final 缺 final 的、两个 name 都是 dup 的、zero-timeout 的 timeout_sec 为 0 的、typo 带未知字段 base_line 的；gate.checks_skip 里 empty-reason 的理由是空白，ok-check 同时出现在 gate.checks 与 checks_skip
  • WHEN运行 slice-gate.py lint
  • THEN退出非 0
  • ANDstderr 里以 checks: 开头的行分别点名 Bad、no-final、dup、zero-timeout、typo、empty-reason、ok-check

Scenario: lint-accepts-valid-checks

  • GIVENgate.checks 有两项：parity 带 baseline、final 与 timeout_sec: 60；linkage 的 baseline 为 null、只有 final；gate.checks_skip 为 {"other": "本 change 不碰共用包"}
  • WHEN运行 slice-gate.py lint
  • THEN退出 0，stdout 打印 waves

Scenario: lint-requires-repo-default-check

  • GIVENopenspec/gate-checks.json 列出 coverage-parity；openspec/changes/c 的 gate.checks 与 gate.checks_skip 都没有它
  • WHEN运行 slice-gate.py lint
  • THEN退出非 0；stderr 有一行以 checks: 开头并点名 coverage-parity

Scenario: lint-accepts-default-check-skipped-with-reason

  • GIVENopenspec/gate-checks.json 列出 coverage-parity；本 change 的 gate.checks_skip 为 {"coverage-parity": "只改文档，见 design D3"}
  • WHEN运行 slice-gate.py lint
  • THEN退出 0

Scenario: lint-repo-defaults-follow-change-dir

  • GIVENchange 目录在 template/openspec/changes/c；template/openspec/gate-checks.json 列出 coverage-parity；template/ 的上一级没有 openspec/；本 change 没写这个检查
  • WHEN运行 slice-gate.py lint
  • THEN退出非 0；stderr 有一行以 checks: 开头并点名 coverage-parity

Scenario: lint-rejects-unreadable-repo-defaults

  • GIVENopenspec/gate-checks.json 的内容不是合法 JSON；本 change 的计划其余部分合法
  • WHEN运行 slice-gate.py lint
  • THEN退出非 0；stderr 有一行以 checks: 开头并含 gate-checks.json

Requirement: 检查命令的运行契约

baseline 与 final 运行检查命令时，SHALL 满足：

- 工作目录是 git toplevel，命令经 shell 执行； - 注入环境变量： - GATE_PHASE = baseline 或 final； - GATE_CHANGE = change 目录名； - GATE_BASE_COMMIT = gate-baseline.json 的 commit（baseline 时就是本次基线记下的 HEAD）； - GATE_CHECK_DIR = <git common dir 的绝对路径>/flight-gate-checks/<change>/<name>/，运行前已存在； - 判定只看退出码：0 为绿，其余为红；slice-gate 不解析输出； - 完整输出（stdout 与 stderr）覆盖写入 $GATE_CHECK_DIR/.gate-<phase>.log；红的提示带日志路径与输出末尾 20 行； - 配置了 timeout_sec 时，到时结束检查进程所在的整个进程组并判红，提示写明「超时 N 秒」；没配置时不设超时。

Scenario: check-env-and-dir-shared-across-phases

  • GIVEN在仓库的另一个 worktree 里有 change c，检查 parity 的 baseline 命令把收到的环境变量与工作目录写进 $GATE_CHECK_DIR，并写一个 seed.txt；final 命令同样记录环境变量，seed.txt 不存在就退出 4
  • WHEN在该 worktree 里依次运行 slice-gate.py baseline 与 slice-gate.py final
  • THEN两次都退出 0
  • AND两次拿到的 GATE_CHECK_DIR 相同，都是主仓库 .git/flight-gate-checks/c/parity
  • AND两次的 GATE_CHANGE 都是 c，GATE_BASE_COMMIT 都等于基线的 commit，工作目录都是该 worktree 的根
  • ANDGATE_PHASE 依次为 baseline、final

Scenario: check-timeout-is-red

  • GIVEN检查 slow 的 baseline 命令是 sleep 30; echo done，timeout_sec 为 1
  • WHEN运行 slice-gate.py baseline
  • THEN退出非 0，整体用时不到 20 秒
  • ANDreasons 有一条点名 slow 并含「超时」

Requirement: baseline 运行并记录检查

slice-gate.py baseline SHALL 在全量 gate.test、lint / typecheck、每片 verify 之后，在运行期间改动判定之前，按 gate.checks 的顺序运行每个 baseline 非空的检查：

- 实跑前先清空该检查的 GATE_CHECK_DIR 再重建； - 结果记入 gate-baseline.json 的 checks.<name> = {exit, sec, cmd, key}，key 按 cmd_key 对该命令计算； - 退出非 0 或超时 → reasons 加一条以 check <name> 开头、写明退出码或超时的理由，基线判红； - baseline 为 null 的检查在这里不运行、不记录； - gate.checks 非空时 gate-baseline.json 有 checks 对象。

下面全部满足时，SHALL 不运行该检查、不清空它的目录，沿用本 change 上一次基线的记录，写 {exit, sec, cmd, key, reused: true}：

- 本次走增量，且候选是本 change 现有的基线； - 严格差异为空（口径与 lint / typecheck 的沿用相同）； - 上一次记录的 cmd 与 key 都与当前相同； - 该检查的 GATE_CHECK_DIR 仍存在。

其余情况一律实跑：跨 change 的池候选、--full、命令或指纹变了、目录不在了。基线池条目不含检查结果。

Scenario: baseline-red-when-check-fails

  • GIVEN检查 parity 的 baseline 命令退出 3；全量、lint 与 verify 都绿
  • WHEN运行 slice-gate.py baseline
  • THEN退出非 0；ok 为 false
  • ANDreasons 有一条以 check parity 开头并含 exit 3；checks.parity.exit 为 3

Scenario: baseline-clears-check-dir-before-run

  • GIVEN检查 parity 的共用目录里有上一次留下的 stale.txt；本次 baseline 要实跑这个检查
  • WHEN运行 slice-gate.py baseline
  • THEN退出 0；stale.txt 不存在，本次检查写下的文件存在

Scenario: baseline-check-reused-when-tree-unchanged

  • GIVENchange c 已有一次全量绿基线，检查 parity 实跑过一次；之后只改了本 change 的 proposal.md
  • WHEN再运行 slice-gate.py baseline
  • THEN退出 0；检查没有再运行
  • ANDchecks.parity.reused 为 true，checks.parity.exit 为 0

Scenario: baseline-check-rerun-when-command-changed

  • GIVENchange c 已有一次全量绿基线，检查 parity 实跑过一次；之后把它的 baseline 命令末尾多加一个参数
  • WHEN再运行 slice-gate.py baseline
  • THEN退出 0；检查又运行了一次；checks.parity 没有 reused

Scenario: baseline-check-rerun-when-dir-missing

  • WHEN再运行 slice-gate.py baseline
  • THEN退出 0；检查又运行了一次；checks.parity 没有 reused

Scenario: baseline-check-rerun-on-cross-change-reuse

  • GIVENchange c 跑过一次全绿的全量基线并进了基线池；change d 的全量脚本与 c 相同，配了检查 parity
  • WHEN对 d 运行 slice-gate.py baseline

  • ANDd 的检查运行了一次；checks.parity 没有 reused

Requirement: preflight 按计划对账检查

plan_sha SHALL 在 gate.checks 非空时，把每个检查的 [name, baseline] 按顺序追加进参与哈希的内容；gate.checks 缺省或为空时，plan_sha 的结果与现状相同。preflight 不为检查新增校验：检查在基线上红时基线 ok 为 false，preflight 报「基线红」；计划新增、删除检查或改了 baseline 命令时 plan_sha 变化，preflight 报「基线过期」。只改检查的 final 或 timeout_sec 不让基线过期。

Scenario: preflight-stale-when-check-added

  • GIVENchange c 已有一次绿基线，当时计划里没有检查；之后在计划里加了检查 parity（baseline 与 final 都是 true）并提交
  • WHEN运行 slice-gate.py preflight
  • THEN退出非 0；stderr 含「基线过期」

Scenario: preflight-ignores-check-final-edit

  • GIVENchange c 的计划有检查 parity（baseline 与 final 都是 true），已有一次绿基线；之后只把它的 final 改成 true x 并提交
  • WHEN运行 slice-gate.py preflight
  • THEN退出 0

Requirement: final 运行检查并以 G9 判定

slice-gate.py final 在 G7 绿时，SHALL 在全量 gate.test 判定之后（全量红也照跑）按顺序处理每个检查：

- 先核对基线：gate-baseline.json 要有 commit；baseline 非空的检查还要有同名记录、exit 为 0、cmd 等于当前 baseline 命令。不满足 → failed 加一条以 G9 check <name> 开头、含「基线」的项，提示重跑 baseline，不运行该检查的 final； - 核对通过 → 运行 final 命令；退出非 0 → failed 加 G9 check <name>：exit N；日志 <路径> 加输出末尾 20 行；超时 → 同样以 G9 check <name> 开头并写明超时； - final 不清空共用目录，目录不存在时创建。

G7 红时 SHALL 不运行任何检查，warnings 加一条「G9 检查未跑：G7 已红，scenario 全绿后重跑 final」；原有的「G2 全量未跑」提示照旧。

Scenario: final-red-when-check-fails

  • THENok 为 false；failed 有一项以 G9 check parity 开头，含 exit 1 与 line-30，不含 line-10，并含 .gate-final.log 的路径
  • AND该日志文件含 line-01

Scenario: final-skips-checks-when-g7-red

  • GIVENscenario 测试仍带 strict xfail；检查 parity 的 final 命令运行时会写一个标记文件
  • WHEN运行 slice-gate.py final
  • THENfailed 有 G7 项；标记文件不存在
  • ANDwarnings 含「G9 检查未跑」，也仍含「G2 全量未跑」

Scenario: final-runs-checks-when-full-suite-red

  • GIVEN基线已绿，检查 parity 的 final 命令运行时会记一笔；之后新增了一个失败的测试并提交；scenario 全绿
  • WHEN运行 slice-gate.py final
  • THENok 为 false，failed 有 G2 test 项
  • AND检查的 final 运行了一次

Scenario: final-red-when-baseline-record-missing

  • GIVENchange c 的基线是在计划里还没有检查时跑的；之后加了两个检查：a 的 baseline 为 true、final 运行时写标记 A；b 的 baseline 为 null、final 运行时写标记 B
  • WHEN运行 slice-gate.py final
  • THENfailed 有一项以 G9 check a 开头并含「基线」；标记 A 不存在

Requirement: 未配置检查时行为不变

计划没有 gate.checks、openspec 根目录下也没有 gate-checks.json 时，baseline / final / preflight / lint SHALL 与本 change 之前一致：gate-baseline.json 不出现 checks 键；plan_sha 等于对 [gate.test, gate.lint, gate.typecheck, [[id, verify], …]] 的原算法结果；final 的输出不出现 G9；git common dir 下不创建 flight-gate-checks。

Scenario: no-checks-behavior-unchanged

  • WHEN依次运行 slice-gate.py baseline 与 slice-gate.py final
  • THEN两次都退出 0；gate-baseline.json 没有 checks 键，plan_sha 等于原算法结果
  • ANDfinal 的 JSON 只有原有字段，failed 与 warnings 都不含 G9；git common dir 下没有 flight-gate-checks

Requirement: 文档写明检查的配置、时机与契约

  • WHEN读取它们的正文

Goals / Non-Goals

Goals: - 给仓库一个「baseline 跑一次、final 跑一次、只看退出码」的成对检查扩展点。 - 检查红时基线红、final 红，与现有门禁一样不收口。 - 仓库能声明默认检查，规划时漏写由 lint 拦下，不靠模型记得。 - 未配置时行为、输出、plan_sha 与本 change 之前一致。

Non-Goals: - 模板不解析检查的输出、不做任何覆盖测量或子项目回归。 - 切片门禁（每片 G1–G8）不跑检查。 - 不做隐式合并：仓库默认检查不会自动加进计划，必须在每个 change 里显式写出或写理由跳过。 - 不给检查设默认超时。 - 不回收共用目录。

Decisions

形状

gate.checks = [{name, baseline?, final, timeout_sec?}]，gate.checks_skip = {name: 理由}。

lint

规则见 spec 第一条 Requirement；每条违规以 checks: 开头，进 lint_plan 的 errors，与现有规则一起报。

不认识的字段报错

写成 base_line 这类笔误时，检查会静默变成「只有 final」，基线不跑。宁可让 lint 红。

name 限制为 [a-z0-9-]+

它要当目录名，这样排除了路径穿越与大小写不敏感文件系统上的撞名。

否决

校验命令能否切词——命令经 shell 执行，切词规则与 shlex 不同，校验反而会误拒。

新增 _run_check(cmd, root, env, timeout)

Popen(cmd, shell=True, cwd=root, env=env, stdout=PIPE, stderr=STDOUT, start_new_session=True)，communicate(timeout=timeout)；超时时 os.killpg(p.pid, 9) 后再 communicate() 收尾。返回 (rc, out, sec, timed_out)。

为什么整组结束

检查通常是包装脚本，脚本的子进程会占住输出管道；只结束 shell，communicate 会一直等。做法照 G7 实跑（:775-790）。

否决

复用 run_cmd_full——它不能注入环境变量也没有超时；给它加参数会改到 lint / typecheck 的调用。

位置

<git common dir 的绝对路径>/flight-gate-checks/<change>/<name>/，<change> 是 change 目录名。与基线池同一处（_pool_dir 的解析方式），同仓各 worktree 可见，不在工作树里，不进 commit，也不会被 D6 当成运行期间改动。

baseline 实跑前清空再建（用户决策 Q4）

final 读到的一定是最近一次基线写的数据。沿用时不清空。

final 只建不清

目录不存在时创建（只有 final 的检查第一次运行时）。

否决
只创建不清理——检查脚本某次没写出文件却退出 0 时，final 会读到上一次基线的数据，可能误判为绿；
放 change 目录——覆盖数据可能很大，会被提交，也会被 D6 判成运行期间改动。
每次运行把完整输出覆盖写到 $GATE_CHECK_DIR/.gate-<phase>.log（用户决策 Q5）。文件名以点开头，作为保留名写进契约，避免与检查脚本自己的文件撞名。
红时的 reasons / failed 项

首行写结论与日志路径，后面接输出末尾 20 行（_tail(out, 20)）。gate-report.md 照旧把换行压成一格。

写日志失败（OSError）不改变判定，提示里写「日志未能写入

<错误>」。

次序

每片 verify 之后、D6 的结束快照之前。检查若在工作树里写了文件，照 D6 的规则处理（新出现的未跟踪文件只警告，改了已跟踪文件判红）。

环境

GATE_PHASE=baseline、GATE_CHANGE=<change>、GATE_BASE_COMMIT=bl["commit"]（本次基线开跑时的 HEAD）、GATE_CHECK_DIR。

记录

bl["checks"][name] = {exit, sec, cmd, key}；超时另记 timed_out: true。gate.checks 非空时才有 bl["checks"]。

红

reasons 加「check <name> 在基线上红（exit N）；日志 <路径>」或「check <name> 在基线上超时（N 秒）；日志 <路径>」，后接末尾 20 行。

基线池

入池按字段白名单挑（:1430），天然不含 checks，池代码不改。

条件

hit is not None、src is own、strict_delta == []、旧记录有 exit 且 cmd、key 都与当前相同、GATE_CHECK_DIR 存在。

满足 → {exit, sec, cmd, key, reused: true}，不运行、不清空。
旧记录的 exit 必为 0

本 change 旧基线要当候选，_try_reuse 先要求候选 ok is True；检查红会让基线 ok 为 false，所以能走到沿用的旧记录都是绿的，不用另判。

为什么要求目录仍在

目录被人删了还沿用，final 会读不到数据。实跑一次成本可接受。

否决
永不沿用——只改计划文件重跑 baseline 时，afa 的覆盖对拍要再等一小时；
跨 change 沿用——池不存检查结果，检查测的又常是本 change 的代码树与它自己的目录。
plan_sha 在 gate.checks 非空时，在原 key 列表末尾追加 [[name, baseline], …]（按配置顺序）；为空或缺省时不追加，旧计划的 sha 不变（用户决策 Q2）。
效果

加 / 删检查、改 baseline 命令 → 「基线过期」；检查在基线上红 → 「基线红」；baseline 运行期间改了检查的 baseline 命令 → 现有的「基线运行期间 gate / verify 被修改」（:1417）。

只改 final 或 timeout_sec 不让基线过期

基线测的东西没变。

否决

照提案 §2.4 在 preflight 逐项核对——与 plan_sha 的判定重叠，多一段要维护的代码。

位置

G7 绿时，在全量 gate.test 判定之后；全量红也照跑，一次看全（提案 §5）。

核对基线

每个检查都要 baseline 有 commit（否则 GATE_BASE_COMMIT 无从给）；baseline 非空的检查还要有同名记录、exit == 0、cmd 等于当前命令。不满足 → G9 check <name>：基线缺记录或与计划不符，重跑 baseline，不运行。/opsx-verify 可以不经 preflight 直接跑 final，这里不能假设 preflight 拦过。

运行

环境 GATE_PHASE=final、GATE_BASE_COMMIT=baseline["commit"]；非 0 → G9 check <name>：exit N；日志 <路径> + 末尾 20 行；超时 → G9 check <name>：超时 N 秒；日志 <路径> + 末尾 20 行。

G7 红

不跑；原「G2 全量未跑」提示不变，另加「G9 检查未跑：G7 已红，scenario 全绿后重跑 final」。

ship 读 final 的 ok，不用改。
路径

os.path.join(os.path.dirname(os.path.dirname(os.path.abspath(change_dir))), "gate-checks.json")，即 openspec 根目录（用户决策 Q3）。安装后的仓库得到 openspec/gate-checks.json，本仓库得到 template/openspec/gate-checks.json。

lint_plan(data, change_dir=None)

change_dir 为 None 时不读默认文件（保持现有直接调用方的行为）；cmd_lint 与 cmd_preflight 传入。

文件读不出、不是数组、元素不是带合法 name 的对象、name 重复 → lint 红（fail-closed

默认检查的意义就是防漏写，读不出不能当没有）。

只对账 name，不比较命令

schema 的 tasks instruction 加一句

照提案

gate.checks / gate.checks_skip / GATE_PHASE · GATE_CHANGE · GATE_BASE_COMMIT · GATE_CHECK_DIR / flight-gate-checks / G9（用户决策 Q6）。

GATE_* 是给仓库脚本的对外契约，与模板内部用的 FLIGHT_G7_* 区分开。
判据

检查命令的退出码，由 slice-gate 自己运行取得，不读任何模型叙述。

命令来源

人类审批过的 slices.json；改了 baseline 命令会让基线过期（D7）。

谁能改弱

检查脚本在仓库里时，执行体改它会被 G6 所有权拦下，除非计划把它划进某片 owns——那是人批准的，评审要看。这与 gate.test 指向仓内脚本时的信任模型相同。

判定不出时

基线缺记录 → final 红（D8）；默认文件读不出 → lint 红（D9）；都是 fail-closed。

Risks / Trade-offs

[检查测的是仓外状态（数据仓指纹等），沿用看不出仓外变化] → 与 lint / typecheck 一样用 baseline --full；文档写明。
[检查脚本被划进切片 owns 后可能被改弱] → 计划审批时可见；建议门禁脚本不与被它守护的改动放进同一个 change。afa 的 S0 要落地这两份脚本，S0 自己只能把检查放进 checks_skip，从 S1 起再启用。
[共用目录没有回收，覆盖数据会在 .git 下累积] → 每个检查只保留最近一次基线的数据（D3 清空）；按 change 分目录，人可以按 change 名手动删除。记入 Open Questions。
[检查一跑一小时，baseline 在后台跑得更久] → preflight 已能识别「基线仍在跑」；沿用（D6）避免只改计划时重跑。
[检查在工作树里写文件] → 走 D6 的既有规则；契约里建议写进 GATE_CHECK_DIR。

Migration Plan

  • afa 侧：等本 change 合入并 install.sh --upgrade 后，在 afa 放 openspec/gate-checks.json 与两份脚本。
