Why · 01为何而做

门禁现在只回答测试「对不对」，不回答「多贵」：

- 没有逐用例耗时。baseline 与 final 只留整套秒数（gate-baseline.json 的 test.sec、final 时间线里的「测试 Xs」）；有分层文件时多一行层合计（tier_sec）。哪条用例慢、慢在哪一层，只能事后手工解析 junit（afa 2026-11-18 的测试分层体检就是这么做的）。 - 变更与测试成本对不上账。一次 change 新增了几条用例、加了多少秒、有没有把别的用例拖慢，飞行记录和 PR 正文里都没有。afa 的集成用例两周从 1383 条涨到 1956 条（+41%），是体检时才发现的。 - 后面两件事都要以它为前提：分层预算与豁免（C5b tier-budgets）要有逐用例耗时才能判线；体检与整改命令（C6）要有一份可列出的账本。

2026-11-18 用户在方案页 docs/flight-fixes-and-test-governance.html 第 04 节提出「每次变更要知道新增了哪些用例、速度如何、要不要优化」，并回复「按推荐」。本 change 是该页 C5 的前半（C5a）：只做留账、归因、可见，不改任何判红规则。范围与取舍来自方案页与主会话的拆分指令，没有另开 grill-me 访谈。

What · 02变更范围

  • 逐用例采集（template/.claude/hooks/slice-gate.py，只加采集点）：
  • 依赖图插件在记逐用例结局的同时累计该用例 setup + call + teardown 的耗时；_read_deps 的返回值多一个 secs。
  • 依赖图没测到（包装脚本丢了插件、非 pytest）时退用 junit：按 classname::name 取结局与耗时。
  • 增量重跑（_pytest_outcomes）恒取逐用例耗时，不再只在调用方要分层耗时时才取。
  • 部件形态的适配器部件按 run_part 已有的逐用例秒数上报。
  • 门禁进程把每次测试运行的「本次实测」记进进程内观测表，供落账时合并；不改任何函数的既有返回值含义。
  • 账本（新文件 template/.claude/hooks/test-ledger.py）：
  • 把观测合成一份账本：每条用例记结局、秒、所属层、是本次实测还是沿用；耗时取不到记 null，不编数。
  • 存在 <git common dir>/flight-ledger/<change>/ 下（baseline.json / final.json / delta.json），不进仓库；只保留最近若干个 change 的目录。
  • 子命令 show（按层、按耗时列账本）与 delta（打印对账结果）。
  • baseline 与 final 落账（slice-gate.py，各一个落账点）：
  • baseline：写基线账本；gate-baseline.json 只多一段十来个数的 ledger 摘要；写出的锚点带上逐用例耗时 secs，增量运行里没重跑的用例靠它沿用耗时。
  • final：写收口账本，与基线账本对账，结果进输出 JSON 的 tests、时间线的一小段摘要（用例 +A/-R（新增 Xs））与 delta.json。
  • 账本的任何失败都只留一条警告，不改 baseline / final 的结论。
  • 对账与「测试变更」（test-ledger.py）：新增、删除、变慢、各层用例数与耗时的前后对比、最慢的新增用例、沿用未实测与无耗时的条数；几条固定规则的建议行。只报告，不判红。
  • PR 正文（slice-gate.py ship --markdown）：本机有与 final 对应的对账结果时，末尾附「## 测试变更」一节。
  • 体检（template/.claude/hooks/flight-doctor.py doctor）：新增 [tests] 一节——最近一份账本的各层用例数与耗时、最慢用例、最近几个 change 的新增用例与新增耗时；没有账本时说明原因。
  • 文档：flight-runner-contract.md 新增「测试账本」一节；commands/test-tiers.md、commands/pr-ship.md、README.md 各补相应说明。
  • 不做（留给 C5b / C6）：
  • 分层文件里的 budget、slow_allow 的 limit_sec / expires、集成层单条上限与棘轮、层总量预算判定、任何新的判红。现有 G10 / G11 / G12 的判定与文本不动。
  • 体检与整改命令。
  • 切片门禁（gate）不落账：它只跑该片 verify 与 scenario 用例，覆盖不到整套。
  • 部件形态下区域运行不采集、账本不带部件维度（只有层）。
  • GATE_TEST_RESULT 结果文件不加字段。

test-ledger

Specs · 04行为规范 (Gherkin)

test-ledger ADDED

Requirement: 门禁的每次测试运行留下逐用例结局与耗时的观测

slice-gate.py SHALL 在门禁进程内维护一张观测表，ledger_observations() 返回它的副本；每条观测形如 {"form": "nodeid" | "junit", "outcomes": {用例 id: 结局}, "secs": {用例 id: 秒}}，另可带 "tier": 层名（上报方已经知道这批用例属于哪一层时）。三个入口各上报一次本次实测：run_test_gate（依赖图测到时 form 为 nodeid，用例 id 为仓库相对 nodeid，耗时为该用例 setup + call + teardown 之和；依赖图没测到而 junit 可解析时 form 为 junit，用例 id 为 classname::name，结局与耗时取自 junit）、_pytest_outcomes（form 为 nodeid，无论调用方是否传了 durations 都带耗时）、run_part（pytest 部件与适配器部件都报：form 为 nodeid，用例 id 与耗时取自它返回的 secs，outcomes 为空，tier 为 unit；secs 为 None 时不报）。run_test_gate 返回的依赖图 SHALL 多一个 secs = {nodeid: 秒}，其余键与含义不变。run_test_gate 带 cwd 运行时 MUST NOT 上报。上报与采集 MUST NOT 改变任何入口的既有返回值含义，也 MUST NOT 让测试运行失败。 Feature: 门禁看得到每条用例跑了多久 Rule: 依赖图测到用 nodeid，没测到用 junit；采集只追加，不改判定

Requirement: 账本由实测与沿用合成，存在 git common dir

test-ledger.py SHALL 提供 build(meta, observations, universe=None, source=None, rerun_files=None, root=None, tier_of=None)，把观测合成账本：顶层带 v、id_form、tiered、complete 与 meta 里的字段，cases 为 {用例 id: {"o": 结局, "s": 秒 | null, "t": 层 | null, "m": 1 | 0}}。规则：给了 universe（{nodeid: 结局}）时只用 nodeid 形式的观测，账本的用例恰为 universe 的键；没给时，观测里有 junit 形式或来源的 id_form 为 junit 就用 junit 形式（此时 nodeid 形式的观测按 pytest 写 junit 的规则换算后并入：文件路径去掉 .py、/ 换成 .，中间的类名以 . 相连，得 classname，最后一段为 name），否则用 nodeid 形式（junit 形式的观测丢弃）；账本的用例为实测到的用例，rerun_files 给了时再并上来源里「文件仍存在且不在 rerun_files 里」的用例。实测到的用例 m 为 1；其余 m 为 0，耗时取自来源，来源没有该用例或没有耗时时 s MUST 为 null，不得填 0 或估算值。同一用例有多条观测时以后来的为准。结局统一成小写的 passed / failed / error / skipped / xfailed / xpassed，未知为 null。complete 为真当且仅当每条 m 为 0 的用例都在来源里。层的归属：观测带 tier 时该观测里的用例取它；否则 tier_of 给了时 t 为 tier_of(用例所在文件)，junit 形式的文件由 classname 从长到短试出 root 下存在的 .py；两者都没有时 t 为 null。tiered 为真当且仅当给了 tier_of 或有观测带 tier。from_anchor(锚点) SHALL 把带 nodes 的锚点条目转成来源（secs 缺失时耗时全为 null）。save(root, change, name, obj) SHALL 原子写 <git common dir>/flight-ledger/<change>/<name>.json 并只保留最近 30 个 change 的目录；load 读不到返回 None。summary(账本) SHALL 给出 {cases, measured, inherited, no_sec, id_form, complete, tiers: {层: {cases, sec}}}，没有层的用例归在 - 下。子命令 show --change-dir DIR [--phase baseline|final] [--tier 层] [--top N] [--json] SHALL 按耗时由大到小列出账本里的用例，退出码 0 有账本 / 1 没有 / 2 参数不可用。 Feature: 一份账本说清每条用例的结局、耗时、所属层与来源 Rule: 取不到的耗时记空，沿用的标沿用

Requirement: final 账本与基线账本对账得出测试变更

Design · 05技术设计

Context

现状（读 template/.claude/hooks/ 现行代码，main b1be3db，已含 plan-hygiene、machine-test-lock 与 ship-rerun-hardening）：

  • 门禁里跑测试的入口有三个，各自留下的逐用例信息不同：
  • run_test_gate(cmd, …)：跑任意 gate.test / 区域命令 / gate.impacted。恒注入 --junitxml（经 PYTEST_ADDOPTS 与 FLIGHT_PYTEST_ARGS）；deps=True 时另加载依赖图插件，返回 deps.nodes = {nodeid: PASSED|…}；probe=True（有分层文件）时另有探针的逐用例 sec。junit 在临时目录里，函数返回前就删了，只在有 gate.checks 的 final 里留一份副本。
  • _pytest_outcomes(root, targets, …)：G7 实跑、增量重跑、基线补跑、final 无图退路的重跑。用 G7 插件记逐用例结局；逐用例耗时（FLIGHT_G7_SEC）只在调用方传了 durations 时才取。
  • run_part(top, name, part)：部件形态的单元层。适配器部件直接 subprocess.run，返回 secs = {顶层 id: 秒}；pytest 部件转给 run_test_gate（带 cwd）。
  • 逐用例结局已经随锚点保存（nodes），增量运行靠 _anchor_forward 把没重跑文件的旧结局带到新锚点。逐用例耗时哪里都不保存。
  • baseline 有四条路：全量、经锚点增量（_try_anchor）、复用旧基线或基线池（_try_reuse）、部件形态。final 有七种结局：全量、内建增量、gate.impacted、无图退路（ship-rerun-hardening：没有可用锚点、上次绿 final 之后只改了测试文件时，经 _pytest_outcomes 只重跑这些文件，不写锚点）、部件形态、同树沿用（不跑）、G7 红或选测复核未过（不跑套件）。
  • final 时间线备注的现行格式（machine-test-lock design D8）：[全量（原因）|增量（…）] [单元 Xs · 集成 Ys ·] 测试 Xs · 检查 a Xs / b Ys · 排队 Xs · 负载 a→b/N ok|red，片段以 · 相连，结论词在末尾。解析方：timeline.py（按末尾取结论）、flight-doctor.py（parse_note 认「全量（」「增量」；TEST_RE / WAIT_RE / CHECKS_RE 取秒数，CHECKS_RE 到下一个 · 为止）。
  • ship --markdown 只在有 reasons 或 blocked 时有输出；tests/test_ship_verdict.py 钉住「ready 时输出为空」。
  • tests/test_gate_checks_baseline.py::test_no_checks_behavior_unchanged 钉住 final 输出 JSON 的键集合。

已定决策（2026-11-18，方案页第 04 节与主会话的拆分）：C5 拆成 C5a（本 change：留账 + 归因 + 可见，不判红）与 C5b（预算、豁免扩展、棘轮）。

在役 ADR 与本设计的关系：

  • DRAFT-baseline-reuse-via-dependency-anchor / DRAFT-final-incremental-by-dependency-anchor：锚点是「可沿用的测试结论」。本设计给锚点条目加一个可选字段 secs，不改任何选锚点、判全量的规则。
  • DRAFT-gate-test-result-handoff-and-runner-contract：GATE_TEST_RESULT 结果文件的字段与含义不变，本设计不加字段。
  • DRAFT-measurements-stay-out-of-plan-files：度量不进计划文件。账本在 git common dir，gate-baseline.json 只加摘要，slices.json 不动。
  • DRAFT-machine-wide-test-lock：baseline / final 的测量在独占锁内。账本记下本次的锁状态，供以后判断这份耗时可不可信。
  • DRAFT-gate-evidence-not-self-reported：账本与对账由脚本写，不经模型。
  • 没有需要 supersede 的 ADR。

  • 边界：采集留在 slice-gate.py（它才看得到测试进程）；账本的合成、存取、对账、渲染全在 test-ledger.py。slice-gate.py 对账本模块只有「上报观测 / 落账 / 读对账结果」三类调用。
  • 强制力：无。本 change 的所有输出都是报告。

Goals / Non-Goals

Goals：

  • 每次 baseline / final 的测试运行留下逐用例账本：结局、耗时、所属层、实测还是沿用。
  • final 与基线对账，得出本 change 的「测试变更」，在时间线、PR 正文、体检里看得见。
  • 耗时取不到就记 null，沿用的就标沿用，不把猜测混进数字。
  • 账本出任何问题都不影响门禁结论。

Non-Goals：

  • 不判红：预算、单条上限、棘轮、豁免扩展属于 C5b。G10 / G11 / G12 不动。
  • 切片门禁不落账。
  • 部件形态：区域运行不采集，账本不带部件维度。
  • 不改 GATE_TEST_RESULT、不改锚点的选取规则、不改 plan_sha。
  • 不做跨机器同步：账本只在产生它的机器上。

Decisions

test-ledger.py 按 flight-lock.py 的方式由 slice-gate.py 按路径加载（importlib），加载失败或调用抛错 → 落账函数返回一条警告，门禁照常。
flight-doctor.py 同法加载它来读账本。
test-ledger.py 不反向加载 slice-gate.py

层的归属由调用方传一个 tier_of(文件) -> 层名 | None 进来。

为什么

slice-gate.py 已 6075 行，五个在途 change 都要改它；新逻辑独立成文件，冲突面只剩调用点。

备选

写进 slice-gate.py——被否，理由同上。

依赖图插件多写一种记录 {"sec_node": nodeid, "sec": 秒}；_read_deps 把它读成 secs（同一用例多条取最大值——xdist 的主进程与 worker 各写一份）。旧的读取逻辑遇到不认识的记录本来就跳过。
一份账本只用一种 id 形式

有依赖图全集时用 nodeid；否则观测里有 junit 形式、或来源账本是 junit 形式，就用 junit；否则 nodeid。

junit 形式的账本里，nodeid 形式的观测按 pytest 写 junit 的规则正向换算成 classname::name 再并入（文件路径去掉 .py、/ 换成 .，类名以 . 相连）。正向换算是确定的；反向（从 classname 猜文件）才有损，所以 nodeid 形式的账本直接丢弃 junit 形式的观测。典型情形

依赖图没测到的仓库里，G7 实跑与补跑（经 _pytest_outcomes，恒是 nodeid）要与套件的 junit 观测、junit 形式的来源账本并到一起。

为什么不统一用 junit

junit 的 classname::name 映射回 nodeid 是有损的；而依赖图没测到的仓库（afa 现状）恰恰只有 junit。两头各用原生的。

为什么不用探针的 sec

Risks / Trade-offs

[依赖图插件改动影响每一次测试运行] → 新增逻辑只有「按 nodeid 累加一个浮点数、会话结束多写几行」；在一次性原型上跑全量（579 条）没有新增失败。
[锚点文件变大，选锚点时要读全部锚点] → 每条用例多一个数；万级用例的锚点从约 0.5 MB 到约 1 MB，最多 20 条。读取变慢时把 secs 挪到旁路文件（ceiling，实现时标注）。
[耗时有噪声，「变慢」会误报] → 只报告不判红；阈值取「翻倍且多 0.5 秒」；测量在独占锁内。阈值是草案，C5b 用实测数据再定。
[升级后头几次飞行对账不完整] → 来源锚点没有 secs 时如实记「无耗时」；建议行第 3 条会提示跑一次全量。锚点链上限（缺省 5 代）也会周期性带来全量。
[换机器 / 清了 common dir 后没有基线账本] → 对账为空并说明原因；重跑 baseline 即恢复。
[模块级观测表] → 见 D3 的代价。
[ship --markdown 在 ready 时也可能有输出] → pr-ship.md 同步说明；本机没有对账结果时与现状一致，tests/test_ship_verdict.py 钉的「ready 时为空」仍成立。
[部件形态的账本不完整（没有区域、没有部件维度、适配器部件没有结局）] → 文档写明；C5b 设计部件维度时补。

Migration Plan

- 随 install.sh --upgrade 分发：test-ledger.py 是新文件，其余是既有文件的增量改动。 - 不需要人工迁移。升级后： 1. 下一次 baseline 开始写基线账本；经旧锚点的增量基线里，沿用的用例没有耗时； 2. 第一次全量（baseline 或 final）之后锚点带上 secs，此后的增量运行沿用得到耗时。 - 回退：删掉 test-ledger.py 即可——落账点返回警告，门禁其余行为不变；<git common dir>/flight-ledger/ 可直接删除。
