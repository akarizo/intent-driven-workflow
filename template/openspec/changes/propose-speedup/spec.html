Why · 01为何而做

/opsx-propose 太慢。审批页 docs/flight-routing-config.html 第 02 节的实测（20 次有工件的 propose）： - 四个阶段的平均耗时：P0 准备 23.4 分钟、P1 成稿 16.3 分钟、P2 4.1 分钟、P3 收尾 15.5 分钟； - 时间花在哪：每次串行输出约 16 万 token，工具执行不到 4 分钟。所以快慢由「模型逐字写了多少」决定； - 写入量的构成：测试骨架占 24%，模型自己写的 /tmp 脚本占 20%，切片包占 16%，verify 脚本占 5%。其中很多是机械搬运：Gherkin 原文抄进 GWT 注释、owns / verify / deps 抄进切片包、tasks.md 按 slices.json 抄一遍、每个工件分别调用一次 openspec instructions； - P3 卡在 baseline：P3 主要在等 baseline，afa 的中位数是 8.9 分钟，最长 64 分钟，而且它排在最后才开始跑。

用户 2026-11-19 回复「全按推荐」，C2 相关的选择： - Q8-A：只在补断言这一步用 fork 并行，调研和决策类工件由主会话亲自做； - Q9-A：做 baseline 预热； - Q10-A：顺序为 C4 → C1 → C2 → C3。

另有用户原话约束：「最终的解决方案和规划还是要继承主会话」。规划期的模型产出只能来自主会话或 fork（铁律 11，C1 已落地）。

  • 规划期不变式测试放宽一处：规划类文档里的派发只允许 fork（subagent_type: "fork"），其他派发仍判红。

Specs · 04行为规范 (Gherkin)

baseline-warm ADDED

Requirement: 规划开始时在后台预热全量，结果写成本 change 的旧基线

slice-gate.py warm --change-dir D [--cmd CMD] SHALL 按以下顺序定命令： 1. --cmd 显式给出时用它； 2. 否则，openspec 根有 test-tiers.json 时，打印以「跳过预热」开头的一行，exit 0，不写任何文件； 3. 否则，在 changes 根（不含 archive/）下，取 slices.json 最新且不是本 change 的那个 change，用它的 gate.test（连同 gate.pytest）； 4. 都没有时，打印以「跳过预热」开头的一行，exit 0。

命令引用的、位于来源 change 目录下的文件，SHALL 复制到 D 的同一相对位置（已存在则不覆盖），并把命令里的来源目录换成 D。

随后 SHALL 以与 baseline 相同的机制跑一次全量：只用 gate.test，不跑 verify、检查、lint 与 typecheck，不复用候选。结果写入 D/gate-baseline.json： - 带 "warm": true，plan_sha 为 null； - 带 change、cmd_key 与 snapshot； - 运行期间的改动检测与 baseline 相同。

时间线记 warm 事件，stdout 的 JSON 带 test_cmd。

Feature: 基线预热 Rule: 提前跑全量，命令沿用最近的 change，分层仓库跳过

Scenario: warm-runs-full-suite-as-own-baseline

  • GIVEN一个仓库：change prev 的 gate.test 是直接的 pytest 全量命令；新 change c 只有目录，没有 slices.json
  • WHEN运行 slice-gate.py warm --change-dir openspec/changes/c
  • THEN退出 0；c/gate-baseline.json 的 warm 为 true、change 为 c、ok 为 true、mode 为 full、plan_sha 为 null
  • ANDstdout JSON 的 test_cmd 等于 prev 的 gate.test，c/timeline.md 有 warm 事件

Scenario: warm-adopts-latest-change-wrapper

  • GIVENchange prev 的 gate.test 运行 openspec/changes/prev/verify/full.py
  • WHEN对新 change c 运行 warm
  • THENopenspec/changes/c/verify/full.py 被创建，内容与 prev 的相同
  • ANDstdout JSON 的 test_cmd 引用 openspec/changes/c/verify/full.py，不再引用 prev 的目录

Scenario: warm-skips-tiered-repo

  • GIVENopenspec 根有 test-tiers.json
  • WHEN对新 change c 运行 warm
  • THEN退出 0，输出以「跳过预热」开头，c/gate-baseline.json 不存在

Requirement: 正式 baseline 等待预热并按旧基线规则复用

slice-gate.py baseline SHALL 在读取旧基线之前检查 gate-baseline.json：如果它是 warm: true 的运行标记，且 pid 仍存活，SHALL 等它结束，等待期间 stderr 打印一行「等待预热结束」。

之后 SHALL 按现有的本 change 旧基线规则判断复用。复用规则本身 MUST NOT 改动。

Feature: 复用预热结果 Rule: 先等预热，再按原规则复用

Scenario: baseline-reuses-warm-when-only-tests-changed

  • GIVEN新 change c 已预热成功
  • AND之后写入 c/slices.json（gate.test 等于预热打印的命令），并新增一个测试文件 tests/test_new.py
  • WHEN运行 baseline --change-dir
  • THEN退出 0，mode 为 incremental，incremental.from.change 为 c，incremental.rerun_files 为 ["tests/test_new.py"]

Scenario: baseline-waits-for-running-warm

  • GIVEN对新 change c 在后台启动 warm，它的全量要跑几秒
  • AND预热写出运行标记后，写入 c/slices.json（gate.test 等于同一命令）
  • WHEN预热还在跑时运行 baseline --change-dir
  • THENstderr 含「等待预热结束」，结果 mode 为 incremental，incremental.from.change 为 c

plan-kit-commands ADDED

Requirement: 一次取全部待建工件的 instruction

.claude/hooks/plan-kit.py instructions --change <name> SHALL 按以下步骤工作： 1. 运行一次 openspec status --change <name> --json； 2. 对每个状态不是 done 的工件，运行 openspec instructions <id> --change <name> --json； 3. 按工件依次打印一节，节标题为 ## <id> → <outputPath>，内容依次是 instruction、template，以及非空的 rules。

带 --all 时，done 的工件也打印。任一次 openspec 调用失败时 MUST 以 exit 2 退出，并在 stderr 写出失败的命令。

Feature: 汇总 instruction Rule: 一次运行拿全待建工件的写作要求

Scenario: kit-instructions-prints-pending-artifacts

  • GIVEN一个 openspec 桩命令：proposal 已 done，design 与 tasks 待建，每个工件的 instruction 与 template 各不相同
  • WHEN运行 plan-kit.py instructions --change c
  • THEN退出 0，输出有 ## design → design.md 与 ## tasks → tasks.md 两节，各含自己的 instruction 与 template
  • AND输出没有 proposal 那一节

Scenario: kit-instructions-fails-loud

  • GIVEN一个 openspec 桩命令，instructions design 以非 0 退出
  • WHEN运行 plan-kit.py instructions --change c
  • THENexit 2，stderr 含 openspec instructions design

Requirement: 由 slices.json 生成 tasks.md

plan-kit.py tasks --change-dir D SHALL 生成 D/tasks.md： - 第一行是生成声明注释，接着是 ## 切片； - 每片一行：- [ ] <id> <title> （deps: <逗号分隔的依赖或 -> · verify: \<verify>\），与 templates/tasks.md 的格式一致； - 旧 tasks.md 里已勾选的切片 id MUST 保持 [x]。

Feature: 生成 tasks.md Rule: 格式与模板一致，勾选状态不丢

Scenario: kit-tasks-generates-from-slices

  • GIVEN两片计划：S1 无依赖，S2 依赖 S1，各有 verify
  • WHEN运行 plan-kit.py tasks --change-dir
  • THENtasks.md 有 - [ ] S1 <S1 标题> （deps: - · verify: \<S1 verify>\） 与 - [ ] S2 <S2 标题> （deps: S1 · verify: \<S2 verify>\） 两行

Scenario: kit-tasks-keeps-checked-state

  • GIVEN旧 tasks.md 里 S1 已勾选
  • WHEN再次运行 plan-kit.py tasks --change-dir
  • THENS1 那一行仍是 - [x]，S2 那一行是 - [ ]

Requirement: 切片包的机械区由脚本渲染，说明原样保留

plan-kit.py packets --change-dir D SHALL 为每个切片渲染 slices/<S>.md 的机械区，放在 <!-- plan-kit:begin --> 与 <!-- plan-kit:end --> 之间。机械区依次包含： - 标题行 # <S> · <title>； - owns 列表； - 依赖切片（id、标题、包路径）； - 每个 scenario 的能力名、scenario 名、映射的测试，以及取自 specs/<能力>/spec.md 的 GIVEN / WHEN / THEN / AND / BUT 原文； - verify。

已存在的包 MUST 只替换标记之间的内容，标记之外的文字保持不变。已存在但没有标记时，机械区插到最前面，原内容整体保留。

Feature: 渲染切片包 Rule: 机械部分由脚本写，判断部分由主会话写

Scenario: kit-packets-renders-mechanical-region

  • GIVEN两片计划：S2 依赖 S1，S2 有一个 scenario，其 spec 原文含 GIVEN / WHEN / THEN 各一行
  • WHEN运行 plan-kit.py packets --change-dir
  • THENslices/S2.md 的标记之间含标题行、S2 的每个 owns、S1 的标题、该 scenario 的 GIVEN 原文与映射的测试，以及 S2 的 verify

Scenario: kit-packets-preserves-notes

  • GIVENslices/S1.md 已有机械区，标记之后有主会话写的一段说明
  • AND之后 slices.json 里 S1 的 owns 多了一个文件
  • WHEN再次运行 plan-kit.py packets --change-dir
  • THEN机械区出现新文件，标记之后的说明逐字不变

propose-fork-assertions ADDED

Requirement: propose 改用工具链，补断言按测试文件用 fork 并行

/opsx-propose 命令与 openspec-propose skill（同改）SHALL 按以下顺序使用工具链： 1. 建 change 目录之后，在后台运行 slice-gate.py warm --change-dir …； 2. 用 plan-kit.py instructions --change 一次读取全部 instruction； 3. 写完 slices.json 后，依次运行 plan-kit.py packets、plan-scaffold.py scaffold； 4. 补断言：按测试文件分组。多于 1 组时，在同一条消息里为每组派一个 fork；fork 报错或不可用时，由主会话串行补完；只有 1 组时由主会话自己写； 5. 然后依次运行 plan-scaffold.py gwt（须 exit 0）、plan-kit.py tasks、slice-gate.py lint、model-routing.py pin。

两份文档的工具调用顺序 MUST 一致。

Scenario: propose-docs-use-plan-kit-in-order

Scenario: propose-docs-fork-with-serial-fallback

scenario-scaffold ADDED

Requirement: 按 scenario 映射生成 strict-xfail 骨架

.claude/hooks/plan-scaffold.py scaffold --change-dir D SHALL 对 scenario_tests 的每一项 path::func 按以下规则处理： - path 不是 .py → 列入 skipped，不改文件； - 函数已存在 → 列入 existing，不改文件； - 否则追加一个函数，列入 created，形式如下： - 带 @pytest.mark.xfail(strict=True, reason="<切片 id> 未实现")； - 函数体是 # Given: / # When: / # Then: 三行注释，内容取自对应 scenario 的 Gherkin 原文，AND / BUT 并入它前面那个关键字所在的行； - 最后一行是 assert False, "PLAN-SCAFFOLD-PLACEHOLDER：换成真实断言"。

文件缺 import pytest 时 SHALL 补上。stdout 输出 {"created", "existing", "skipped"}。映射里的 scenario 在 specs 中找不到时 MUST 以 exit 2 退出，并点名该 scenario。

Feature: 测试骨架生成 Rule: 只补缺的函数，GWT 取 Gherkin 原文

Scenario: scaffold-creates-strict-xfail-skeletons

  • GIVEN一个计划：S1 有一个 scenario，映射到尚不存在的 tests/test_new.py::test_alpha

  • WHEN运行 plan-scaffold.py scaffold --change-dir
  • THENtests/test_new.py 含 import pytest 与带 strict=True 的 xfail 函数 test_alpha
  • AND它的 Given 行含「已有订单」与「订单已付款」，When 行含「用户申请退款」，Then 行含「订单变为退款中」，函数体含 PLAN-SCAFFOLD-PLACEHOLDER
  • ANDstdout 的 created 是 ["tests/test_new.py::test_alpha"]

Scenario: scaffold-leaves-existing-functions

  • GIVENtests/test_old.py 已有写好断言的 test_beta，计划同时映射 test_beta 与尚不存在的 test_gamma
  • WHEN运行 scaffold
  • THENtest_beta 的源码逐字不变，文件末尾多出 test_gamma
  • ANDstdout 的 existing 含 test_beta，created 含 test_gamma

Scenario: scaffold-skips-non-python

  • GIVEN一个 scenario 映射到 web/a.test.js::renders
  • WHEN运行 scaffold
  • THEN退出 0，stdout 的 skipped 含 web/a.test.js::renders，web/a.test.js 没有被创建

Requirement: 规划期自查 GWT 与占位残留

plan-scaffold.py gwt --change-dir D SHALL 只针对 scenario_tests 映射到的函数做两项检查，逐条打印问题，有任何一条即 exit 1，全部通过时 exit 0： - 用与切片门禁 G4 相同的判据，检查 GWT 注释； - 检查函数体里有没有残留 PLAN-SCAFFOLD-PLACEHOLDER。

Feature: 规划期 G4 自查 Rule: 骨架补完才算规划完成

Scenario: gwt-reports-missing-steps-and-placeholders

  • GIVEN一个映射函数缺 # When: 注释，另一个映射函数仍含 PLAN-SCAFFOLD-PLACEHOLDER
  • WHEN运行 plan-scaffold.py gwt --change-dir
  • THENexit 1，输出分别点名这两个函数
  • AND把两处都修好后再运行，退出 0

Design · 05技术设计

Context

现状（main @ 03a2077，C1 已合入）：

  • propose 的 step 3 要求逐个工件调用 openspec instructions <id> --change <name> --json。openspec 1.3.1 一次只出一个工件，5 个工件就是 5 次工具往返；输出里有 instruction / template / rules 等字段。
  • 切片包、tasks.md、测试骨架全由模型逐字写，没有生成器。tasks.md 的格式见 schemas/intent-driven/templates/tasks.md：一片一行，- [ ] S<n> <标题> （deps: … · verify: \…\）。
  • 现有 G4 检查是 slice-gate.py 的 gwt_violations(root, test_files)，切片门禁时才运行；G7 用 scenario_status 判 xfail 标记与实跑结果。
  • baseline 的复用候选依次是：本 change 旧基线 → 锚点 → 基线池（_baseline_candidates）。
  • 本 change 旧基线（_try_reuse(own=True)）的条件：ok 或 test_ok 为真；cmd_key 相同；Δ 只有 test_*.py。计划工件不算进 Δ（PLAN_FILES / PLAN_DIRS）；本 change 目录里在 gate.test 闭包内、且内容没变的脚本也不算。满足时只补跑 Δ 里的测试文件，允许有预存红，只要改动的测试文件不在预存红里。
  • 有 test-tiers.json 时没有任何候选，恒走全量（nocand = args.full or tiers is not None，原设计 D5：G10 / G11 要单元层探针）。
  • cmd_key 把命令文本与命令直接引用的仓库内文件（含 shell 闭包）的内容做指纹；本 change 的目录名会被归一成 <change>。所以只要文件内容按词边界替换后相同，在另一个 change 目录下的同名包装脚本也算同一个指纹。
  • cmd_baseline 在取锁之前读旧基线；旧基线是运行标记（running: true）时按 None 处理。preflight 用 pid 判断运行标记是「仍在跑」还是「已中断」。
  • afa 的 gate.test 是每个 change 自带的包装脚本（bash openspec/changes/<name>/verify/full_suite.sh），没有分层文件。本仓库是 python3 -m pytest -q tests，也没有分层文件。

在役 ADR： - DRAFT-baseline-reuse-by-content-fingerprint：本 change 旧基线复用； - DRAFT-baseline-reuse-via-dependency-anchor：锚点； - DRAFT-execution-routing-by-config：规划期只用主会话或 fork。

本 change 只是给这些规则多提供一个候选、多一种派发方式，不改其中任何一条。

Goals / Non-Goals

Goals - 机械搬运的部分改由脚本生成：instruction 汇总、tasks.md、切片包的机械区、测试骨架。 - 补断言这一步按测试文件用 fork 并行，fork 不可用时由主会话串行补，语义与现状一致。 - baseline 的全量提前到规划开始时在后台跑，正式 baseline 能复用就只补跑骨架。 - 骨架没补完不能起飞（机械红线）。

Non-Goals - 不改 baseline 的复用规则；分层仓库不预热。 - 不改 /opsx-continue、schema 的 tasks instruction 与 spec.html。 - 不让 fork 写 proposal / design / specs / ADR / slices.json（Q8-A）。 - 不预估提速分钟数，合入后用探针实测。

Decisions

plan-kit.py（instructions / tasks / packets）与 plan-scaffold.py（scaffold / gwt）都是新文件。两个文件能在同一个 wave 里并行实现，也不会把 6000 多行的 slice-gate.py 再撑大。
warm 要复用 cmd_baseline 的整套机制

快照、指纹、锁、锚点、账本、运行期间改动检测，所以只能放进 slice-gate.py。

gwt 按路径加载 slice-gate.py，复用 gwt_violations，不复制判据。
先运行 openspec status --change <name> --json，取 artifacts；对其中每个 status != "done" 的工件，再运行 openspec instructions <id> --change <name> --json。
按工件依次打印一节

## <id> → <outputPath>，下面依次是 instruction、template、rules（rules 为空就省略）。

--all 时 done 的工件也打印。
命令在当前目录运行（与 openspec CLI 一致），任一次失败 → exit 2，stderr 写出失败的命令与它的 stderr。
格式与 templates/tasks.md 逐字一致
文件头是注释行 <!-- 本文件由 slices.json 生成，不要手写编辑；改动请改 slices.json 后重新生成。 -->；
然后是 ## 切片；
每片一行 - [ ] <id> <title> （deps: <逗号分隔或 -> · verify: \<verify>\）。
旧 tasks.md 里已勾选（[x]）的切片 id 保持勾选。
标题行 # <S> · <title>；

每个 dep 一行「<dep> · 标题 · 包路径」，没有依赖时写「无」；

## scenario

每个 scenario 一个小节，含能力名、scenario 名、映射的测试 path::func，以及取自 specs/<能力>/spec.md 的 GIVEN / WHEN / THEN / AND / BUT 原文；

## verify。
path 不是 .py → 记进 skipped，不动文件；
函数已存在（与 G7 同样的 def <func>( 匹配）→ 不动；
否则追加

slice-gate.py lint

运行标记与结果都带 "warm": true；
结果的 plan_sha 为 null；
锚点、基线池、账本照常写（它就是一次合法的全量）；
运行期间的改动检测照旧

主会话在预热期间改了已有文件或测试文件 → 结果 ok: false、test_ok: false，不会被复用。

计划的 gate.test 与 warm 打印的命令相同；

多于 1 组

同一条消息里为每组派一个 fork（Agent 工具，subagent_type: "fork"）。prompt 写明「只改这些文件：把 PLAN-SCAFFOLD-PLACEHOLDER 那行换成真实断言，保留 GWT 注释与 xfail 标记；不碰其他文件；完成后运行 plan-scaffold.py gwt --change-dir …，回报改了哪些函数」。

fork 报错或不可用 → 由主会话串行补完剩下的组。
只有 1 组 → 主会话自己写。

Risks / Trade-offs

[风险] 多个 fork 同时写测试，写法各自为政 → 按文件分组避免互相覆盖；gwt 与 lint 机械验收；不合格的组由主会话接手。
[风险] fork 在非交互会话里是否默认开启，文档没写 → 每处都有主会话串行回退（铁律 10）。
[取舍] 预热与规划争 CPU → 预热与正式 baseline 一样持全机测试锁；锁被别人持有时预热排队，不会叠两套全量。
[风险] 预热期间改了被测代码 → 运行期间改动检测把结果判为不可复用，正式 baseline 回退到原路径，不会误用。
[取舍] 有新 ADR 的 change 命不中复用 → 与现状一致，不放宽规则；是否把 openspec/adr/ 声明为 inert 由各仓库决定，留作后续。
[未验证] 提速幅度 → 合入后用审批页第 02 节同一套探针重测 3 次 propose。

Migration Plan

  • 合入后：下游 install.sh --upgrade 拿到新的 hooks 与文档即可生效，不需要迁移数据。
  • 回滚：revert 即可。预热写的 gate-baseline.json 一定会被正式 baseline 覆盖；packets 的标记是注释，旧流程会忽略它。
