Why · 01为何而做

执行层的模型是写死的：执行体与评审员 = 会话主模型 · high，integrator = sonnet · low（铁律 11，opsx-apply.md 路由表）。这带来三个问题：

- 用户要执行体用 opus · medium、评审保留 high，现在做不到：执行体与评审员共用 <main>，effort 写死在文档和 agent frontmatter 里； - 仓库之间没法各配各的：路由只存在于模板文本，没有一份按仓库生效的配置； - 起飞前没有一处让人类看见并确认本次飞行用什么模型；收口只对账模型，不对账 effort。

另外有两处派发漏写了 model，实际落到 CLAUDE_CODE_SUBAGENT_MODEL 的默认值 sonnet：bulk-apply 派发的子 agent，以及 legacy 逐 task 模式的实现 / 修复派发。

意图访谈以四轮审批页代替：docs/flight-routing-config.html v1–v4（主仓库工作区，未入库）。用户 2026-11-19 回复「全按推荐」，C1 相关：Q1-A 无配置文件走内建默认、Q3-A 一个派发用途一个键共 10 个、Q4-A 规划期确认后钉进 slices.json、Q5-A 旧 change 缺 routing 停飞并提示 pin、Q6-A 本仓库按第 05 节取值、Q7-A 评审类不设下限、Q13-A 修复不属于规划期。另有两条用户原话约束：「不写 main，必须是直接模型名称」；「最终的解决方案和规划还是要继承主会话」。

What · 02变更范围

  • 新增路由配置 openspec/model-routing.json：只写模型名（opus | sonnet | haiku | fable）与 effort（low | medium | high | xhigh | max），main / inherit 判红。按派发用途登记 10 个键：
  • flight：executor / executor-large / fixer / reviewer / integrator；
  • ship：reviewer / followup；
  • archive.sync · claudemd.evidence · bulk.apply。
  • 新增 .claude/hooks/model-routing.py，四个子命令：
  • show：打印生效的路由表及每个键的来源；
  • pin --change-dir：把 flight 与 ship 两组键钉进 slices.json.routing；
  • resolve --change-dir：起飞时读钉住的路由，输出工作流用的 models / efforts；缺 routing 时停飞并提示 pin；设了 CLAUDE_CODE_EFFORT_LEVEL 或 CLAUDE_CODE_SUBAGENT_MODEL_FORCE 时停飞；
  • get <组.键>：其他派发点取单个键，change 钉过的优先。
  • opsx-apply.js 按 5 个角色派发：大片档执行体走 executor-large，批量修复与 wave 跨片修复走 fixer；两者缺省时同 executor，兼容旧调用；effort 值不在允许集合内时拒绝起飞。
  • 收口对账加 effort：session-decompose.py 新增 --expect-efforts，读子 agent 转录 assistant 行的 effort 字段对账；fix 开头的标签判为 fixer；--turns 把大片档切片判为 executor-large；fixer 与 executor-large 没派发时不算零覆盖。
  • spec.html 显示钉住的路由表；缺 routing 时显示「起飞会被拒绝」的提示。
  • 文档（命令与 skill 同改）：
  • /opsx-apply：step 4 改为 model-routing.py resolve，打印路由表；回退路径的 Agent 派发显式传 model 与 effort；收口加 --expect-efforts；去掉 <main> / --model=。
  • /opsx-propose：tasks 阶段运行 pin。
  • /pr-ship、/opsx-archive、/claudemd-standardize、/opsx-bulk-apply、legacy 逐 task 模式：派发都改用 model-routing.py get <键>，补上 bulk 与 legacy 漏写的 model。
  • 铁律 11 改写（根 CLAUDE.md 与 template/CLAUDE.md.snippet）：执行层按派发用途从配置显式路由，只写模型名；规划期产出只来自主会话或 fork，不进路由配置，规划类命令与 skill 不写 model / effort。README、docs/WORKFLOW_zh.md、install.sh 说明同步。
  • 新 ADR：取代 DRAFT-model-routing-defaults-for-template 决策第 2 条中的「需推理的 subagent 保留 inherit」。
  • BREAKING（下游行为）：没有配置文件的下游仓库，执行体与评审员从「随会话主模型」改为固定 opus · high（Q1-A）。旧 change 起飞前要先 pin，并重新批准一次（Q5-A）。
新增：template/.claude/hooks/model-routing.py、template/openspec/model-routing.json（本仓库配置）、tests/test_model_routing.py、tests/test_workflow_routing_roles.py、tests/test_route_audit_efforts.py、tests/test_spec_html_routing.py、tests/test_routing_docs.py。修改：代码：template/.claude/workflows/opsx-apply.js、template/.claude/hooks/session-decompose.py、template/.claude/hooks/spec_html.py；命令与 skill：apply、propose、pr-ship、archive、claudemd-standardize、bulk-apply、legacy；文档与安装：根 CLAUDE.md、template/CLAUDE.md.snippet、README、docs/WORKFLOW_zh.md、install.sh；钉住旧措辞的测试：tests/test_template_docs.py、tests/test_docs_iron_rules.py、tests/test_agents_workflow.py。不变：session-model.py 保留，session-decompose 仍用它的 alias_of 把模型 id 归一成别名；agent frontmatter 不改，派发时显式传的 model / effort 优先于 frontmatter；takeoff-gate 的新鲜度规则不改：slices.json 本来就是计划工件，pin 改了它，批准自然过期。下游：install 不种配置文件，下游缺省走内建默认；升级后在途的 change 起飞前要先 pin。

Specs · 04行为规范 (Gherkin)

execution-model-routing ADDED

Requirement: 路由配置只登记执行层的 10 个键，只写模型名

.claude/hooks/model-routing.py SHALL 读取 openspec 根下的 model-routing.json。注册表固定为 10 个键：flight.executor / flight.executor-large / flight.fixer / flight.reviewer / flight.integrator / ship.reviewer / ship.followup / archive.sync / claudemd.evidence / bulk.apply。

每个写出的键 MUST 同时有 model 与 effort： - model ∈ opus | sonnet | haiku | fable； - effort ∈ low | medium | high | xhigh | max。

出现以下任一情况时，show / pin / get MUST 以 exit 2 退出，并在 stderr 点名出错的键： - 未登记的组或键； - 组名是 propose / explore / new / continue / mini，提示「规划期不进路由配置」； - 模型写成 main / inherit 等非模型名，提示「只写模型名」； - effort 不在允许集合内。

没有配置文件或缺某个键时，SHALL 取内建默认：flight.integrator / archive.sync / claudemd.evidence 为 sonnet · low，bulk.apply 为 opus · medium，其余为 opus · high。

Feature: 执行层路由配置 Rule: 只收执行层的键与模型名，缺省走内建默认

Scenario: routing-builtin-defaults-without-config

  • GIVEN一个 openspec 根下没有 model-routing.json 的仓库
  • WHEN运行 model-routing.py show --json
  • THEN退出 0，输出 10 个键
  • ANDflight.executor 是 opus · high，flight.integrator 是 sonnet · low，bulk.apply 是 opus · medium，每个键的来源都是 builtin

Scenario: routing-config-overrides-per-key

  • GIVENmodel-routing.json 只写了 flight.executor 为 opus · medium
  • WHEN运行 show --json
  • THENflight.executor 是 opus · medium，来源为 repo
  • ANDflight.reviewer 仍是 opus · high，来源为 builtin

Scenario: routing-rejects-planning-keys

  • GIVENmodel-routing.json 含组 propose（如 propose.skeleton）
  • WHEN运行 show
  • THENexit 2，stderr 含「规划期不进路由配置」并点名 propose.skeleton

Scenario: routing-rejects-non-model-names

  • GIVENmodel-routing.json 里 flight.reviewer 的 model 写成 main
  • WHEN运行 show
  • THENexit 2，stderr 含「只写模型名」并点名 flight.reviewer

Requirement: 规划期把 flight 与 ship 两组钉进 slices.json，起飞只认钉住的值

model-routing.py pin --change-dir D SHALL 把生效配置里 flight 组的 5 个键与 ship 组的 2 个键，写进 D/slices.json 顶层的 routing，形如 {source, flight, ship}；其余顶层键 MUST 原样保留。

resolve --change-dir D SHALL 只读钉住的 routing.flight，stdout 输出 {"models": {5 个角色}, "efforts": {5 个角色}}。以下情况 MUST 以 exit 3 退出： - routing 缺失或不合法：stderr 给出 model-routing.py pin --change-dir D 的命令，并说明 pin 之后要重新批准； - 环境变量 CLAUDE_CODE_EFFORT_LEVEL 或 CLAUDE_CODE_SUBAGENT_MODEL_FORCE 非空：stderr 点名该变量。

Feature: 钉住与解析 Rule: 起飞用的路由来自计划工件，环境覆盖时停飞

Scenario: routing-pin-writes-flight-and-ship

  • GIVEN一个 change 的 slices.json（含 gate 与 slices），仓库配置把 flight.executor 设为 opus · medium
  • WHEN运行 pin --change-dir
  • THENslices.json 多出 routing，其中 flight 有 5 个键、flight.executor 为 opus · medium，ship 有 2 个键
  • AND原有的 gate 与 slices 不变

Scenario: routing-resolve-requires-pin

  • GIVEN一个没有 routing 的 slices.json
  • WHEN运行 resolve --change-dir
  • THENexit 3，stderr 含 model-routing.py pin --change-dir 与「重新批准」

Scenario: routing-resolve-outputs-workflow-args

  • GIVEN一个已 pin 的 change
  • WHEN运行 resolve --change-dir
  • THEN退出 0，stdout 的 JSON 有 models 与 efforts，各含 executor / executor-large / fixer / reviewer / integrator 5 个角色，取值等于钉住的值

Scenario: routing-resolve-refuses-env-override

  • GIVEN一个已 pin 的 change，环境变量 CLAUDE_CODE_EFFORT_LEVEL=high
  • WHEN运行 resolve --change-dir
  • THENexit 3，stderr 点名 CLAUDE_CODE_EFFORT_LEVEL

Requirement: 其他派发点按键取值，钉住的优先

model-routing.py get <组.键> [--change-dir D] SHALL 在 stdout 输出 {"model", "effort", "source"}。取值顺序： 1. D 的 slices.json.routing 里钉住的值（source 为 pinned）； 2. 仓库配置（repo）； 3. 内建默认（builtin）。

未登记的键 MUST 以 exit 2 退出。

Feature: 单键查询 Rule: 钉住 > 仓库配置 > 内建默认

Scenario: routing-get-prefers-pinned

  • GIVEN仓库配置把 ship.reviewer 设为 sonnet · medium，而 change 钉住的 ship.reviewer 是 opus · high
  • WHEN分别运行 get ship.reviewer --change-dir D 与不带 --change-dir 的 get ship.reviewer
  • THEN前者输出 opus · high、来源为 pinned
  • AND后者输出 sonnet · medium、来源为 repo

flight-role-routing ADDED

Requirement: 飞行工作流按 5 个角色派发

template/.claude/workflows/opsx-apply.js SHALL 按以下角色派发： - 轮次档为 large 的切片执行体：models['executor-large'] / efforts['executor-large']； - 批量修复（label fix）与 wave 跨片修复（label fix:w<i>）：models.fixer / efforts.fixer； - 其余切片执行体、评审、integrator：仍按原来的 executor / reviewer / integrator。

executor-large 与 fixer 缺省时 SHALL 取 executor 的值（model 与 effort 分别回落），只传 3 个角色的旧调用行为不变。任一角色的 effort 不在 low | medium | high | xhigh | max 之内时，MUST 抛错拒绝起飞。返回值里的 models 与 efforts SHALL 含全部 5 个角色。

Feature: 飞行角色路由 Rule: 大片档与修复各有路由，缺省同执行体

Scenario: workflow-routes-large-slice-to-executor-large

  • GIVEN两片计划：S1 的 turns 为 large，S2 为标准档
  • ANDargs 的 models['executor-large'] 为 fable、efforts['executor-large'] 为 high，models.executor 为 opus、efforts.executor 为 medium
  • WHEN运行工作流
  • THENS1 的执行体派发带 model fable、effort high
  • ANDS2 的执行体派发带 model opus、effort medium

Scenario: workflow-routes-fixes-to-fixer

  • GIVEN一片计划，评审返回一条 HIGH finding；args 的 models.fixer 为 fable、efforts.fixer 为 high
  • WHEN运行工作流
  • THENlabel 为 fix 的派发带 model fable、effort high

Scenario: workflow-defaults-new-roles-to-executor

  • GIVENargs 只有 executor / reviewer / integrator 三个角色，efforts.executor 为 medium
  • WHEN运行工作流（含一片大片档与一次批量修复）
  • THEN大片档执行体与 fix 的派发都带 models.executor 与 effort medium
  • AND返回值的 models 与 efforts 含 5 个角色

Scenario: workflow-rejects-unknown-effort

  • GIVENargs 的 efforts.reviewer 为 huge
  • WHEN运行工作流
  • THEN工作流抛错，错误信息点名 reviewer 与允许的 effort 集合，且没有派发任何 agent

route-audit-efforts ADDED

Requirement: 收口对账覆盖 effort 与新角色

session-decompose.py SHALL 新增两个参数： - --expect-efforts '<JSON>'：角色 → effort，与 --expect-models 一样需要 --workflow； - --turns '<JSON>'：slice-gate.py turns 的输出。

effort 取值：每个 agent 的实际 effort 取它转录里第一条带 effort 字段的 assistant 行。 - 所有 agent 都没有该字段时，SHALL 打印「转录无 effort 字段，effort 对账跳过」，effort 对账不判红； - 有字段且与期望不符时，MUST 列出不符项（标签 · 期望 · 实际），并以 exit 3 退出。

角色判定按以下顺序： 1. label 去掉 :retry 后等于 fix 或以 fix: 开头 → fixer； 2. label 在 --turns 里为 large → executor-large； 3. 其余沿用 agentType → label 前缀 → 阶段；agentType slice-executor-large 判为 executor-large。

回落：期望表里没有 fixer / executor-large 时，这两个角色按 executor 对账。

零覆盖：fixer 与 executor-large 没有被采样到时 MUST NOT 判为零覆盖。核心三角色的零覆盖规则不变。

Feature: 收口路由对账 Rule: model 与 effort 都机械对账，可选角色未派发不算缺

Scenario: audit-flags-effort-mismatch

  • GIVEN一个 workflow 目录：S1（Implement）实际 opus、effort high，review:S1 实际 opus、effort high，integrate:w1 实际 sonnet、effort low
  • WHEN带 --expect-models（executor / reviewer = opus，integrator = sonnet）与 --expect-efforts（executor 为 medium，其余与实际相同）运行
  • THENexit 3，输出含 S1、期望 medium 与实际 high

Scenario: audit-maps-fix-labels-to-fixer

  • GIVEN一个 workflow 目录：S1 实际 opus · medium，fix:w1 实际 fable · high，review 与 integrate 与期望一致
  • WHEN期望表 executor = opus · medium、fixer = fable · high，运行对账
  • THEN退出 0，路由对账一致，且列出 fixer=fable

Scenario: audit-maps-large-slices-by-turns

  • GIVEN一个 workflow 目录：S2（Implement，meta 的 agentType 为 workflow-subagent）实际 fable，其余与期望一致
  • WHEN期望表 executor = opus、executor-large = fable，并传 --turns '{"S2": "large"}'
  • THEN退出 0，S2 按 executor-large 对账通过

Scenario: audit-skips-undispatched-optional-roles

  • GIVEN一个只有执行体、评审、integrator 的 workflow 目录，取值都与期望一致
  • WHEN期望表含全部 5 个角色
  • THEN退出 0，输出不含 fixer 或 executor-large 的「未采样到角色」

Scenario: audit-warns-when-effort-unrecorded

  • GIVEN一个 workflow 目录，所有 assistant 行都没有 effort 字段，模型与期望一致
  • WHEN带 --expect-efforts 运行
  • THEN退出 0，输出含「转录无 effort 字段，effort 对账跳过」

Design · 05技术设计

Context

现状（main @ dc6c26a）：

  • opsx-apply.js 只认 3 个角色：args.models 必须有 executor / reviewer / integrator，否则抛错；efforts 缺省为 {executor: high, reviewer: high, integrator: low}。大片档执行体、批量修复、wave 跨片修复都用 models.executor。
  • /opsx-apply 起飞时用 session-model.py 判定会话主模型 <main>，然后传入 models: {executor: <main>, reviewer: <main>, integrator: "sonnet"}。
  • 收口时运行 session-decompose.py --expect-models，只对账模型，不对账 effort。角色判定的顺序是 agentType → label 前缀 → 阶段。
  • 回退路径的文档写着「Agent 工具没有 effort 参数，effort 由 agent frontmatter 决定」。本会话的 Agent 工具定义已有 effort 参数（low | medium | high | xhigh | max），这句话已过时。
  • 其他派发点：
  • /pr-ship 评审与复核：model: "<main>"；
  • archive 的 sync：model: "sonnet"；
  • claudemd-standardize 的证据调查：model: sonnet；
  • bulk-apply 的子 agent：没写 model；
  • legacy 的实现 / 修复：没写 model；legacy 的评审：<main>。

已核实的事实：

  • 转录里有实际 effort：Workflow 子 agent 的转录，assistant 行顶层有 effort 字段（另有 perTurnEffort，以及 api-request 里的 output_config.effort）。本仓库上一次飞行（wf_8435375a）实测：integrator 为 low，review 与切片为 high，与当时传入的 efforts 一致。
  • meta 里看不出大片档：useAgentTypes: false 时，meta 的 agentType 是 workflow-subagent。大片档执行体的 label 就是切片 id，单看 meta 区分不出。
  • 环境变量会覆盖 effort（code.claude.com/docs/en/model-config，2026-11-19 读取）：「A subagent's effort applies while the subagent runs … If CLAUDE_CODE_EFFORT_LEVEL is set, that level applies instead」；maxEffortLevel 或组织上限同样会压低子 agent 的 effort。

在役 ADR：

  • DRAFT-model-routing-defaults-for-template：第 2 条「需推理的 subagent 保留 inherit」与本 change 冲突，由新 ADR 取代这一条；第 1、3、4 条仍在役（CLAUDE_CODE_SUBAGENT_MODEL=sonnet 兜底、主会话低推理命令只做软引导、纪律下发到 snippet）。
  • DRAFT-apply-as-flight 等 ADR 不涉及模型取值，不冲突。

Goals / Non-Goals

Goals

  • 执行层每个派发用途的 model 与 effort 都来自按仓库生效的配置，只写模型名。
  • 人类在审批 spec.html 时看到本次飞行的路由；它被钉进计划工件，改动会让批准过期。
  • 收口时机械对账 model 与 effort。
  • 规划期不变式变成机械检查：配置里出现规划期的组名即判红；测试扫描规划类命令与 skill。

Non-Goals

  • 主会话的模型与 effort（规划期一律继承主会话；机械命令的主会话层由 C3 处理）。
  • agent frontmatter 的取值（派发时显式参数优先，frontmatter 只在参数缺失时兜底）。
  • 评审类的下限（Q7-A：不设）。
  • 自动迁移在途 change：由人运行 pin，并重新批准。

Decisions

组或键不在注册表里 → 「未登记的键」；
组名是 propose / explore / new / continue / mini → 「规划期不进路由配置」；
model 不是 opus | sonnet | haiku | fable，包括 main / inherit → 「只写模型名」；
effort 不是 low | medium | high | xhigh | max；
值缺 model 或缺 effort。
propose 在 tasks 阶段运行 model-routing.py pin --change-dir，把 flight 与 ship 两组共 7 个键写进 slices.json 顶层的 routing
spec.html 渲染这张表；人类发出 /opsx-apply 即确认。
slices.json 本来就在 takeoff-gate 的 PLAN_FILES 里，pin 之后再改，批准自动过期，不需要改 takeoff-gate。
archive / claudemd / bulk 三组不钉，它们不属于某一次飞行，用的时候用 get 现取。
放进 slice-gate.py lint（否决）

51 个测试文件的计划夹具都没有 routing，放进 lint 会让这些夹具全部判红，owns 会扩散到几十个无关测试。

放在 resolve（采用）

它在 apply 的 step 2 紧跟 lint 和 preflight 运行，非 0 就停下报告。效果与 lint 判红相同：在派发任何 agent 之前停飞，并给出 pin 的命令。

opsx-apply.js 用 execRole(s) 选角色

大片档 → executor-large，其余 → executor；fix / fix:w<i> 的派发用 fixer。

models['executor-large'] 与 models.fixer 缺省取 models.executor；effort 同理。这样旧的 3 角色 args（测试夹具、未升级的命令文档）行为不变。
每个 effort 必须在 low | medium | high | xhigh | max 之内，否则抛错拒绝起飞。
开头的路由日志打印 5 个角色；返回值里的 models / efforts 也是 5 个角色。
effort 来源

每个 agent 取第一条带 effort 字段的 assistant 行。所有 agent 都没有这个字段时（旧版 Claude Code），打印「转录无 effort 字段，effort 对账跳过」并跳过 effort 对账，不判红。部分 agent 有而对不上 → exit 3。

角色判定顺序
期望表没有新角色时

fixer / executor-large 回落到 executor，旧的 3 角色 --expect-models 行为不变。

零覆盖

fixer 与 executor-large 没有派发是常态，不算零覆盖。核心三角色的零覆盖规则不变。

apply 回退路径

Agent 派发显式传 model 与 effort，取值来自 resolve。如果 Agent 工具没有 effort 参数（旧版本），由 agent frontmatter 决定，与路由不一定一致；回退路径不经 Workflow，收口不对账（与现状一致）。

钉住的值 → 仓库配置 → 内建默认。stdout 带 source。设了覆盖环境变量时，get 只往 stderr 打警告，不阻断：这些派发点不属于飞行，停下的代价大于收益。

apply、pr-ship、legacy 不再判定 <main>；--model= 旗标删除；.flight 的 raw 字段删除，source 改记路由来源。

Risks / Trade-offs

执行体降到 medium，一次做对的比例可能下降（风险） → 先跑 2–3 次飞行，用 timeline 与 flight-doctor 看重派与修复次数，再决定是否调回；调回只需改一行配置并重新 pin。
下游从「随主会话」变为固定 opus（风险） → proposal 标为 BREAKING；README 写明可以用 model-routing.json 改回。
D4 偏离审批页的「lint 判红」措辞（取舍） → 停飞效果等价，在 spec.html 写明，由人类审批。
Workflow 是否真按 effort: "medium" 运行未实测（未验证） → 本 change 合入后的第一次飞行由 --expect-efforts 机械验证；对不上即 HIGH，PR 判 draft。
maxEffortLevel 或组织上限会压低 effort（风险） → resolve 不读 settings，由收口的 effort 对账发现。
回退路径不对账 effort（取舍） → 与现状一致，回退本身就是降级路径。

Migration Plan

1. 合入后，本仓库的在途 change 起飞前运行 python3 .claude/hooks/model-routing.py pin --change-dir <dir>，然后重新批准。 2. 下游 install.sh --upgrade 拿到新的 hooks 和文档；不写配置时走内建默认；在途 change 同上先 pin。 3. 回滚：revert 本 change 即可。slices.json.routing 是新增的顶层键，旧脚本会忽略它。
