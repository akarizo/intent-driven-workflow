Why · 01为何而做

/opsx-propose 每次都跑一遍完整基线；改了计划要不要重跑、重跑多少，全靠模型判断。原仓（Mod 版 akarizo/intent-driven-claude-code）2026-10-15 合入 #65（855b834，change baseline-incremental-reuse），按内容指纹增量复用基线。本仓 slice-gate.py 里没有对应实现（2026-10-15 检索 fingerprint / 指纹 / 基线池 / 复用，无结果）。

本仓实测（2026-10-15，main 3f98011，用 change workflow-edition 的 4 片计划按 cmd_baseline 的顺序串行计时）：

| 段 | 耗时 | |---|---| | 全量 python3 -m pytest -q tests | 50.6 秒 | | lint（compileall） | 0.1 秒 | | 4 片 verify 串行 | 49.0 秒（S2 36.6 · S4 11.8 · S1 0.5 · S3 0.1） | | 合计 | 约 100 秒 |

4 片 verify 跑的测试文件都在全量的 tests 里，全量刚跑过一遍。#65 只省「改计划后重跑」那一遍，第一次全量基线里的这 49 秒省不掉。

#65 合入时独立评审留了 13 条 deferred（原仓 template/openspec/changes/baseline-incremental-reuse/review-findings.json），其中 MEDIUM 4 条：

- 红判成绿：跨 change 复用会整份沿用对方的预存红名单。名单里如果混进指纹之外的差异造成的红，本 change 把这些用例改坏时，final 会当预存红放过。原仓 ADR 写的「不会把红判成绿」不成立。 - 副产物死循环：全量测试写出的未跟踪副产物，第二次全量时已经在开始快照里，被改写就判红，重跑仍红。人删掉它，preflight 又判过期。 - 软链崩溃与假差异：git hash-object --stdin-paths 跟随软链。断链直接 traceback 并留下运行标记；有效软链算出的是目标内容的 blob，与 git 树里的链接文本 blob 对不上。 - 重复补跑：同一组差异测试文件对最多 11 个候选各补跑一次，补跑红时还要按超时上限重复 11 遍，才回到全量。

LOW 6 条： - 不复用的理由被丢弃； - 池里有孤儿临时文件； - 指纹为空的条目也会写进池； - 运行期改动判定与差异的排除口径不一致； - 文档漏写一条复用条件； - 池的保留与容错没有测试。

本仓没有账本，#65 用「账本有无 takeoff」决定 preflight 是否按内容判过期，这里要改用本仓自己的起飞事实（ADR DRAFT-workflow-edition-repo 第 3 条：依赖插件的部分在本仓重新设计）。

用户决策（2026-10-15，会话内逐项问答，代替 grill-me 访谈）： - 移植 #65； - 跨 change 只复用全绿（test.exit == 0）的全量； - 一并修掉 #65 的 deferred 问题； - 代码树没变时 lint / typecheck 也沿用； - 全量可度量时 verify 从全量结果推导； - 不做「lint / typecheck 与全量并行」。

Requirement: 基线记录内容指纹

slice-gate.py baseline 结束时 SHALL 在 gate-baseline.json 写入： - change：本 change 名；mode：full 或 incremental； - snapshot：基线结束时工作区相对 HEAD 的未提交改动，路径映射到 git blob id，删除为 null。规则： - 不含字节码与 .pytest_cache； - 不含本 change 的计划工件，即 proposal.md、design.md、tasks.md、slices.json、spec.html、gate-baseline.json、.openspec.yaml、记账文件、specs/ 与 slices/； - 符号链接记链接文本的 blob id，与 git 树里的表示一致，不跟随链接； - cmd_key：全量命令指纹。取 gate.test 文本，把本 change 目录相对路径换成占位符 <change>，再加上命令里每个指向仓库内已存在文件的词所对应的文件内容。只算命令里直接写出的仓库内文件，不追踪它 source / import 的文件； - byproducts：运行副产物路径（见下）； - 每片 verify 的 exit 与 cmd。

基线运行期间的改动，开始与结束各取一次快照对比；<changes 根> 下其他 change 目录里的路径不比： - 运行开始时就存在的文件（已跟踪或未跟踪）或测试文件内容有变 → 基线 SHALL 判红，原因含「重跑 baseline」； - 例外：本 change 上一次基线 byproducts 里的非测试路径被改写 → SHALL 只记警告，仍算副产物； - 运行期间新出现的非测试文件 SHALL 只记一条警告，并记入 snapshot 与 byproducts； - 上一次基线 byproducts 里仍未提交的路径 SHALL 继续留在 byproducts。

Requirement: 只改测试文件时复用全量

有可复用的全量结果时，slice-gate.py baseline SHALL 不跑 gate.test，改走增量。

差异 Δ 的定义： - 按内容比较 → 候选所测的代码树（候选 commit 加上候选的 snapshot）与当前代码树（HEAD 加上工作区）； - 不计 → 字节码、.pytest_cache、<changes 根>/**，以及候选 byproducts 中在候选 commit 与当前 HEAD 都未跟踪的路径； - 例外 → 候选来自本 change 时，本 change 目录里计划工件以外的文件照计。

复用条件（全部满足）： - 候选基线 ok，且测试结果可度量：exit 0，或记有 test.failed； - 候选来自别的 change 时，test.exit 为 0（没有预存红）； - cmd_key 与当前相同； - 候选 commit 是当前 HEAD 的祖先； - 没有给 --full； - Δ 里的路径全是文件名匹配 test_*.py 的文件； - 候选 test.failed 里没有哪条的 classname 以点分段后含 Δ 中某个测试文件的文件名主干； - Δ 里现存的测试文件用 gate.pytest 前缀补跑一次，结果同时满足：没有 FAILED / ERROR、没有超时、退出码为 0 或 5。

补跑规则： - 路径与内容都相同的一组 Δ 文件，在一次 baseline 里 SHALL 至多补跑一次； - 补跑红、超时或退出码不是 0 / 5 时，SHALL 不再尝试其余候选，直接跑全量。

复用时： - test 沿用候选的 exit、sec、failed； - 记 mode: incremental 与 incremental: {from: {change, commit, at}, files, sec}； - 不改已有的 gate.full_suite_sec；本 change 还没有时，写入候选的 test.sec。

任一条件不满足 → 跑全量，mode: full。有候选但都没复用时，SHALL 在 reuse_skipped 记下判过的候选（change、commit、不复用的理由），至多 5 条。

Requirement: 跨 change 复用全量

每次全量基线同时满足以下条件时，slice-gate.py baseline SHALL 把这次结果写进基线池： - 基线绿； - test.exit 为 0； - cmd_key 非空。

基线池的规则： - 位置：git common dir 下的 flight-baseline-pool/，同一仓库的各 worktree 共享； - 每条记录含 change、commit、at、ok、cmd_key、snapshot、byproducts、test； - 写入：先写临时文件再改名； - 保留：按 at 保留最新 30 条，清理时顺带删除一小时以前留下的 .tmp-* 临时文件； - 容错：写池失败 SHALL 只记警告，不影响本次基线；读池时坏 JSON 跳过。

选候选的顺序： 1. 本 change 现有的 gate-baseline.json； 2. 池里 cmd_key 相同的条目，按 at 由新到旧，最多看 10 条。

逐个按上一条 Requirement 的复用条件判断，取第一个满足的。

Requirement: verify 按需重跑

增量基线 SHALL 只重跑下面这些片的 verify： - 上一次没有记录（包括候选来自别的 change）、或记录的 cmd 与当前不同的片； - 命令里有路径覆盖到 Δ 中某个文件的片； - 命令里一个路径都认不出的片。

其余片沿用本 change 上一次基线的 exit，并标 reused: true。

路径的认法：命令按 shell 规则切词，每个词去掉 :: 之后的部分；它指向已存在的路径、或等于 Δ 里的路径时算路径。Δ 文件等于它、或位于它这个目录下，即为覆盖。

全量基线照旧处理全部 verify。

为什么要严格 Δ

lint 常扫全仓（如 ruff check .），其他 change 的门禁脚本变了会改变 lint 输出。普通 Δ 为了跨 change 复用全量排除了它们，这里不能排除。

为什么要 key

命令里直接写出的计划工件（如 markdownlint openspec/changes/x/proposal.md）不在 Δ 里，靠 key 的文件内容看出变化。

边界

lint 扫描本 change 计划工件目录（不是逐个写出文件）时看不出变化。写进文档：这种情况用 --full。

否决
用普通 Δ → 其他 change 的改动会让沿用过时；
跨 change 沿用 → 池里不存 lint 结果，lint 范围也常含各 change 自己的文件。
前提

本次跑了全量，且结果可度量（rc 0，或 failed 非 None）。

数据

run_test_gate 在 rc 0 与可度量的 rc 1 时都解析 junit，返回 cases（全部 testcase 的 classname 集合）。解析失败时 cases = None，不推导。

可推导条件
前缀

gate.test 按 shlex 切词后，以 pytest 启动前缀开头。启动前缀的认法与 _g7_runner 从 gate.test 推导的规则相同：之前不能有 cd、&&、||、;、|、环境变量赋值。这里忽略 gate.pytest：verify 要和全量是同一种启动方式，包装脚本不算。

gate.test 其余词

前缀之后只含白名单选项（-q -qq -v -vv -x -s --no-header --tb=*，以及成对的 -p no:cacheprovider）与路径。

verify 的前缀

verify 切词后，开头与该前缀逐词相同，其余词只含同一白名单选项与路径。

verify 的路径

至少一个；每个都不含 ::，是仓库内已存在的普通文件，文件名匹配 test_*.py 或 *_test.py。

全量里有、且都通过

每个路径对应模块 m = 路径去 .py 后 / 换 .。cases 里有 classname == m 或以 m. 开头的；failed 里没有 classname 部分（:: 之前）== m 或以 m. 开头的。

推导结果

{exit: 0, cmd, derived: "full"}。不满足任一条 → 照旧运行。

为什么只推导「绿」

范围内有失败时，单独跑的结果才是 verify 的真值，照跑。

为什么 classname 对不上就照跑

rootdir 推断不同会让 classname 前缀不同，此时 cases 里找不到 m，自然退回运行。安全方向是多跑，不会判错。

风险（用户已接受）

顺序依赖（全量里绿、单独跑红）的用例推导不出来，要到飞行中 G1 才暴露。

否决
用 gate.pytest 前缀匹配 → 包装脚本设置的环境（如 source _env.sh）verify 不具备，推导会掩盖「verify 单独不可运行」，这正是 #32 要在起飞前抓的那一类；
verify 之间并行 → 共享资源（端口、数据库、固定路径）在一般项目里会冲突。
开跑前（s0、cmd_key）出错 → `die("内容快照失败

…")，不写运行标记，不碰现有 gate-baseline.json`。

候选求 Δ 出错 → 该候选作废，记进 reuse_skipped。
结束快照 s1 出错 → 写一份红基线，原因「基线结束时内容快照失败

…；重跑 baseline」。运行标记一定被结果覆盖。

Risks / Trade-offs

[测试读取 changes 根下的文件] → D2 把 <changes 根> 排除在 Δ 之外，这类读取看不出来。范围有限，final 收口照跑全量。
[同一 change 内的预存红沿用] → 两次之间只差测试文件、且补跑不红才沿用；名单来自本 change 自己的全量，不混入别人的指纹外差异。
[被 source 的脚本 / 仓外漂移] → 跨 change 看不出差异；跨 change 只复用全绿，所以最坏是 d 上本来红的用例被当成绿
不会被放过

final 跑全量时，它不在 d 的预存红名单里，会判红；

会多出一条

收口时多一条红，不会把红判成绿。

改了 _env.sh 里的解释器、PYTHONPATH 时，用 --full。
[verify 推导的顺序依赖] → 用户已接受；G1 运行 verify 时暴露，按门禁红处理。
[lint 扫描计划工件目录] → 文档写明用 --full。
[副产物不计入 Δ] → 测试若把副产物当输入读取，内容变化看不出来。副产物名单在 warnings 与 byproducts 里可见，需要时提交或 gitignore 它。
[池并发] → 每条一个文件，rename 原子；清理遇 ENOENT 忽略。
[命中率] → 跨 change 只在同一 main commit、或之间只改测试文件、且全绿时命中；同一 change 的增量不受影响。
