Why · 01为何而做

PR #30（mechanical-layer-followups）的干净评审留下 2 条 MEDIUM 与 4 条 LOW：

- doctor 会把 model-routing.py 自己的崩溃误报成漂移，并给出错误的修法； - 两个 doctor 用例绑在仓库真实的命令文件上，有人改本仓库 cleanup.runner 的路由就会误红； - 另有若干 LOW：doctor 解码兜底、文档措辞、断言强度。

另外，用户（2026-11-20）要求 openspec/model-routing.json 默认就存在，便于直接调整，并且每个键自带说明。现状是：

- 下游仓库装完没有这个文件，11 个键里有几个、各管哪个派发点，只能去翻 README； - 本仓库的文件也只写了 2 个键。

What · 02变更范围

  • frontmatter 渲染：model-routing.py frontmatter 读写命令文件失败时（不是 UTF-8、读不了、写不了），以退出码 2 点名文件，不再带 traceback 以 1 退出。退出码 1 只表示漂移。
  • doctor [routing] 段：
  • 退出码 1 但 stdout 没有漂移条目时，报「不可用」加 stderr 末行，不给修法；
  • 子进程输出按 UTF-8 宽松解码，解码失败不再吞掉整份 doctor 报告。
  • doctor 用例隔离：两个 doctor 用例改为在临时目录里运行复制出来的 hooks 与命令文件，不再读仓库真实的 clean-after-merged.md。
  • /clean-after-merged 文档：
  • 运行方式一节注明 context: fork 命令本身未单独实测；
  • step 1 注释措辞与运行方式一节对齐；
  • 相应断言改为整句匹配。
  • 新增 model-routing.py init：
  • openspec 根没有 model-routing.json 时，写出全部 11 个键：内建默认值，每键带 desc，顶层带 $comment；
  • 文件已存在时只补缺失的键与缺失的 desc，不改已有的 model / effort；
  • 配置非法时以退出码 2 报错，不动文件。
  • 校验器：接受每键的 desc 字段与顶层 $comment。
  • 安装：install.sh 安装与 --upgrade 都运行 init，失败不改变 install 的退出码。
  • 本仓库配置：本仓库的 template/openspec/model-routing.json 用 init 补全为 11 键，flight.executor 两档保持 opus · medium。
代码：template/.claude/hooks/model-routing.py：frontmatter 报错、init 子命令、校验放宽 desc / $comment；template/.claude/hooks/flight-doctor.py：doctor_routing；install.sh：运行 init 与收尾提示措辞。文档：template/.claude/commands/clean-after-merged.md；README.md 模型路由一节。配置：template/openspec/model-routing.json 补全为 11 键。测试：tests/test_routing_followups.pytests/test_fork_commands_docs.pytests/test_install_routing.py新增 tests/test_routing_seed.py下游：install.sh --upgrade 后，目标仓库多出（或补全）openspec/model-routing.json；已有的值不变；以后模板改内建默认，已装仓库里写好的值不会跟着变（用户 2026-11-20 选定全写显式值）。

Specs · 04行为规范 (Gherkin)

cleanup-doc-precision ADDED

Requirement: 起点依据写明实测范围

/clean-after-merged 命令的运行方式一节 SHALL 写明「主会话 cd 过也一样」的实测依据只覆盖 Agent 工具派发的子 agent，context: fork 命令本身未单独实测。step 1 代码块里 pwd 的注释 SHALL 与运行方式一节使用同一说法「主会话当前所在目录」。

Feature: 合并后清理的文档 Rule: 依据说到实测为止，同一件事只用一种说法

Scenario: cleanup-doc-marks-fork-command-untested

  • GIVEN模板的 /clean-after-merged 命令文件
  • WHEN读取运行方式一节与 step 1 的代码块
  • THEN运行方式一节含整句「主会话 cd 过也一样」，并写明 context: fork 命令本身未单独实测
  • ANDstep 1 代码块里 pwd 那一行的注释含「主会话当前所在目录」

routing-config-seeded ADDED

Requirement: 路由配置默认存在且自带说明

model-routing.py init 在 openspec 根没有 model-routing.json 时 SHALL 写出全部已登记的键，每个键的 model / effort 等于内建默认，并带非空的 desc 说明该键对应的派发用途；顶层 SHALL 带 $comment 说明可选的模型名与 effort。写出的文件 SHALL 能被 show / get / pin 正常读取。

Feature: 执行层路由配置 Rule: 打开文件就能看到所有派发用途和它们的当前值

Scenario: init-writes-full-config

  • GIVENopenspec 根没有 model-routing.json
  • WHEN运行 model-routing.py init
  • THEN退出 0，model-routing.json 含全部 11 个键，每个键的 model / effort 等于没有配置文件时 show 给出的内建默认，且带非空的 desc
  • AND顶层有非空的 $comment，随后运行 show 退出 0，11 个键的来源都是 repo

Requirement: 补全配置不改已有的值

model-routing.py init 在 model-routing.json 已存在且合法时 SHALL 只补缺失的键（内建默认值加 desc）与已有键缺失的 desc。已有键的 model / effort 与已有的 desc SHALL 保持原样。配置非法时 SHALL 以退出码 2 点名错误，文件 SHALL 保持不变。

Feature: 执行层路由配置 Rule: 用户写过的值只由用户改

Scenario: init-fills-missing-keeps-values

  • GIVENmodel-routing.json 只写了 flight.executor = haiku · low，没有 desc
  • WHEN运行 model-routing.py init
  • THEN退出 0，flight.executor 仍是 haiku · low 并补上了 desc
  • AND其余 10 个键补上了内建默认值与 desc

Scenario: init-leaves-invalid-config-untouched

  • GIVENmodel-routing.json 把 flight.executor 的 model 写成 main
  • WHEN运行 model-routing.py init
  • THEN退出 2，stderr 点名 flight.executor
  • ANDmodel-routing.json 的字节不变

Requirement: 安装与升级种下路由配置

install.sh 安装与 --upgrade SHALL 运行 model-routing.py init：目标仓库没有 model-routing.json 时种下完整文件；已有时只补缺。init 失败 SHALL NOT 改变 install 的退出码。

Feature: 安装时的路由配置 Rule: 装完就有可直接改的配置，升级不冲掉用户的值

Scenario: install-seeds-routing-config

  • GIVEN一个还没装过本模板的目标仓库
  • WHEN运行 install.sh <目标>，再把目标的 flight.executor 改成 haiku · low 后运行 install.sh --upgrade <目标>
  • THEN两次都退出 0；第一次之后目标的 openspec/model-routing.json 含 11 个带 desc 的键
  • AND升级之后 flight.executor 仍是 haiku · low

routing-doctor-hardening ADDED

Requirement: frontmatter 渲染读写失败时报配置不可用

model-routing.py frontmatter（含 --check）在命令文件读不了、不是 UTF-8 文本或写不了时 SHALL 以退出码 2 退出，并在 stderr 点名路由键与文件路径。它 SHALL NOT 带 traceback 以退出码 1 退出：退出码 1 只表示 --check 发现漂移。命令文件 SHALL 保持不变。

Feature: fork 命令 frontmatter 渲染 Rule: 退出码 1 只留给漂移

Scenario: frontmatter-rejects-non-utf8-command

  • GIVEN命令目录里的 clean-after-merged.md 含 context: fork，frontmatter 里夹着一段不是 UTF-8 的字节；openspec 根没有 model-routing.json
  • WHEN运行 model-routing.py frontmatter --check
  • THEN退出 2，stderr 点名 cleanup.runner 与 clean-after-merged.md，并说明它不是 UTF-8 文本
  • ANDstderr 里没有 traceback，命令文件的字节不变

Requirement: doctor 把崩溃报成不可用

flight-doctor.py doctor 的 [routing] 段 SHALL 只在 frontmatter --check 退出 1 且 stdout 有漂移条目时报漂移并给出修法。退出 1 但 stdout 没有漂移条目时，SHALL 报「不可用」并附 stderr 的最后一个非空行，SHALL NOT 给出修法。doctor SHALL 恒 exit 0。

Feature: 路由漂移体检 Rule: 修法只给真正的漂移

Scenario: doctor-reports-unreadable-command-as-unavailable

  • GIVEN一份独立安装的 hooks，命令目录里的 clean-after-merged.md 含 context: fork 但夹着不是 UTF-8 的字节
  • WHEN运行该 hooks 的 flight-doctor.py doctor --openspec-root <根>
  • THEN退出 0，[routing] 段报「不可用」并说明命令文件不是 UTF-8 文本
  • AND[routing] 段没有「修法」行

Scenario: doctor-reports-crash-as-unavailable

  • GIVEN一份独立安装的 hooks，其中的 model-routing.py 一运行就抛出未捕获的 RuntimeError: boom
  • WHEN运行该 hooks 的 flight-doctor.py doctor --openspec-root <根>
  • THEN退出 0，[routing] 段报「不可用：RuntimeError: boom」
  • AND[routing] 段没有「修法」行

Requirement: doctor 不因子进程输出解码失败丢掉报告

flight-doctor.py doctor 读取 frontmatter --check 的输出时 SHALL 按 UTF-8 宽松解码。输出含不是 UTF-8 的字节时，doctor SHALL 照常输出包括 [routing] 在内的全部段落，SHALL NOT 退化为一行失败提示。

Feature: 路由漂移体检 Rule: 一段的异常不拖垮整份报告

Scenario: doctor-survives-undecodable-output

  • GIVEN一份独立安装的 hooks，其中的 model-routing.py 往 stdout 写一段不是 UTF-8 的字节和「frontmatter 与路由一致」后退出 0
  • WHEN运行该 hooks 的 flight-doctor.py doctor --openspec-root <根>
  • THEN退出 0，输出同时含 [runner] 段与 [routing] 段
  • AND输出里没有「flight-doctor doctor 失败」

Design · 05技术设计

Context

本 change 命中「跨模块」触发器：model-routing.py（渲染 / 初始化 / 校验）、flight-doctor.py（体检）、install.sh（种子）、/clean-after-merged 命令文档与本仓库路由配置各改一处，彼此通过 model-routing.py 的退出码与 model-routing.json 的形状相连。

现状（main 851183a）：

  • frontmatter 渲染的退出码：cmd_frontmatter 用 path.read_bytes().decode("utf-8") 读命令文件。
  • 文件不是 UTF-8 时抛 UnicodeDecodeError，Python 带 traceback 以 1 退出，与「--check 发现漂移」的 exit 1 撞号。
  • PR #30 评审的定向抽查证实了这一点。
  • doctor [routing] 段：doctor_routing 认定退出码 1 就是漂移。它原样打印 stdout 各行，再追加「修法：…frontmatter」。
  • 崩溃时 stdout 为空，用户只看到一行错误的修法。
  • subprocess.run(..., text=True) 按 locale 严格解码。子进程输出解码失败时异常越过 doctor_routing，被 main() 的兜底吞掉，整份 doctor 报告只剩一行「flight-doctor doctor 失败」。
  • doctor 用例（tests/test_routing_followups.py）：
  • drift 与 in-sync 两个用例运行仓库真实的 flight-doctor.py，后者调用的 model-routing.py 读的是仓库真实的 template/.claude/commands/clean-after-merged.md；
  • drift 用例硬断言该文件是 sonnet · low，in-sync 用例要求它等于内建默认。
  • 路由配置文件：
  • install.sh 的 openspec 种子是显式清单（.gitignore config.yaml changes/.gitkeep adr/.gitkeep superpower/.gitkeep），没有 model-routing.json，下游装完没有这个文件；
  • 本仓库的 template/openspec/model-routing.json 只写 flight.executor / flight.executor-large 两键；
  • 校验器 validate() 拒绝未登记的顶层键（$comment 会判红）。check_value() 不检查额外字段（desc 目前就能过）。
  • 文档：
  • clean-after-merged.md 第 16 行写「普通子 agent 与 fork 子 agent 的首条 pwd 都是该子目录」，但探针（2026-11-20）用的是 Agent 工具派发，没有直接跑 context: fork 命令；
  • 第 26 行注释仍是「主会话所在目录」。

Goals / Non-Goals

Goals: - model-routing.py frontmatter 的退出码 1 只表示漂移；读写失败点名文件、以 2 退出。 - doctor 的 [routing] 段：崩溃或解码异常时报「不可用」，不给错误修法，也不吞掉其他段。 - doctor 用例不读仓库真实的命令文件与配置。 - openspec/model-routing.json 默认存在：11 键全写显式值，每键带 desc，用户直接改值即可（用户 2026-11-20 选定）。 - 安装与升级只补缺，不改用户写过的值。

Non-Goals: - 不改「文件缺失 / 缺键走内建默认」的语义，effective() 照旧。老仓库没跑 init 也照常工作。 - 不改 show / pin / resolve 的输出形状。show 的 source 列在补全后会显示 repo，这是如实反映。 - 不随升级刷新已有键的值或已有的 desc：用户可能改过。 - 不处理 #29 的 LOW（用户 2026-11-20 只要 #30 遗留）。 - 不改 ADR。

Decisions

cmd_frontmatter 对每个命令文件
read_bytes() 抛 OSError → `die(EXIT_INVALID, ["<键>

读不了命令文件 <路径>：<错误>"])`；

decode("utf-8") 抛 UnicodeDecodeError → `die(EXIT_INVALID, ["<键>

<路径> 不是 UTF-8 文本"])`；

write_bytes() 抛 OSError → `die(EXIT_INVALID, ["<键>

写不了命令文件 <路径>：<错误>"])`。

文件头退出码说明的 exit 2 一行补上「命令文件读不了 / 不是 UTF-8 / 写不了」。
备选

只在 doctor 侧兜。被否：exit 1 仍然二义，install.sh 等其他调用方照样分不清（用户 2026-11-20 选定两端都修）。

subprocess.run 改为 encoding="utf-8", errors="replace"

解码不再抛异常，其他段照常输出。

备选

在 doctor() 里给 doctor_routing 包 except (Exception, SystemExit)。被否：异常会让 [routing] 段整段丢失；宽松解码更直接，且保留输出内容。

测试 helper 把仓库的 template/.claude/hooks/ 复制到 tmp/.claude/hooks/（忽略 __pycache__），在 tmp/.claude/commands/ 写一份命令文件，openspec 根取 tmp/openspec/，再运行复制出来的 flight-doctor.py doctor --openspec-root tmp/openspec，cwd 为 tmp。
model-routing.py 的命令目录缺省值是 <自身目录>/../commands，复制后自然指向 tmp/.claude/commands，产品代码不用为测试加参数。
in-sync 用例

命令文件的 model / effort 取复制出来的 model-routing.py get cleanup.runner --openspec <空根> 的输出，不在测试里写死内建默认。

崩溃 / 解码类场景

把复制出来的 model-routing.py 换成桩脚本（抛异常 / 输出非 UTF-8 字节）。

备选

从真实文件当前值推导期望。被否：仍读真实文件；in-sync 的前提会从「内建默认」变成「当前值」（用户 2026-11-20 选定复制 hooks）。

说明文本的唯一来源

model-routing.py 里新增 DESC = {"组.键": "<一句话>"}，键集合与 BUILTIN 相同（测试校验）。文本依据 README 模型路由表的「派发点」列：

顶层 $comment

一个字符串，写明：

每个「组.键」是一个派发用途；
model 只写模型名（MODELS），effort 取 EFFORTS；
删掉某键 = 走内建默认；
desc 只作说明；
改 cleanup.runner 后要运行 frontmatter。
init [--openspec DIR]，按文件状态分三种
写出格式

json.dumps(cfg, ensure_ascii=False, indent=2) + "\n"。补全已有文件时会重排格式，这是可接受的代价：只在确实有缺项时才写。

校验放宽
validate() 跳过顶层 $comment（值须是字符串）；
check_value() 接受可选的 desc（须是字符串）。
其余未登记字段照旧不检查（不收紧，避免打破已有配置）。
备选

只写说明与只读的 default，写了值才覆盖。被否：要分清哪些是提示、哪些是覆盖，用户选定「所见即所用」。

代价

模板以后改内建默认，已装仓库里写好的值不跟着变（用户 2026-11-20 接受）。

install.sh 在 fork 命令渲染（frontmatter）之前运行 python3 "$TARGET/.claude/hooks/model-routing.py" init --openspec "$TARGET/openspec"，安装与 --upgrade 都跑
成功 → log_add / log_info 打印它的一行输出；
失败 → log_err 点名，并提示修好 openspec/model-routing.json 后在目标仓库根重跑 init，不改变 install 的退出码；
没有 python3 → 与现有分支一致，只打印提示。
收尾说明（第 521 行一带）的「缺省内建默认，仓库可写 openspec/model-routing.json 覆盖」改为「安装时种下 openspec/model-routing.json（11 键全写、每键带 desc），直接改值」。
本仓库

template/openspec/model-routing.json 由 S3 运行一次 init 补全。flight.executor 两档的 opus · medium 不变，所以已钉进 slices.json.routing 的值与生效值一致。

README 模型路由一节同步

「文件缺失或缺键走内建默认」后补一句「安装与升级时 model-routing.py init 种下完整文件（11 键、每键带 desc），只补缺、不改已有值」。

边界
model-routing.py 是 model-routing.json（init）与 fork 命令 frontmatter（frontmatter）唯一的写方；
doctor 只读；
install 只调用、不判定。
假设

init 运行在 frontmatter 之前，所以首次安装渲染出的 frontmatter 等于种下的值（与内建默认相同）。

Risks / Trade-offs

[风险] 补全时重排了用户手写的格式（缩进、键顺序） → 缓解

只在确实有缺项时写；值与 desc 逐字保留。

[风险] show 的 source 列在补全后全是 repo，看不出哪些等于内建默认 → 缓解

如实反映「值来自文件」；用户要回到内建默认就删掉该键。不在本 change 加标记（Non-Goals）。

[权衡] 内建默认不再自动传到已装仓库

用户选定「所见即所用」的代价，写进 README。

[风险] doctor 用例复制整个 hooks 目录变慢 → 缓解

hooks 目录是几十个小文件，复制在毫秒级；测试仍是单元层。

Migration Plan

  • 下游执行 install.sh --upgrade：
  • 拿到新脚本；
  • init 种下或补全 openspec/model-routing.json；
  • 已有值不变，frontmatter 随后按它渲染。
  • 回滚：revert 本 change 的代码 commit。已种下的 model-routing.json 内容等于内建默认（或用户原值），留着不影响旧脚本：旧校验器对 $comment 会判红，回滚时需一并删掉 $comment 键或整个文件。
