Why · 01为何而做

final 每次都全量跑 gate.test 和每项 gate.checks，没有任何增量或复用：改一行代码就要重跑全量。业务仓库 afa 的 change test-tiering-unit-integration（2026-10-28）里，一次完整 final 实测 29–42 分钟。这个 change 一共起了 7 次 final，约 5 次尝试全量，其中 4 次被中断或失败；人类两次明确说「修复了 6 条，为何要跑全量」「只跑增量局部，不跑全量 final」。本仓库也一样：PR #5 修 1 条 HIGH 后又全量跑了一次 final（约 130 秒）。

查下来根因有三条： 1. cmd_final 没有增量机制。 2. 同一棵代码树会反复跑 final：fix 子代理一次，final-gate 一次，主会话还会在后台再跑一次。 3. 全量跑完却判「不可度量」。afa 唯一跑完的那次 final 报「计数不一致（汇总行 14，junit 0）」，根因是测试里起的嵌套 pytest 继承了库经 PYTEST_ADDOPTS 注入的 --junitxml，在会话结束后覆盖了父会话的 junit。afa 侧已在 e59e0e0c8 修掉自己的插件，库侧至今没有防护。

同日人类追加：/pr-ship 的独立评审出 CRITICAL/HIGH 时直接自动修复并 push，不再询问。

What · 02变更范围

  • 嵌套会话防护：库注入的 pytest 运行（全量、区域、增量重跑）都带一个防护插件。用例里起的嵌套 pytest 会话不写 junit，也不写探针 / 依赖图记录，父会话的度量不会再被覆盖或混入幽灵用例。插件加载失败时退回不带插件的运行，只给警告。
  • 依赖图与锚点：每次全量运行（baseline 全量、final 全量）顺带记录每个测试文件实际用到的仓库文件，即依赖图。依赖图来自三处：静态 import 闭包、运行时 open / exec、Python 子进程。子进程经 sitecustomize 记录；env 被剥掉、录不到的子进程，把所在测试文件标为「盲」。同时记逐用例结论。这些连同代码树指纹写进 git common dir 下的锚点池，跨 worktree、跨 change 共用。
  • 增量 final（默认）：在锚点池里取一个可用锚点，算出锚点树与当前树的差 Δ。只重跑以下测试文件，其余用例沿用锚点结论，再按基线差分判红：
  • 依赖图与 Δ 相交的；
  • Δ 里的测试文件；
  • 锚点里失败的；
  • 被标为盲的。
  • 自动全量的触发条件：
  • --full；
  • 没有可用锚点（池空、命令指纹变了、锚点不是 HEAD 的祖先、依赖图没测到）；
  • 基线缺逐用例记录；
  • Δ 含全局文件（conftest.py、pytest.ini、pyproject.toml、setup.cfg、tox.ini、setup.py、依赖清单、test-tiers.json）；
  • Δ 含锚点时已存在、依赖图从没见过、且不是 Python 也不是文档的文件。
  • 同树沿用：final 记树指纹与命令指纹。代码树、计划、命令都没变且上次 final 是绿的，就直接沿用上次结论，不跑任何测试。ship 判 final 是否过期时，改为比较两边的树：内容相同就算新鲜，不再要求 final commit 是 HEAD 的祖先。
  • checks 注入 Δ：final 运行 gate.checks 时新增三个环境变量：GATE_FINAL_MODE（incremental / full）、GATE_DELTA_FILE（Δ 清单）、GATE_ANCHOR_COMMIT。由检查命令自己决定跑多大范围；不认这些变量的检查行为不变。
  • gate.impacted（可选）：仓库已有自己的选测命令时配上它，增量时由它代替内建选测，库只把 Δ 交给它，按基线差分判红。
  • 与测试分层叠加：配置了 test-tiers.json 时：
  • 单元层只重跑选中的文件，并挂探针判 G10 / G11；
  • 集成区域只在选中的文件落在该区域时才运行，否则沿用。
  • /pr-ship 评审自动修复：CRITICAL/HIGH 直接自动修复并 push（至多 2 轮），不再问「自动修还是只贴评论」。全程不问询；跑满 2 轮仍阻断就停下交人。
  • 文档：/opsx-verify、/opsx-apply 与同名 skill、/pr-ship、schema 的 tasks instruction（gate.impacted）、README。
代码：template/.claude/hooks/slice-gate.py新增防护 / 依赖图插件与 sitecustomize 的注入；run_test_gate 与 _pytest_outcomes 可选记录依赖图；新增锚点池与 final 记录；cmd_final 走增量 / 全量 / 沿用三条路径；_final_fresh 改按树比较；_check_env 在 final 阶段新增三个变量；lint 校验 gate.impacted。计划格式：slices.json 新增可选字段 gate.impacted。gate-baseline.json 的 test 段新增 failed_nodes（仓库相对 nodeid）。final JSON 新增 incremental 段。新存储：<git common dir>/flight-anchors/（锚点池）与 <git common dir>/flight-final/<change>.json（同树沿用的 final 记录），都不入库。测试：tests/test_final_guard.py、tests/test_final_deps.py、tests/test_final_incremental.py、tests/test_final_reuse.py、tests/test_final_checks_env.py、tests/test_final_impacted.py、tests/test_final_tiers.py、tests/test_incremental_final_docs.py。文档：template/.claude/commands/pr-ship.md、opsx-verify.md、opsx-apply.md、同名 skill、template/openspec/schemas/intent-driven/schema.yaml、README.md。ADR：新增 DRAFT-final-incremental-by-dependency-anchor.md，修订基线复用 ADR 里「final 跑全量兜底」的安全论证前提（原 ADR 不改）。兼容：旧的 gate-baseline.json 没有 failed_nodes：带预存红时第一次 final 走全量。锚点池为空时第一次 final 走全量，跑完即有锚点。没有 gate.impacted / gate.checks 的仓库不受新字段影响。非 pytest 的 gate.test 没有依赖图，final 照旧全量，并给警告。叠放：本 change 从 worktree-test-tiers（PR #5）分出，依赖其中的探针与分层代码。PR 先指向该分支，#5 合入后改指 main。afa 落地：库合入后再升级 afa 的安装版。那是 afa 仓库里的动作，不在本 change 内。

Specs · 04行为规范 (Gherkin)

incremental-final ADDED

Requirement: 嵌套 pytest 会话不污染门禁的度量

库注入的每次 pytest 运行（run_test_gate 跑的全量与区域、增量 final 的重跑）SHALL 同时加载一个防护插件。防护插件这样区分外层与嵌套：

- 外层会话：没有外层标记、也不是 xdist worker 的会话。它在 pytest_configure 里设外层标记，自己起的 xdist worker 带上「属于外层」的标记。 - 嵌套会话：其余一切会话。它们 SHALL 关掉 junit 输出，不写探针记录，也不写依赖图记录。

于是，用例里起的、继承了环境的嵌套 pytest，既不会覆盖外层的 junit，也不会把自己的 nodeid 混进外层的探针或依赖图。

防护插件加载失败时（包装脚本覆写了 PYTHONPATH 等），门禁 SHALL 不带插件重跑一次并用这次的结果。这时依赖图判为没测到，同时给出警告。

Scenario: nested-pytest-does-not-overwrite-junit

  • GIVEN被测套件有一个必然失败的用例 test_bad
  • AND另一个用例用子进程起一个嵌套 pytest，嵌套会话继承全部环境变量，并在外层会话结束前跑完 0 个失败用例
  • WHEN门禁以 run_test_gate 运行这个套件
  • THEN结果可度量，失败清单恰好是 test_bad，不报「计数不一致」

Scenario: nested-pytest-not-recorded-in-probe-or-deps

  • GIVEN被测套件有一个用例用子进程起嵌套 pytest，嵌套会话跑的用例 nodeid 在外层套件里不存在
  • WHEN门禁以依赖图与探针方式运行这个套件
  • THEN依赖图与探针记录里都没有嵌套会话的用例或测试文件

Scenario: guard-plugin-load-failure-falls-back

  • GIVENgate.test 是一个包装脚本，它把 PYTHONPATH 覆写成固定值后再运行 pytest
  • WHEN门禁运行它
  • THEN门禁用不带插件重跑的结果判定（与没有防护插件时一致）
  • AND依赖图判为没测到，并给出说明原因的警告

Requirement: 全量运行记录依赖图并写入锚点池

gate.test 是 pytest 时，每次全量运行（baseline 跑全量、final 跑全量）SHALL 顺带记录依赖图，以测试文件为单位（仓库相对路径）。一个测试文件的依赖是下列仓库内文件的并集：

- 它的静态 import 闭包，只算仓库内的 .py 模块； - 收集期间与它的每个用例窗口内被 open 的文件；从 __pycache__ 读字节码的，映射回对应的源文件； - 它的用例起的子进程，命令行里出现的仓库内路径； - 这些子进程若是 Python 解释器，并且继承了门禁注入的 sitecustomize：该进程加载过的模块文件与 open 过的文件。

一个用例起 Python 子进程时，如果显式给的 env 不含门禁注入的 PYTHONPATH，或者带 -I / -S / -E，录不到的那个测试文件 SHALL 记为「盲」。

运行结束后，门禁 SHALL 把一条锚点写进 <git common dir>/flight-anchors/（原子写，只留最新若干条）。锚点含：

- change、commit、at； - 未提交改动的快照； - gate.test 的命令指纹，以及分层文件指纹（有分层时）； - 全部测试文件清单； - 失败用例（仓库相对 nodeid）； - 依赖图与盲文件清单； - measured 标记，表示依赖图是否测到。

baseline 跑全量时，SHALL 同时在 gate-baseline.json 的 test 段记 failed_nodes：仓库相对 nodeid 形式的预存红。

  • WHENbaseline 跑全量

Requirement: final 默认增量运行

final 在 G7 绿、且没有命中任何自动全量条件时，SHALL 增量运行 gate.test。

取锚点：从锚点池里挑可用的锚点。可用的条件：命令指纹与分层指纹都与当前相同，measured 为真，锚点 commit 是 HEAD 的祖先。可用的不止一个时，取 Δ 最小的，同样小取最新。Δ 是锚点树与当前树（含未提交改动）的内容差，按 blob 比较，不含本 change 的计划工件与其他 change 目录。

选测：重跑下列测试文件，用 gate.pytest（缺省从 gate.test 推导）实跑，并同样挂防护与依赖图插件：

- 依赖与 Δ 相交的测试文件； - Δ 里现存的测试文件； - 锚点里有失败用例的测试文件； - 盲文件。

判红：没选中的用例沿用锚点结论。重跑出的失败里，不在基线 failed_nodes 里的，记 G2 test 红并逐条列出。重跑以超时、收集错误或异常退出码结束时，也记红并给出原因。

前移锚点：增量 final 结束后 SHALL 写一条新锚点。重跑过的测试文件用本次的结论与依赖，其余的沿用旧锚点。

输出：final 的 JSON SHALL 带 incremental 段，含 mode（incremental）、source（builtin / impacted）、锚点的 change 与 commit、Δ 文件数、重跑的测试文件清单 rerun 与用例数、沿用的用例数。summary 末尾追加 ；增量：重跑 a 个文件（b 个用例）/ 沿用 c 个，锚点 <commit 前 10 位>。timeline 备注写 增量（锚点 <commit 前 10 位>，重跑 a 个文件 / 沿用 c 个用例） ok|red，结论词仍在末尾。

Requirement: 命中触发条件时 final 自动跑全量

final 在下列任一条件成立时，SHALL 改为全量运行 gate.test（与今天的全量判定相同，按基线差分）：

- 带了 --full； - 没有可用锚点：池空、命令或分层指纹不同、锚点不是 HEAD 的祖先、依赖图没测到； - 基线有预存红，但缺 failed_nodes； - Δ 含全局文件：任何目录下的 conftest.py，或文件名是 pytest.ini、pyproject.toml、setup.cfg、tox.ini、setup.py、requirements*.txt、Pipfile、Pipfile.lock、poetry.lock、uv.lock、.python-version，或分层文件 test-tiers.json； - Δ 含这样的文件：锚点时已存在、不在任何测试文件的依赖里、不是测试文件、扩展名不是 .py、也不是文档（.md / .mdx / .markdown / .txt / .rst / .html）。

全量跑完后同样写锚点。

incremental.mode 为 full，并在 incremental.full_why 写明命中的条件；timeline 备注写 全量（<原因>） ok|red。

Δ 里有锚点时已存在、不在任何依赖里的 .py 文件（非测试）时，不触发全量，只给警告「未被任何用例加载」。

Requirement: 同一棵代码树的 final 沿用上次结论

每次 final 结束后，SHALL 把以下内容写进 <git common dir>/flight-final/<change>.json：本次结果、commit、未提交改动快照，以及指纹集合。指纹集合包括：plan_sha、scenario_tests，以及 gate.test / gate.lint / gate.typecheck / gate.checks / gate.impacted / 分层文件的命令指纹。

下一次 final 开始时，如果同时满足以下条件，SHALL 直接沿用记录里的结论，不运行任何测试、lint、typecheck 或检查：

- 记录的结果是绿； - 记录的树与当前树内容相同（不含记账文件）； - 指纹集合全部相同。

沿用时：结果的 commit 是当前 HEAD，incremental.mode 为 reused，带被沿用记录的 commit；照常追加一行 gate-report，timeline 备注写 同树沿用 <commit 前 10 位> ok。

记录是红时不沿用，照常运行。

ship 判 final 是否过期时，SHALL 比较 final 行的 commit 与 HEAD 的树：两者之差只含记账文件（或没有差别）就算新鲜，不再要求 final commit 是 HEAD 的祖先。final commit 在本地不存在时仍判过期。

  • THENfinal 绿，incremental.mode 为 reused；计数文件的行数没有增加
  • ANDtimeline 备注含「同树沿用」

Scenario: red-final-is-not-reused

  • GIVEN上一次 final 红，之后代码没有变
  • WHEN再运行一次 final
  • THENfinal 照常运行，incremental.mode 不是 reused

Scenario: ship-fresh-when-tree-unchanged

  • GIVENfinal 在 commit X 上绿过
  • AND随后把 X 改写成内容相同、但不是 X 后代的 commit Y（例如 amend 只改提交说明），HEAD 为 Y
  • WHEN运行 ship
  • THENreasons 里没有「过期」

Requirement: final 给检查命令注入 Δ 与锚点

final 运行 gate.checks 的 final 命令时，SHALL 在既有运行契约的环境变量之外再注入三个：

- GATE_FINAL_MODE：incremental 或 full； - GATE_DELTA_FILE：一个文件的绝对路径，文件内容是 Δ 的仓库相对路径，每行一个；全量且没有锚点时为空串； - GATE_ANCHOR_COMMIT：锚点 commit；没有锚点时为空串。

baseline 阶段不注入这三个变量。同树沿用时，检查不运行。

Scenario: final-checks-receive-delta-and-anchor

  • GIVEN依赖图已记录的仓库，配置了一项检查，它的 final 命令把上述三个环境变量和 Δ 文件内容写到仓库外的文件里
  • AND随后只改了 src/a.py
  • WHEN运行 final
  • THEN写出的记录里：GATE_FINAL_MODE 为 incremental，Δ 文件恰好含 src/a.py，GATE_ANCHOR_COMMIT 等于 final 输出里的锚点 commit

Requirement: 仓库可用 gate.impacted 代替内建选测

Design · 05技术设计

Context

  • 现状：cmd_final（slice-gate.py）只要 G7 绿，就跑以下全部：
  • lint / typecheck，按基线差分；
  • gate.test 全量：有分层时是单元层加探针，再加已选区域；
  • 每项 gate.checks 的 final。

增量复用只在 cmd_baseline 里（_try_reuse / _delta / 基线池），而且只在「代码树之差只有测试文件」时复用。final 一律全量。 - 实测代价： - 本仓库全量约 130 秒。 - afa 的 gate.test 是 verify/full_suite.sh（exec pytest -n auto），全量 193–249 秒；三项 checks 各自跑 executor 全量，一次完整 final 观测到 29–42 分钟。 - 重复 final： - fix 子代理修完自跑 final（opsx-apply.js:212），final-gate 再跑一次（:233），主会话还常在后台再跑。 - ship 只认对齐 HEAD 的 final；_final_fresh 只放过记账文件的 commit，而且要求 final commit 是 HEAD 的祖先。 - 计数不一致的根因（已查清）：run_test_gate 经 PYTEST_ADDOPTS 注入 --junitxml。afa 的预算插件在会话结束时起一个复测子进程，它继承了这个变量，把父会话已写好的 junit 覆盖成自己的 0 失败。afa 在 e59e0e0c8（2026-10-28 16:20 +0800）修了自己的插件。库侧任何嵌套 pytest 都可能重演；探针插件同样经 PYTEST_ADDOPTS -p 注入，嵌套会话会把幽灵 nodeid 混进探针记录（PR #5 切片评审的 deferred MEDIUM）。 - 可复用的零件： - _snapshot：未提交改动快照； - _delta：两棵树按 blob 比较，排除计划工件与其他 change； - cmd_key：命令指纹； - _pool_write / _pool_candidates：git common dir 下的池，原子写、只留最新 N 条； - _pytest_outcomes：G7 的直接 pytest 实跑，带结果插件； - TIER_PROBE_PLUGIN：审计钩子探针； - _check_env：检查命令的运行契约。 - 约束： - 本仓库没有 CI，final 是唯一的全量关口。 - 基线复用 ADR（DRAFT-baseline-reuse-by-content-fingerprint）的盲区论证写着「final 跑全量时……会判红。所以最坏是收口多出一条红，不会把红判成绿」。这个前提要被修订。 - 本 change 叠在 test-tiers（PR #5）之上，那里的 design 写着「final 按分层运行」。

Goals / Non-Goals

Goals: - final 默认增量：只重跑改动真正影响到的测试文件，其余沿用锚点结论；改一行代码的 final 从分钟级降到秒级。 - 同一棵树的 final 只跑一次，重复调用秒回。 - 嵌套 pytest 不再覆盖 junit、不再污染探针与依赖图。 - checks 能拿到 Δ，自行收窄范围。 - 仓库可用自己的选测命令代替内建选测。 - /pr-ship 评审出 CRITICAL/HIGH 时自动修复，不问询。

Non-Goals: - 不改 G7：scenario 用例每次照跑，它是验收本身。 - 不改 baseline 的复用规则：baseline 只多记锚点与 failed_nodes。 - 不加 CI，不改 afa 仓库，不改工作流脚本 opsx-apply.js（Q3 选了「工作流不改」）。 - 不做函数级选测：粒度是测试文件。 - 非 pytest 仓库不做内建依赖图，只能用 gate.impacted，否则全量。

Decisions

装载

run_test_gate 与增量重跑时写进临时目录，和 --junitxml 一起经 PYTEST_ADDOPTS 的 -p flight_guard 加载。

判外层（pytest_configure，tryfirst=True）
环境里没有 FLIGHT_GUARD_OWNER、也没有 workerinput 的会话是外层。外层设 os.environ["FLIGHT_GUARD_OWNER"] = str(os.getpid())，子进程会继承。外层再用 pytest_configure_node（optionalhook=True，有 xdist 才生效）给自己的 worker 写 workerinput["flight_outer"] = 1。
worker 带 flight_outer 就算外层的一部分。
其余是嵌套会话

设 config.option.xmlpath = None，抢在 junitxml 插件读它之前，并设 os.environ["FLIGHT_GUARD_NESTED"] = "1"。

生效范围

探针插件与依赖图插件在写记录前检查 FLIGHT_GUARD_NESTED，嵌套时什么都不写。

为什么用 worker 标记而不是比 ppid

嵌套会话自己的 xdist worker 也有 workerinput，但嵌套的 controller 已判为嵌套，不会给它们写 flight_outer。显式标记比进程关系可靠。

加载失败

泛化现有的 TIER_PLUGIN_FAIL 检测，按「-p 的模块导入失败」的输出特征识别。识别到就去掉防护、探针、依赖图三个插件，只带 junit 重跑一次，用这次的结果，再给警告「防护插件加载失败（包装命令覆写了 PYTHONPATH？），依赖图未测」。

备选

只在 _read_probe 里取第一段 start、或和 junit cases 取交集（评审 deferred 给的退路）。只能治探针，治不了 junit 覆盖，否决。

粒度

测试文件，用仓库相对路径。由 item.path（3.8 下用 item.fspath）对 FLIGHT_ROOT 求相对路径。不用 nodeid 的文件部分，因为 afa 这类在子目录运行的仓库，rootdir 不是仓库根。

静态闭包

会话结束时，对每个测试文件解析 AST，取全部 Import / ImportFrom（含函数体内的），按模块搜索根解析到仓库内的 .py，求传递闭包。模块搜索根是 rootdir、测试文件所在目录链，以及 sys.path 里落在仓库内的项。

理由

同进程里模块有 sys.modules 缓存，第二个 import 同一模块的测试文件运行时观察不到加载。静态闭包补上这一块。

运行时

审计钩子在两类窗口里记 open 事件：收集窗口（pytest_pycollect_makemodule 的 hookwrapper）与用例窗口（setup / call / teardown）。

__pycache__/<stem>.<tag>.pyc 映射回 <dir>/<stem>.py。
subprocess.Popen / os.exec* / os.posix_spawn 的 argv 里，落在仓库内的路径记为依赖。
只收仓库内的文件，排除 .git/、门禁临时目录与字节码。
Python 子进程
每个用例窗口开始时，设 os.environ["FLIGHT_DEPS_FILE"] = <该测试文件>，子进程会继承。
门禁临时目录里放一个 sitecustomize.py，经 PYTHONPATH 生效。它装同样的审计钩子；atexit 时把 sys.modules 里仓库内模块的 __file__ 与 open 过的文件，按 FLIGHT_DEPS_FILE 追加进 FLIGHT_DEPS_OUT。
FLIGHT_GUARD_NESTED 为真时不写。嵌套 pytest 进程本身也是 Python 子进程，它在外层用例窗口里加载的东西照样归外层那个测试文件。这是正确的归属

嵌套会话用到的文件，确实是外层用例的依赖。

盲

subprocess.Popen 的审计参数含 env。如果 executable 或 argv[0] 的文件名像 Python 解释器（以 python 开头），而 env 不是 None 且其 PYTHONPATH 不含门禁临时目录，或者 argv 带 -I / -S / -E，就把当前测试文件记为盲。

逐用例结论

插件同时在 pytest_runtest_logreport 记 [仓库相对 nodeid, outcome]，与 G7 插件同一口径。基线据此得到 failed_nodes，锚点据此得到失败用例。junit 形式的 test.failed 照旧保留，供现有差分使用。

写入

复用 _pool_write 的原子写与只留最新 N 条（锚点单独一个目录与上限，ANCHOR_KEEP = 20）。写入时机：

增量 final 后

旧锚点的 deps / failed 去掉重跑过的文件，再并入本次结果。

选取

对 cmd_key 与 tiers_key 都匹配、measured 为真的最新 10 条，逐条算 _delta(root, cand, cur_snap, head, change_rel, same_change)（返回 None 即不可用），取 |Δ| 最小者，同样小取最新。

跨 change 共用

锚点不必来自本 change。Δ 按两棵树的真实内容差算，正确性不依赖锚点的来源。锚点的失败用例总会被重跑，所以别的 change 留下的红不会被当成绿沿用。

为什么放 git common dir、不入库

afa 有上万个用例，依赖图体积大，入库会让每次飞行记录 commit 变重；放在 git common dir 里，跨 worktree 共用，与基线池一致。代价：换一台机器就没有锚点，第一次 final 全量（D5 的「没有可用锚点」）。

算 Δ

Δ 用 _delta(...)，strict=False：排除本 change 的计划工件与其他 change 目录，忽略字节码。

全量触发

任一成立即全量，full_why 写明第一条命中的原因：

--full；
没有可用锚点；
基线 test.failed 非空但缺 failed_nodes；
Δ 含全局文件（清单见 spec）；
Δ 含「锚点时已存在（旧 blob 非空）、不在任何 deps 里、不是测试文件、扩展名不是 .py、不是文档」的文件。
为什么 .py 例外

Python 进程（含继承了 sitecustomize 的子进程）加载过的 .py 一定会被记下。依赖图里没有某个 .py，说明全量运行时也没有任何用例加载它，再跑一次全量照样测不到它，白花时间，所以只给警告。非 Python 文件可能被看不见的读者读取（例如 shell 脚本 source 另一个脚本），这时全量能让间接用到它的用例重跑，所以触发。

新文件

锚点时不存在的新文件不触发全量。能用到它的唯一途径是某个已存在的文件引用了它，而那个文件本身也在 Δ 里，依赖它的测试文件会被选中。

选中

依赖与 Δ 相交的测试文件 ∪ Δ 里现存的测试文件 ∪ 锚点 failed 所在的测试文件 ∪ blind。选中集合为空时不运行 pytest，记「增量：0 个文件需要重跑」。

剥 env 的 Python 子进程把所在文件标为盲，每次都重跑；
非 Python 文件未见即全量；
全局文件变动即全量；
--full 随时可用；
新 ADR 写明这是接受的盲区。
[锚点只在本机] 换机器或 git common dir 被清，第一次 final 全量。
[sitecustomize 遮蔽仓库自己的 sitecustomize] 门禁临时目录在 PYTHONPATH 最前。
[-p flight_guard 在剥了 PYTHONPATH、却保留 PYTEST_ADDOPTS 的嵌套 pytest 里导入失败] 嵌套会话会因此报错，导致该用例失败。探针今天已有同样的风险。
[静态闭包解析不准] 例如 sys.path 魔改、命名空间包。
[同树沿用掩盖偶发绿] 上次绿是偶发。
[叠在未合入的 PR #5 上] #5 改动会导致本分支 rebase。

Migration Plan

  • 无需迁移：
  • 旧 gate-baseline.json 没有 failed_nodes 时：无预存红照常增量，有预存红则第一次 final 全量（D4）；
  • 锚点池为空时第一次 final 全量；
  • 没有 gate.impacted / gate.checks 的仓库不受新字段影响。
  • 回退：final 带 --full 即今天的行为；删掉 <git common dir>/flight-anchors/ 即回到「每次全量」，下一次全量又会自动重建锚点。
  • afa：合入后升级 afa 的安装版，下一次 baseline 或 final 全量后即开始增量；afa 可把 tools/testgate --scope impacted 配成 gate.impacted。afa 仓库内的动作不在本 change。
