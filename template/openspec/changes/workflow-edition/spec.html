Why · 01为何而做

2026-10-15 定下：Workflow 引擎版（stable-v2.0 那一套）另起独立仓库 akarizo/intent-driven-workflow 维护；原仓 akarizo/intent-driven-claude-code 的 main 继续 Mod 版，不动。新仓 main 已推为 stable-v2.0（49533dd = 原仓 PR #34），stable-v1.0 / stable-v2.0 两个 tag 同时推上。取舍在决策页（原仓 worktree 的 docs/remove-mod-decisions.html）与会话里逐项定下，代替 grill-me 访谈。

stable-v2.0 之后原仓合入了 #35–#63 共 29 个 PR，大多是 flight 插件（Mod）专属。其中 12 个 PR 里有不依赖插件的通用改进，修的都是 v2.0 上实测到或从代码核实的问题：

- G7 假绿：只看源码文本，认不出别名 xfail，final 报「36/36」而实际 18 条仍是 xfail。证据：原仓 flight-integrity-fixes proposal（#35 飞行）。修复：#36。 - 抛错重派失效：执行体 agent() 抛错时重派被跳过，blocked 原因却写「已重派一次」；integrator、final-gate、评审员抛错会让整个工作流 reject。证据：同上与 flight-integrity-followups。修复：#36 #37。 - Stop hook 误拦：单片 wave 的执行体在主 worktree 里写切片标记，Stop hook 误拦主会话与评审员。证据：flight-integrity-fixes。修复：#36。 - G7 用错测试环境：用会话的 python3 跑 scenario 测试，下游依赖装在 venv / uv 时全部判「未被收集」，且没有超时。证据：flight-integrity-followups。修复：#37。 - 门禁白跑：final 先跑全量、最后才跑秒级的 G7；基线上有预存红就判红，afa 每个 change 要先跑一遍全量、手写 deselect（约 33 分钟）；审批面板要等基线跑完才出。证据：flight-gate-speedup（afa dlib-recorder-param-patch 实测）。修复：#45。 - 覆盖率漏判：基线有预存红时，pytest-cov 覆盖率未达标被逐条差分放过。证据：#45 评审 MEDIUM。修复：#60。 - 冲突统计恒为 0：/pr-ship 第 4 步统计旧版 merge-tree 的输出，那里的冲突标记前带 +。证据：#46 实际 2 个冲突文件，报 0。修复：#47。 - 安装器三处缺陷：--upgrade 用模板整份覆盖用户的 .claude/settings.json（copy_tree 只保留 preferences.md）；把本仓自己的 change 与 ADR 草稿拷进用户项目；pipe 模式装不了 tag。证据：install.sh 代码、install-openspec-seeds、install-from-tag。修复：#35 #36 #38 #55。 - 路由缺口：legacy 逐 task 守门派 code-reviewer 时不写 model（铁律 11）。证据：v2.0 skill 原文。修复：#51。

What · 02变更范围

  • Workflow 引擎可靠性（原仓 #36 #37）：
  • 执行体 agent() 抛错按未返回处理、重派一次；仍失败记 blocked（infra），原因如实；
  • 每个执行体（含单片 wave 与 fix）一律 isolation: worktree，每个 wave 都由 integrator 合回，主 worktree 不再出现切片标记；
  • fix 先做基点校验（G0），抛错 / 未返回 / G0 拒绝都重派一次，fix 的 commit 在 final 之前合回；
  • integrator 与 final-gate 抛错或未返回重派一次，仍失败记 blocked（infra），工作流照常走完；评审员抛错只记 blocked（infra）、不重派，由 /pr-ship 的整 PR 评审兜底；
  • opsx-apply 命令与同名 skill 的 Agent 回退段、openspec-git-discipline 的临时 worktree 例外条款同改。
  • 门禁结论留存与找回（#36 #37）：切片门禁绿时，判定器把结论写进 refs/flight/<change>/gate-<S>；重派的 start --resume-checkpoint 在基点吻合时以 3 退出、原样交出这份结论；record 写回后与首轮起跑时清理；改计划后不会找回旧结论。
  • G7 按实际运行结果判（#36 #37）：对映射到 .py 的 scenario 实跑一次 pytest，只认 PASSED；运行方式取 gate.pytest → 从 gate.test 推导 → 退回本解释器并警告；有超时；收集失败附退出码与错误行。
  • 改动口径（#41 #46 #40）：未提交的字节码不算切片改动；G3 不把切片标记当源码；final 之后只改了同一 changes 根下任一 change 的记账文件（含 slices/_interfaces.md）仍算新鲜。
  • 门禁提速（#45 #60）：final 先跑 G7，红了就不跑全量；gate.test 是 pytest 时全量测试按基线逐条差分，度量不可信或覆盖率未达标时按退出码判；final 在脏工作树上加警告；baseline 先写运行标记，preflight 区分「仍在跑」与「已中断」；/opsx-propose 先渲染审批面板、基线放后台。
  • BREAKING：slices.json 必须显式写 gate.test（slice-gate.py lint 拦截），baseline 不再自动探测后写回。
  • 放宽：基线有可度量的预存红时 baseline 判 ok、可以起飞（原先判红）。
  • /pr-ship 预合并检查（#47）：改为 git merge-tree --write-tree --name-only 按退出码判断冲突；需要 git ≥ 2.38。
  • legacy 守门的评审派发显式 model（#51 的通用部分）：先跑 session-model.py 判出 <main>，三处 code-reviewer 派发都带 model。
  • 安装器（#35 #36 #38 #55 + 本仓新增）：
  • REPO_URL 缺省改为本仓 https://github.com/akarizo/intent-driven-workflow，IDT_BRANCH 缺省仍是 main；
  • pipe 模式 IDT_BRANCH 认分支或 tag，下载后交给归档自带的 install.sh 执行；
  • --upgrade 保留用户的 .claude/settings.json，只补模板里缺失的顶层键；
  • openspec/ 只下发种子清单，列出疑似旧版误拷的本库开发工件（不代删）；
  • 目标项目已启用 flight@intent-driven 插件时醒目提示并打印卸载命令（不代执行）；列出 Mod 版遗留的 .claude/hooks/ledger.py、plan_fp.py 可手动删除。
  • README：仓库名与安装地址改为本仓；新增「安装指定版本」「与 Mod 版的关系 / 从 Mod 版切换」两段。
  • ADR：新增 DRAFT-workflow-edition-repo；原样带入原仓两份通用 ADR：DRAFT-installer-versioned-with-template、DRAFT-test-gate-baseline-diff。
  • 起飞批准仍是会话转录里人发的 /opsx-apply + 计划工件 mtime；铁律、CLAUDE.md、template/CLAUDE.md.snippet、docs/WORKFLOW_zh.md 维持 v2.0 原文。
  • G5 仍读 evidence.log，「未见先红」仍只警告。
  • 原仓 Mod 时代的其余机制一律不带：批准带、账本、计划指纹、测量协议与护栏、能力包络、无人值守、--reuse-fix、「blocked 即停飞」、落地前预合并等。
  • 在 Workflow 引擎上重做 Mod 时期的优化（决策页 R1–R6）留作后续 change。

Specs · 04行为规范 (Gherkin)

gate-change-scope ADDED

Requirement: 跑测试的副产物与切片标记不算切片改动

未提交的 __pycache__ 目录与 .pyc 文件是跑测试的副产物，SHALL NOT 计入切片改动（已提交的 SHALL 照常受所有权检查）；G3 源码配对 SHALL NOT 把 .openspec-slice 标记当成源码。 Feature: gate-change-scope

Scenario: gate-ignores-uncommitted-bytecode

  • GIVEN切片 S1 已提交合规的实现与测试；工作树里另有未提交、未被 git 忽略的 src/__pycache__/mod.cpython-39.pyc，owns 不含它
  • WHEN运行 slice-gate.py gate S1
  • THENok 为 true
  • ANDfailed 里没有点名这个字节码文件的项

Scenario: gate-flags-committed-bytecode

  • GIVEN切片 S1 的提交里夹带了 src/__pycache__/mod.cpython-39.pyc（git add -f），owns 不含它
  • WHEN运行 slice-gate.py gate S1
  • THENG6 点名这个已提交的字节码

Scenario: gate-pairing-ignores-marker

  • GIVEN切片 S1 已 start，区间内没有任何提交，工作树里只有未提交的 .openspec-slice 标记
  • WHEN运行 slice-gate.py gate S1
  • THEN输出 JSON 的 failed 里没有以「G3」开头的项

Requirement: final 新鲜度只放行记账文件

final 之后的提交只改了同一 changes 根下任一 change 的记账文件（timeline.md · gate-report.md · evidence.log · review-findings.json · tasks.md · slices/_interfaces.md）时，ship SHALL 仍视 final 为新鲜；任何其它改动 SHALL 让它过期。

Scenario: final-fresh-ignores-other-change-bookkeeping

  • GIVENchanges 下有 c、b 两个 change；c 的 final 记在提交 X 且 ok；X 之后一次提交只改了 b 的 gate-report.md 与 timeline.md
  • WHEN对 c 运行 ship；之后再提交一次代码改动，再对 c 运行 ship
  • THEN前者 reasons 没有「过期」
  • AND代码改动之后 reasons 含「过期」

Scenario: final-fresh-ignores-interfaces-summary

  • GIVENchange c 的 final 记在提交 X 且 ok；X 之后一次提交只改了 c 的 slices/_interfaces.md
  • WHEN对 c 运行 ship
  • THENreasons 没有「过期」

gate-full-suite-baseline ADDED

Requirement: final 先判 G7，G7 红就不跑全量

slice-gate.py final SHALL 先跑 scenario 状态（G7），再跑 lint / typecheck，最后跑全量测试；G7 红时 SHALL NOT 跑全量，SHALL 返回红并警告「G2 全量未跑」。 Feature: gate-full-suite-baseline

Scenario: final-skips-full-suite-when-g7-red

  • GIVENcap#adds 的测试仍带 strict xfail；gate.test 运行时写下 ran-g2，gate.lint 运行时写下 ran-lint
  • WHEN运行 slice-gate.py final
  • THENok 为 false 且 failed 含点名 cap#adds 的 G7 项
  • AND全量没跑、lint 照跑；warnings 含「G2 全量未跑」

Scenario: final-runs-g7-before-full-suite

  • GIVENcap#adds 的测试通过、运行时向 order.log 追加 g7；gate.test 运行时向 order.log 追加 g2
  • WHEN运行 slice-gate.py final
  • THENok 为 true
  • ANDorder.log 依次为 g7、g2

Requirement: 全量测试按基线逐条差分

gate.test 是 pytest 且结果可度量时（退出码 1、junit 可解析、汇总行恰一行、汇总与 junit 的失败计数一致且非 0），baseline SHALL 把失败用例记进 gate-baseline.json 的 test.failed 并判 ok，final SHALL 只为基线之外的失败判红；不可度量时 SHALL 按退出码判，原因写明「按退出码」。

Scenario: baseline-records-preexisting-failures

  • GIVENgate.test 为 pytest；tests 里 test_old 失败、其余通过
  • WHEN运行 slice-gate.py baseline
  • THEN退出 0；gate-baseline.json 的 ok 为 true，test.failed 恰 1 条且含 test_old
  • ANDwarnings 含「预存红」

Scenario: final-excludes-baseline-failures

  • GIVEN上述基线已生成；test_old 仍失败，cap#adds 的测试通过
  • WHEN运行 slice-gate.py final
  • THENok 为 true，warnings 含「按基线排除」

Scenario: final-flags-new-failures

  • GIVEN上述基线已生成；又新增一个失败的 test_new
  • WHEN运行 slice-gate.py final
  • THENok 为 false
  • ANDfailed 有一项以「G2 test」开头、含「新增」与 test_new、不含 test_old

Scenario: diff-falls-back-when-unmeasurable

  • GIVENgate.test 先后运行两次 pytest（输出两行汇总），其中有失败
  • WHEN运行 slice-gate.py baseline
  • THEN退出 1；reasons 有一项含「按退出码」与「汇总行」

Scenario: non-pytest-gate-keeps-exit-code

  • GIVENgate.test 为 sh -c 'exit 1'
  • WHEN运行 slice-gate.py baseline
  • THEN退出 1；reasons 有一项含「exit 1」与「按退出码」

Scenario: exit-1-without-failures-is-red

  • GIVENgate.test 为 pytest；全部用例通过，但 tests/conftest.py 在 sessionfinish 把 exitstatus 设成 1
  • WHEN运行 slice-gate.py final
  • THENok 为 false
  • ANDfailed 有一项以「G2 test」开头且含「按退出码判」

Requirement: 覆盖率未达标不被差分放过

输出里出现 pytest-cov 的覆盖率失败标记时，本次结果 SHALL 按不可度量处理、按退出码判红，原因 SHALL 提示可在 gate.test 加 --no-cov。

Scenario: final-red-on-coverage-failure

  • GIVENgate.test 为 pytest；基线已生成（test_old 预存红，其余通过）；之后提交了按 pytest-cov 做法报覆盖率未达标的 tests/conftest.py
  • WHEN运行 slice-gate.py final
  • THENok 为 false
  • ANDfailed 有一项以「G2 test」开头，含「按退出码判」与「覆盖率」

Scenario: baseline-red-on-coverage-failure

  • GIVENgate.test 为 pytest；test_old 失败，且 tests/conftest.py 按 pytest-cov 做法报覆盖率未达标
  • WHEN运行 slice-gate.py baseline
  • THEN退出 1
  • ANDreasons 有一项含「覆盖率」与 --no-cov

Requirement: final 在脏工作树上如实标注

工作树有未提交改动（本 change 的记账文件除外）时，final 的结果 SHALL 带 dirty: true 并在 warnings 里列出路径（final 测的是工作树，合回只带已提交内容）。

Scenario: final-marks-dirty-worktree

  • GIVEN已提交的单片计划；工作树另有未跟踪的 src/extra.py
  • WHEN运行 slice-gate.py final
  • THEN结果带 dirty: true
  • ANDwarnings 有一项含「未提交改动」与 src/extra.py

Scenario: final-ignores-bookkeeping-dirt

  • GIVEN已提交的单片计划；只有本 change 的 timeline.md 未提交
  • WHEN运行 slice-gate.py final
  • THEN结果不带 dirty，warnings 不含「未提交改动」

Requirement: gate.test 必须显式写出

slice-gate.py lint SHALL 要求 slices.json 的 gate.test 非空；baseline SHALL NOT 自动探测测试命令后写回 slices.json。

Scenario: lint-requires-gate-test

  • GIVENslices.json 合法，但 gate 里没有 test
  • WHEN运行 slice-gate.py lint
  • THEN退出码非 0，stderr 含 gate.test

Requirement: 基线运行期间可识别，结束时不覆盖计划修改

baseline SHALL 开跑即把 gate-baseline.json 写成运行标记 {running, pid, started}，结束时整体覆盖为结果；结束时 SHALL 重读 slices.json、只写回全量耗时；运行期间 gate 命令或某片 verify 被改时 SHALL 判红「重跑 baseline」。preflight 见到运行标记时 SHALL 拒绝起飞：进程仍在说「仍在跑」，进程已不在说「中断」并提示重跑 baseline。

Scenario: baseline-marks-running

  • GIVENgate.test 是一个读取 gate-baseline.json、running 为 true 才退出 0 的脚本
  • WHEN运行 slice-gate.py baseline
  • THEN退出 0
  • AND结束后 gate-baseline.json 的 ok 为 true，且没有 running 字段

Scenario: baseline-keeps-plan-edits-made-while-running

  • GIVENgate.test 运行时把 S1 的 owns 改成 ["src/", "tests/", "docs/**"]
  • WHEN运行 slice-gate.py baseline
  • THEN退出 0
  • ANDslices.json 里 S1 的 owns 保留了 docs/**，且 gate.full_suite_sec 已写入

Scenario: baseline-red-when-verify-edited-while-running

  • GIVENgate.test 运行时把 S1 的 verify 改成 test -d src
  • WHEN运行 slice-gate.py baseline，再运行 preflight
  • THENbaseline 退出非 0、reasons 有一项含「重跑 baseline」
  • ANDslices.json 保留新的 verify；preflight 拒绝起飞

Scenario: preflight-reports-running-baseline

  • GIVENgate-baseline.json 为运行标记，pid 是当前仍存活的进程
  • WHEN运行 slice-gate.py preflight
  • THEN退出码非 0，stderr 含「仍在跑」

Scenario: preflight-reports-interrupted-baseline

  • GIVENgate-baseline.json 为运行标记，pid 是一个已经退出的进程
  • WHEN运行 slice-gate.py preflight
  • THEN退出码非 0，stderr 含「中断」与 baseline

gate-scenario-run ADDED

Requirement: G7 对 pytest 目标按实际运行结果判定

scenario 映射到 .py 测试时，G7 SHALL 在原有源码文本检查之外再实跑一次 pytest，只认 PASSED；XFAIL / XPASS / SKIPPED / FAILED / ERROR / 未被收集 SHALL 判未通过。切片门禁 SHALL 只跑本片的 scenario，final SHALL 跑全部 scenario。 Feature: gate-scenario-run

Scenario: g7-rejects-aliased-xfail

  • GIVENscenario cap#adds 映射的测试用别名装饰器 XF = pytest.mark.xfail(strict=True) 标记，断言尚未满足
  • WHEN运行 slice-gate.py final
  • THENok 为 false
  • ANDfailed 里有一条 G7 点名 cap#adds 并含实际结果 XFAIL

Scenario: g7-rejects-imperative-skip

  • GIVENscenario cap#adds 映射的测试在测试体内调用 pytest.skip()
  • WHEN运行 slice-gate.py final
  • THENok 为 false
