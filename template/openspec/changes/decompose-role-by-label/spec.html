Why · 01为何而做

/opsx-apply 收口时，session-decompose.py --expect-models 对每个 Workflow agent 先判角色，再拿实际模型与路由表比对（铁律 11）。角色只认两样：meta 里的 agentType；没有时退回按阶段判（template/.claude/hooks/session-decompose.py:23-25、:216）。

useAgentTypes=false（agent 定义没注册时的回退路径）下派发不带 agentType。wave integrator 在 Implement 阶段派发（template/.claude/workflows/opsx-apply.js:180），于是被判成 executor。2026-10-15 change baseline-incremental-reuse 的两轮飞行里，integrate:w1、integrate:w2 实际按路由表跑在 sonnet 上，却被判成「期望 opus，实际 sonnet」，HIGH 写进 blocking，PR #2 被强制 draft，最后由人类放行。

这个缺陷两个方向都错： - 误报：路由正确的 integrator 被判不符。本仓根目录不注册 template/.claude/agents，dogfood 每次都走回退路径，每次都会误报。 - 漏报：integrator 真被错路由到 opus 时，被当成 executor，判为一致，违规被放过。

session-decompose.py:22 的注释已经点出「只看阶段会误判成 executor」，但只修了带 agentType 的主路径。铁律 10 要求回退路径语义一致，现在不满足。

What · 02变更范围

  • session-decompose.py 判角色改为三级：agentType → label → 阶段。
  • label 就是 Workflow agent meta 的 description，由 opsx-apply.js 派发时写入，格式固定。
  • 只认两类显式格式：integrate:*、final-gate* → integrator；review:* → reviewer。
  • 其余 label（切片 id、fix 等）不认，退回按阶段判，与现在相同。
  • 新增测试锁住两个方向：无 agentType 的 integrate:w1 跑 sonnet 判一致、跑 opus 判不符。
  • 新增契约测试：opsx-apply.js 里 integrator / reviewer 的 label 模板，与 session-decompose.py 认的格式一一对应。脚本改 label 而不改对账，测试会红。
  • 不改 opsx-apply.js，不改路由表，不改 --expect-models 的输出格式与退出码。
代码：template/.claude/hooks/session-decompose.py（角色判定一处）。测试：tests/test_evidence_timeline.py（对账行为）、tests/test_agents_workflow.py（label 契约）。行为：只影响没有 agentType 的 Workflow agent。带 agentType 的路径与既有测试不变。不在范围：仓库根 .claude/ 是否接入 template/.claude 的 agents / commands（独立的结构决定）；回退用 Agent 派发路径的对账（它不经过 --workflow）。

Specs · 04行为规范 (Gherkin)

route-audit-role-resolution ADDED

Requirement: 对账按 agentType、label、阶段的顺序确定 Workflow agent 的角色

session-decompose.py --expect-models 对每个 Workflow agent 确定路由角色时，SHALL 依次： - meta 的 agentType 是 slice-executor / code-reviewer / integrator 时，取对应角色 executor / reviewer / integrator； - 否则看 label（meta 的 description）：以 integrate: 或 final-gate 开头 → integrator；以 review: 开头 → reviewer； - 否则按阶段：Implement / Fix → executor，Review → reviewer，Finalize → integrator； - 仍判不出时不参与对账。

角色确定后，按路由表比对实际模型的别名；输出格式与退出码不变。

Scenario: integrator-label-without-agent-type-matches

  • GIVEN一个 workflow journal，各 agent 的 meta 都没有 agentType：S1（Implement，claude-opus-5）、integrate:w1（Implement，claude-sonnet-5）、integrate:w2:retry（Implement，claude-sonnet-5）、review:S1（Review，claude-opus-5）
  • WHEN带路由表 {"executor":"opus","reviewer":"opus","integrator":"sonnet"} 运行收口对账
  • THEN退出 0；输出没有 ❌
  • AND对账结论把 integrator 记成 sonnet

Scenario: integrator-label-on-wrong-model-flagged

  • GIVEN一个 workflow journal，各 agent 的 meta 都没有 agentType：S1（Implement，claude-opus-5）、integrate:w1（Implement，claude-opus-5）、review:S1（Review，claude-opus-5）
  • WHEN带同一路由表运行收口对账
  • THEN退出非 0
  • AND有一条 ❌ 行点名 integrate:w1，期望 sonnet，实际 claude-opus-5

Scenario: unknown-label-falls-back-to-phase

  • GIVEN一个 workflow journal，各 agent 的 meta 都没有 agentType，label 都不匹配显式格式：S1（Implement，claude-opus-5）、fix（Fix，claude-opus-5）、judge（Review，claude-opus-5）、final（Finalize，claude-sonnet-5）
  • WHEN带同一路由表运行收口对账
  • THEN退出 0；输出没有 ❌
  • AND对账结论同时记有 executor=opus、reviewer=opus、integrator=sonnet

Requirement: label 格式是工作流脚本与对账之间的契约

opsx-apply.js 派发 integrator 与 code-reviewer 时写下的 label 模板，SHALL 与对账认的 label 格式一一对应：模板展开后的样例 label（含 :retry 变体）按对账判出的角色，等于同一派发调用里 agentType 对应的角色。

Scenario: label-contract-matches-workflow-script

  • GIVENtemplate/.claude/workflows/opsx-apply.js 与 template/.claude/hooks/session-decompose.py
  • WHEN读出脚本里 integrator 与 code-reviewer 的 label 模板，并把样例 integrate:w1、integrate:w1:retry、final-gate、final-gate:retry、review:S1 交给对账的 label 判定
  • THEN每个模板都和它对应的 typed('integrator') / typed('code-reviewer') 写在同一个派发调用里
  • AND前四个样例判为 integrator，review:S1 判为 reviewer

Design · 05技术设计

Context

  • 对账入口：session-decompose.py 的 workflow_agents（:171）从 <wf>/agent-*.meta.json 取 description（即 label）、workflowPhase、agentType；audit_routes（:209）按 AGENT_ROLE.get(atype) or PHASE_ROLE.get(phase) 定角色（:216）。
  • label 的来源：opsx-apply.js 派发时写入，五处，格式固定：

| 行 | label | agentType（typed(...)） | 阶段 | |---|---|---|---| | :153 | S1 / S1:retry | slice-executor | Implement | | :180 | integrate:w1 / integrate:w1:retry | integrator | Implement | | :189 | review:S1 | code-reviewer | Review | | :213 | fix / fix:retry | slice-executor | Fix | | :235 | final-gate / final-gate:retry | integrator | Finalize |

只有 :180 的阶段与角色对不上，这就是误判的唯一来源。 - 跨模块：判定改用 label 后，opsx-apply.js 的 label 格式成为 session-decompose.py 依赖的接口，所以写本 design。

Goals / Non-Goals

Goals: - 没有 agentType 时，integrator / reviewer 按派发方写下的 label 判角色，消除误报与漏报。 - label 格式成为显式契约，由测试守住，任何一侧单改都会红。

Non-Goals: - 不改 opsx-apply.js（不新增 meta 字段、不改 label）。 - 不改带 agentType 时的判定。 - 不处理回退用 Agent 派发路径的对账，也不处理仓库根是否注册 template/.claude/agents。

Decisions

agentType 是派发方声明的角色，最可靠，保持第一。
label 也是派发方写下的，比阶段更贴近角色

阶段是流程位置，integrator 恰好在 Implement 阶段派发。

**否决

给 meta 新增 role 字段**。要改 opsx-apply.js 和 Workflow 运行时写 meta 的方式，后者不在本仓控制内。

**否决

只改 PHASE_ROLE**。Implement 阶段同时有执行体和 integrator，按阶段无论怎么映射都会错一类。

^integrate: 与 ^final-gate → integrator；^review: → reviewer。
切片 id（任意字符串）和 fix 不登记格式

它们的阶段（Implement / Fix）本就判为 executor，结果一致。

不认识的 label 退回按阶段判，与改动前相同。将来脚本新增的 label 漏登记时，最坏只是退回今天的行为。
否决「不认识一律判 executor」

会把 Review / Finalize 阶段的未知 label 判错。否决「不认识不对账并告警」：会漏账，把告警当红又引入新误报。

tests/test_agents_workflow.py 新增一条
读 opsx-apply.js，断言 integrator / reviewer 的 label 模板（` integrate:w${i + 1} 、'final-gate'、 review:${s} ）各自和对应的 typed('integrator') / typed('code-reviewer')` 写在同一个派发调用里；
加载 session-decompose.py，断言这些模板展开后的样例 label（含 :retry 变体）判出的角色与 agentType 对应的角色相同。
只改脚本的 label 或只改对账的格式，都会让这条测试红。

Risks / Trade-offs

[label 是字符串约定，不是类型] → D3 的契约测试两侧都校验；漏登记时退回按阶段，不会更差。
[有人给切片起名 review:x] → 切片 id 由 slices.json 定，实际不会这样写；真出现时会被判成 reviewer，期望模型与 executor 相同（都是会话主模型），对账结果不变。
[description 缺失] → workflow_agents 已用文件名兜底（:192），这类 label 不匹配任何格式，退回按阶段。

Migration Plan

  • 只改判定函数，输出格式与退出码不变；无数据迁移。
  • 回滚：还原该函数即可，回到按阶段兜底。
