## Context

**现状**（读 `template/.claude/hooks/` 现行代码，main `b00a219`，已含 plan-hygiene、machine-test-lock、ship-rerun-hardening、test-ledger）：

- **唯一的时间线**是单元层的 3 秒：`UNIT_MAX_SEC = 3.0` 写死；`tier_verdicts` / `part_tier_verdicts` 用探针（或部件 junit）的逐用例耗时找候选，`_tier_rerun` 单独重跑确认，命中 `slow_allow` 的降为警告。
- **`slow_allow` 条目只有 `reason` 与 `approved`**，形状校验拒绝其他字段；没有上限，没有期限。
- **集成区域只判对错**：baseline 记每个已选区域的失败用例，final 按它差分（`G2 region`）。耗时只有墙钟（`tier_sec.regions`）。
- **账本已经有逐用例耗时**（test-ledger）：
  - 简写形态：单元层与区域的运行都经 `run_test_gate`（不带 `cwd`），逐用例耗时进观测表，账本里每条用例带层 `t`、耗时 `s`、是否实测 `m`；
  - 部件形态：单元层经 `run_part` 上报（只有耗时，层恒为 `unit`）；**区域运行带 `cwd`，不上报**，账本里没有区域用例；
  - 账本记了本次运行的锁状态 `lock`，没人用。
- **降级只认一种**：`_time_verdicts` 在锁状态为 `timeout` 时把以 `G10 slow unit test` 开头的失败挪进警告。
- **锁的持有上限**：`_lock_expect_sec` 先取基线的 `test.sec`；增量基线里它是补跑的秒数（本仓 test-ledger 的第一份基线是 25.1 秒），上限于是落到下限 300 秒。

**在役 ADR 与本设计的关系**：

- `DRAFT-test-tiers-unit-baseline-by-audit-probe`：两层、按路径归层、探针判纯度与耗时、放行要人类原话——都保留。其中「阈值不可配置」一句由本设计修订，见 D2 与 Open Questions。它否决的「阈值用环境变量可调」「一次超线即红」继续否决。
- `DRAFT-machine-wide-test-lock` 第 7 条：时间类判定只在确知争抢（`timeout`）时降级，`off` / `unavailable` 照常判。本设计把新判定并进同一条规则，不另立口径。
- `DRAFT-test-ledger-outside-repo-follows-anchors` 第 5、6 条：「要不要按账本判红由后续决策另定」「账本永不让门禁失败」。本设计就是那个后续决策；判定失败时退回不判。
- `DRAFT-tier-file-diffed-by-entry-in-final`：分层指纹取单元层条目。`budget` 写在 `unit` 条目里，改它会让锚点不可用、下一次 final 全量——这正是需要的（换了线，沿用的用例要重判）。区域条目同理（该区域必跑）。`slow_allow` 只比较用例 id 清单，`limit_sec` / `expires` 的改动不触发重跑。
- `DRAFT-measurements-stay-out-of-plan-files`：预算是判据，写在仓库级分层文件里；度量在账本里。计划文件不动。
- `DRAFT-gate-evidence-not-self-reported`：判定与报告都由脚本出。

## Goals / Non-Goals

**Goals**：

- 每一层都能有单条上限与总量预算，写在仓库级分层文件里。
- 放行有上限、有期限，到期与临期都有人被提醒。
- 集成层不再变坏：新增的超线用例判红；已有的如实列出。
- 判定只在测量可信时判红；不可信、不完整、判不了的都说清楚为什么没判。
- 没写预算的仓库升级后没有任何判定变化。
- 预算与放行的数据格式、判定函数能被 C6 的体检命令直接用。

**Non-Goals**：

- 不做体检与整改命令（C6）。
- 不替仓库定数字，不自动生成预算。
- 不给集成层用例做单独重跑确认（见 D4）。
- 切片门禁不判预算。
- 不改账本的形状（不加字段），不改锚点、`GATE_TEST_RESULT`、`plan_sha`。
- 不处理「持锁方被并跑者污染」（见 Risks）。

## Decisions

### D1 · 预算写在分层文件里，按「范围」摊平

- 形状：`unit` / 区域条目里可选的 `budget = {"case_sec": 数, "total_sec": 数}`；部件形态写在 `parts.<部件>.unit` 与 `parts.<部件>.regions.<区域>` 里。
- 判定时摊平成范围：简写形态 `unit` + 区域名；部件形态 `<部件>/unit` + 区域名（区域名本来就全仓唯一）。
- 账本不加部件字段：部件形态下单元层用例属于哪个部件，由用例 id 推出——适配器部件的 id 首段就是部件名（`sh::sh::TestS`），其余 id 是顶层路径，取 `root` 最长的那个部件。
- **为什么不放计划文件**：预算是仓库的长期判据，不是某个 change 的；放计划里等于每个 change 自己给自己定线。
- **为什么不加账本字段**：C5a 的测试钉住了用例记录恰好四个键；部件能从 id 推出来，就不动账本。
- **备选**：单独一个 `test-budgets.json`——被否：层的定义与层的预算分在两个文件里，改名、增删区域时要两头对。

### D2 · 单元层：线可配，放行有上限与期限；判定机制不变

- 线取 `case_sec`，缺省仍是 3 秒。候选、单独重跑确认、探针不可度量时只警告——都不动。
- 放行条目：
  - `limit_sec`：确认耗时（有重跑取首跑与重跑的较小值）超过它 → 判红；
  - `expires`：今天晚于它 → 这条放行不再算数，按没放行判红；到期日当天仍有效；
  - 距到期 ≤ 14 天：警告文本带「将于 <日期> 到期」（**14 是草案，没有数据**）；
  - 两个字段都没有的旧条目：与现在完全一样。
- 「今天」取 UTC 日期，由 `slice-gate.py` 取，传给判定函数（纯函数可测）。
- **修订了在役 ADR 的一句话**：`DRAFT-test-tiers-unit-baseline-by-audit-probe` 写的是「阈值不可配置」，理由是被门禁的一方不该能改判据。本设计允许在分层文件里改，并用 D7 把改动摆到评审的人面前；环境变量与计划文件仍然改不了它。
- **备选**：到期后只警告——被否：没有人必须回应的提醒等于没有（方案页根因 R2）。代价见 Risks。

### D3 · 集成层单条：按账本判，新增的判红，已有的只警告 ⚠ 与方案页不同

- 判定对象：收口账本里层为某区域、该区域写了 `case_sec`、**本次实测**（`m = 1`）且有耗时的用例。
- 用例的线：有未过期的放行且带 `limit_sec` → 该上限；有未过期的放行而没上限 → 不设线；否则区域的 `case_sec`。
- 超线之后分三类：

  | 情形 | 处置 | 理由 |
  |---|---|---|
  | 不在基线账本里（本 change 新增） | `G13` 判红 | 是这个 change 带来的；作者当场能改或申请放行 |
  | 在基线账本里，基线时已超线 | 警告，计「老债」 | 不是这个 change 带来的 |
  | 在基线账本里，基线时未超线 | 警告，计「本次量到超线」，**不判红** | 见下 |

- **为什么「涨过线」不判红**：方案页与 Q7-A 写的是判红。数据不支持——afa 集成层在没有针对性改动的两次运行之间，60 秒线有 2–12 条、30 秒线有 2–14 条用例从线下到线上；同一棵树连跑两次也有 3–6 条。集成用例的耗时里含共享准备（谁先跑谁付）与缓存状态，单次测量分不出「真的变慢」。照判，几乎每次 final 都红在没人动过的用例上。
  - 加余量救不了：要求基线低于线的 1/3，仍有 0–8 条。
  - 这些数据测于加锁之前，加锁之后会好一些，好多少没有数据。等账本攒够加锁后的重复运行，再决定要不要收紧（Open Questions）。
- **「新增超线」同样是单次测量**，但范围只限本 change 自己加的用例，条数少，误判了作者有三条路：提速、拆小、申请带上限的放行。这是有意保留的一道判红。
- **基线账本缺失或不完整** → 分不出新增与已有 → 一条都不判红，警告里写原因。
- **baseline 阶段**：全部超线都是老债，只警告。
- **备选**：
  - 取基线与本次的较小值再判——对「涨过线」恒不成立（基线本来就在线下），等价于不判。
  - 超线候选整区域重跑一次确认——区域命令是仓库自己的，库无法只跑其中几条；整区域重跑在 afa 是四到十分钟，而候选几乎每次都有。

### D4 · 集成层不做单独重跑确认

- 单元层能重跑，是因为 `gate.pytest` 加 nodeid 就能只跑那几条。
- 区域的 `cmd` 是任意命令（带环境、带服务、可能不是 pytest），没有「只跑这几条」的通用办法；单独跑一条还会把共享准备的成本全算在它头上，测出来更慢。
- 所以集成层的判红只保留对噪声最不敏感的一类（D3 的新增），其余交给报告。

### D5 · 层总量：取账本里整层逐用例耗时之和

- 合计 = 该范围全部用例（实测 + 沿用）的 `s` 之和。
- **为什么不用墙钟**：增量 final 只重跑一部分文件，墙钟与预算不可比；并行度一变墙钟也变。逐用例之和在全量与增量之间是同一个量。
- 单元层超预算 → `G14` 判红（baseline 与 final 都判）；区域超预算 → 警告，列最慢 3 条与本 change 新增的秒数（新增 = 不在基线账本里的用例，归因是确定的）。
- 不判的两种情形（各一条「未判」警告）：账本 `complete` 为假；该范围无耗时的用例超过一成（沿用 test-ledger 的 `NO_SEC_RATIO`，**草案**）。
- **预算要留余量**：afa 7 次运行里层合计的最大 / 最小比，单元层 1.81、集成层 1.53（加锁之前）。文档建议总量预算不低于当前合计的 2 倍；模板不强制。
- **备选**：「层合计比基线上涨超过 X% 判红」——被否：两次运行之间的合计本身就能差五成以上，这条线只会量到噪声。上涨多少由「本 change 新增的秒数」如实报告。

### D6 · 降级只认 `timeout`，与 G10 同一条规则

- `_time_verdicts` 的前缀从一个扩成三个：`G10 slow unit test`、`G13 slow integration test`、`G14 tier budget`。
- `off`、`unavailable`、`nested` 照常判（`DRAFT-machine-wide-test-lock` 第 7 条的理由不变：否则关锁的 CI 里时间判定永久失效）。
- 基线账本是在 `timeout` 下量的：只影响「老债」与「本次量到超线」的划分，两者都是警告，不另作处理。

### D7 · 预算与放行的改动摆到评审面前

- final 用 `git show <基线 commit>:<分层文件>` 取基线时的版本，摊平后与当前版本逐项比：
  - 预算数值变了（标「放宽」/「收紧」；取消算放宽）；
  - 放行条目新增、移除、`limit_sec` 或 `expires` 变了。
- 有变动 → 一条以「预算变更」开头的警告，各行进 `tests.budget.changes`，随「## 测试变更」进 PR 正文。
- 基线 commit 上没有分层文件（本 change 新建的）→ 不比。取不到、解析不了 → 不比，不报错。
- 只报告，不判红：改预算是正当动作，要的是第二处人类审批（PR review）看得见。
- **已知缺口不变**：手工改 `slow_allow` 仍然只靠评审发现（在役 ADR 已记为已知缺口），现在至少每一条改动都会被点名。

### D8 · 对账里两个噪声项对区域用例停用

- 「变慢」（翻倍且多 0.5 秒）：同树连跑的 afa 集成层命中 114 条，相邻门禁运行之间 41–198 条；单元层 0–4 条。→ 层为区域的用例不再计入「变慢」；单元层与未分层的照旧。
- 「某层耗时上涨 ≥ 20% 且 ≥ 5 秒」的建议行：区域合计两次之间能差 35%–53%。→ 不再对区域给出；区域的增长由「本 change 新增 +X 秒」与总量预算报告。
- 阈值本身（2 倍、0.5 秒、20%、5 秒）不动：单元层的数据说它们够用。

### D9 · 判定放在哪、失败怎么办

- `test-ledger.py`：`budget()` 与 `budget_changes()`，纯函数。返回值里直接带好 `failed` / `warnings` 的文本，`slice-gate.py` 只做转发与降级。
- `slice-gate.py`：`_budget_judge` 包住调用——取分层文件、摊平预算、取今天、取基线账本、调用、再过一遍 `_time_verdicts`。整体在 `try` 里：
  - 账本模块不可用、账本没写成、判定抛错 → `warnings` 加一条「预算未判：<原因>」，结论不变（铁律 10）；
  - 没有任何范围写 `budget` → 不调用，输出里没有 `budget`。
- 接入点：baseline 与 final 各自落账之后（final 有两处落账：部件形态与其余）。baseline 的 G14 进 `reasons`，但不算「基线无效」那一类（`test_ok` 不受影响）；与 G10 红一样，这次基线写出的锚点不可用。
- G10 不经这条路：它在探针那边判，账本坏了也照判。

### D10 · 部件形态只补两处

- **区域运行进账本**：部件区域带 `cwd` 运行时让 `run_test_gate` 留一份 junit（已有的 `keep_junit`），用部件单元层同一个函数 `_junit_secs` 换成顶层 id，按 `tier = 区域名` 上报。只有耗时，没有结局（与适配器部件的单元层一致）。拿不到 junit → 不上报，该区域在账本里没有用例，自然不判。
- **单元层合计按部件**：D1 的范围推导，不改账本。
- **不补的**：适配器部件用例的结局、部件区域的依赖图。它们不挡预算判定。

### D11 · 放行命令

- `allow-slow` 加 `--limit-sec`、`--expires`；人类证据的判据一字不改。
- `--expires` 早于今天直接拒绝（写一条已经过期的放行没有意义）。
- 两个都没给：照常写，stderr 提示一行。不强制——集成层的老用例申请放行时，人未必说得出期限；体检会把「没有上限」的条目数出来。
- **备选**：缺省给 90 天期限——被否：没有数据支持任何缺省值，替人填的期限等于没人定过。

### D12 · 锁持有上限的取值是缺陷修复，放在本 change

- `_lock_expect_sec` 改为取三者的最大值：基线的 `full_suite_sec`、计划里旧的 `gate.full_suite_sec`、基线不是增量时的 `test.sec`；都没有 → 不声明，上限用缺省 1800 秒。
- `machine-test-lock` design D5 写的就是「有上次全量耗时 → max(300, 3 × 耗时)」，实现取成了基线的 `test.sec`，增量基线下两者不是一回事。`flight-lock.py` 的公式与常数不动。
- **为什么放这里**：G13 / G14 只在锁状态不是 `timeout` 时判红。上限说短了，后到的飞行会放弃排队并跑——它自己降级了，**持锁的那一方却仍然是 `held`**，带着被污染的耗时判红。预算判定的可信度直接依赖这条。
- 实例：2026-11-18 `test-ledger` 的 baseline 持锁 600 秒（补跑 76 个测试文件 512 秒），`slice-resume-deterministic` 的 baseline 到达时判「已持有 600.6 秒，超过上限 300.0 秒」，不加锁开跑。

### D13 · 只重跑区域的增量 final 把其余用例丢了：一并修

- **现象**（propose 期在一次性副本上复现）：有分层文件、Δ 只命中区域文件时，final 不起 pytest（单元层没有文件要重跑），只重跑区域。此时 `_anchor_forward` 收到的「重跑清单」含区域文件而依赖图记录为空，它据此判断「有重跑但依赖图没测到」，把新锚点的逐用例结局清空；随后只并回区域的用例。
- **后果**：新锚点的 `nodes` 与收口账本里没有单元层用例（`tests` 的计数还在，所以摘要看不出来），对账把它们记成「未重测」；之后经这条锚点的增量运行继续缺。
- **为什么在本 change 修**：层总量按账本里整层用例之和判（D5）。单元层用例整层缺席时合计是 0，单元层总量预算在这类 final 上永远不红。
- **修法**：给 `_anchor_forward` 一个带缺省值的参数，表示「本次有没有真的起 pytest 重跑」；`cmd_final` 传入 `bool(run_sel)`。与同一段里 `nodes_ok` 的口径一致，其余调用点不变。在一次性副本上按此修改，新骨架通过，`test_final_tiers` / `test_tier_file_incremental` / `test_final_incremental` / `test_final_nodes_diff` / `test_gate_test_result` / `test_ledger_final` / `test_baseline_anchor_reuse` 共 42 条保持全绿。

### D14 · 给 C6 留的接口

- 数据：分层文件的 `budget`、`slow_allow` 的 `limit_sec` / `expires`；账本不变。
- 函数（`test-tiers.py` 已按路径加载 `slice-gate.py`，同法可加载 `test-ledger.py`）：
  - `slice-gate.py`：`tier_budgets(tiers)`、`budget_scope_of(tiers)`、`allow_view(allow, today)`；
  - `test-ledger.py`：`budget(final, base, budgets, scope_of, allow, phase)`——以 `phase="baseline"`、`base=None` 调用就是「眼下这份账本里全部不合规的用例」，正是体检要的清单。
- C6 的体检子命令只需要决定退出码与输出格式，不需要再实现判定。

## Risks / Trade-offs

- [新增超线基于单次测量，可能误红] → 只限本 change 新增的用例；误红时重跑 final 会重新测量，或申请带上限的放行。Open Questions 里列为人类拍板点。
- [放行到期会让之后每个 change 的 baseline 变红，哪怕它与这条用例无关] → 这是「逼人重新看一眼」的代价；到期前 14 天起每次门禁都有警告，体检也列出。只有写了 `expires` 的条目才会这样，旧条目不会。
- [单元层总量预算写得太紧，争抢或机器变慢时误红] → 判定只在持锁（或显式关锁）时判红；文档建议留 2 倍余量；预算是可选的。
- [持锁方被并跑者污染而不自知] → D12 让放弃排队只在持有者确实超过 3 倍全量耗时时发生。完全消除需要持锁方感知「有人放弃后并跑」，不在本 change。
- [基线账本在另一台机器上] → 集成层单条不判红，只警告并说明；单元层的 G10 不受影响。
- [`budget` 写进 `unit` 条目会改变分层指纹，升级后第一次写预算的那个 change final 全量] → 语义上正确（换了线要重判），成本只有一次。
- [`limit_sec` / `expires` 改了但用例没重跑，新上限要到下次实测才生效] → 有分层文件的 baseline 恒跑全量单元层，下一个 change 的 baseline 就会判到；集成层用例按区域整体重跑。
- [改 `tier_verdicts` 等函数的签名] → 新参数都带缺省值，旧的四参数调用（`tests/test_tiers_verdict.py`）不变。
- [与 `slice-resume-deterministic` 同改 `slice-gate.py`、`README.md`] → 本 change 碰的是分层校验、`tier_verdicts` 一族、baseline / final 的落账点之后、`_final_parts`、`_lock_expect_sec`；对方碰 `start` / `merge` / `record` / 留痕。`cmd_final` 两边都不动同一段。README 各加各的行。
- [C4（`wave-integration-guard`）以后要在切片门禁与 wave 之间加检查] → 本 change 不给切片门禁加任何东西，不占那块地方。

## Migration Plan

- 随 `install.sh --upgrade` 分发，全部是既有文件的增量改动，没有新文件。
- **升级后不改分层文件 → 判定零变化**。逐条说明：

  | 新判定 | 升级后何时生效 | 首版是红还是警告 | 理由 |
  |---|---|---|---|
  | 单元层线可配 | 写了 `unit.budget.case_sec` 之后 | 红（沿用 G10） | 机制不变，只是线可调 |
  | 放行超上限 | 条目写了 `limit_sec` 之后 | 红 | 上限是放行时人自己说的 |
  | 放行到期 | 条目写了 `expires` 且到期之后 | 红；到期前 14 天警告 | 见 D2；⚠ 人类拍板点 |
  | 集成层新增超线 G13 | 区域写了 `case_sec` 之后 | 红 | Q7-A 的前半；⚠ 人类拍板点 |
  | 集成层已有用例超线 | 同上 | 警告 | Q7-A（老债）；涨过线见 D3 |
  | 单元层总量 G14 | 写了 `unit.budget.total_sec` 之后 | 红 | 方案页；⚠ 人类拍板点 |
  | 区域总量 | 写了 `total_sec` 之后 | 警告 | 方案页 |
  | 预算变更 | 分层文件相对基线有变动时 | 警告 | 只为可见 |

- **无条件生效的三处**（都不会让任何门禁变红）：
  1. 锁持有上限变长（300 秒下限不变，增量基线不再把补跑秒数当全量）；
  2. 「## 测试变更」里区域用例不再计「变慢」，区域不再出「层耗时上涨」的建议。
  3. 有分层文件、只重跑区域的增量 final 不再把其余用例从锚点与账本里丢掉（D13）；此前这类 final 写出的锚点缺用例结局，升级后第一次经它的增量运行里这些用例没有沿用的耗时，下一次全量即补齐。
- **旧版 hooks 读到带 `budget` 的分层文件会报未知字段**：先升级 hooks，再写预算。
- **在途 change**：升级时基线已经跑过的 change 不受影响；它们的 final 只有在分层文件写了预算之后才多出判定，而那需要有人提交分层文件的改动。
- **回退**：删掉分层文件里的 `budget` 与放行的两个新字段即回到现状；删掉 `test-ledger.py` 则 G13 / G14 不判，G10 照旧。
