# 校准数据（tier-budgets propose 期，2026-11-18）

设计里几处「判红还是只警告」的取舍来自这里的数字。脚本只读，输入不在本仓库：

| 输入 | 是什么 | 位置（本机） |
|---|---|---|
| 同树连跑 | afa 集成层同一棵树的三次运行：cold1（冷缓存）、warm1（仍在补建 85 个缓存产物）、warm2（缓存齐全）；顺序执行，负载 3–16 / 18 核 | `~/afa-ops/test-tiers-audit-20261118/int_run/*-junit.xml` |
| 门禁运行 | afa 7 个 change 的全范围门禁 junit（体检时收集，测于全机测试锁合入之前，负载高），每条用例带层 | `/tmp/tiers_audit/junit_runs.json`（体检的中间产物，不保证长期存在） |

| 脚本 | 量什么 |
|---|---|
| `noise_same_tree.py` | 同树两次运行之间：逐用例耗时的比值与差值、以若干秒为线时两次判定不一致的条数、加余量之后还剩多少、「翻倍且多 0.5 秒」的命中数 |
| `noise_gate_runs.py` | 7 次门禁运行之间：每层「始终超线 / 始终不超 / 时超时不超」的条数、层合计的波动、相邻两次「翻倍且多 0.5 秒」的命中数 |
| `crossing.py` | 「基线不超线、本次超线」若判红会命中多少条；要求基线低于线的 1/2、1/3 之后还剩多少 |

输出存档：`noise-20261118.txt`。

## 读数时要记住的三件事

1. **这些数测于加锁之前**（门禁运行那一组负载 37–45 / 18 核）。全机测试锁 2026-11-18 才合入，加锁之后的重复测量还没有。结论因此是「现有数据不支持判红」，不是「永远不能判红」。
2. **同树那一对不是纯噪声**：warm1 跑的时候还在补建缓存产物（构建耗时合计 681 秒摊在各用例上），warm2 没有。它量到的是「缓存状态不同 + 噪声」，这正是真实门禁里相邻两次运行的常态。
3. **门禁运行那一组的代码树各不相同**（7 个不同的 change）。用例耗时的差异里混着真实的代码差异；但这些 change 都没有以「让集成用例变慢」为目的，所以把差异当作「没有针对性改动时会看到的波动」是合理的上界。

## 没有数据支撑、标为草案的值

- 放行临期提醒的 14 天（`ALLOW_SOON_DAYS`）。
- 层总量「无耗时超过一成不判」（沿用 test-ledger 的 `NO_SEC_RATIO`）。
- 文档里「总量预算不低于当前合计的 2 倍」的建议：依据只有上面两组里层合计的最大 / 最小比（单元层 1.81、集成层 1.53），同样测于加锁之前。
