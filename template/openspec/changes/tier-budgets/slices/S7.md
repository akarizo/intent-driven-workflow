# S7 · slice-gate.py：部件区域运行进账本；锁的预计耗时取全量秒数

## 做什么

两件互不相干的小事，都在 `template/.claude/hooks/slice-gate.py` 里，放在同一片只是因为同一个文件在同一个 wave 里只能有一个主人：

1. 部件形态下，已选区域的运行结果进观测表，使区域用例出现在账本里（之后 S4 接好的预算判定自然对它们生效）。规则原文见 `specs/tier-budgets/spec.md` 的「部件形态的区域进账本」；取舍见 `design.md` D10。
2. 全机测试锁取锁时声明的预计耗时改为取全量秒数。规则原文见「全机测试锁的持有上限取全量耗时」；取舍见 `design.md` D12。

## 依赖

S4（预算判定已接入 baseline / final，含部件形态的落账点）。

既有可用的东西：

- `run_test_gate(cmd, root, …, cwd=…, keep_junit=路径)`：临时目录删除前把 junit 复制到 `keep_junit`（没有 junit 就不复制）；
- `_junit_secs(paths, root, name)`：把 junit 报告换成 `{顶层 id: 秒}`（testcase 带 `file` → `<root>/<file>::<name>`，否则 `<部件名>::<classname>::<name>`），一份都解析不了 → `None`；
- `_ledger_observe(form, outcomes, secs, tier=None)`；
- `_tier_regions(tiers)[区域名]` → `(所属部件, 区域条目)`；部件名要从 `tiers["parts"]` 里按对象身份或遍历找回（`_tier_regions` 现在返回的是部件对象，不是名字——需要名字时遍历 `tiers["parts"].items()` 找到含该区域的那个）。

## 怎么做

TDD：`tests/test_budget_parts.py` 的 3 条骨架现在是红的。

### A · 部件区域运行进账本

两处带 `cwd` 运行区域的地方：`cmd_baseline` 的区域循环（`parts` 为真的那个分支）与 `_final_parts` 的区域循环。各自：

1. 在临时目录里准备一个 junit 路径（`tempfile.TemporaryDirectory`），把它作为 `keep_junit` 传给 `run_test_gate`；
2. 运行结束后，文件存在则 `secs = _junit_secs([路径], 部件的 root, 部件名)`；
3. `secs` 不是 `None` 且非空 → `_ledger_observe("nodeid", {}, secs, tier=区域名)`；
4. 拿不到 junit（非 pytest 的区域命令、命令自己没写报告）→ 什么都不做，不加警告、不改结论。

建议抽一个小函数（如 `_observe_part_region(top, part_name, part, rname, junit_path)`）给两处共用。

要点：

- 只在部件形态这样做。简写形态的区域运行不带 `cwd`，`run_test_gate` 自己已经上报，别重复。
- 上报用 `"nodeid"` 形式、`outcomes` 为空——与部件单元层（`run_part`）一致：部件形态的账本只有耗时，没有结局。
- `run_test_gate` 的返回值、差分逻辑（`_diff_verdict`）、区域墙钟都不动。
- 骨架 `test_parts_region_run_is_observed`：基线账本与收口账本里都有 `t == "api"` 的用例，`s` 不是 `None`、`m == 1`。
- 骨架 `test_parts_region_new_slow_case_is_red`：区域 `api` 的 `case_sec` 是 0.4，基线之后新增一条睡 1 秒的区域用例，final 红在 `G13 slow integration test`，文本含 `api` 与 `test_slow`。这一条不需要再写判定代码——区域用例进了账本，S4 的 `_budget_judge` 就会判；如果它不红，先查用例 id 在基线账本与收口账本里是否同一种形式。

### B · 锁的预计耗时

`_lock_expect_sec(baseline, gate)` 改成：

- 候选值（只取数值，`bool` 不算）：
  - `baseline["full_suite_sec"]`；
  - `gate["full_suite_sec"]`（计划里的旧字段；`cmd_baseline` / `cmd_final` / `cmd_gate` 调用前已经把 `suite_sec(...)` 放进了内存里的 `gate`）；
  - `baseline["test"]["sec"]`——**仅当** `baseline.get("mode") != "incremental"`；
- 返回候选里的最大值；一个都没有 → `None`（`flight-lock.py` 的持有上限随之取缺省 1800 秒）。
- `baseline` 不是字典（`None`、运行标记读不出）时按没有处理。
- 函数的文档串改成现在的口径，并点明「增量基线的 test.sec 只是补跑秒数」。

`flight-lock.py` 不改（公式 `max(300, 3 × 预计耗时)` 与常数都不动）。

骨架 `test_lock_cap_uses_full_suite_seconds` 的四个取值：

| 基线 | `gate` | 期望 |
|---|---|---|
| 增量，`test.sec` 25，`full_suite_sec` 400 | `{}` | 400 |
| 增量，`test.sec` 25，`full_suite_sec` 为 `None` | `{}` | `None` |
| 全量，`test.sec` 300，`full_suite_sec` 300 | `{}` | 300.0 |
| 增量，`test.sec` 25，`full_suite_sec` 为 `None` | `{"full_suite_sec": 600}` | 600 |

## 注意

- 本片是三个 wave 里最后改 `slice-gate.py` 的一片。
- `tests/test_ledger_final.py::test_parts_runs_write_ledger` 钉着部件形态账本里单元层用例的确切形状（`{"o": None, "s": 0.01, "t": "unit", "m": 1}`）与「新增 / 删除都是 0」：那个仓库没有区域，本片不影响它；别改单元层的上报。
- `tests/test_gate_lock.py` 与 `tests/test_flight_lock.py` 里凡是靠 `FLIGHT_LOCK_MAX_HOLD_SEC` 控制持有上限的用例不受 B 影响（环境变量优先于预计耗时）。
- `tests/test_budget_gate.py`（S4 的骨架，已解锁）在 verify 里，必须保持全绿。
