Why · 01为何而做

测试账本（change test-ledger，C5a）让每次 baseline / final 留下逐用例耗时，但门禁仍然只对单元层的 3 秒线判红，其余一概不管：

- 集成层没有任何上限。afa 体检（2026-11-18）里集成层占测试耗时的 96–98%，最慢 20 条占 42%，两周内用例数 +41%，没有一条规则会因此变红或警告。 - 放行没有边界。slow_allow 的条目只有理由与人类原话，放行之后可以慢到任意秒数、永远有效，没人会再看它一眼。 - 单元层的线写死在代码里。3 秒对多数仓库合适，但想收紧到 1 秒的仓库只能改模板。 - 层的总量没人管。单元层每次门禁都跑，它的总耗时是所有飞行都要付的固定成本，目前只打印不判。

2026-11-18 用户在方案页 docs/flight-fixes-and-test-governance.html 第 04 节提出「每一层的用例每一条的执行时间都要有限制和必要的豁免设定」，Q7 选了棘轮（老债只警告，新增的判红）。本 change 是该页 C5 的后半（C5b）：把账本里的数字变成有判定的预算。范围与取舍来自方案页、Q5 / Q7 的已定结论与主会话的拆分指令，没有另开 grill-me 访谈。

propose 期用 afa 体检留下的数据量了噪声（calibration/），结论改变了方案页的一处设计，见 What Changes 的「与方案页不同」。

What · 02变更范围

  • 分层文件声明预算（openspec/test-tiers.json，slice-gate.py 校验形状）：
  • 单元层、每个区域（简写形态与部件形态都一样）可选 budget = {case_sec, total_sec}，两个字段各自可选。
  • slow_allow 的条目新增两个可选字段：limit_sec（放行到多少秒）与 expires（YYYY-MM-DD，到期日当天仍有效）。
  • 没写的一律按现状：单元层单条 3 秒，区域不判，旧放行条目无上限、不过期。
  • 单元层单条上限（G10，仍由探针测、单独重跑确认）：线取 unit.budget.case_sec，缺省 3 秒；放行带上限时超过上限判红；放行过期后回到判红；距到期 14 天内在警告里提示。
  • 集成层单条上限（新增 G13 slow integration test，按账本判）：
  • 本 change 新增的用例实测超线 → 判红；
  • 基线账本里就有的用例超线 → 只警告（「老债」与「本次量到超线」分开计数）；
  • 没实测的（沿用）、没有耗时的、所在区域没写 case_sec 的不判。
  • 层总量预算（新增 G14 tier budget，按账本里该层全部用例耗时之和判）：单元层超预算判红（baseline 与 final 都判）；区域超预算只警告，并列出最慢的 3 条与本 change 新增的秒数。
  • 争抢下降级：排队放弃后不加锁跑出来的那一次，G13 / G14 与 G10 一样降为警告（沿用 DRAFT-machine-wide-test-lock 第 7 条的口径）。
  • 预算与放行的改动要被看见：final 把分层文件里的预算、放行名单与基线 commit 上的版本逐项比较，有变动就写进警告与 PR 正文的「## 测试变更」。
  • 放行命令（test-tiers.py allow-slow）：新增 --limit-sec 与 --expires；两者都没写时照常放行，但打印一行提示。
  • 报告：
  • 「## 测试变更」多出预算一段：新增超线、老债、各层合计对预算、放行的到期情况、预算变更；
  • flight-doctor.py doctor 的 [tests] 多出各层预算对实际、放行名单里已过期 / 快到期 / 没有上限的条目。
  • 补上部件形态的两处缺口（C5a 留下、挡着预算判定的）：部件区域的运行结果进账本；单元层合计按部件分开算。
  • 修一处挡着层总量的既有缺陷：有分层文件、只重跑区域的增量 final，会把没重跑的用例（整个单元层）从新锚点的逐用例结局与收口账本里丢掉，对账记成「未重测」。propose 期在一次性副本上复现并验证了修法（design D13）。
  • 对账里两个噪声项收窄（C5a 留给本 change 定的阈值）：「变慢」与「某层耗时上涨」的建议行不再对区域用例计数。
  • 全机测试锁的持有上限取全量耗时：现在取的是上次基线的 test.sec，增量基线里它只是补跑的秒数，于是持有上限恒为下限 300 秒；本仓 2026-11-18 一次 512 秒的补跑期间，后到的飞行直接放弃排队、不加锁并跑。改为取最近一次已知的全量耗时，不知道时用缺省 1800 秒。
  • 文档：flight-runner-contract.md 新增「时间预算与放行」一节；commands/test-tiers.md 与 README.md 补分层文件的新字段与放行命令的新参数。
  • 「从线下涨到线上」不判红，只警告。方案页与 Q7-A 的后半是判红。afa 集成层 7 次全范围门禁运行里，以 60 秒为线，始终超线的用例 11 条，时超时不超的 26 条；同一棵树连跑两次（warm1 / warm2），以 30 秒为线有 3–6 条用例「涨过线」。照此判红，几乎每次 final 都会红在没人动过的用例上。加余量（基线须低于线的 1/2、1/3）也消不掉。
  • 层总量按账本里逐用例耗时之和判，不按墙钟判。增量 final 只重跑一部分文件，墙钟与预算不可比；账本里没重跑的用例沿用上次的耗时，合计才是整层的数。
  • 不新增入库的报告文件：预算结论进现有的 final 输出、时间线之外的警告与「## 测试变更」，不写 gate-report.md 的新小节（理由同 test-ledger design D4）。
  • 体检与整改命令（test-tiers.py audit、/test-audit）属于 C6；本 change 只保证它要读的数据与函数已经在。
  • 不替仓库定预算数字：模板只有单元层 3 秒这一个缺省值，其余都由仓库自己写。
  • 不给集成层用例做「单独重跑确认」：区域命令是仓库自己的，库没有办法只跑其中几条。
  • 切片门禁（gate）不判预算：它不落账。
  • 没有分层文件的仓库没有任何变化。

Specs · 04行为规范 (Gherkin)

tier-budgets ADDED

Requirement: 分层文件可声明时间预算与放行期限

openspec/test-tiers.json 的单元层与每个区域 SHALL 可带可选的 budget 对象，只认 case_sec（单条上限，秒）与 total_sec（层总量预算，秒）两个字段，各自可选，写了就必须是大于 0 的数（布尔不算数）。部件形态下 parts.<部件>.unit 与 parts.<部件>.regions.<区域> 同样可带。slow_allow 的条目 SHALL 可带可选的 limit_sec（大于 0 的数）与 expires（YYYY-MM-DD，须是真实日期）。形状不合法时 slice-gate.py lint MUST 判红并点名所在的层（或用例 id）与字段；没有这些字段的分层文件 MUST 与现在一样通过校验。slice-gate.py SHALL 提供 tier_budgets(tiers)，把预算摊平成 {范围: {kind, case_sec, total_sec, part}}：简写形态的范围是 unit 与各区域名，部件形态是 <部件>/unit 与各区域名；单元层没写 case_sec 时取 3 秒，区域没写时为 null。budget_scope_of(tiers) SHALL 返回一个把（用例 id，账本里的层）映射到范围的函数：区域名原样返回；unit 在简写形态返回 unit，在部件形态按用例 id 定出所属部件（id 首段等于部件名，或 id 的路径落在该部件 root 之下，多个命中取 root 最长的）。 Feature: 预算与放行期限写在仓库级分层文件里，随 PR 评审 Rule: 没写的一律按现状；写错了在 lint 就红

Requirement: 单元层单条上限取预算，放行带上限与期限

单元层的 G10 判定 SHALL 以该层的 case_sec 为线（没写时 3 秒），判定方式不变：首跑不低于线的用例是候选，单独重跑仍不低于线（或重跑拿不到）才确认。确认的用例在 slow_allow 里有条目时：条目已过期（今天晚于 expires）→ 判红，文本含「到期」与该日期；条目带 limit_sec 且确认耗时（有重跑取首跑与重跑的较小值，否则取首跑）超过它 → 判红，文本含「放行上限」；其余 → 与现在一样只警告，且距到期不超过 14 天时警告文本带「将于 <日期> 到期」。没有 limit_sec 与 expires 的旧条目 MUST 与现在一样只警告。部件形态下各部件用自己 unit.budget.case_sec 的线。 Feature: 单元层必须一直干净，放行是有边界、有期限的例外 Rule: 放行不是无限放行；到期后回到判红

Design · 05技术设计

Context

现状（读 template/.claude/hooks/ 现行代码，main b00a219，已含 plan-hygiene、machine-test-lock、ship-rerun-hardening、test-ledger）：

  • 唯一的时间线是单元层的 3 秒：UNIT_MAX_SEC = 3.0 写死；tier_verdicts / part_tier_verdicts 用探针（或部件 junit）的逐用例耗时找候选，_tier_rerun 单独重跑确认，命中 slow_allow 的降为警告。
  • slow_allow 条目只有 reason 与 approved，形状校验拒绝其他字段；没有上限，没有期限。
  • 集成区域只判对错：baseline 记每个已选区域的失败用例，final 按它差分（G2 region）。耗时只有墙钟（tier_sec.regions）。
  • 账本已经有逐用例耗时（test-ledger）：
  • 简写形态：单元层与区域的运行都经 run_test_gate（不带 cwd），逐用例耗时进观测表，账本里每条用例带层 t、耗时 s、是否实测 m；
  • 部件形态：单元层经 run_part 上报（只有耗时，层恒为 unit）；区域运行带 cwd，不上报，账本里没有区域用例；
  • 账本记了本次运行的锁状态 lock，没人用。
  • 降级只认一种：_time_verdicts 在锁状态为 timeout 时把以 G10 slow unit test 开头的失败挪进警告。
  • 锁的持有上限：_lock_expect_sec 先取基线的 test.sec；增量基线里它是补跑的秒数（本仓 test-ledger 的第一份基线是 25.1 秒），上限于是落到下限 300 秒。

  • 没有的数据：加锁之后的重复运行。全机测试锁 2026-11-18 才合入，本机只有一份账本（test-ledger 的 final）。

在役 ADR 与本设计的关系：

  • DRAFT-test-tiers-unit-baseline-by-audit-probe：两层、按路径归层、探针判纯度与耗时、放行要人类原话——都保留。其中「阈值不可配置」一句由本设计修订，见 D2 与 Open Questions。它否决的「阈值用环境变量可调」「一次超线即红」继续否决。
  • DRAFT-machine-wide-test-lock 第 7 条：时间类判定只在确知争抢（timeout）时降级，off / unavailable 照常判。本设计把新判定并进同一条规则，不另立口径。
  • DRAFT-test-ledger-outside-repo-follows-anchors 第 5、6 条：「要不要按账本判红由后续决策另定」「账本永不让门禁失败」。本设计就是那个后续决策；判定失败时退回不判。
  • DRAFT-tier-file-diffed-by-entry-in-final：分层指纹取单元层条目。budget 写在 unit 条目里，改它会让锚点不可用、下一次 final 全量——这正是需要的（换了线，沿用的用例要重判）。区域条目同理（该区域必跑）。slow_allow 只比较用例 id 清单，limit_sec / expires 的改动不触发重跑。
  • DRAFT-measurements-stay-out-of-plan-files：预算是判据，写在仓库级分层文件里；度量在账本里。计划文件不动。
  • DRAFT-gate-evidence-not-self-reported：判定与报告都由脚本出。

Goals / Non-Goals

Goals：

  • 每一层都能有单条上限与总量预算，写在仓库级分层文件里。
  • 放行有上限、有期限，到期与临期都有人被提醒。
  • 集成层不再变坏：新增的超线用例判红；已有的如实列出。
  • 判定只在测量可信时判红；不可信、不完整、判不了的都说清楚为什么没判。
  • 没写预算的仓库升级后没有任何判定变化。
  • 预算与放行的数据格式、判定函数能被 C6 的体检命令直接用。

Non-Goals：

  • 不做体检与整改命令（C6）。
  • 不替仓库定数字，不自动生成预算。
  • 不给集成层用例做单独重跑确认（见 D4）。
  • 切片门禁不判预算。
  • 不改账本的形状（不加字段），不改锚点、GATE_TEST_RESULT、plan_sha。
  • 不处理「持锁方被并跑者污染」（见 Risks）。

Decisions

形状

unit / 区域条目里可选的 budget = {"case_sec": 数, "total_sec": 数}；部件形态写在 parts.<部件>.unit 与 parts.<部件>.regions.<区域> 里。

判定时摊平成范围

简写形态 unit + 区域名；部件形态 <部件>/unit + 区域名（区域名本来就全仓唯一）。

账本不加部件字段

部件形态下单元层用例属于哪个部件，由用例 id 推出——适配器部件的 id 首段就是部件名（sh::sh::TestS），其余 id 是顶层路径，取 root 最长的那个部件。

为什么不放计划文件

预算是仓库的长期判据，不是某个 change 的；放计划里等于每个 change 自己给自己定线。

为什么不加账本字段

C5a 的测试钉住了用例记录恰好四个键；部件能从 id 推出来，就不动账本。

现象（propose 期在一次性副本上复现）

Risks / Trade-offs

[新增超线基于单次测量，可能误红] → 只限本 change 新增的用例；误红时重跑 final 会重新测量，或申请带上限的放行。Open Questions 里列为人类拍板点。
[放行到期会让之后每个 change 的 baseline 变红，哪怕它与这条用例无关] → 这是「逼人重新看一眼」的代价；到期前 14 天起每次门禁都有警告，体检也列出。只有写了 expires 的条目才会这样，旧条目不会。
[单元层总量预算写得太紧，争抢或机器变慢时误红] → 判定只在持锁（或显式关锁）时判红；文档建议留 2 倍余量；预算是可选的。
[持锁方被并跑者污染而不自知] → D12 让放弃排队只在持有者确实超过 3 倍全量耗时时发生。完全消除需要持锁方感知「有人放弃后并跑」，不在本 change。
[基线账本在另一台机器上] → 集成层单条不判红，只警告并说明；单元层的 G10 不受影响。
[budget 写进 unit 条目会改变分层指纹，升级后第一次写预算的那个 change final 全量] → 语义上正确（换了线要重判），成本只有一次。
[limit_sec / expires 改了但用例没重跑，新上限要到下次实测才生效] → 有分层文件的 baseline 恒跑全量单元层，下一个 change 的 baseline 就会判到；集成层用例按区域整体重跑。
[改 tier_verdicts 等函数的签名] → 新参数都带缺省值，旧的四参数调用（tests/test_tiers_verdict.py）不变。
[与 slice-resume-deterministic 同改 slice-gate.py、README.md] → 本 change 碰的是分层校验、tier_verdicts 一族、baseline / final 的落账点之后、_final_parts、_lock_expect_sec；对方碰 start / merge / record / 留痕。cmd_final 两边都不动同一段。README 各加各的行。
[C4（wave-integration-guard）以后要在切片门禁与 wave 之间加检查] → 本 change 不给切片门禁加任何东西，不占那块地方。
