Why · 01为何而做

切片门禁只看本片自己的 verify，合回之后没有任何一步检查「合在一起还对不对」。afa 的 key-features-keyft 飞行里这条缺口出了四件事（交接文档 F4 / F5 / F6 / F7）：

- 跨片问题拖到下游才爆，爆了没有修复通道。S8 新增了一个没声明的跨包 import，它自己的门禁是绿的（verify 不含分层测试），合回后把下一个 wave 的 S3、S7 拖红。工作流的 Fix 阶段只吃评审 finding，而且排在所有 wave 之后，只能人工手写一个「前置 fix」工作流。 - 全局守护不在每片门禁里。分层 / 依赖声明 / 组合根这类几秒就能跑完的检查，只出现在部分切片的 verify 里，引入新跨包依赖的切片照样绿。 - owns 漏列靠连红两次才暴露。规划期预测不准哪个替身、哪个桩要跟着接口变，每漏一个就是一次停飞、改计划、重新批准；重新起飞时已经合回的切片还要再派一遍执行体。 - owns 上限 12 条逼人放宽通配。回放本机 6 个仓库 805 个切片：大片档（现存文件多于 8 个）的切片有 28.7% 恰好写满 12 条，写满的切片里 48% 用了通配（其他切片是 7%–17%），门禁报「写了 owns 之外的文件」的比例是 19.2%（其他切片 2%–4%）。数据与脚本在 calibration/。

What · 02变更范围

  • 全局守护：gate.checks 的每个检查新增可选的 slice 命令，与 baseline / final 并列。写了 slice 的检查在 baseline（证明起点是绿的）、每片门禁（新门禁项 G15 guard）与每次 wave 集成检查里运行。仓库默认清单 gate-checks.json 里声明了 slice 的检查，计划里的同名检查必须带上。
  • wave 集成检查：新子命令 slice-gate.py wave-check，integrator 每个 wave 合回后运行：先跑全部守护，再按依赖图只重跑受影响的测试（与增量 final 同一选法）。没有可用锚点、估算耗时超过预算（缺省 120 秒，计划可调）、或仓库配了分层文件时，测试那一半跳过并在时间线写明原因，不退化成全量。结论记进 gate-report.md 的 wave 行与时间线的 wave-check 事件；ship 见到最新的 wave 行是红的就判 draft。
  • 跨片修复通道：集成检查红 → 工作流当场派一个不受 owns 限制的修复执行体，修完在它自己的 worktree 里重跑一次集成检查；绿了由 integrator 合回并把结论写回分支，修复提交照常进评审。仍红才记 blocked：守护红时后面的 wave 全部停下，只有测试红时只停依赖本 wave 的切片。修复改了哪些文件、哪些落在所有切片的 owns 之外，写进集成检查的输出并进 PR 正文。
  • owns 上限按轮次档：标准档 12 条不变，大片档 30 条。单条通配展开出 20 个以上现存文件时，须在该片的 owns_wide 里写理由；lint 把每条通配展开的文件数打印出来。已经批准过的在途 change 不因这条新规则变红。
  • 重新起飞不重做已落地的切片：新子命令 slice-gate.py landed 列出「门禁绿、提交已在分支上、计划里本片没再改过」的切片；工作流收到后不再派它们的执行体，只照常派评审。补 owns 之后的重新起飞因此只花被改那一片的钱。
  • 审批页显示哪些检查是全局守护、哪些通配写了理由；flight-doctor.py cost 多一行 wave 集成检查的次数与秒数；命令文档、同名 skill、运行器契约、README、schema 同步。
template/.claude/hooks/slice-gate.py：检查的 slice 字段（lint、plan_sha、baseline、gate 的 G15）；新子命令 wave-check 与 landed；record 认 wave 行；ship 读 wave 行；lint 的 owns 上限与 owns_wide。template/.claude/workflows/opsx-apply.js：integrator 的合回派发带上集成检查；红时派跨片修复并合回；停飞范围；新参数 args.landed（可选）；返回值多 waves。template/.claude/agents/integrator.md、slice-executor.md：各补一段。template/.claude/hooks/flight-doctor.py（cost 多一行）、spec_html.py（审批页两处）。template/.claude/commands/opsx-apply.md 与同名 skill、pr-ship.md、opsx-propose.md 与同名 skill、template/.claude/flight-runner-contract.md、README.md、template/openspec/schemas/intent-driven/schema.yaml。运行契约：检查命令的 GATE_PHASE 多两个取值 slice 与 wave；slice 阶段会被同一 wave 的多个切片并行调用。每个 wave 多一次集成检查的墙钟：守护是仓库自己声明的快检查；测试那一半有预算。本仓实测一次改到 slice-gate.py 的增量要 512–571 秒，会被预算挡下、留给 final。与待飞的 tier-budgets（C5b）同改 slice-gate.py、flight-doctor.py、契约文档与 README，函数与段落不重叠，见 design 的风险一节。

Specs · 04行为规范 (Gherkin)

owns-tiers ADDED

Requirement: owns 条数上限随轮次档

计划校验（lint、waves、turns、preflight）SHALL 按切片的轮次档决定 owns 条数上限：标准档 1–12 条，大片档 1–30 条。档位与 slice-gate.py turns 的算法相同（计划写 "turns": "large"，或 owns 展开后的现存文件数多于 8 个）；不在 git 仓库里时只认计划里的 turns。超限时 MUST 判计划不合法，点名该切片并写出两档的上限。 Feature: 大切片可以把文件一条条写清楚 Rule: 上限跟着切片的大小走，小切片想多写要先声明自己是大片

Scenario: owns-cap-follows-turn-tier

  • GIVEN切片 S1 的 13 条 owns 都是现存文件；切片 S2 的 13 条 owns 里只有 2 个现存文件
  • WHEN运行 waves；给 S2 写上 "turns": "large" 后再运行；再把 S1 的 owns 加到 31 条后运行
  • THEN第一次以 2 退出，stderr 点名 S2 并含 12 与 30，不点名 S1
  • AND第二次退出 0
  • AND第三次以 2 退出，stderr 点名 S1

Requirement: 宽通配要写理由

带通配符的 owns 条目在轮次档所用的那棵树上展开出多于 20 个现存文件时，该切片 MUST 在 owns_wide（对象，键是该片 owns 里的条目原文，值是非空理由）里为它写理由，否则计划不合法，stderr 点名该切片、该条目、展开的文件数与 owns_wide。owns_wide 的键不是该片的 owns 条目、或理由为空时同样不合法。计划合法时 stderr SHALL 为每个带通配的条目打印一行 owns: <切片> <条目> → <N> 个文件。change 的时间线已有 approve 事件时，缺理由 MUST NOT 判红，只打印提示。不在 git 仓库里时不做这项检查。 Feature: 一条通配盖住很多文件时，批准的人看得到为什么 Rule: 宽不是错，但要有一句话的理由

Scenario: wide-glob-needs-reason

  • GIVEN切片 S1 的 owns 是一条展开出 21 个现存文件的通配
  • WHEN运行 waves；在 owns_wide 里为它写了理由后再运行；再把理由改成空串后运行；再把 owns_wide 的键换成不在 owns 里的条目后运行
  • THEN第一次以 2 退出，stderr 含该通配、21 与 owns_wide
  • AND第二次退出 0
  • AND后两次都以 2 退出，stderr 含 owns_wide

Scenario: lint-prints-glob-expansion

  • GIVEN切片 S1 的 owns 有一条展开出 21 个现存文件的通配并写了理由，另有一条字面路径
  • WHEN运行 waves
  • THEN退出 0，stderr 有一行 owns: S1 <该通配> → 21 个文件
  • AND字面路径不出现在这类行里

Scenario: approved-change-not-reddened-by-wide-rule

  • GIVEN切片 S1 的 owns 是一条展开出 21 个现存文件的通配，没有写理由；该 change 的时间线已有 approve 事件
  • WHEN运行 waves
  • THEN退出 0
  • ANDstderr 仍有该通配的展开行，并提示 owns_wide

retakeoff-landed ADDED

Requirement: 脚本列出已落地的切片

slice-gate.py landed --change-dir DIR SHALL 打印一个 JSON 对象，把每个已落地的切片 id 映射到它最新门禁行里的 commit，退出 0；计划不合法时与 lint 一样以 2 退出。一个切片已落地须同时满足：gate-report.md 里它的最新一行是绿的；那一行的 commit 能解析且是 HEAD 的祖先；从那个 commit 到当前工作树，该片的切片包与本 change 的 specs/ 没有改动，且 slices.json 里该片的条目除 owns 与 owns_wide 外与那个 commit 上的相同。没有任何门禁行时输出空对象。 Feature: 重新起飞时知道哪些切片不用再做 Rule: 门禁绿、提交在分支上、计划里这一片没再改过，三条都满足才算

Scenario: landed-lists-green-merged-slices

  • GIVEN三个切片：S1 的最新门禁行是绿的且 commit 在分支历史里；S2 的最新门禁行是红的；S3 的门禁行是绿的但 commit 不在对象库
  • WHEN运行 slice-gate.py landed
  • THEN退出 0，输出只有 S1，值是它门禁行里的 commit

Scenario: landed-excludes-slice-whose-plan-changed

  • GIVENS1、S2 的门禁行都是绿的且 commit 在分支历史里
  • WHEN改了 S1 的切片包后运行 landed；还原后只改 S2 的 owns 再运行；再改 S2 的 verify 后运行
  • THEN第一次输出没有 S1、有 S2
  • AND第二次 S1、S2 都在
  • AND第三次输出没有 S2

Requirement: 工作流不重做已落地的切片

opsx-apply 工作流 SHALL 接受可选参数 args.landed（landed 子命令的输出）：其中的切片 MUST NOT 派执行体，返回值的 slices 里记 {slice, ok: true, commit, landed: true}；评审照派，审的是 landed 给出的 commit。一个 wave 只要有已落地或本次合回的切片就 SHALL 做集成检查；整个 wave 都已落地时 integrator 的派发 MUST NOT 含 slice-gate.py merge，只运行 wave-check 并带回 check。没传 landed 时行为与没有本功能时相同。 Feature: 补完计划重新起飞，只花没落地那几片的钱 Rule: 执行体不重派，评审与集成检查不省

Scenario: workflow-skips-landed-slices

  • GIVENargs.landed 含 S1（commit 为 1…1）；另一次飞行的 args.landed 含第一个 wave 的全部切片
  • WHEN各跑一遍工作流
  • THEN第一次没有 S1 的执行体派发，有 review:S1 且 prompt 含 1…1，返回值的 slices 里 S1 带 landed: true
  • AND第二次第一个 wave 的合回 prompt 含 wave-check、不含 slice-gate.py merge，第二个 wave 的切片照常派发

slice-guards ADDED

Requirement: 检查可以声明每片门禁都运行的 slice 命令

gate.checks 的每一项 MAY 带 slice（非空字符串；缺省或 null 表示不是全局守护）。slice-gate.py lint SHALL 接受它，slice 是空白串或非字符串时 MUST 判计划不合法并点名该检查与 slice。<openspec 根>/gate-checks.json 的某项带非空 slice 时，计划里的同名检查 MUST 也带非空 slice，否则计划不合法（点名该检查与 slice）；该检查写进 gate.checks_skip 时按跳过处理。任一检查带 slice 时 plan_sha SHALL 把各检查的 [name, slice] 计入；没有检查带 slice（含显式 null）时 plan_sha MUST 与不认识该字段时相同。 Feature: 仓库把秒级的全局守护交给每一片的门禁 Rule: 守护是检查的第三条命令，沿用检查已有的清单、跳过与超时

Scenario: slice-command-is-part-of-plan-sha

### 调查二：wave 里重跑受影响测试要花多少

同一份脚本的 D 段统计各仓时间线里「增量」运行的测试秒数（wave 集成检查的测试那一半与增量 final 用同一选法）。43 次增量运行：74% 不超过 60 秒，77% 不超过 120 秒，其余全部在 500 秒以上，120–300 秒之间一次都没有。分布是两头的：要么只动了几个叶子文件，要么动到被几乎所有测试依赖的文件（本仓的 slice-gate.py：512–571 秒）。预算取 120 秒，落在两头之间的空档里。样本小（本仓带秒数的增量 final 只有 7 次，其他仓库的增量运行都不超过 37 秒），草案。

### 调查三：补 owns 之后「回一句起飞加续跑」现在通不通

结论：起飞通，续跑没有。

Goals / Non-Goals

Goals:

  • 仓库声明的全局守护在每片门禁里运行，引入问题的那一片自己就红。
  • 每个 wave 合回后有一次集成检查，红了能在下一个 wave 之前修。
  • 集成检查的成本有上限、进时间线、进成本归因。
  • owns 条数不再逼大切片放宽通配；宽通配有理由可审。
  • 补计划后的重新起飞只花没落地那几片的钱。

Non-Goals:

  • 不做 owns 的静态预测（按接口扫描替身与桩）。Q6 已定：不靠预测更准。
  • 不放宽所有权：跨片修复是集成检查红了之后的专用通道，切片执行体写 owns 之外的文件仍然是 G6。
  • 集成检查的测试那一半不支持配了分层文件的仓库（两种形态都不支持），也不支持 gate.impacted：前者要处理探针与区域，部件形态的 final 本来就恒全量；后者的选测只有仓库自己的命令知道。这些仓库的集成检查只跑守护。
  • 集成检查不写锚点、不落测试账本（D5）。
  • final 红之后的修复通道不在本 change 里（final 之后仍是评审修复与人工）。
  • 不改 MAX_SLICES / MAX_DEPTH。
  • 跨片修复执行体仍用标准档定义，不走 start / gate（与现有 Fix 阶段相同）。

Open Questions

1. 测试那一半的预算缺省 120 秒是否合适？ 依据见调查二，样本小。它决定本仓的集成检查几乎只跑守护。 2. 修不好时的停飞范围：本设计按红的种类分（守护红全停，测试红只停下游）。方案页写的是「让依赖它的下游切片停下」一种。守护红时不全停的话，后面每片的门禁都会因 G15 白跑一轮再红。 3. ship 是否该因为红的 wave 行判 draft？ 本设计判（铁律 5）。代价是多一种要人处理的 draft 原因。 4. 已落地的切片重新起飞时是否重审？ 本设计重审（不重审会丢上一次飞行的评审结论）。更省的做法是把上一次的 review-findings.json 合并进来，那要改收口步骤，留作后续。 5. 大片档 owns 上限 30、宽通配 20 都是草案，依据见调查一。 6. 本仓要不要给 schema-validate 加 slice？ 不在本 change 里做（它要改 template/openspec/ 下的仓库声明并重跑所有在途基线）。
