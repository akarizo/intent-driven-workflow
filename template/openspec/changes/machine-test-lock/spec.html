Why · 01为何而做

门禁把机器当成自己独占的：每条飞行的 baseline、final、切片 verify 都直接开跑，彼此不知道对方存在。afa 的测试分层体检（2026-11-18）取证时，18 核机器上另一条飞行正在收口，负载 37–45。后果有三个：

- 墙钟被拉长，而且拉长了多少没有记录； - 时间类判定失真——项目侧的单条 3 秒预算在负载高于核数时只能退化成告警，模板的 G10 慢单测判定在同样条件下会不会误判，没有运行样本； - 时序敏感的用例偶发红，把 MR 打成 draft。

模板里没有任何并发闸：slice-gate.py 全文没有文件锁，也不读负载。

同一份体检还指出收口的成本在留痕里是 0：final 的时间线备注没有秒数，各项检查的耗时算出来又丢了（slice-gate.py 的 _final_checks 丢弃 _run_check 返回的秒数），flight-doctor.py cost 因此报「final：全量 3 次（0.0 秒）」。最贵的一步无法归因，违背铁律 8（度量必打印）。

2026-11-18 的方案页（docs/flight-fixes-and-test-governance.html）定了两点：

- Q1 粒度：读写锁——全量类运行独占，切片 verify 之间共享。 - Q2 排队超时：放弃等待后不加锁继续跑，标记争抢，时间类判定降为警告，对错判定不变。

What · 02变更范围

  • 新增全机测试锁 template/.claude/hooks/flight-lock.py（锁逻辑全在这一个文件）：
  • 用户级目录（缺省 ~/.claude/flight-lock/，FLIGHT_LOCK_DIR 可改）下的一把读写文件锁，跨仓库、跨 worktree 共用；用系统的 flock，持有进程退出时内核自动放锁。
  • 独占与共享两种持有方式；独占方排队时后来的共享方进不来（不饿死）。
  • 持有期间给子进程带重入标记：被测进程里再调门禁不会自己等自己。
  • 持有者把自己是谁（change、命令、pid、起始时间、持有上限）写在锁目录里；排队方立刻打印在等谁，之后每 30 秒打印一次。
  • 放弃等待：最早的在世持有者持锁超过它声明的上限（缺省为它上次全量耗时的 3 倍、不低于 300 秒；没有耗时记录时 1800 秒；FLIGHT_LOCK_MAX_HOLD_SEC 可改）→ 排队方不再等，不加锁继续跑。
  • 回退：平台没有 flock、锁目录不可用、flight-lock.py 缺失或抛错 → 不加锁照跑并记「未加锁」；FLIGHT_LOCK=off 显式关闭（给已经隔离的 CI 容器用）。锁自身的任何问题都不让门禁失败。
  • CLI：flight-lock.py run <exclusive|shared> -- <命令>（门禁之外的测试运行也能排队）与 flight-lock.py status。
  • 门禁持锁（slice-gate.py 只加调用点）：
  • baseline、final 从第一条测试命令到最后一项检查整段独占；
  • 切片 gate 的 verify 到 G7 整段共享；
  • test-tiers.py run / probe 独占。
  • 争抢时降级：放弃等待后跑出来的那一次，G10 慢单测由判红降为警告并写明原因；G11 及所有对错判定不变。
  • 留痕：
  • baseline / final / gate 的输出 JSON 带 lock（方式、状态、排队秒数、起止负载、核数），时间线备注带「排队 N 秒 · 负载 起→止/核数」；
  • final 的 JSON 带 sec（gate.test 秒数与每项检查秒数），时间线备注带「测试 N 秒 · 检查 <名> N 秒」；
  • 结论词仍在备注末尾，旧时间线照常能读。
  • 成本归因与体检（flight-doctor.py）：
  • cost 认新备注：final 的秒数不再是 0，另列排队秒数；
  • doctor 新增 [checks]（某项检查耗时接近 gate.test → 疑似检查在重跑测试）与 [lock]（当前持有者）。
  • 文档：flight-runner-contract.md 新增一节；opsx-apply / opsx-propose 命令与同名 skill、test-tiers.md、README.md 各补一句排队说明。
  • 不做：
  • 共享方之间的并行度配额（已知天花板，先看上线后的负载数字）；
  • 逐用例耗时账本、分层预算与豁免（另一个 change）；
  • baseline 回写 slices.json、契约未接的表态（另一个 change）；
  • 多用户共用一台机器时跨用户排队（锁在用户级目录）。
代码：新增 template/.claude/hooks/flight-lock.py；改 template/.claude/hooks/slice-gate.py（调用点、输出字段、备注、G10 降级）、test-tiers.py（run / probe 持锁）、flight-doctor.py（cost 解析、doctor 两节）。测试：新增 tests/test_flight_lock.py、tests/lock_helpers.py、tests/test_gate_lock.py、tests/test_gate_cost_note.py、tests/test_flight_doctor_lock.py、tests/test_lock_docs.py；tests/conftest.py 给整个套件指定临时锁目录（本仓测试会在子进程里跑门禁，不能去排真实的全机锁）。文档：template/.claude/flight-runner-contract.md、template/.claude/commands/{opsx-apply,opsx-propose,test-tiers}.md、template/.claude/skills/{openspec-apply-change,openspec-propose}/SKILL.md、README.md。ADR：新增 template/openspec/adr/DRAFT-machine-wide-test-lock.md。行为变化：同一用户在同一台机器上的多条飞行，全量类运行改为排队；FLIGHT_LOCK=off 恢复原行为。输出 JSON 与时间线只增不改；flight-doctor.py cost --json 的新数据放在新的顶层键里，已有键的形状不变。下游：已安装的仓库跑 ./install.sh --upgrade 拿到新 hook；项目侧缓存键按契约第 4 节已须剔除 FLIGHT_ 前缀，新增的 FLIGHT_LOCK_* 变量不需要额外处理。与方案页的两处出入（详见 design D5、D6）：放弃等待的上限按持有者算而不是按排队方自己算；FLIGHT_LOCK=off 与平台不支持时 G10 不降级。

Specs · 04行为规范 (Gherkin)

machine-test-lock ADDED

Requirement: 全机测试锁区分独占与共享

flight-lock.py SHALL 在锁目录（缺省 ~/.claude/flight-lock/，环境变量 FLIGHT_LOCK_DIR 可改）下提供一把跨仓库、跨 worktree 共用的读写锁：独占持有与任何其他持有互斥，共享持有之间可以并存。有独占方在排队时，后来的共享方 MUST NOT 先于它拿到锁。持有者 SHALL 把方式、change、命令标签、pid 与起始时间写在锁目录里；排队方 SHALL 在第一次没拿到锁时立刻往 stderr 打印一行含「排队中」与持有者标签的提示，之后每 30 秒一行。持有进程退出（含被杀）后锁 MUST 自动释放。flight-lock.py run <exclusive|shared> -- <命令> SHALL 取锁后运行命令、以命令的退出码退出，并在 stderr 末尾打印一行 flight-lock: <JSON> 给出本次的方式、状态与排队秒数；flight-lock.py status --json SHALL 列出在世的持有者。 Feature: 一台机器同一时刻只有一套满核并行的测试 Rule: 独占排队、共享并存；锁跟着门禁进程走，进程没了锁就没了

Scenario: exclusive-holders-mutually-exclude

  • GIVEN进程 A 经 flight-lock.py run exclusive 持有锁，命令尚未结束
  • WHEN进程 B 以同一锁目录运行 flight-lock.py run exclusive -- <命令>
  • THENB 的 stderr 出现含「排队中」与 A 的标签的一行，B 的命令没有开始
  • ANDA 结束后 B 的命令才运行，B 以命令的退出码退出
  • ANDB 的 flight-lock: 行里状态为 held、排队秒数大于 0

Scenario: shared-holders-run-together

  • GIVEN进程 A 经 flight-lock.py run shared 持有锁，命令尚未结束
  • WHEN进程 B 以同一锁目录运行 flight-lock.py run shared -- <命令>
  • THENA 还没结束时 B 的命令已经开始运行

Scenario: exclusive-waiter-blocks-new-shared

  • GIVEN进程 A 持有共享锁；进程 X 请求独占并已在排队
  • WHEN进程 C 请求共享
  • THENC 的命令没有开始，C 的 stderr 出现「排队中」
  • ANDA 结束后 X 的命令先运行；X 结束后 C 的命令才运行

Scenario: killed-holder-releases-lock

  • GIVEN进程 A 持有独占锁，进程 B 请求独占并在排队
  • WHENA 的 flight-lock.py 进程被 SIGKILL 杀掉
  • THENB 的命令随即运行
  • ANDflight-lock.py status --json 不再列出 A

Scenario: status-lists-live-holders

  • GIVEN进程 A 以 --change demo --label "final gate" 持有独占锁
  • WHEN运行 flight-lock.py status --json
  • THEN输出的持有者列表恰有一项，方式为 exclusive，change 为 demo，标签为 final gate，pid 为 A 的 pid

Requirement: 持锁期间的子进程不再排队

持有锁的进程 SHALL 给它启动的子进程带上重入标记（环境变量 FLIGHT_LOCK_HELD，含锁目录）；带着同一锁目录的重入标记请求锁的进程 MUST NOT 等待，状态记为 nested。标记里的锁目录与当前锁目录不同 → 不算重入，照常取锁。本仓测试套件 SHALL 经 tests/conftest.py 把 FLIGHT_LOCK_DIR 指到本次会话的临时目录，使测试里启动的门禁不去排用户级目录里的锁。 Feature: 被测进程里再调门禁不会自己等自己 Rule: 重入只认同一把锁；测试套件用自己的锁目录

Scenario: nested-run-does-not-wait

  • GIVEN外层 flight-lock.py run exclusive -- <命令>，其命令是以同一锁目录再次运行 flight-lock.py run exclusive -- <内层命令>
  • WHEN外层运行
  • THEN内层命令运行完成，外层以 0 退出
  • AND内层的 flight-lock: 行里状态为 nested、排队秒数为 0

Scenario: test-suite-uses-isolated-lock-dir

  • GIVEN本仓的 pytest 会话
  • WHEN测试读取环境变量 FLIGHT_LOCK_DIR
  • THEN它指向一个存在的目录，且不在用户主目录的 .claude 之下

Requirement: 锁不可用或持有者停滞时不加锁继续

排队方 SHALL 在最早的在世持有者持锁时间超过该持有者声明的上限时放弃等待，状态记为 timeout，随后不加锁运行。上限由持有者在取锁时声明：设了 FLIGHT_LOCK_MAX_HOLD_SEC 取它；否则为持有者上次全量耗时的 3 倍且不低于 300 秒；没有耗时记录时为 1800 秒。FLIGHT_LOCK=off 时 MUST NOT 取锁，状态记为 off。平台没有 flock、锁目录不可创建或不可写时状态记为 unavailable 并带原因。这三种状态下命令 MUST 照常运行，退出码 MUST 只取决于命令本身。 Feature: 锁坏了或有人占着不放，门禁照样能跑 Rule: 锁自身的任何问题都不让命令失败；没拿到锁要留下原因

Scenario: waiter-gives-up-on-stalled-holder

  • GIVEN进程 A 以 FLIGHT_LOCK_MAX_HOLD_SEC=0.3 持有独占锁且一直不结束
  • WHEN进程 B 以同一锁目录运行 flight-lock.py run exclusive -- <以 7 退出的命令>
  • THENB 在 A 仍持有时运行了它的命令，并以 7 退出
  • ANDB 的 flight-lock: 行里状态为 timeout，原因点名 A 的标签

Scenario: lock-off-or-unavailable-runs-unlocked

  • GIVEN进程 A 持有独占锁
  • WHEN进程 B 带 FLIGHT_LOCK=off 运行 flight-lock.py run exclusive -- <命令>；另一次把 FLIGHT_LOCK_DIR 指到一个普通文件之下的路径再运行
  • THEN两次的命令都立即运行、以命令的退出码退出
  • AND第一次状态为 off；第二次状态为 unavailable 且原因非空

Requirement: 门禁各命令按方式持锁

slice-gate.py baseline 与 final SHALL 在运行第一条测试命令之前取独占锁、在最后一项检查结束之后释放（同树沿用的 final 不运行任何测试，不取锁）；slice-gate.py gate SHALL 从运行 verify 之前到 G7 结束之后持共享锁；test-tiers.py run 与 probe SHALL 整个运行期间持独占锁。这些命令的输出 JSON（baseline 另写进 gate-baseline.json）SHALL 带 lock 字段：mode、state、waited（排队秒数）、why、load（起止负载，取不到为 null）、cores。flight-lock.py 缺失或加载失败时门禁 MUST 照常运行，lock.state 为 unavailable。 Feature: 全量类运行排队，切片 verify 并行 Rule: 整段测量只排一次队；锁只加在调用点，判定逻辑不动

Scenario: baseline-and-final-hold-exclusive-lock

  • GIVEN一个有计划、测试全绿的仓库，锁目录里没有其他持有者
  • WHEN依次运行 slice-gate.py baseline 与 slice-gate.py final
  • THEN两次输出 JSON 的 lock.mode 都是 exclusive、lock.state 都是 held、lock.waited 是数字
  • ANDgate-baseline.json 里有同样的 lock 字段

Scenario: slice-gate-holds-shared-lock

  • GIVEN同一个仓库，切片 S1 已 start
  • WHEN运行 slice-gate.py gate S1
  • THEN输出 JSON 的 lock.mode 是 shared、lock.state 是 held

Scenario: final-queues-behind-exclusive-holder

  • GIVEN另一个进程在同一锁目录持有独占锁
  • WHEN运行 slice-gate.py final
  • THENfinal 的 stderr 出现「排队中」，持有者结束之前 final 不结束
  • AND持有者结束后 final 以 0 退出，lock.waited 大于 0

Scenario: gate-runs-when-lock-module-missing

  • GIVEN一份不含 flight-lock.py 的 hooks 目录副本
  • WHEN用副本里的 slice-gate.py 运行 baseline
  • THENbaseline 以 0 退出，lock.state 是 unavailable

Scenario: test-tiers-run-and-probe-hold-exclusive-lock

  • GIVEN一个有分层文件的仓库，另一个进程在同一锁目录持有独占锁
  • WHEN分别运行 test-tiers.py run unit 与 test-tiers.py probe
  • THEN两次的 stderr 都出现「排队中」，持有者结束之前都不结束
  • AND持有者结束后两次都以 0 退出

Requirement: 争抢时时间类判定降为警告

lock.state 为 timeout 的 baseline 或 final 里，G10 慢单测 SHALL 由失败降为警告，警告文字 SHALL 保留原判定内容并写明因放弃等待而降级；G11 及其他判定 MUST 不变。lock.state 为 held、nested、off 或 unavailable 时 G10 MUST 照常判定。 Feature: 只有确知有人同时在跑的那一次，秒数才不作数 Rule: 降级只针对时间；关掉锁或平台不支持不等于放宽

Scenario: contended-run-downgrades-slow-unit-verdict

  • GIVEN分层文件合法、单元层有一个每次睡 3.1 秒的纯函数用例；另一个进程以 FLIGHT_LOCK_MAX_HOLD_SEC=0.3 持有独占锁且不结束
  • WHEN以同一锁目录运行 slice-gate.py baseline
  • THENbaseline 以 0 退出，lock.state 是 timeout
  • ANDreasons 里没有 G10；warnings 里有一条同时含 G10、该用例的 id 与「降为警告」

Scenario: lock-off-keeps-slow-unit-verdict

  • GIVEN同样的仓库
  • WHEN带 FLIGHT_LOCK=off 运行 slice-gate.py baseline
  • THENlock.state 是 off，baseline 以非 0 退出，reasons 里有一条以 G10 开头并点名该用例

Requirement: 时间线记录排队、负载与收口各项耗时

baseline、final、gate 的时间线备注 SHALL 带锁片段：持锁时为「排队 <秒>s」，放弃等待时为「排队 <秒>s 后放弃（<原因>）」，未加锁时为「未加锁（<原因>）」，重入时为「重入」；取得到负载时其后接「 · 负载 <起>→<止>/<核数>」。final 实际运行了 gate.test（全量、增量或 gate.impacted）时，输出 JSON SHALL 带 sec.test，备注 SHALL 带「测试 <秒>s」；运行了检查时 JSON SHALL 带 sec.checks（{检查名: 秒}），备注 SHALL 带「检查 <名> <秒>s」，多项以「 / 」分隔。final 与 gate 备注的结论词（ok / red）MUST 仍在末尾，gate 备注 MUST 仍以切片 id 开头，已有的「全量（…）」「增量（…）」「单元 …s · 集成 …s」文字 MUST 不变。 Feature: 慢了能看出慢在排队、测试还是检查 Rule: 备注只增不改；旧的解析方照常工作

Scenario: timeline-records-wait-and-load

  • GIVEN一个有计划、测试全绿的仓库，切片 S1 已 start
  • WHEN依次运行 baseline、gate S1、final
  • THEN三条时间线备注都匹配「排队 <数字>s」
  • ANDfinal 的备注以 ok 结尾；gate 的备注以 S1 开头、以 ok 或 red 结尾
  • AND平台取得到负载时，三条备注都含「负载 」

Scenario: final-note-records-test-and-check-seconds

  • GIVEN计划配了一项检查 probe-check，baseline 已绿，之后有一处代码改动
  • WHEN运行 slice-gate.py final
  • THEN输出 JSON 的 sec.test 是数字，sec.checks 恰含 probe-check 且值是数字
  • ANDfinal 的时间线备注匹配「测试 <数字>s」与「检查 probe-check <数字>s」，并以 ok 结尾

Requirement: 成本归因与体检读得到排队和收口耗时

flight-doctor.py cost SHALL 从 final 备注的「测试 <秒>s」取该次运行的秒数、从 baseline 与 final 备注的「排队 <秒>s」取排队秒数：全量 final 的秒数计入 final.full_sec 与对应 full_runs 项的 sec；--json 另给顶层 wait_sec（{"baseline": 秒, "final": 秒}），文本输出在各事件行写出排队秒数。baseline 与 final 两个对象已有的键 MUST 不增不减；没有这些片段的旧时间线 MUST 得到与改动前相同的结果。flight-doctor.py doctor SHALL 新增两节：[checks] 逐个在途 change 读最近一条 final 备注，某项检查的秒数不低于 10 秒且不低于「测试」秒数的一半时点名该 change 与检查并写明疑似在重跑测试；[lock] 列出当前在世的持有者（方式、change、标签、已持有秒数），没有时写「空闲」，FLIGHT_LOCK=off 时写明已关闭。两个子命令仍恒以 0 退出。 Feature: 收口的成本不再是 0，重跑测试的检查会被点名 Rule: 只读、只报告、不阻断

Scenario: cost-reads-final-seconds-and-wait

  • GIVEN一份时间线：一条旧格式的全量 baseline、一条带「排队 12.5s」的全量 baseline、一条带「测试 524.3s」与「排队 212.0s」的全量 final、一条带「测试 8.0s」的增量 final
  • WHEN运行 flight-doctor.py cost --json 与不带 --json 的 cost
  • THENfinal.full_sec 等于 524.3，对应 full_runs 项的 sec 等于 524.3

Design · 05技术设计

Context

现状（读 template/.claude/hooks/ 现行代码，main b7be9ed）：

  • slice-gate.py 的三个测量命令各自直接开跑，没有任何互斥，也不读负载：
  • cmd_baseline：复用判定里的补跑 → run_test_gate(gate.test) → lint / typecheck → 每片 verify → 已选区域 → 检查；
  • cmd_final：G7 实跑 scenario → lint / typecheck → gate.test（全量 / 增量 / gate.impacted）→ 区域 → 检查；
  • cmd_gate：该片 verify → lint / typecheck → G7。
  • test-tiers.py run / probe 同样直接跑单元层。
  • 时间线备注的现行格式与解析方：
  • baseline：exit 0, 529.9s ok；全量：<原因>；verify 推导 N 片，或 增量（…） ok；
  • final：[全量（原因）|增量（…）] [单元 Xs · 集成 Ys] ok|red，结论词在末尾；
  • gate：S1 [单元 Xs · 集成 Ys] ok|red；
  • timeline.py report 取 gate 备注的第一个词作切片 id、按 endswith(" ok") / endswith("red") 取结论；
  • flight-doctor.py 的 parse_note 按「全量：」「全量（」「增量」「同树沿用」分类，秒数只认 baseline 的 exit N, Xs（SEC_RE）；final 没有秒数，cost 里恒为 0；
  • tests/test_flight_doctor.py 断言 cost --json 的 baseline 对象整体相等，所以这两个对象不能加键。
  • _final_checks 调 _run_check 拿到每项检查的秒数后丢弃（rc, out, _, timed_out）；baseline 的检查秒数已记在 gate-baseline.json。
  • 本仓测试套件大量以子进程运行 slice-gate.py baseline / final / gate（tests/conftest.py 的 run_hook 把 os.environ 原样传下去）。门禁一旦取用户级目录里的锁，本仓的测试就会去排真实飞行的队。
  • 门禁给子进程的环境来自 dict(os.environ)；_drop_inherited 只清 FLIGHT_ENV 名单里的变量。Python 打开的文件描述符缺省不被子进程继承。

已定决策（2026-11-18，方案页 docs/flight-fixes-and-test-governance.html Q1、Q2，用户回复「按推荐」）：

  • Q1：读写锁——全量类运行独占，切片 verify 共享。
  • Q2：排队超时后不加锁继续跑，标记争抢，时间类判定降为警告。

在役 ADR：

  • DRAFT-gate-test-result-handoff-and-runner-contract：FLIGHT_ / GATE_ 前缀是每次运行都变的变量，项目缓存键须剔除，白名单重建环境时须放行 FLIGHT_ 前缀。本设计新增的 FLIGHT_LOCK_* 沿用这条约定，不偏离。
  • DRAFT-test-tiers-unit-baseline-by-audit-probe：G10 慢候选单独重跑确认。本设计不改这套判定，只在确知争抢的那一次把结论降级。
  • DRAFT-gate-evidence-not-self-reported：留痕由脚本写。排队与耗时同样由脚本写进时间线。
  • 没有需要 supersede 的 ADR。

``` C4 · 组件图（轻量 C4 风格；★ 新增，◆ 修改）

飞行 A（仓库 X） 飞行 B（仓库 Y） 人 / CI ◆ slice-gate.py ◆ slice-gate.py flight-lock.py run … -- pytest baseline / final ─独占─┐ gate S3 ─共享─┐ │独占 / 共享 ◆ test-tiers.py run ─独占┤ │ │ ▼ ▼ ▼ ★ flight-lock.py（acquire / release / holders / note） │ flock │ 读写 ▼ ▼ ~/.claude/flight-lock/gate.lock · main.lock holders/<pid>.json │ lock 信息 ──────┴──▶ ◆ 输出 JSON 的 lock / sec ──▶ ◆ timeline.md 备注 │ 读 ▼ ◆ flight-doctor.py cost（排队、final 秒数）· doctor [checks] [lock] ```

  • 边界：锁逻辑只在 flight-lock.py；slice-gate.py 与 test-tiers.py 只有「取锁 / 放锁 / 把 info 写进输出」三类调用点。
  • 强制力：锁是协作式的，只约束经门禁或 flight-lock.py run 启动的运行；人直接敲 pytest 不受约束。
  • 假设：同一个用户在一台机器上跑多条飞行（体检取证的情形）；多用户共用机器不在范围。

Goals / Non-Goals

Goals：

  • 同一用户、同一台机器上，同一时刻至多一套全量类测试在跑；同一 wave 的切片 verify 仍然并行。
  • 每次门禁运行留下排队秒数、起止负载；final 留下 gate.test 与每项检查的秒数；cost 据此归因。
  • 锁出任何问题门禁照跑，并留下「这次没拿到锁」的原因。
  • 确知争抢的那一次，时间类判定不再判红。

Non-Goals：

  • 共享方之间的并行度配额。
  • 先来先到的严格公平。
  • 多用户、多机、网络文件系统上的互斥。
  • 逐用例耗时账本、分层预算（另一个 change）；baseline 回写 slices.json（另一个 change）。
  • 给 gate.test 加运行超时。

Decisions

共享方

取闸口（独占）→ 取主锁（共享）→ 放闸口。

独占方

取闸口（独占）并一直拿着→ 取主锁（独占）→ 放闸口。

独占方在等主锁时握着闸口，后来的共享方过不了闸口，所以不会被源源不断的共享方饿死。
为什么用 flock

进程退出（含 SIGKILL）时内核放锁，没有「死锁文件」要清；标准库 fcntl 就有，零依赖。

否决
pid 文件 + 轮询存活

进程崩溃后要靠别人判死，判错就双持或永久占用；

单把 flock 直接用 LOCK_SH / LOCK_EX

BSD 语义不保证写方不饿死；

信号量文件（N 个槽位）

能做配额，但「全量独占」要一次拿满 N 个槽，死锁与部分持有的处理都更复杂；配额本身是 Non-Goal。

描述符不外泄

两个锁文件用 os.open 打开，Python 缺省不可继承，被测子进程拿不到这把锁。门禁进程一退出锁就释放，哪怕它起的测试进程还活着。

为什么

排队期间要做三件事——第一次失败立刻打印在等谁、每 30 秒再打印、判断持有者是否停滞（D5）。阻塞调用做不了。

代价

不保证先来先到（谁先轮询到谁拿）。写进 ADR 的已知天花板。

baseline

写完运行标记之后取锁，到检查全部结束、结束快照之前放锁。

final

同树沿用判定之后（沿用就不取锁）、G7 实跑之前取锁，到检查全部结束放锁。

gate

verify 之前取锁，G7 之后放锁。

test-tiers.py run / probe

整个子命令。

为什么不逐条命令
一次 final 有 G7、gate.test、若干区域、若干检查，逐条取锁要重新排 5–8 次队，总等待不可预期，时间线也没法用一个数字说明；
baseline 有「运行期间的改动」检测（开跑快照与结束快照之差），拉长墙钟只会增加误报；
整段持有时，一次测量内部的各步骤彼此不受别的飞行干扰，秒数才可比。
代价

lint / typecheck 夹在中间也占着独占锁。它们通常远短于测试；真成问题再拆。

baseline 的取锁点为什么在运行标记之后

preflight 靠运行标记分辨「还在跑」与「缺基线」，排队期间也应该报「还在跑」。开跑快照仍在运行标记之前取（保持 unified-test-result-reuse design D12：快照失败不碰现有基线）；排队期间的改动会被结束快照比出来、判基线无效，这是对的。

为什么带目录

本仓的测试套件会把 FLIGHT_LOCK_DIR 指到会话临时目录（D9）。外层门禁（真实锁目录）下跑的测试再起门禁时，应该在临时目录里真正取锁并判定，而不是被外层标记短路。

不做祖先进程检查

包装脚本若按白名单重建环境又没放行 FLIGHT_ 前缀，被测进程里再调门禁会排到持有上限后不加锁继续。契约第 1 节已要求放行 FLIGHT_ 前缀；文档再点名一次。

持有者取锁时在 holders/<pid>.json 里声明自己的持有上限 cap_sec
设了 FLIGHT_LOCK_MAX_HOLD_SEC → 取它；
否则有上次全量耗时 → max(300, 3 × 耗时)；
否则 1800。
排队方每次轮询读在世的持有者

最早的那个已持有超过它的 cap_sec → 放弃，状态 timeout，why 写「<change> · <标签> 已持有 N 秒，超过上限 M 秒」。

读不到任何持有者信息（刚取到锁还没写文件的瞬间）→ 按排队方自己的同一公式兜底。
为什么改
按排队方算，小仓库排在大仓库后面必然超时

本仓全量约 5 分钟，afa 约 10 分钟，再排两条 afa 的飞行就是 20 分钟——正常排队被当成超时，一超时就并跑，等于没锁；

方案页 Q2 的前提写的是「超时只对应持有者真的跑了很久」，按持有者判才是这句话的字面意思；
队伍里每换一个持有者，时钟自然重置，排多久都不算超时，只有某一个持有者卡住才算。
上次全量耗时从哪来

本 change gate-baseline.json 的 test.sec（baseline 命令读覆盖前的旧基线）；读不到再退 slices.json 的 gate.full_suite_sec。另一个 change 要把后者挪走，先读基线使两边都成立。

数字都是草案

3 倍、300 秒、1800 秒没有数据支撑，上线后看时间线里的排队秒数再调。

为什么
timeout 是确知有别的运行同时在跑，秒数必然不可信；
unavailable（没有 flock 的平台、锁目录不可写）下如果也降级，这些环境里 G10 就永远不会红——相对今天是放宽，违背「门禁只能加严」；今天的行为（带单独重跑确认的判定）应当保持；
off 是人显式声明「这里已经隔离」（CI 容器），正是最该照常判的地方；如果 off 就降级，CI 里 G10 永不判红。
降级的形状

把以 G10 slow unit test 开头的失败项挪进警告，原文保留，末尾加「（排队放弃后未持锁，时间类判定降为警告：<why>）」。G11（纯度）与差分判定不动。

实现位置

slice-gate.py 一个纯函数处理 (failed, warnings, lock_info)，在 baseline 与 final 取得 G10 / G11 结论的各处调用（简写形态的全量与增量、部件形态的 _baseline_parts / _final_parts）。

flight-lock.py run <exclusive|shared> [--change NAME] [--label TEXT] [--expect-sec N] -- CMD [ARG…]

取锁 → 不经 shell 运行 CMD → 放锁 → stderr 末行 flight-lock: <info 的 JSON> → 以 CMD 的退出码退出（CMD 起不来为 127）。

flight-lock.py status [--json]

holders() 的内容，另带 dir 与 enabled；恒退出 0。

final

[全量（…）|增量（…）] [单元 Xs · 集成 Ys] [测试 Xs] [检查 a Xs / b Ys] <锁片段> ok|red。新片段之间、以及与前面的分层片段之间用 · 连接；与「全量（…）」「增量（…）」之间仍是一个空格；结论词前一个空格。同树沿用的备注不变。

gate

S1 [单元 Xs · 集成 Ys] <锁片段> ok|red，连接规则同上。integrator 的 record 写回分支的那一行不变（见 Risks）。

baseline

现有三种备注末尾各接 ；<锁片段>。

例

全量（没有可用锚点） 测试 524.3s · 检查 ratchet 3.1s / linkage 2.4s · 排队 212.0s · 负载 2.9→17.8/18 ok。

三个命令都加 lock（即 info）；baseline 同时写进 gate-baseline.json（入池与锚点只挑固定键，不带它）。
final 加 sec

{"test": 秒 | null, "checks": {名: 秒}}。test 是 gate.test 这一步的墙钟（全量、增量重跑或 gate.impacted，不含区域）；没跑到（G7 红、scope 复核未过、部件形态）为 null，此时备注没有「测试」片段。checks 只含本次实际运行的检查。

测试 ([\d.]+)s → 该 final 的秒数；全量时计入 final.full_sec 与 full_runs[].sec；
排队 ([\d.]+)s → 排队秒数，按事件累加到新的顶层键 wait_sec；
检查 (.+?)(?= · | ok$| red$) 再按 / 拆成「名 秒」；
没有这些片段的行按旧逻辑，结果与改动前相同；baseline / final 两个对象不加键（现有测试整体断言）。
为什么不用 FLIGHT_LOCK=off

关掉之后门禁输出里就没有 held 状态可测；而且套件应当走真实的取锁路径。

为什么够用

套件里的门禁子进程在临时目录取锁，串行执行、互不等待；外层若有真实门禁持锁，重入标记里的目录不同（D4），不会短路。

专测并发的用例各自再建锁目录，经环境显式传给每个子进程。
[checks]

每个在途 change 取时间线里最近一条带「测试」片段的 final 备注；某项检查 ≥ 10 秒且 ≥ 测试秒数的一半 → 一行点名 change、检查、两个秒数，写「疑似检查在重跑测试，改读 $GATE_TEST_RESULT（契约第 3 节）」。没有命中写「无」。阈值是草案。

[lock]

锁目录、是否启用、holders()；没有持有者写「空闲」；FLIGHT_LOCK=off 写「已关闭（FLIGHT_LOCK=off）」。flight-lock.py 加载失败写原因。

Risks / Trade-offs

[共享方之间仍可能超订] 五个切片同时 verify 且各自满核并行 → 不做配额；时间线里有负载数字，上线后据此决定。
[不保证先来先到] 轮询取锁，后到的可能先拿 → 独占方握着闸口，最多被一个后到的独占方插队；写进 ADR。
[锁只在用户级目录] 多用户共用机器互不可见；主目录在网络文件系统上时 flock 可能不可靠 → 文档写明可用 FLIGHT_LOCK_DIR 指到本机路径。
[包装脚本剥掉 FLIGHT_LOCK_HELD 且被测进程里再调门禁] → 内层排到持有上限后不加锁继续；契约文档点名这个变量须放行。
[baseline 排队期间运行标记显示「仍在跑」] 起始时间早于实际开跑 → 排队提示打在 baseline 的 stderr 里；preflight 的文案不改。
[切片 gate 的排队秒数到不了分支的时间线] gate 在临时 worktree 里跑，integrator 用 record --json 写回的只有固定字段 → 本 change 不改工作流脚本与 record

切片 gate 的排队信息只在它的输出 JSON（lock）与临时 worktree 的时间线里，分支上的 cost 只统计 baseline 与 final 的排队。要带回分支得给工作流的门禁结构加字段，留给后续 change。

[并发测试的时序] 用「开始文件 / 放行文件 / stderr 里的排队提示」作同步点，只有「持有者超过上限」一条依赖真实时间（0.3 秒上限，轮询 0.2 秒）→ 断言留足余量（等待上限 10 秒）。
[gate.test 挂死会占着锁] 本 change 不给 gate.test 加超时 → 排队方按 D5 放弃并留痕，不会被永久卡住。
[与并行中的 plan-hygiene change 冲突] 两边都改 slice-gate.py 的 baseline 段与 flight-doctor.py → 后合的那个 PR 预合并 main 时解冲突；本设计不依赖 gate.full_suite_sec 的去留（D5）。
