# S6 · 文档：全机测试锁的说明

## 做什么

把全机测试锁写进随模板下发的文档：运行器契约新增一节；`opsx-apply` / `opsx-propose` 的命令与同名 skill、`test-tiers.md`、`README.md` 各补一句排队说明。规则原文见 `specs/machine-test-lock/spec.md` 最后一条 Requirement。

只加文字，原有句子不改、不挪：这些文件被十几个文档测试钉着（见 verify）。命令与同名 skill 同改。

## 依赖的接口

无代码依赖。行为以 S1（锁）、S3（门禁持锁、降级、留痕）、S5（test-tiers 持锁）为准，写文档时对照 `design.md` D1–D8；环境变量与状态名照抄，不要另起名字。

## 怎么做

TDD：`tests/test_lock_docs.py` 的 2 条骨架现在是红的。

1. **`template/.claude/flight-runner-contract.md`**：在「## 7. 接入步骤」之后新增「## 8. 全机测试锁」（标题里必须有「全机测试锁」四个字；第 1–7 节的标题与编号不动）。这一节写清：
   - 是什么：用户级目录（缺省 `~/.claude/flight-lock/`）下的一把读写锁，跨仓库、跨 worktree 共用，持有进程退出即释放；
   - 谁用哪种：**独占**——`baseline`、`final`、`test-tiers.py run` / `probe`；**共享**——切片 `gate`（verify 到 G7）；独占方排队时后来的共享方不插队；
   - 环境变量表：`FLIGHT_LOCK=off`（关闭）、`FLIGHT_LOCK_DIR`（锁目录，主目录在网络盘时指到本机路径）、`FLIGHT_LOCK_MAX_HOLD_SEC`（持有上限：某次运行持锁超过它，排队方不再等；缺省为上次全量耗时的 3 倍、不低于 300 秒，没有记录时 1800 秒）、`FLIGHT_LOCK_HELD`（重入标记，门禁自己设；包装脚本按白名单重建环境时须随 `FLIGHT_` 前缀放行，否则被测进程里再调门禁会排到持有上限）；
   - CI：容器已经隔离时设 `FLIGHT_LOCK=off`；
   - 门禁之外的测试运行想排队：`python3 .claude/hooks/flight-lock.py run exclusive -- <命令>`；看谁在占：`flight-lock.py status`；
   - 放弃等待（`timeout`）的那一次不加锁继续跑，G10 慢单测降为警告；`off` 与平台不支持（`unavailable`）时 G10 照常判；
   - 留痕：输出 JSON 的 `lock`、时间线的「排队 Ns · 负载 起→止/核数」、final 的「测试 Ns · 检查 <名> Ns」；`flight-doctor.py cost` 与 `doctor` 的 `[checks]` `[lock]`；
   - 已知限制：共享方之间不限流、不保证先来先到、多用户之间互不可见。
2. **四个流程文档**（`commands/opsx-apply.md`、`commands/opsx-propose.md`、`skills/openspec-apply-change/SKILL.md`、`skills/openspec-propose/SKILL.md`）：各加一行（同一行里同时出现「全机测试锁」与「排队」），放在各自讲 baseline 后台运行 / 测试成本预告的段落附近。例：
   > baseline、final 与切片门禁会排队等全机测试锁（同一台机器同一时刻只有一套全量在跑）；stderr 里的「排队中」不是卡死，时间线会记下排队秒数，详见 `.claude/flight-runner-contract.md` 第 8 节。

   命令与同名 skill 用同一句话。
3. **`commands/test-tiers.md`**：在「驱动命令」一节加一行：`run` 与 `probe` 运行期间持全机测试锁（独占），有别的全量在跑时会排队；指向契约第 8 节。
4. **`README.md`**：在讲门禁 / 测试成本的那一组条目里（现有「依赖图未测」一条附近）加一条「全机测试锁」：一句话说明独占与共享、会排队、`FLIGHT_LOCK=off`，指向 `flight-lock.py` 与契约文档。目录树里 `hooks/` 一行的注释不必改。
5. 写完跑一遍 verify；文档测试里有钉句子的断言，红了说明动到了原有文字，恢复原文，把新句子换个位置。
