Why · 01为何而做

PR 送出前后各有一个收尾动作没有闭环。两处都在 2026-11-07 至 11-09 的 submodule-aware-flight 中实际出过问题。

合并后清理靠手写命令，判错就失败或丢数据。 - PR #11 合并后要清理 9 个 worktree、9 个分支。按人工给出的命令清单执行，6 个已合并分支的 git branch -d 报 not fully merged。 - 根因：这些分支没有 upstream。git branch -d 此时按本地 HEAD 判断是否已合并，而本地 main 还没同步 origin/main。 - 要不要 --force、要不要 -D，都靠人和模型临场判断。openspec-git-discipline 只写了「由人确认后在主仓库根手动 git worktree remove」。 - 本仓库刚支持 submodule，又多了一处隐患（2026-11-09 用玩具仓实测）： - 在 linked worktree 里初始化的子仓，仓库本体在 <主仓>/.git/worktrees/<id>/modules/<P>； - 不加 --force 时，git worktree remove 拒绝删除含子仓的 worktree； - 加 --force 会连同这个子仓库一起删掉，其中未推送的子仓提交随之丢失，主 checkout 的子仓和子仓远端都没有它。

知识沉淀依赖人记得跑 /claudemd-commit，反复出现的错误没有去处。 - /pr-ship 的「典型使用顺序」要求先跑 /claudemd-commit，但它是一个独立命令，要逐条问用户确认，与飞行收口「全程不问询」接不上。submodule-aware-flight 就跳过了它。 - 本轮有两条反复出现的错误： - 自举飞行时文档切片先合回，导致后续两次门禁红； - 合并后清理 -d 失败。 - 这两条只记进了个人 auto-memory，模板的载体体系里没有。 - /claudemd-commit 在 2026-08-25 废除了 C 类「本轮发现的工程偏差」，理由是它没有上限。结果连有证据、反复出现的错误也只能进 backlog。

What · 02变更范围

  • 新增判定脚本 template/.claude/hooks/merged-cleanup.py（零 token，plan / apply 两个子命令）。它在主 worktree 根运行，检测以下四类对象：
  • 所有 linked worktree；
  • 本地 worktree-* 分支；
  • 远端 <remote>/worktree-* 分支；
  • 已落地 change 留下的 refs/flight/<change>/* 快照。
  • 合并状态：
  • ancestor：tip 是 target 的祖先；
  • content：squash 等方式合入，merge-tree 结果与 target 树相同；
  • fresh：tip 落在 target 主线上，没有独有提交；
  • unmerged：未合并。
  • 是否需要 --force，及原因：
  • 只剩飞行记录（timeline.md / gate-report.md / evidence.log / .openspec-slice）；
  • 含已填充的子仓；
  • 有其他未提交改动。
  • 执行档位：safe / manual / keep。
  • 新增命令 /clean-after-merged：
  • 先跑 plan --markdown 展示结果，再跑 apply 执行 safe 档：
  • fetch --prune；
  • --ff-only 同步 target；
  • worktree remove，脚本判定后可带 --force；
  • worktree prune，包括家子仓里借出的 linked worktree；
  • 删除已落地 change 的 refs/flight/*；
  • branch -d。
  • manual 档原样输出成命令清单交给用户执行，包括：
  • branch -D；
  • push --delete；
  • 含其他改动、被锁定、位于仓库约定目录之外的 worktree。
  • 铁律 6 加一条授权例外（根 CLAUDE.md 与 template/CLAUDE.md.snippet）：显式运行 /clean-after-merged = 授权它文档内的 safe 档。branch -D 与 push --delete 仍只交人执行。openspec-git-discipline 的清理条款同步改写。
  • /claudemd-commit 改为自动识别与录入：
  • 只有「与已有认知有较大差异」的条目才和用户对齐。较大差异包括：删除或反转既有规则、与既有条目或在役 ADR 矛盾、改动铁律或核心约束段、写到仓库外的全局 ~/.claude/CLAUDE.md。
  • 新增有上限的 E 类「反复错误」：本轮至少出现 2 次，且每次都有证据指针才收。证据可以是门禁红记录、review-findings.json 条目、fix commit，或用户原话纠正。
  • E 类能写成测试、lint 或 hook 的，进 backlog 立项，常驻层只留一行过渡条目。只出现 1 次的照旧进 backlog。
  • C 类维持废除。
  • /pr-ship 新增 step 2b「记忆层沉淀」（不问询）：
  • 巡视三处来源：本会话对话（含 compact 摘要）、分支 diff、飞行记录与评审。
  • 按 /claudemd-commit 的自动模式产出一个独立的 docs(memory) commit。
  • 需要对齐的条目不落盘，列进 PR 正文「记忆层：需与你对齐」，由用户在 PR review 时裁决。
  • 飞行模式下，沉淀 commit 之后重跑 slice-gate.py final，让 ship 裁决的 final 行对齐新 HEAD。
  • 收尾提示合并后跑 /clean-after-merged。
  • slice-gate.py 的门禁、合回与 ship 判据；
  • claudemd-lint / memory-lint 的判据与阈值；
  • /claudemd-commit 的准入四问与预算中性规则；
  • /pr-ship 的评审与自动修复流程。
新增：template/.claude/hooks/merged-cleanup.pytemplate/.claude/commands/clean-after-merged.md三个测试文件：tests/test_merged_cleanup.py、tests/test_clean_after_merged_docs.py、tests/test_ship_memory_docs.py修改：template/.claude/commands/pr-ship.mdtemplate/.claude/commands/claudemd-commit.mdtemplate/.claude/claudemd-standard.md（§13 合约表）template/.claude/skills/openspec-git-discipline/SKILL.mdtemplate/CLAUDE.md.snippet根 CLAUDE.mdREADME.mddocs/WORKFLOW_zh.mdinstall.sh（命令计数）依赖：只用 git（≥ 2.38，merge-tree --write-tree，与 /pr-ship 的要求一致）。不调用 gh / glab，不访问网络，fetch 除外。兼容：没有 linked worktree 或 worktree-* 分支的仓库，plan 输出空清单，apply 什么都不做。已安装模板的仓库重新安装后获得新命令。

clean-after-merged-command ADDED

Requirement: /clean-after-merged 先展示再执行 safe 档

Rule: 命令 template/.claude/commands/clean-after-merged.md SHALL 按以下顺序执行： 1. 定位主 worktree 根； 2. 运行 python3 .claude/hooks/merged-cleanup.py plan --markdown 并展示结果； 3. 运行 python3 .claude/hooks/merged-cleanup.py apply； 4. 打印 done / failed； 5. 把 manual 命令原样输出成命令块交给用户； 6. 运行 git worktree list 验证。

命令 SHALL 有回退段：脚本不可用时只做 fetch --prune 与 --ff-only 同步，然后输出人工清单，不自动删除任何东西。

openspec-git-discipline/SKILL.md 的 Worktree Isolation 节 SHALL 指向该命令与 merged-cleanup.py，并保留「只在主仓库根」。飞行临时 worktree 的清理条款同样指向它。

merged-cleanup-plan ADDED

Requirement: 合并状态与档位由脚本判定

Rule: 脚本 merged-cleanup.py plan SHALL 对每个 linked worktree、本地 worktree-* 分支、已合并的远端 worktree-* 分支、已落地 change 的 refs/flight/* 各输出一项。每项包含： - merged：ancestor / content / fresh / unmerged / landed / -； - tier：safe / manual / keep； - force； - 以稳定标记开头的 reasons； - 确切的 command。

判定依据 target_ref：有 <remote>/<target> 时用它，否则用本地 <target>。

- tip 在 target 第一父链上 → fresh，keep； - tip 是 target 的祖先 → ancestor； - 不是祖先，但 merge-tree 结果与 target 树相同 → content； - 其余 → unmerged，keep。

Scenario: plan-removes-merged-clean-worktree

  • GIVEN分支 worktree-a 带一个提交，已在远端以 --no-ff 合并提交合入 main，本地 main 已同步
  • AND它的 worktree .worktrees/a 没有未提交改动
  • WHEN在主 worktree 运行 merged-cleanup.py plan
  • THENworktree 项 .worktrees/a 的 merged 为 ancestor、tier 为 safe、force 为假，command 为 git worktree remove .worktrees/a
  • AND分支项 worktree-a 的 tier 为 safe，command 为 git branch -d worktree-a

Scenario: plan-detects-squash-merge

  • GIVEN分支 worktree-s 的改动在远端以 squash 方式合入 main，tip 不是 main 的祖先，worktree 干净
  • WHEN运行 plan
  • THEN分支项 worktree-s 的 merged 为 content、tier 为 manual，command 为 git branch -D worktree-s，reasons 有以 content 开头的一条
  • AND它的 worktree 项 tier 为 safe（删除干净的 worktree 不丢提交）

Scenario: plan-keeps-fresh-and-unmerged

  • GIVEN刚从 main 当前提交建出的 .worktrees/f（分支 worktree-f，无独有提交）
  • AND分支 worktree-u 带一个未合并提交，worktree 为 .worktrees/u
  • WHEN运行 plan 再运行 apply --no-fetch
  • THEN两个 worktree 与两个分支的 tier 均为 keep，merged 分别为 fresh 与 unmerged
  • ANDapply 之后两个 worktree 目录与两个分支都还在

Requirement: 是否需要 --force 按改动与子仓判定

Rule: 脚本 SHALL 把未提交改动按 status --porcelain --ignore-submodules=none --untracked-files=all 列到文件，并按以下规则判定档位： - 全部是飞行记录（.openspec-slice，或任意前缀下 openspec/changes/<c>/ 的 timeline.md / gate-report.md / evidence.log）→ safe 且 force，原因标 flight-records； - 还有其他改动 → manual 且 force，原因标 dirty，并列出文件； - 被 lock → manual，原因标 locked； - 路径不在 .worktrees/ 或 .claude/worktrees/ 下 → manual，原因标 outside； - manual 档的命令汇总进 manual，apply 不执行它们。

Scenario: plan-forces-flight-records-only

  • GIVEN已合并的临时 worktree .claude/worktrees/wf_1
  • AND它的未提交改动只有已跟踪的 openspec/changes/c/timeline.md 被改，以及未跟踪的 openspec/changes/c/gate-report.md
  • WHEN运行 plan
  • THEN该 worktree 项 tier 为 safe、force 为真，command 为 git worktree remove --force .claude/worktrees/wf_1，reasons 有以 flight-records 开头的一条

Scenario: plan-defers-other-dirty-to-user

  • GIVEN已合并的 worktree .worktrees/d 里有一个未跟踪的 src/new.py
  • WHEN运行 plan、plan --markdown，再运行 apply --no-fetch
  • THEN该项 tier 为 manual、force 为真，dirty 含 src/new.py，reasons 有以 dirty 开头的一条
  • AND顶层 manual 含 git worktree remove --force .worktrees/d，markdown 输出也含这条命令
  • ANDapply 之后 .worktrees/d 与其中的 src/new.py 仍在，apply 的 manual 含这条命令

Scenario: plan-defers-locked-and-outside-worktrees

  • GIVEN已合并且干净的 .worktrees/l，被 git worktree lock --reason "agent running" 锁定
  • AND已合并且干净的 worktree 位于仓库目录之外
  • WHEN运行 plan 再运行 apply --no-fetch
  • THEN前者 tier 为 manual，reasons 有以 locked 开头且含 agent running 的一条
  • AND后者 tier 为 manual，reasons 有以 outside 开头的一条
  • ANDapply 之后两个 worktree 都还在

Requirement: 子仓提交不能存活时不进 safe 档

Rule: worktree 含已填充的子仓时 SHALL 需要 force。

如果子仓库本体会随 worktree 一起删除（common dir 位于该 worktree 的 gitdir 或路径之下），则子仓 HEAD 与本地分支 tip 必须满足下面任一条件： - 存在于主 checkout 的子仓； - 能从子仓的 remote-tracking ref 到达。

否则判 manual，原因标 unpushed-submodule。

子仓若是从家子仓借出的 linked worktree，则判 safe。apply 删除后在家子仓运行 worktree prune。

Scenario: plan-guards-unpushed-submodule-commit

  • GIVEN主仓含 submodule mods/sub
  • ANDchange worktree .worktrees/c 里初始化了子仓，在子仓提交了一个未推送的提交，父仓钉了 gitlink
  • AND分支 worktree-c 已在远端合入 main
  • WHEN运行 plan
  • THEN.worktrees/c 的 tier 为 manual、force 为真，reasons 有以 unpushed-submodule 开头且含 mods/sub 的一条
  • AND把该子仓提交推送到子仓远端后再运行 plan，tier 变为 safe，reasons 有以 submodule 开头的一条

Scenario: apply-prunes-borrowed-submodule-worktree

  • GIVEN同上的 change 家 .worktrees/c，其子仓提交未推送
  • AND临时 worktree .claude/worktrees/wf_1（分支 worktree-wf_1）的 mods/sub 是从家子仓借出的 linked worktree
  • ANDworktree-wf_1 的提交经 worktree-c 合入远端 main，wf_1 干净
  • WHEN运行 apply --no-fetch（此前已 fetch）
  • THEN.claude/worktrees/wf_1 被删除，done 含 git worktree remove --force .claude/worktrees/wf_1
  • AND家子仓的 git worktree list 不再列出 wf_1 的子仓路径
  • AND.worktrees/c 仍在（unpushed-submodule，manual）

Requirement: branch -d 按 git 规则推算，target 落后先同步

Rule: 脚本 SHALL 按 git 自身规则推算 branch -d 的参照点：分支有 upstream 且能解析时用 upstream，否则用有效 HEAD。

满足以下全部条件时，sync SHALL 为 git merge --ff-only <remote>/<target>，此时有效 HEAD 取 target_ref： - 主 worktree 的当前分支就是 target； - HEAD 落后于 target_ref，且是它的祖先； - 没有已跟踪文件的改动。

apply SHALL 先同步，再删除分支。

Scenario: apply-syncs-target-before-branch-delete

  • GIVEN分支 worktree-wf_1（无 upstream）经 change 分支 worktree-c 合入远端 main，远端已删除 worktree-c
  • AND两者的 worktree 已不存在
  • AND主 worktree 在 main 上、没有改动，但落后于 origin/main
  • WHEN运行 apply
  • THEN本地 main 快进到 origin/main
  • ANDworktree-wf_1 与 worktree-c 被删除，done 依次含 git merge --ff-only origin/main、git branch -d worktree-wf_1
  • ANDfailed 为空，退出码为 0

Scenario: plan-lists-remote-delete-for-user

  • GIVEN分支 worktree-a 已合入远端 main，远端分支 worktree-a 仍在
  • WHENfetch 之后运行 plan，再运行 apply --no-fetch
  • THENremote 项 origin/worktree-a 的 tier 为 manual，command 为 git push origin --delete worktree-a
  • ANDapply 之后远端分支 worktree-a 仍在

Requirement: 已落地 change 的飞行快照 ref 一并清理

Rule: refs/flight/<change>/* 的 change 目录（任意前缀下的 openspec/changes/<change>/）已在 target 树里时，SHALL 判 landed、safe，command 为 git update-ref -d <ref>；未落地的不列出。

Scenario: apply-removes-landed-flight-refs

  • GIVEN远端 main 树里有 openspec/changes/c/proposal.md，没有 openspec/changes/d/
  • AND本地有 refs/flight/c/S1 与 refs/flight/d/S1
  • WHEN运行 apply --no-fetch（此前已 fetch）
  • THENrefs/flight/c/S1 被删除，refs/flight/d/S1 仍在

Requirement: 只在主 worktree 运行

Rule: 在 linked worktree 里运行 plan 或 apply 时，SHALL 退出 2，stdout 为 {"ok": false, "reasons": [...]}，不做任何改动。

Scenario: plan-refuses-outside-main-worktree

  • GIVEN已合并且干净的 .worktrees/a
  • WHEN以 .worktrees/a 为当前目录运行 plan 与 apply --no-fetch
  • THEN两次都退出 2，JSON ok 为假，reasons 有以 not-main-worktree 开头的一条
  • AND.worktrees/a 与分支 worktree-a 都还在

ship-memory-sedimentation ADDED

Requirement: /claudemd-commit 自动录入，较大差异才对齐

Rule: claudemd-commit.md 中通过准入四问与预算闸的新增条目 SHALL 直接写入，不逐条问询。不丢含义的迁移（指针化、分流）同样直接执行。

「较大差异」条目 SHALL 与用户对齐，包括： - 删除或反转既有含义； - 与既有条目或在役 ADR 矛盾； - 改动铁律或核心约束段； - 写到全局 ~/.claude/CLAUDE.md。

对齐方式分两种：单独运行时用 AskUserQuestion；被 /pr-ship 调用时不落盘，返回给调用方列进 PR 正文。

claudemd-standard.md §13 的合约表同步写明自动录入。

Scenario: claudemd-commit-auto-records

  • GIVENclaudemd-commit.md 与 claudemd-standard.md
  • WHEN读取 claudemd-commit 的 step 6 与 standard §13 的 /claudemd-commit 一行
  • THENstep 6 写明自动录入，且不再有「与用户逐类确认」
  • AND列出四种较大差异：「删除或反转」「矛盾」「铁律」「~/.claude/CLAUDE.md」，较大差异条目才用 AskUserQuestion
  • AND写明被 /pr-ship 调用时较大差异条目不落盘
  • ANDstandard §13 的 /claudemd-commit 行含「自动录入」

Design · 05技术设计

Context

合并后清理：现状只有 openspec-git-discipline 的两句话。 - 「清理只在主仓库根：worktree remove → branch -d → worktree list」； - 飞行临时 worktree「有残留时由人确认内容已由 integrator record 写回后手动 remove」。

判断全靠人和模型临场完成。2026-11-09 的实测和玩具仓实验暴露了四处 git 行为。它们都不直观，判错的后果要么是命令失败，要么是丢数据：

| git 行为 | 依据 | 判错的后果 | |---|---|---| | branch -d 有 upstream 且能解析时按 upstream 判，否则按 HEAD 判 | git help branch；实测 6 个分支无 upstream、本地 main 落后时报 not fully merged | 命令失败；或者被诱导改用 -D | | squash 合并后分支 tip 不是 target 的祖先，-d 永远失败 | git 语义 | 被诱导盲目使用 -D | | 不加 --force 时，worktree remove 拒绝删除含已填充子仓或有未提交改动的 worktree | git help worktree；实测报 working trees containing submodules cannot be moved or removed | 命令失败 | | linked worktree 里初始化的子仓，仓库本体在 <主仓>/.git/worktrees/<id>/modules/<P>；--force 删除时连同它一起删 | 2026-11-09 玩具仓实测：未推送的子仓提交在主 checkout 子仓和子仓远端都不存在 | 静默丢失子仓提交 |

知识沉淀： - /claudemd-commit 有准入四问、§12b 分流、预算中性，但 step 6 要逐类用 AskUserQuestion 确认。 - /pr-ship 全程不问询，测试断言全文不含 AskUserQuestion。 - 两者只能靠人记得先后跑。 - C 类「本轮发现的工程偏差」2026-08-25 被废除，理由是它是增长引擎里唯一的无界项。

用户决策（2026-11-09，AskUserQuestion）： - 知识沉淀：/claudemd-commit 改为自动识别与录入，只有与已有认知有较大差异的条目才对齐。 - 反复错误：有上限地恢复。 - 清理：安全档自动执行，铁律 6 加授权例外。 - 组织方式：一个 change 分三片。

在役 ADR 中相关的是 DRAFT-memory-as-fifth-resident-carrier 原则 4：「准入判断由人守，lint 不得裁决」。本设计不让 lint 裁决。人的审核点从逐条问答移到「较大差异对齐 + PR review」，见 Open Questions。

Goals / Non-Goals

Goals: - 每个 worktree、worktree-* 分支、远端分支和飞行快照 ref，都由脚本给出合并状态、是否需要 --force、档位和确切命令。模型不临场判断。 - safe 档在显式调用 /clean-after-merged 时自动执行。manual 档只输出命令，模型永不执行。 - 复现 2026-11-09 的失败场景（无 upstream、本地 target 落后）后，apply 一次清理干净。 - 子仓提交只存在于将被删除的子仓库时，永不进入 safe 档。 - /pr-ship 不问询地完成知识沉淀。只有较大差异的条目留给人类在 PR review 时裁决。 - 反复出现、且有证据的错误能进入载体体系，并且有上限。

Non-Goals: - 不调用 gh / glab 查询 PR 状态。合并判定纯 git，平台中立，可离线。 - 不推送子仓，也不替用户 push --delete、branch -D、worktree unlock。 - 不清理 worktree-* 以外的本地分支（其他分支的用途未知）。 - 不做归档（/opsx-archive 另行触发）。 - 不机械抽取「反复错误」的证据。证据来源已经是结构化文件，由模型阅读；见 Open Questions。 - 不改 claudemd-lint / memory-lint。

已知假阴性

squash 之后 target 又改了同一处，merge-tree 会冲突或产出不同的树 → unmerged，保守保留。

参照点

分支有 upstream 且能解析时用 upstream；否则用「有效 HEAD」。这是 git 自身的规则，见 builtin/branch.c 的 branch_merged。

有效 HEAD

计划了同步时取 target_ref 的 SHA，否则取 HEAD。

同步条件

主 worktree 的当前分支就是 T，HEAD ≠ target_ref，HEAD 是 target_ref 的祖先，且没有已跟踪文件的改动。子仓检出漂移不计入改动：--ff-only 不碰子仓工作树，而主 checkout 的子仓落后于 gitlink 是常态。满足时 sync = {from, to, command: "git merge --ff-only <R>/<T>"}，属于 safe 档。

不满足时

写进 warnings，例如「当前不在 T」或「T 与 <R>/<T> 分叉」，不同步。

是参照点的祖先 → safe 档 git branch -d；
是 target 的祖先但不是参照点的祖先 → manual 档 git branch -D，原因标 reference；
content 状态 → manual 档 git branch -D，原因标 content，并附 merge-tree 证据。
未提交改动的列法

git -C W status --porcelain=v1 -z --ignore-submodules=none --untracked-files=all。这与 git 自身的干净检查口径一致，只是展开到单个文件。

飞行记录白名单

白名单为什么可以丢

只有 tip 已合并时才进入 safe 档。这时 change 分支上由 integrator record 写回的版本已经随 PR 落地，临时 worktree 里那份是过程中的残片。

判定子仓库是否随 W 一起删除

取 common = git -C W/P rev-parse --path-format=absolute --git-common-dir。common 落在 W 自己的 gitdir 之下，或落在 W 路径之下 → 这个子仓库会随 W 一起被删。

会被删除时

取子仓 HEAD、refs/heads/*、refs/flight-sub/* 的每个 tip。每个 tip 必须满足下面任一条件：

存在于主 checkout 的子仓（git -C <root>/P cat-file -e <sha>^{commit}）；
能从该子仓的 refs/remotes/* 到达。
不会被删除时（借出的 linked worktree，例如 submodule-aware-flight 的 start / sub-sync）

子仓库本体在家子仓里，不会被删 → 记入 prune_subs。W 删除后执行 git --git-dir=<common> worktree prune，清掉家子仓里残留的 worktree 元数据。

失败时

单项失败不中断，后续项照常执行，失败项收进 failed。

命令的两种形式

执行时用参数列表，不经 shell；command 字段是给人看的 shlex 引号形式。

分支跟随 worktree 档位

分支若被某个 worktree 检出，就跟随该 worktree 的档位。worktree 为 keep → 分支 keep；为 manual → 分支 manual，排在该 worktree 命令之后。原因是 git 拒绝 -d 一个正被检出的分支。

landed 判据

git ls-tree -r --name-only <target_ref> 中有路径匹配 (^|/)openspec/changes/<change>/。

处理

landed → safe 档 git update-ref -d <ref>；未落地的不列出。

Risks / Trade-offs

[风险] merge-tree 假阴性（squash 后 target 又改同一处）→ 判 unmerged 保留，宁漏删不误删。
[风险] 飞行记录白名单丢掉了未写回的残片 → 只在 tip 已合并时适用。change 分支上的权威版本已随 PR 落地。白名单只含 3 个记账文件和标记文件，不含源码。
[风险] 正在运行的 agent 的 worktree 被删 → 运行中工作的 tip 不在 target 里，判 unmerged / fresh 保留；被 lock 的进 manual。⚠ Claude Code 是否 lock 隔离 worktree 未实测，所以不依赖 lock 作为唯一防线。
[风险] 子仓存活校验漏掉了某个只在子仓 reflog 或 stash 里的提交 → 校验覆盖 HEAD、refs/heads、refs/flight-sub。reflog 与 stash 不在合同内，文档写明「子仓 stash 不受保护」。
[风险] 自动录入让 CLAUDE.md 混入低质条目 → 准入四问、预算中性、lint 全绿照旧，较大差异要对齐，最后还有 PR review 兜底。沉淀写成独立 commit，可以整体 revert。
[风险] E 类仍可能膨胀 → 上界是证据数。能机械化的条目会被引导去写防线，常驻层只留一行。
[取舍] fresh 判定会保守地保留 ff 或 rebase 合并的分支 → plan 表格里写明原因，用户可手动处理。

Migration Plan

  • 安装：纯新增加文档修改，无数据迁移。已安装模板的仓库重新运行 install.sh 即获得新命令和脚本，install.sh 的命令计数改为 17。
  • 回滚：revert 本 change 的合并提交。脚本不持久化任何状态，已删除的 worktree 和分支不可回滚，这也是 safe 档判据从严的原因。
  • 自举：本仓库本身就是使用者。合并后在主仓根跑一次 /clean-after-merged，作为实地验收。
